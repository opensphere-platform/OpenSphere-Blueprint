## 1. 결론 요약

1. **에이전트 구성의 핵심은 "어떤 에이전트 프로그램을 쓰느냐"가 아니라 "에이전트를 어디에 가두고, 무엇만 밖으로 내보내느냐"다.**
   - 권고 구조는 **KubeVirt VM(자리, seat)을 에이전트의 격리 경계**로 쓰는 것이다.
   - VM 밖으로 나가는 길은 세 개뿐이다: **사원 영역 모델 게이트웨이, 사원 영역 Shell, 기록되는 웹 출구.**
   - 이 구조는 아카이브의 Developer 결정(IMPL-ADR-0017 "Agent를 자리 안으로")과 같은 방향이다. 그것을 사원 영역 전체로 넓힌 것이다.
2. **OpenBot은 기능 면에서 사원 영역 에이전트 작업공간에 매우 가깝다.** 상주 에이전트, 에이전트별 작업공간, 작업 큐, 에이전트 간 메시지, 내장 브라우저, Computer Use, 여러 모델 CLI 지원이 있다.
3. **그러나 그대로 채택할 수는 없다.** 이유는 네 가지다(§3).
   - **비상업 라이선스(PolyForm Noncommercial).** 상업 라이선스는 Starter(1인)와 Team(2~10인)만 공개돼 있다.
   - **"전체 접근 + 승인 없음"이 기본 보안 모델**이다.
   - **각자의 벤더 구독 로그인으로 모델을 쓰는 구조**다. 조직 사용은 Anthropic 약관상 API 키 방식을 요구한다.
   - **외부 계정 서비스와 원격 접속 경로**가 있다.
4. 검토 의견은 OpenBot을 설계 참고로만 두자는 것이었다. 그러나 **보스 결정(D-50)은 OpenBot을 주 하네스로 정하고 OEM 라이선스 협상을 우선 진행**하는 것이다. 계약 전에는 포함·수정·배포하지 않는다. 하네스는 계속 교체 가능한 부품으로 설계한다(§8.2).

|---|---|---|---|
| **라이선스** | PolyForm Noncommercial 1.0.0. 상업 사용은 별도 라이선스(Starter 1인, Team 2~10인). 0.1.11 이하만 Apache-2.0(README, LICENSE) | OpenSphere는 회사에 납품·운영되는 상업 제품 | **차단 요인.** 전사 규모(10인 초과)·재배포(OEM) 조건은 공개돼 있지 않다. 라이선스 확인 없이 소스를 포함하거나 수정·배포하지 않는다 |

| **공급망** | 모델 CLI를 시작 시와 매시간 upstream 최신으로 자동 업데이트(README Agent setup) | 버전·릴리스 정책(고정 산출물) | 자동 업데이트를 끄고 고정 버전만 쓰게 해야 한다(`OPENBOT_*_PATH` 등 지원 여부 실증 필요) |

## 4. KubeVirt 현황

| 항목 | 상태(아카이브 기준) |
|---|---|
| KubeVirt Provider | 읽기 전용 관리 화면만 있다. VM 생성은 `409 NotReady`. 사유: 하드웨어 가상화 미연결, Foundation에 compute 모델 없음 |
| KubeVirt CR | `kubevirt` 네임스페이스에 수동 적용. **Developer standalone의 자리 VM과 공유** 중이라 Provider가 소유하지 않는다(`SharedPlatformNotOwned`) |
| 하드웨어 | 노드의 `devices.kubevirt.io/kvm` 할당 가능 여부를 확인하지 못했다. 현재 운영 RKE2에서는 미확인 |
| 선행 설계 | Developer IMPL-ADR-0017(2026-09-14 채택). 사원의 Agent는 사원의 자리 VM 안에서 돈다. 손(도구)은 `127.0.0.1`로만 연다. **LLM·벤더 키·DB는 VM 밖**에 두고, 본체 창구가 대신 호출한다. 열쇠는 뿌리 열쇠에서 자리별로 파생하며 뿌리 열쇠는 자리에 넣지 않는다 |

**IMPL-ADR-0017이 이미 풀어 둔 문제:** 에이전트가 클러스터 공용 Pod로 망을 건너 여러 사원의 기계에 손을 뻗는 구조에서는, 정책 하나만 틀려도 모든 사원 기계에 닿는다(감사 RT-C-02). 에이전트를 자리 VM 안으로 넣으면 건널 망이 사라진다.

## 5. 권고 구성

```
 사원 영역
 ┌────────────────────────────── 에이전트 자리 VM (KubeVirt, 단위별) ──────────────────────────────┐
 │  에이전트 하네스(교체 가능 부품) · 작업 큐 · 작업공간 디스크 · 브라우저 · 데스크톱(Computer Use)   │
 │  도구는 VM 안 127.0.0.1에서만 열림.  VM 안에서는 "전체 접근"이어도 VM 밖으로는 못 나감            │
 │  키 없음: 벤더 키 · DB 자격 · 뿌리 열쇠 없음. 워크로드 신원으로 짧은 토큰만 받음(D-45)            │
 └────────┬───────────────────────────┬───────────────────────────┬──────────────────────────────┘
          │ ① 모델 호출                │ ② 업무 효과·데이터 조회     │ ③ 웹 열람
          ▼                           ▼                           ▼
   사원 영역 모델 게이트웨이(D-29)   사원 영역 Shell(D-36)          기록되는 웹 출구(egress proxy)
   단위별 가상 키·사용량·비용       Governance 판단(D-15·46·47)    도메인 정책·기록
                                   위험 상한 → 사람 확인 대기
                                   ▼
                     Workspace 앱 · PFSS 자원 · 지식 저장소(요청자 권한으로 필터)
```

**원칙:**
- **R-1 격리 경계 = VM.** 에이전트 하네스가 내부에서 무엇을 하든, 영향은 그 VM 디스크와 세 출구로 한정된다. 하네스 자체의 보안 약속에 의존하지 않는다.
- **R-2 집행 지점 = VM 밖.** 권한 판단(교집합, 상시 위임, 위험 상한, 사람 확인)은 모두 Shell과 Governance가 한다. 하네스 안의 승인 설정은 보조다.
- **R-3 비밀 없음.** VM 안에는 장기 비밀이 없다. 모델 키는 게이트웨이에, 앱 관리자 자격은 어댑터에 있다(Governance §8).
- **R-4 네트워크 기본 차단.** VM의 egress는 세 출구만 허용한다. 다른 VM, 앱 관리 API, DB, 클러스터 API로는 나갈 수 없다.
- **R-5 하네스 교체 가능.** 하네스와 VM 사이의 계약은 세 출구와 작업공간 디스크뿐이다. OpenBot, 다른 오픈소스 하네스, 자체 하네스 중 무엇이든 같은 자리에 들어갈 수 있어야 한다.
- **R-6 에이전트 간 대화도 Shell 경유.** 하네스 자체의 에이전트 간 메시지·원격 기능(OpenBot Team API 등)은 끈다. 다른 에이전트 호출은 Shell을 통해 D-47 교집합으로 처리한다.

### 5.1 VM을 어떻게 나눌 것인가

| 에이전트 | 자리 VM | 이유 |
|---|---|---|
| 개인 에이전트 | **그 사원의 자리 VM 1대.** 개발자는 Developer 자리 VM을 공유하고(IMPL-ADR-0017), 일반 사원은 에이전트 전용 소형 VM을 쓴다 | 사원 데이터와 기억이 한 VM에 모이고, 퇴사 시 VM 단위로 보존·폐기(D-33) |
| 부서·프로젝트 에이전트 | **단위별 VM 1대**(단위 안의 여러 에이전트가 공유) | 단위 데이터 경계와 VM 경계가 같아진다 |

**자원 비용이 크다.** 사원 100명에 VM당 2 vCPU·4GiB면 200 vCPU·400GiB다. 그래서 다음을 기본으로 둔다.
- 개인 자리는 **필요할 때 켜고 쉬면 끄는 방식**(온디맨드 + 유휴 정지)으로 운영한다.
- 데스크톱·Computer Use가 필요 없는 **헤드리스 에이전트는 더 가벼운 격리**를 쓰는 선택지를 둔다. 예: Kata Containers 같은 VM급 컨테이너 격리. 선택은 §8 Q-3.

### 5.2 PFSS·Governance에 생기는 변화

| 대상 | 변화 |
|---|---|
| PFSS Foundation | **compute 모델 신설**(지금은 없음). Claim 요청 종류에 `VirtualMachine`(자리)을 둔다. KubeVirt CR 소유를 Developer와 정리해야 한다(공유 플랫폼 문제) |
| 공급 풀(O-2) | vCPU, 메모리, 디스크, GPU, 동시 실행 VM 수를 공급 한도로 둔다. KVM 가능 노드를 Pool의 Instance로 묶는다 |
| Governance 서비스 메뉴 | "에이전트 자리(소형·표준·데스크톱)" Offering을 둔다. 단위별 quota와 결재 정책을 붙인다 |
| 사용량·비용 | VM 가동 시간, 자원, 모델 사용량을 단위별 showback에 합산한다(D-25, D-41) |
| 에이전트 신원(D-45) | VM 워크로드 신원 → SSO 토큰 교환. IMPL-ADR-0017식 자리별 파생 열쇠는 Shell·게이트웨이 인증에 재사용할 수 있다 |
| 데이터(D-33) | VM 디스크 = 에이전트 작업공간. 퇴사·단위 해체 시 VM 스냅샷 보존 후 Governance 결정으로 폐기 |

## 6. OpenBot을 쓰고 싶을 때의 조건

다음을 **모두** 만족할 때만 자리 VM 안의 하네스 후보가 된다.
1. 상업 사용과 OEM 재배포를 포함하는 라이선스 계약. 규모 제한(10인)을 넘어야 한다.
2. 모델 접근을 **OpenAI 호환 엔드포인트(사원 영역 게이트웨이) 하나**로 고정한다. 벤더 로그인은 비활성화한다.
3. OpenBot 계정 서비스, Team API 원격 공개, 자동 업데이트를 끈다. 버전은 고정한다.
4. Linux 데스크톱 VM에서 Computer Use, 브라우저, 큐가 동작하는지 실증한다.
5. 하네스 내부 승인이 없어도 R-1~R-6만으로 Governance 결정이 지켜지는지 반례 시험을 통과한다.

라이선스 대안으로 0.1.11 이하 Apache-2.0 버전을 포크하는 방법도 있다. 하지만 기능 차이가 크고 유지보수를 우리가 떠안게 되므로 권고하지 않는다.

## 8. 결정이 필요한 사항

| ID | 질문 | 권고안 |
|---|---|---|
| Q-1 | OpenBot을 어떻게 다루는가 | **설계 참고로만 쓴다.** 하네스는 교체 가능 부품으로 두고, 허용적 라이선스 후보와 함께 같은 조건(§6)으로 실증 비교한다. OEM 라이선스를 협상할지는 비교 결과를 보고 정한다 |
| Q-2 | 에이전트의 격리 경계 | **KubeVirt 자리 VM.** 개인 에이전트는 사원별 VM, 부서·프로젝트 에이전트는 단위별 VM. 세 출구만 허용한다 |
| Q-3 | 데스크톱이 필요 없는 에이전트도 VM을 쓰는가 | **데스크톱·Computer Use 에이전트는 KubeVirt VM, 헤드리스 에이전트는 VM급 경량 격리(Kata 등)도 허용.** 비용 때문이다 |
| Q-4 | 에이전트의 인터넷 접근 | **기록되는 웹 출구로만 허용**한다. 도메인 정책은 관리자 설정(D-37 원칙)이다 |

### 8.2 D-50 진행 조건

1. **협상 대상**(라이선스 문의처 `licenses@openbot.run`, LICENSE의 Required Notice). 다음 항목을 계약 범위로 확인한다.
   - **상업 사용**
   - **회사 고객사에 대한 재배포(OEM)**
   - **10인 초과 규모**
   - **수정 허용**
   - **서버·VM 다중 설치**
   - **모델 CLI 자동 업데이트 비활성화 등 설정 변경의 허용**
   - **소스 접근과 보안 패치 제공**
   - 협상 연락과 계약은 회사(CMARS)가 직접 수행한다. 이 문서 작성으로 외부에 연락한 것은 없다.
2. **계약 전 금지 사항:** OpenBot 소스를 OpenSphere 저장소에 포함하거나, 수정본을 만들거나, 고객 환경에 배포하지 않는다. PolyForm Noncommercial 조건상 상업 목적 사용이 허용되지 않는다. 계약 전 기술 실증도 상업 개발 목적이면 같은 제약을 받을 수 있으므로, **실증 범위도 라이선스 문의에 포함**한다.
3. **계약 후에도 §6의 2~5 조건은 그대로 적용한다:** 게이트웨이 단일 엔드포인트, 계정·원격·자동 업데이트 비활성화, Linux 데스크톱 VM 실증, R-1~R-6 반례 시험. OpenBot의 "전체 접근" 모델은 VM 경계(D-51)와 VM 밖 집행(R-2) 덕분에 허용되는 것이지, 하네스 자체를 신뢰하는 것이 아니다.
4. **대비책:** R-5(하네스 교체 가능)는 유지한다. 협상이 실패하거나 조건이 맞지 않으면, 같은 자리 VM 계약에 다른 하네스를 넣는다.
