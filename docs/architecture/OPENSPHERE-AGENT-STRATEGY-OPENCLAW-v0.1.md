## 1. 결론

1. **방향은 OpenSphere에 맞다.** 전략의 중심 다섯 가지가 기존 설계의 원칙과 같다.
   - 중심은 에이전트 엔진이 아니라 업무 데이터 환경과 권한이다(기준선 §1).
   - 집행은 프롬프트 · VM 안 설정이 아니라 바깥의 업무 서비스가 한다(재검토 R-2).
   - Gateway 하나가 신뢰 경계 하나이므로 사원마다 따로 둔다(D-51).
   - 에이전트 기능도 같은 서명 패키지 계약에 넣는다(D-95 · D-98).
   - 엔진을 고치지 않고, 교체 가능성을 남긴다(재검토 R-5).
2. **D-50의 가장 큰 막힘이 풀린다.** OpenBot은 비상업 라이선스라 OEM 계약 전에는 포함 · 수정 · 배포를 못 했다. OpenClaw는 **MIT**다 `[확인]`. 대체 하네스가 문서에 없다는 레드팀 v0.1의 지적도 함께 풀린다.
3. **그러나 전략 문서 그대로는 채택할 수 없다.** 문서 스스로 밝히듯 Blueprint 원문 · 소스 · 실환경과 대조하지 않고 쓰였다. 그대로 옮기면 기존 불변식과 부딪히거나 빠진 곳이 18군데이고(§4), 그 가운데 넷은 고치지 않으면 채택할 수 없는 수준이다.
   - 세 출구 불변식과 OpenClaw의 기본 경로(공개 스킬 허브 · 자체 업데이트 · 메신저 채널)
   - 사람의 데스크톱과 에이전트가 같은 VM에 있을 때의 승인 탈취
   - 업데이트를 받는 길(스토어 밖 자체 갱신)과 승인 규모(자리마다 MFA)
   - 순서(지금 없는 Governance · Workspace를 전제로 한 1단계)
4. **조정한 투영은 한 문장이다.** *공식 OpenClaw를 고치지 않고 쓰되, **들어오는 길은 스토어**, **나가는 길은 세 출구**, **판단은 원장**, **집행은 VM 밖**이다.* 전략의 확정 방향 아홉 개(F-01~F-09)는 모두 지켜진다. 바뀌는 것은 권장 설계의 일부(배치 · 업데이트 실행 방식 · 관리 계층의 자리)다.
5. **구현한 OS는 대부분 그대로 쓴다.** 스토어 · 실행 원형 · Claim · 에이전트 운용 적합성(D-102)이 이 전략의 받침이 된다. 새로 필요한 것은 여섯 가지다(§7.2): 자리(compute) 공급, 모델 게이트웨이, 에이전트 런타임 패키지, 사원 영역 Shell의 에이전트 입구, 릴리스 단위 승인과 단계 적용, Governance 결정으로 도는 프로비저닝.
6. **지금 순서를 밀어내지 않는다.** 스토어만으로 다시 구성(D-118)과 수직 PoC가 먼저다. 지금 병행할 수 있는 것은 0단계(실행 · 업데이트 검증)와 Console 에이전트(R2D2)의 업데이트 경로뿐이다(§8).

## 2. 전략 문서의 요약과 지위

### 2.1 확정 방향(D-119로 기록)

| 전략 번호 | 내용 | 청사진에서의 자리 |
|---|---|---|
| F-01 | Console의 OpenClaw는 Console 전용으로 독립 운영한다 | R2D2. D-12 · B-1~B-4와 같다 |
| F-02 | Workspace에는 별도의 OpenClaw를 설치한다 | **D-50(주 하네스 = OpenBot)을 대체한다** |
| F-03 | Workspace는 관리형 서비스 경험(설치 없이 쓰고, 계속 돌고, 운영은 서비스가 맡는다)을 준다 | 새 요구. 어셈블리 `agent.seat`의 제공 품질 기준이 된다 |
| F-04 | 사원별 전용 VM이 업무 컴퓨팅의 기본 단위다 | D-51 · D-55와 같다 |
| F-05 | OpenClaw 자체 개선보다 활용에 집중한다 | 재검토 R-5와 같은 방향. 자체 엔진 규격을 만들지 않는다 |
| F-06 | 공식 OpenClaw 업데이트를 계속 받는다 | **새 불변식.** 받는 방식은 §5.4에서 정한다 |
| F-07 | 기업 업무 환경과 데이터 거버넌스를 중심으로 통합한다 | 기준선 §1, 업무 데이터 환경 계약과 같다 |
| F-08 | Supabase는 Console 전용이다 | B-3과 같다. 사원 영역의 상태를 Backbone 저장소에 두지 않는다 |
| F-09 | 모듈의 기능은 같은 서명 패키지로 관리하고 Backbone 재빌드를 요구하지 않는다 | D-95 · D-98과 같다 |

### 2.2 권장 설계와 그 지위

전략의 권장 설계 R-01~R-17(사원 VM 안의 Gateway, 장기 Fork 금지, 최소 플러그인, 바깥 집행, 설치당 업데이트 소유자 하나, 버전 조합 검증 등)은 **제안**이다. 이 문서의 §5가 그것을 청사진의 자리에 놓으면서 일부를 조정한다. 전략 문서의 번호 R-xx는 재검토 문서의 원칙 R-1~R-6과 이름이 겹치므로, 이 문서에서는 전략 쪽을 "전략 R-01"처럼 부른다.

### 2.3 전략 문서의 전제 가운데 청사진과 다른 것

| 전략의 전제 | 실제 | 처리 |
|---|---|---|
| 백엔드는 Go 중심 | 직접 만드는 백엔드 런타임은 모두 **Rust**다(소유자 지시 2026-11-12). 제품의 MCP 연동은 공식 Rust SDK를 쓴다 | 전략의 "Go 백엔드 모듈"은 Rust로 읽는다. 새 구성요소(연결 어댑터 · 자리 관리 프로그램)도 Rust다 |
| "Workspace Manager"라는 관리 계층 하나 | 청사진은 그 일을 네 면에 나눠 둔다(§5.2) | 한 덩어리로 만들지 않는다(RT-7) |
| "Module Store" | OSR 스토어(D-99 · D-109~D-113). 패키지는 등록된 스토어에서만 온다 | 용어를 스토어로 통일한다 |
| Olares를 사원용 Web OS로 쓰는 기존 방향 | 청사진에 Olares 결정이 없다 | 전제로 삼지 않는다. 사원 데스크톱의 형태는 별도 결정(Q-A8) |
| Synology 등 기업 문서 체계 | 청사진의 파일 엔진은 Stalwart(D-70), 객체 저장은 RustFS다 | 공식 문서의 정본은 Workspace의 문서 서비스로 읽는다. 외부 NAS 편입은 외부 자원 편입 절차를 따른다 |
| MyClaw와 비슷한 경험 | 참고 대상은 서비스 경험뿐이다. 격리 · 보안은 검증하지 않았다(전략 문서도 같은 말을 한다) | 그대로 유지 |

## 4. 레드팀 검토

관점: 이 전략이 OpenSphere의 목적(권한이 정확히 투영된 업무 데이터 환경)에 정말 맞는가, 그대로 가면 어디서 깨지는가. 등급은 S1(고치지 않으면 채택 불가) · S2(설계에 반영해야 함) · S3(보완)이다.

### 4.1 맞는 점(유지할 것)

- 업데이트 수용을 "제품 기능"으로 본 것. 자체 수정이 쌓여 공식 릴리스를 못 따라가는 것이 이런 제품의 가장 흔한 실패다.
- 승인과 OpenClaw의 실행 승인을 다른 판단으로 본 것(전략 7.4). G-INV-2(에이전트는 결재 불가)와 같다.
- 팀 에이전트의 위험을 "요청자 토큰 교체"로 풀 수 없다고 본 것(전략 4.5 · 7.5). D-15의 빈 곳을 채운다.
- 상태 복구가 외부 효과를 되돌리지 않는다는 것, 멱등 키와 "결과 불명"을 따로 둔 것(전략 14.4). OS의 fence · 영속 작업 id(D-102 A4 · O8)와 같은 계약이다.
- 플러그인을 최소로 두고 자체 엔진 규격을 만들지 않는 것(전략 6.5 · 6.6).

### 4.2 S1 — 고치지 않으면 채택할 수 없는 것

**RT-1. 세 출구 불변식과 OpenClaw의 기본 경로가 부딪힌다.**
- 사실 `[확인]`: 공개 등록소(ClawHub)가 **스킬과 플러그인을 함께** 배포한다. 문서에서 등록소를 끄는 스위치는 찾지 못했다. 설치 정책(`security.installPolicy`)으로 설치 · 갱신을 허용 · 차단할 수 있지만 **기본은 꺼져 있다**(켜고 유효한 정책 명령이 없으면 설치가 막힌다). 제3자 스킬은 문서 스스로 "신뢰할 수 없는 코드"라고 한다. 플러그인은 Gateway 프로세스 안에 로드된다. Gateway 자체 업데이트는 기본으로 꺼져 있지만, 오래 도는 패키지형 headless node는 기본으로 자동 업데이트한다. 릴리스 채널은 npm dist-tag다. MCP 서버는 설정으로 어디든 붙일 수 있다(Streamable HTTP · SSE · stdio, OAuth · 헤더).
- 영향: 전략대로 "VM 안에서 공식 기능을 그대로" 쓰면 에이전트가 사는 VM에서 npm · ClawHub · 임의 MCP 서버 · 메신저 서비스로 가는 길이 열린다. D-51 · D-53(세 출구)과 D-113(패키지는 등록된 스토어에서만)이 함께 깨진다. 레드팀 v0.1의 R-08(에이전트가 웹에서 읽은 것이 공급망 경로가 됨)이 그대로 실현된다.
- 조치: 세 출구를 **네트워크로** 강제한다(R-4 유지). OpenClaw의 각 경로를 §5.3의 표대로 끄거나 세 출구로 돌린다. 스킬과 런타임은 스토어의 서명 패키지로만 들어온다.

**RT-2. 사람의 데스크톱과 에이전트가 같은 VM에 있으면 승인을 빼앗길 수 있다.**
- 사실 `[확인]`: OpenClaw의 샌드박스는 **도구 실행만** 가두고 기본으로 꺼져 있다. Gateway 프로세스는 호스트에 남는다. Gateway · 노드 호스트의 명령 실행 기본 정책은 `full`(허용 목록 없음)이고 묻기 기본값은 꺼짐이다. `full`은 권한 상승이 아니라 그 프로세스 계정이 가진 권한을 그대로 쓴다는 뜻이다. 명령은 호스트나 샌드박스의 파일시스템이 허락하는 어디든 고칠 수 있다(작업 폴더 표시가 명령 실행을 가두지 않는다). `tools.elevated`는 샌드박스 밖 실행의 명시적 통로다.
- 영향: D-55는 개발자 자리와 에이전트 자리를 한 종류의 VM으로 합쳤고, 전략은 사람의 Web OS · 브라우저와 에이전트를 같은 VM에 둔다. 주입된 지시를 따른 에이전트가 사람의 로그인된 브라우저를 움직이면 **사람의 세션으로** 결재 · 공유 · 발송을 할 수 있다. 토큰 교환의 `act` 표시도, "에이전트는 결재할 수 없다"(G-INV-2)도 지나쳐 간다. 권한 모델 전체의 전제(누가 했는지 안다)가 무너진다.
- 조치(모두 필요):
  1. 결재 · 활성화 · 역할 부여 · 외부 발송 승인은 **세션만으로 통과하지 못한다.** 그 순간의 본인 확인(MFA 또는 같은 강도)을 요구한다. Backbone은 이미 그렇게 한다. Governance · Workspace 승인에도 같은 규칙을 둔다.
  2. 에이전트는 사람과 **다른 OS 사용자**로 돌고, 사람의 홈 · 브라우저 프로필 · 키체인을 읽지 못한다. 샌드박스를 켜는 것을 관리 프로파일의 필수 항목으로 둔다. `tools.elevated`는 금지한다.
  3. 화면 조작(Computer Use)은 에이전트 전용 데스크톱 세션에서만 한다. 사람의 세션을 조작하는 것은 사람이 그 자리에서 허락한 경우로 한정한다.
  4. 더 강한 선택지: Gateway를 사람의 VM 밖(사원별 경량 격리)에 두고 VM은 실행 노드로만 붙인다(Q-A2).

**RT-3. 업데이트를 받는 길과 승인의 규모가 지금 OS와 맞지 않는다.**
- 전략의 기본 권고는 "검증 후 **VM 안에서 공식 업데이트 명령을 실행**"이다. 이 방식은 VM이 공식 배포처(npm)에 닿아야 하고, 무엇이 설치됐는지를 OS의 서명 · digest 체계 밖에서 믿어야 한다. D-113과 재검토 §3(고정 산출물)에 어긋난다.
- 반대로 지금 OS의 규칙(설치 · 갱신 · 내리기마다 관리자 본인 MFA)은 사원 수만큼의 자리에 맞지 않는다. 전략이 "매번 사람의 결재를 기다리지 않는다"고 한 이유가 여기 있다.
- 조치: 전략의 세 경로 가운데 **"소유 배포 체계의 갱신"을 운영 기본**으로 삼는다. 공식 릴리스를 바이트 그대로 받아 스토어 패키지로 내고, 호환 기록을 통과한 판을 **릴리스 단위로 한 번 승인**한 뒤 자리에는 단계적으로 자동 적용한다(§5.4). "공식 자체 자동 업데이트"는 격리된 시험 고리에서만 쓴다. 이것은 호스트에 새 기능(릴리스 단위 승인 · 단계 적용)을 요구한다(§7.2).

**RT-4. 순서: 전략의 1단계는 지금 없는 것을 전제로 한다.**
- 전략 1단계의 완료 조건("서로 다른 두 사원과 Console의 인증 · 상태 · 자료 분리")은 사원 신원(AD · Keycloak), Governance 원장, Workspace 진입점, 자리 VM 공급, 사원 영역 모델 게이트웨이가 있어야 잰다. 2026-11-28 현재 운영에는 KubeVirt CRD가 없고, Governance · Workspace는 설치된 것이 없으며, Keycloak · Samba AD는 스토어 패키지로 다시 만드는 중이다(D-118).
- 영향: 지금 이 전략을 구현 순서에 넣으면 수직 PoC · 스토어 재구성과 자원을 다투고 둘 다 늦어진다.
- 조치: §8의 순서. 지금은 0단계(검증)와 Console 트랙만 병행한다. 나머지는 선행 조건이 닫힌 뒤에 연다.

### 4.3 S2 — 설계에 반영해야 하는 것

**RT-5. 모델 게이트웨이를 Console과 Workspace가 함께 쓰는 그림.** 전략 3.2의 그림은 세 Gateway가 한 모델 게이트웨이로 간다. "자격 · 정책 · 비용은 분리한다"고 덧붙였지만, 한 인스턴스면 운영자가 사원 사용량과 키에 닿는다. D-29와 B-3에 어긋난다. → 같은 패키지를 **영역별 인스턴스**로 둔다. LiteLLM의 2026년 보안 이력에 따른 채택 조건(AI 운영 §3.2)은 그대로다.

**RT-6. 상시 실행 기본값은 비용이 가장 큰 결정이다.** 기존 추정으로 사원 100명에 200 vCPU · 400 GiB다(재검토 §5.1). OpenClaw의 예약 실행은 Gateway가 떠 있어야 하므로 전략은 상시 실행을 기본으로 권한다. 사람 데스크톱까지 실은 VM을 사원 수만큼 늘 켜 두는 것은 1차 범위에 맞지 않는다. → Gateway(작고 늘 켜짐)와 데스크톱(크고 필요할 때 켜짐)을 나누는 배치를 0단계에서 실측해 비교한다(Q-A2 · Q-A3).

**RT-7. "Workspace 관리 계층" 하나가 네 면의 책임을 가로지른다.** 전략 5.1의 여섯 책임(프로비저닝 · 라우팅 · 구성 · 정책 연결 · 생명주기 · 상태)을 한 서비스가 쥐면, 그 서비스가 사원 배분을 정하는 자리(Governance)와 엔진을 운영하는 자리(Backbone · Fabric)를 함께 갖는다. B-2(운영자는 누구에게 무엇을 줄지 정하지 않는다)와 D-45(신원 정본 = 원장)가 흐려진다. → §5.2처럼 나눈다. 관리 "계층"이 아니라 원장을 따르는 **대사(reconcile)**다. AI 운영 문서가 가장 큰 위험으로 꼽은 것(원장과 집행 지점의 어긋남)도 이 구조여야 드러난다.

**RT-8. 모듈마다 MCP 서버를 두면 집행 지점이 흩어진다.** 전략 8.2는 설치된 모듈의 도구를 에이전트에 노출한다고만 한다. 모듈마다 서버 · 인증 · 권한 검사를 따로 두면 집행 지점이 모듈 수만큼 생기고(R-2), 패키지 추가마다 에이전트 쪽 설정이 바뀐다. D-102 A5는 반대로 정했다: 고정 도구 + 데이터. → 사원 영역 Shell(D-36)에 MCP 어댑터를 하나 두고, 패키지의 명령 정의 · 지침 · 지식은 **데이터로** 흐르게 한다. 스킬은 공개 허브가 아니라 서명 패키지에서만 온다.

**RT-9. OpenClaw의 기본값은 "서로 믿는 단일 운영자"를 전제한다.** `[확인]` 같은 Gateway 안에서 세션은 기본으로 모두 보이고(`tools.sessions.visibility: all`), 에이전트 간 호출은 기본으로 켜져 있으며, 샌드박스는 꺼져 있다. → 기업 기본 설정을 **관리 프로파일**로 정하고, 그것을 호환 기록의 일부로 시험하며, 실제 설정이 프로파일에서 벗어났는지 주기적으로 확인한다. 사원이 VM 관리자면 설정을 바꿀 수 있으므로(전략 4.4), 프로파일은 방어선이 아니라 기본값이다. 방어선은 VM 밖이다.

**RT-10. 한 업스트림에 대한 의존.** `[확인]` 플러그인 API는 전부 실험적이라고 문서가 밝힌다. Gateway 통신 규격은 검증한 버전 조합을 함께 고정하라고 안내한다. → 플러그인은 **없는 것을 목표**로 한다(전략의 "최소"보다 한 걸음 더). OpenSphere가 직접 의존하는 표면은 둘로 묶는다: Gateway 통신 어댑터 하나, 관리 프로파일 하나. 하네스가 바뀌어도 남는 계약은 세 출구와 D-102의 최소 적합 조건이다. 업스트림의 지배 구조 · 릴리스 간격 · 보안 공지 경로는 0단계에서 확인해 기록한다 `[미확인]`.

**RT-17. 업데이트할 수 있는 권한과 업무 도구의 권한이 같은 계정에 모인다.** 전략 4.3은 공식 업데이트가 되도록 설치 위치 · 서비스 계정 · 업데이트 실행 계정을 맞추라고 한다. 설치본을 갱신할 수 있는 권한은 설치 파일 · 설정 · 확장 · 정책 파일을 바꿀 수 있는 권한이다. 같은 권한으로 모델의 일반 도구가 호스트 명령을 실행하면(기본 `full`), 주입된 지시 하나가 런타임 자체와 관리 프로파일을 바꾼다. → 유지보수 권한을 업무 도구의 실행 경로에서 뺀다. §5.4처럼 런타임을 **자리 밖에서 통째로 바꾸면** 자리 안에는 갱신 권한이 필요 없다(설치본은 읽기 전용). 자리 안 공식 업데이터를 쓰는 고리에서는 도구 실행을 샌드박스에 가두고, 설치 위치 · 정책 파일 · 관리 자격을 도구가 보거나 고치지 못하는지 시험으로 확인한다.

**RT-18. 연결용 확장이 빠져도 업무가 열려 있으면 장애가 권한 우회가 된다.** `[확인]` 공식 업데이트는 플러그인이 갱신 · 로드되지 못해도 경고로 남기고 코어 업데이트를 마친다. 신원 전달 · 승인 확인을 플러그인에 맡겼다면, 플러그인이 빠진 Gateway가 그대로 업무 요청을 보낸다. → 닫힌 실패를 **받는 쪽**에 둔다. 사원 영역 Shell과 업무 서비스는 검증된 신원 · 위임 · 승인이 없으면 보호 대상 요청을 거절한다(재검토 R-2). 이것이 플러그인을 없는 것으로 두려는 이유이기도 하다(RT-10): 권한에 관한 일은 OpenClaw 안의 확장이 아니라 출구 ②가 한다.

채택한다. 다만 §5의 조정과 §9의 결정을 조건으로 한다. 조정의 요지는 전략이 "권장 설계"로 둔 세 가지(전략 R-01 배치, R-12 업데이트 실행 방식, R-06 관리 계층)를 기존 불변식에 맞추는 것이고, 확정 방향 F-01~F-09는 바꾸지 않는다.

### 4.6 전략 작성 측의 답변 검토(2026-11-28)

위 지적(기본값이 기업 환경과 맞지 않는다)을 전략 문서를 쓴 쪽에 물었고, 답을 받았다. 그쪽은 Blueprint 원문과 구현을 보지 못한 채 답했다는 한계가 있다(D-50의 원문도 보지 못했다고 밝힌다). 사실 주장은 같은 날 공식 문서로 다시 확인했다.

**답의 요지:** 지적의 핵심에 동의한다. 기본 설정 그대로는 사원용 서비스에 맞지 않는다. 다만 라이선스 · 실행 권한 · 사용자 격리 · 확장 공급망 · 인터페이스 안정성은 서로 다른 문제이고, 결론은 "검증된 기업용 구성에 한해 공식 OpenClaw를 도입한다"이다.

| 답의 내용 | 확인 | 처리 |
|---|---|---|
| 개별 기본값보다 **조합**이 위험하다: 신뢰할 수 없는 입력 + 범용 명령 실행 + 샌드박스 없음 + 넓은 호스트 실행 + 자격에 닿는 계정 | 실행 기본값 `[확인]` | 받아들인다. RT-2 · RT-9의 근거로 쓴다 |
| "작업 폴더만 접근"이라는 표시는 명령 실행을 가두지 않는다 | 명령 실행 쪽 `[확인]`, 파일 도구 쪽 `[미확인]` | 받아들인다. 경로별(파일 도구 · 명령 · 브라우저 · 노드 · 플러그인)로 따로 시험한다 |
| Gateway의 승인 정책이 연결된 노드에 자동으로 맞춰지지 않는다 | 노드 승인은 노드에서 읽는다 `[확인]`, 동기화 여부는 `[미확인]` | 0단계에서 확인한다. Gateway와 노드를 한 판 · 한 프로파일로 묶는다 |
| "세션 공개"는 인터넷 공개가 아니라 같은 Gateway 안의 범위다 | `[확인]` | 표현을 그렇게 쓴다(이 문서는 처음부터 "같은 Gateway 안"으로 적었다) |
| ClawHub는 관리해야 할 확장 공급망이다. 검색 · 검토는 열어 두고 운영 설치는 승인된 출처 · 정확한 판으로 제한한다. 설치 정책 기능을 쓴다 | 설치 정책 `[확인]`. "검사 통과가 안전 보장은 아니다"라는 문구는 `[미확인]` | **부분 수용.** 검토는 자리 밖에서 한다. 운영 자리에 들어오는 길은 스토어 하나다(D-113). 자리 안의 설치 정책은 보조 방어선이지 정본이 아니다 — 사원이 VM 관리자면 바꿀 수 있고, 답도 그 점을 인정한다 |
| 플러그인은 Gateway 안에서 도는 신뢰된 코드이고 도구 샌드박스가 가두지 않는다 | 프로세스 안에 로드됨 `[확인]`, 샌드박스 범위 문구는 `[미확인]` | 받아들인다. 제3자 플러그인은 운영 자리에 넣지 않는다 |
| 권한 플러그인이 빠졌는데도 업무 시스템이 요청을 받으면 안 된다 | 업데이트 경고 동작 `[확인]` | 받아들인다 → RT-18 |
| 업데이트할 수 있는 계정의 권한이 모델의 일반 도구에 노출되면 안 된다 | — | 받아들인다 → RT-17. 전략 4.3의 보완점이다 |
| 운영 편입의 기준은 "설정 완료"가 아니라 "금지한 동작이 실제로 막히는가"다 | — | 받아들인다 → §8.1 |
| 모든 행동에 사람 승인을 붙이지 않는다. 범위 안의 조회 · 초안 · 격리된 실행은 자동, 공유 변경 · 외부 발송 · 삭제 · 권한 변경은 승인, 설치 · 정책 · 운영 자격 변경은 별도 유지보수 경로 | — | 받아들인다. D-46(상시 위임)과 D-102 O3(자동 등급)과 같은 구조다 |
| 필수 경계를 지키려면 코어 수정판을 계속 유지해야 하는 것으로 드러나면 기술 선택을 다시 본다 | — | 받아들인다 → §8.1의 중단 조건 |

**답에 없는 것(청사진을 보지 못해 빠진 것):**
- 승인 탈취의 귀결(RT-2). 답은 "브라우저 상태 접근을 제한해야 한다"까지만 간다. 결재 계열 행위에 그 순간의 본인 확인이 필요하다는 조건이 없다.
- 세 출구(D-51 · D-53). 답은 "허용되지 않은 외부 전송 차단"을 시험 항목으로 두지만 무엇이 허용인지의 기준이 없다. 청사진에는 그 기준이 이미 있다.
- 업데이트 실행 방식. 답은 "자리 안에서 공식 업데이터 실행 + 권한 분리"를 기본으로 유지한다. 이 문서는 "자리 밖에서 통째로 교체"를 기본으로 권한다(§5.4, RT-3 · RT-17). 둘은 양립하지만 기본값이 다르다 — Q-A4 · Q-A5.
- 모델 게이트웨이의 영역 분리(D-29), 원장이 정본이라는 것(D-45), 순서(RT-4), 구현 언어, 규제 조건.

**D-50에 관한 답의 유보에 대하여:** 답은 D-50의 원문을 보지 못해 "코어 라이선스 때문이었다면 해소된다"고만 했다. D-50은 "주 하네스 = OpenBot, OEM 협상 우선"이었고, 막힘은 라이선스였다. 다만 재검토 §6의 나머지 조건(게이트웨이 단일 엔드포인트, 계정 · 원격 · 자동 업데이트 비활성, 실증, R-1~R-6 반례 시험)은 하네스가 무엇이든 적용된다. 그래서 D-119는 D-50을 "닫은" 것이 아니라 **조건을 물려받아 대체한** 것이다.

### 5.2 전략의 "관리 계층"을 네 면에 놓기

| 전략의 책임 | 맡는 면 | 구성 요소 | 비고 |
|---|---|---|---|
| 프로비저닝(VM · 설치 · 초기 설정) | Fabric(공급) + Backbone(스토어 · 실행부) | `agent.seat` 어셈블리, compute Claim, 에이전트 런타임 패키지 | 누구에게 줄지는 정하지 않는다(B-2) |
| 에이전트 신원 · 위임 · 배분 · 수명주기 상태 | **Governance** | 원장(`unit.type=agent`, `agent.seat`, `model.usage`), 프로비저닝 컨트롤러 | 정본(D-45). 다른 곳은 원장을 따른다 |
| 연결 · 라우팅(로그인 사원 ↔ 자기 Gateway) | Workspace | Gateway 통신 어댑터(Rust), "내 AI" 화면 | 사원 영역 서비스다. Backbone을 지나지 않는다 |
| 에이전트 구성(역할 · 허용 기능 · 모델 등급) | Workspace(선택) + Governance(허용 범위) | 관리 프로파일 + 사용자 설정 | 전략 13.9의 세 종류 설정과 같다 |
| 정책 연결 · 승인 | Governance + 사원 영역 Shell | 판단(PDP), 승인함 | 에이전트는 결재할 수 없다 |
| 서비스 상태 | 네 축(AI 운영 §6) | 원장 · 하네스 · HISS · 지표 | 전략 5.4의 여섯 상태는 표시 |
| 강제 정지 | HISS | 망 정책, VM 일시정지 | Backbone 보안 동결(D-39)의 집행 지점 |

- 자리 관리 프로그램(전략의 Runtime Supervisor)은 Rust로 만들고, 인증된 정형 요청(상태 보고 · 프로파일 적용 · 런타임 교체 · 백업)만 받는다. 일반 업무 에이전트의 명령 통로가 아니다.
- 사원 영역의 관리 메타데이터는 사원 영역 저장소에 둔다. Backbone의 Supabase로 넓히지 않는다(F-08, B-3).

### 5.3 OpenClaw의 경로와 세 출구

| OpenClaw의 경로 | 기본 동작 | 투영 |
|---|---|---|
| 모델 호출 | 공급자 설정. LiteLLM 공식 경로가 있다 | **출구 ①.** 사원 영역 게이트웨이 하나만. 공급자 직접 로그인 · 구독 인증은 쓰지 않는다 |
| MCP 서버 | 설정으로 임의 서버 연결. 도구 필터가 있다 `[확인]` | **출구 ②.** 사원 영역 Shell의 MCP 어댑터 하나만 등록한다. 다른 서버는 프로파일로 금지하고 망으로 막는다 |
| 웹 열람 · 브라우저 도구 | 자유 | **출구 ③.** 기록되는 웹 출구로만(D-53) |
| 스킬 | 공개 허브 · 로컬 폴더 · 묶음 `[확인]` | 공개 허브는 망과 설치 정책으로 막는다. 스킬은 서명 패키지에서만 온다 |
| Gateway 자체 업데이트 | 기본 꺼짐. 설정 · 환경 변수로 완전히 끌 수 있다 `[확인]` | 끈다. 런타임은 스토어로 들어온다(§5.4) |
| headless node 자동 업데이트 | 기본 켜짐 `[확인]` | 끈다. Gateway와 같은 판으로 함께 바꾼다 |
| 메신저 채널 | 외부 메신저 연동 | 쓰지 않는다. 사내 메신저(Mattermost) 연결이 필요하면 출구 ②의 기능으로 따로 설계한다 |
| 에이전트 간 호출 | 같은 Gateway 안에서 기본 켜짐 `[확인]` | 같은 Gateway 안의 역할 분담만. Gateway 사이는 출구 ②로(D-47) |
| 호스트 명령 실행 | 기본 무승인, 샌드박스 꺼짐 `[확인]` | 샌드박스 필수, `tools.elevated` 금지 |
| Gateway 포트 · 원격 접속 | 설정에 따름 | 자리 밖에서는 Workspace의 통신 어댑터만 닿는다 |

참고: OpenClaw의 샌드박스 백엔드 목록에 OpenShell이 있다 `[확인]`. Backbone은 이미 OpenShell 제어기를 운영한다. 같은 것인지, 자리 안에서 쓸 수 있는지는 0단계에서 확인한다.

### 5.4 공식 업데이트를 받는 길

```
 공식 릴리스(공식 패키지 · 공식 이미지)
   → 받아 두기(바이트 그대로, digest 기록. 수정판이 아니다)
   → 스토어의 에이전트 런타임 패키지 새 판(관리 프로파일 · 허용 출구 · 호환 선언 포함)
   → 격리 호환 시험(전략 13.6의 열 항목 + 재검토 R-1~R-6 반례 + §5.3의 차단 확인)
   → 호환 기록(패키지 릴리스의 서명된 일부)
   → 릴리스 단위 승인 한 번(사람 · MFA)
   → 고리 0(시험 자리) → 고리 1(제한된 사원) → 전체.  실패하면 다음 고리로 가지 않는다
```

- **F-06을 지키는 방법이다.** 재는 것은 전략 13.12의 지표 그대로다: 공식 릴리스에서 운영 적용까지의 시간, 보류된 릴리스 수와 원인, 자체 패치 수.
- 공식 소스의 수정판을 만들지 않는다. 받아 둔 바이트와 공식 배포의 digest가 같아야 한다(전략 8.5: 단순 미러와 수정판을 구분).
- 호환 기록(전략 18.2)은 새 객체가 아니라 **패키지 릴리스의 서명된 부분**이다. 스토어 · 원장이 이미 가진 판 · digest · 프로필 지문 옆에 선다.
- 설치당 업데이트 소유자는 하나다(전략 R-11). 운영 자리에서는 OpenSphere, 실행은 자리 관리 프로그램이다.
- 상태 이행이 되돌릴 수 없는 판은 D-104(되돌릴 수 없는 이행은 사전 보호)를 따른다.
- 공식 `extended-stable` 채널이 운영 자리의 기준으로 맞는지 0단계에서 본다.

### 5.5 Console 에이전트(R2D2)

- R2D2는 지금 OpenClaw 2026.11.3을 고정해 넣은 Backbone 이미지다. 전략의 세 경로 가운데 "공식 이미지 · 소유 배포 체계 갱신"에 해당한다.
- 더할 것: 공식 릴리스를 따라가는 **정해진 경로**. 릴리스 확인 → 고정 판 올림 → 기존 native 검증(스키마 · 설정 검증) + Console 계약 시험 → R2D2 이미지만 발행 → 운영 반영. Core · Console 이미지는 다시 만들지 않는다.
- Workspace와 같은 판일 필요는 없다(전략 13.10).
- R2D2가 Workspace 자리의 생성 · 정지 · 복구를 **제안**할 수는 있다(D-102 O4: 봉인된 제안 → 사람 채택). 사원의 대화 · 기억에는 닿지 않는다(전략 3.1, B-3).

### 7.3 바뀌는 것 · 주의할 것

| 대상 | 영향 |
|---|---|
| Backbone 이미지 발행 | R2D2 이미지가 공식 릴리스를 따라 더 자주 바뀐다. R2D2만 따로 발행 · 반영하는 경로를 정한다. "Backbone은 Backbone 자체 문제일 때만 다시 빌드한다"(D-95)에 R2D2의 업스트림 갱신을 예외가 아니라 정해진 경로로 적는다 |
| OS 통합 계약 | 에이전트용 선언(스킬 · 지침)을 넣으면 계약 판이 오른다. 검증기 세 곳(Rust · Node · Setup 봉인 사본)이 함께 바뀐다 |
| 승인 규칙 | N5 · N6은 "모든 변경은 관리자 본인 MFA"의 범위를 좁힌다. 좁히는 곳은 자리의 런타임 교체와 배분에 따른 자리 생성 둘로 한정하고, 나머지는 그대로 둔다 |
| 운영 자원 | 자리 VM은 지금 클러스터에 없는 종류의 부하다. 공급 한도(vCPU · 메모리 · 디스크 · 동시 VM 수)를 Fabric 공급 풀에 둔다(O-2) |
| 용어 | 화면과 문서에서 "Console의 AI Agent(R2D2)"와 "사원 에이전트"를 섞지 않는다(AI 운영 §9) |
| 지금 진행 중인 일 | 영향 없다. 스토어 재구성(D-118)에서 만드는 Keycloak · Samba AD · PostgreSQL 패키지는 이 전략의 선행 조건이다 |

## 8. 단계 계획(전략 16장의 재배치)

| 단계 | 내용 | 여는 조건 | 완료 기준 |
|---|---|---|---|
| **0. 실행 · 업데이트 검증** (지금 병행 가능, 격리에서만) | 표준 설치 꼴 하나, 관리 프로파일 초안, §5.3의 차단이 실제로 듣는지, 공식 업데이트 한 번과 복구 한 번, Gateway 통신 어댑터의 최소 표면, 자원 실측(Gateway만 / 데스크톱 포함), 업스트림 확인 사항 | 없음 | 전략 16.2의 0단계 조건 + RT-1 · RT-2 · RT-9의 반례 시험 결과 + Q-A2 · Q-A3에 쓸 실측값 |
| **C. Console 트랙** (지금 병행 가능) | R2D2가 공식 릴리스를 따라가는 경로(§5.5) | 없음 | 공식 릴리스 한 번을 정해진 경로로 운영에 올린다 |
| 1. 토큰 공급 | 사원 영역 모델 게이트웨이와 배분(AI 운영 1단계, D-61) | 사원 신원(AD · Keycloak), Governance 최소 구현 | AI 운영 §11의 1단계 기준 |
| 2. 개인 관리형 에이전트 | 자리 공급(N1), 런타임 패키지(N3), 에이전트 입구(N4), "내 AI" | 1단계, N5 · N6 결정, 영향평가 · 노사협의회 협의 | 전략 16.4의 운영 전 검증 기준 전부 + 킬 스위치 실측 |
| 3. 업무 연결 | 문서 조회 · 초안 · 등록의 종단 시나리오(전략 16.3) | Workspace 문서 서비스, 권한 인지 검색 | 전략 16.3의 여섯 확인 |
| 4. 운영 자동화 | 고리 배포, 예약 · 이벤트, 관측 | 2 · 3단계 | 전략 16.2의 3단계 조건 |
| 5. 팀 · 프로젝트 · 공용 | 단위 소유 에이전트(D-15, 후보 E) | 4단계 | 공유 맥락 · 구성원 변경 · 인수인계 검증 |

- 0단계와 C 트랙은 격리 환경과 Backbone 안에서만 한다. 운영의 사원 영역을 건드리지 않는다.
- 1단계부터는 수직 PoC와 스토어 재구성이 끝난 뒤에 연다.

### 8.1 0단계의 합격 기준 — 금지한 동작이 실제로 막히는가

설정을 마쳤다는 사실이 아니라 아래 시험의 결과로 판정한다. 공식 업데이트를 적용할 때마다 같은 시험을 다시 돌린다(호환 기록의 일부).

| 시험 상황 | 통과 조건 |
|---|---|
| 샌드박스가 필요한 작업인데 샌드박스를 쓸 수 없다 | 호스트로 돌려 실행하지 않고 거절한다 |
| 일반 업무 도구가 설치본 · 관리 프로파일 · 설치 정책 · 관리 자격을 읽거나 고치려 한다 | 실제로 막힌다 |
| 사용자가 대화로 전체 접근 · 권한 상승을 요청한다 | 프로파일을 넘는 변경을 거절한다 |
| 다른 사원의 세션 · 파일 · 자격에 접근한다 | 도구 종류와 경로에 관계없이 막힌다 |
| 승인되지 않은 스킬 · 플러그인을 설치 · 갱신하거나 파일을 직접 바꿔 넣는다 | 운영 자리에 반영되지 않는다(망 · 설치 정책 · 쓰기 권한 세 겹) |
| 신원 · 위임 · 승인 연결이 빠진 채 업무 요청이 나간다 | 받는 쪽이 거절한다(RT-18) |
| 세 출구가 아닌 곳으로 자료를 보낸다 | 자리 밖의 망 정책이 막는다 |
| 에이전트가 사람의 세션으로 결재 계열 행위를 시도한다 | 본인 확인 없이는 통과하지 못한다(RT-2) |
| 공식 업데이트를 적용한다 | 위 시험과 필수 업무 연결 시험을 다시 통과한다 |

**중단 조건:** 위 경계를 지키려면 공식 코어의 수정판을 계속 유지해야 하는 것으로 드러나면, 하네스 선택을 다시 본다. 그것은 F-05 · F-06(고치지 않고 쓰고, 공식 업데이트를 계속 받는다)과 양립하지 않기 때문이다. 하네스가 바뀌어도 세 출구와 D-102의 계약은 남는다(R-5).

## 10. 결정 대장에 반영한 것

- **D-119(신규):** 에이전트 전략 — Console은 전용 OpenClaw(R2D2), Workspace는 별도의 공식 OpenClaw를 관리형 서비스로 제공한다. 고치지 않고 쓰고, 공식 업데이트를 계속 받는다. D-50을 대체한다. 투영은 이 문서를 따른다.
- **D-50:** D-119로 대체.
- 그 밖의 조정(§5)과 질문(§9)은 결정이 아니다.
