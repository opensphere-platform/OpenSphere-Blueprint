## 1. 문제

기준선은 두 영역을 나눴다.
- Backbone 관리자는 사원 영역 제품을 **설치·운영·복구**한다(B-2).
- **누구에게 무엇을 줄지와 사원 데이터에는 관여하지 않는다**(B-2, B-3).

그런데 현실에는 이 경계를 넘어야 하는 순간이 생긴다.

| 상황 | 왜 경계를 넘어야 하나 |
|---|---|
| Governance 장애 | 재시작·롤백은 운영이지만, 원장 손상이면 복원이 **권한 내용**을 되돌린다 |
| 소유자 전원 잠금 | 도메인 관리자 암호 분실 등. 사원 영역 안에서는 아무도 복구할 수 없다 |
| AD DC 손상 | AD가 없으면 사원 영역의 누구도 **로그인해서 승인할 수 없다** |
| 보안 사고 | 사원 영역 관리자 계정이 탈취돼 권한이 마구 부여되는 중이다 |
| 최초 설치 | 내장 Samba AD를 설치자가 만들기 때문에, 최초 도메인 관리자를 설치자가 쥔다(D-34 보완) |

**이 문서의 목표:**
- 평상시 Backbone은 사원 영역의 내용에 **접근할 수단 자체가 없게** 한다.
- 비상시에는 **고객이 허락한 범위와 시간만큼만** 접근하고, **모든 행위가 고객 쪽에 남게** 한다.

## 2. 채널 세 가지

| 채널 | 성격 | 고객 허락 | 예 |
|---|---|---|---|
| **C1 운영 관측** | 내용 없는 상태 정보를 상시 받는다 | 불필요(설치 시 범위 고정) | 워크로드 건강, 자원 사용, 공급 풀 합계, 버전·설정 지문, 오류 수 |
| **C2 내용 중립 조치** | 권한·데이터 내용을 읽거나 바꾸지 않는 운영 행위 | 불필요. 사후 통지 | 재시작, 확장, 같은 데이터에서의 이미지 업그레이드·롤백, 인증서 갱신 |
| **C3 비상 진입** | 내용을 읽거나, 권한·데이터를 바꾸거나 되돌리는 행위 | **필수**(§5) | 원장·AD 복원, 소유자 복구, 사원 데이터 열람, 비밀값 복호화 |

**판정 규칙:** 어떤 행위가 C2인지 애매하면 C3로 본다. 특히 **데이터 복원은 항상 C3**다. 복원은 이미 회수한 권한을 되살리거나 삭제한 데이터를 되살릴 수 있기 때문이다.

## 3. C1 운영 관측의 범위

| 허용 | 금지 |
|---|---|
| Pod·노드 수준 CPU·메모리·저장 사용량 | 사원·부서·프로젝트 이름이나 ID가 들어간 지표 라벨 |
| 공급 풀 단위 배분 합계·사용량·추세(Q-D 권고) | 단위별 사용량, 할당 목록, 결재 내역 |
| 서비스 건강(살아 있음, 준비됨, 오류율, 지연) | 사원 영역 앱 로그 원문(메일 제목, 파일명, 사용자명이 섞임) |
| 설치·업그레이드 작업 상태와 결과 | 감사 사건 본문 |
| 버전, 이미지 digest, 설정 지문(값이 아닌 해시) | 비밀값, 설정 원문 |
| Governance 실행 큐 길이, drift **건수**, 실패 **건수** | drift 대상 객체명 |

**구현상 주의:**
- 공유 관측 기반(HISS의 kube-prometheus 등)은 클러스터 전체를 수집한다. 따라서 **네임스페이스 이름과 라벨에 단위 이름을 쓰지 않는다.** 사원 영역 네임스페이스는 불투명 ID로 짓고, 이름은 Governance 원장에만 둔다.
- 사원 영역 앱 로그는 **사원 영역 관측 저장소**로 보낸다. Backbone은 C1 목록의 구조화 지표만 받는다.

## 4. 평상시 원칙: 상시 자격 없음

- **N-1:** Backbone은 사원 영역 **내용**에 접근할 상시 자격을 갖지 않는다. 대상은 Governance 원장 DB, AD 도메인 관리자, 사원 앱 관리자, 사원 영역 비밀 저장소다.
- **N-2:** Backbone이 가진 사원 영역 자격은 C2에 필요한 것으로 한정한다.
  - 워크로드 배포·재시작
  - AD **전용 OU 위임 계정**(D-34 보완 (c))
  - 공급 풀 관리
- **N-3:** C3에 필요한 자격은 비상 진입이 허락될 때 **사원 영역이 그때 발급하는 시한부 자격**뿐이다. Backbone이 미리 보관하지 않는다.
- **N-4:** 사원 영역의 데이터 백업은 **사원 영역 키로 암호화**한다. Backbone은 암호화된 백업을 보관·이동·복원 실행할 수 있지만, 키 없이는 내용을 볼 수 없다. 복원 실행은 C3다.

## 5. C3 비상 진입 절차

### 5.1 누가 허락하는가 — 신뢰 원천 두 가지

| 사원 영역 상태 | 허락 주체 | 방식 |
|---|---|---|
| AD와 Governance 정상 | **Governance 소유자**(D-34) | Governance에서 비상 진입 요청을 승인한다. 소유자 1명 이상이 승인하고 본인 요청 승인은 금지. 정확한 인원은 §9 B-3 |
| AD 또는 Governance 장애, 소유자 전원 잠금 | **고객 복구 키 보유자**(§6) | 설치 시 만든 복구 키를 M-of-N으로 제시한다. AD 없이 검증된다 |

Backbone 관리자 단독으로는 어떤 C3 행위도 할 수 없다.

### 5.2 진행
1. **요청:** Backbone 관리자가 Backbone에서 요청서를 쓴다. 내용은 사유, 대상(구성요소·데이터 범위), 행위 목록, 필요 시간(기본 상한 4시간), 사고 번호다.
2. **허락:** §5.1의 주체가 요청서를 보고 승인한다. 범위를 좁혀 승인할 수 있다.
3. **발급:** 사원 영역의 **복구 발급기**(§6.2)가 승인된 범위만큼의 시한부 자격을 발급한다.
   - 예: 원장 DB 읽기 전용 2시간, AD 특정 계정 암호 재설정 1회.
4. **수행:** 모든 명령과 세션을 기록한다. 기록은 **사원 영역 감사 저장소**에 쓰고 Backbone에는 요약만 남긴다.
5. **종료:** 시간이 끝나거나 작업이 끝나면 자격을 자동 회수한다. 연장은 다시 허락을 받는다.
6. **사후 보고:** Governance 소유자 전원과 감사자에게 자동 통지한다. 사후 검토(무엇을 했고 무엇이 바뀌었는가)를 기한 안에 확인받는다.

### 5.3 금지
- 비상 진입 중에 만든 계정이나 권한은 종료 때 반드시 회수한다. 남겨야 하면 정상 Governance 절차로 다시 만든다.
- 비상 진입으로 **Governance 정의·할당을 직접 바꾸지 않는다.** 복구가 끝나면 사원 영역 관리자가 정상 절차로 정정한다. 예외는 원장 복원 자체가 목적인 경우뿐이다.
- 사원 업무 데이터(메일, 파일, 문서)의 열람은 비상 진입 범위로도 기본 금지다. 필요하면 별도 범위로 명시하고 허락받아야 한다.

## 6. 고객 복구 키와 최초 인계

### 6.1 최초 인계 의식 (내장 Samba AD 모드)

| 단계 | 내용 | 결과 기록 |
|---|---|---|
| 1 | Setup이 Samba AD DC를 만들고 **설치용 임시 관리자**로 기본 구조(OU, 위임 계정)를 구성한다 | 설치 기록 |
| 2 | 고객이 도메인 관리자로 쓸 **사원 계정**을 만들고, **암호를 고객이 직접 설정**한다. Backbone 화면이나 로그를 거치지 않는 입력 경로를 쓴다 | 계정 생성 사건 |
| 3 | 고객이 **소유자 외부 연락처(메일·전화)와 비상 확인 담당자**를 등록한다(D-42). 복구 키 M-of-N은 고객이 켠 경우에만 생성해 보유자별로 나눠 전달한다(선택 기능) | 연락처 등록 사건. 복구 키는 지문만 기록 |
| 4 | 설치용 임시 관리자를 **비활성화**한다. Backbone에는 전용 OU 위임 계정만 남는다 | 비활성 증거 |
| 5 | 인계 완료 선언. 이 시점부터 Workspace를 사원에게 연다 | 인계 완료 사건(해시 앵커) |

외부 AD 모드에서는 1·2·4가 없다. 3(복구 키)은 Governance 원장·키 저장소 복구용으로 똑같이 만든다.

### 6.2 복구 발급기

- 사원 영역 부트스트랩 집합(O-2 §8.2)에 속하는 **작은 구성요소**다.
- 하는 일:
  - 복구 키 M-of-N 서명이나 Governance 소유자 승인을 검증한다.
  - 승인된 범위의 시한부 자격만 발급한다.
- AD와 Governance가 모두 멈춰도 동작해야 한다. 그래서 의존을 최소로 한다: 자체 저장소, 복구 키 공개키 목록, 발급 대상별 최소 권한 템플릿.
- 자기 자신의 설정 변경도 C3 절차를 따른다.

### 6.3 복구 키 수명주기
- 보유자 교체, 키 분실, 보유자 퇴사 시: 남은 보유자 M명 이상의 서명으로 재발급한다.
- 정기 확인(기본 연 1회): 보유자가 키를 실제로 갖고 있는지 서명 시험으로 확인한다. **키가 없는 것이 사고 때 처음 드러나지 않게 하기 위함이다.**

## 7. 보안 동결 (C2와 C3 사이)

사원 영역 관리자 계정 탈취처럼 **지금 권한이 잘못 부여되는 중**이면, 허락을 기다리는 동안 피해가 커진다.

**제안: Backbone이 단독으로 걸 수 있는 "동결"을 둔다.**
- **효과:**
  - Governance의 실행기와 Grant 서명을 멈춘다. 새 투영·배분이 중단된다.
  - 정의 활성화와 할당 변경 접수를 멈춘다.
  - **기존 권한과 데이터는 바꾸지 않는다.** 회수도 하지 않는다.
- **조건:**
  - 사유를 기록하고 소유자·감사자·복구 키 보유자에게 즉시 통지한다.
  - **자동 만료**한다(기본 24시간). 소유자가 확인하면 연장하거나 해제한다.
- **예외:** 퇴사 회수(D-21)는 동결 중에도 계속 돈다. 권한을 줄이는 방향은 막지 않는다.
- ~~전체 SSO 세션을 강제로 끊는 것은 동결에 포함하지 않는다.~~ → **D-39·D-43으로 대체:** 기존 세션 차단(재인증 강제)은 동결에 포함한다. 새 로그인까지 막는 전면 차단은 C3로 유지한다.

## 9. 결정이 필요한 사항

| ID | 질문 | 권고안 |
|---|---|---|

| D-44 | D-41 전달 방식 확정: 단위 이름은 지표 라벨이 아니라 Governance가 보내는 사용량 보고서로 전달. 할당·결재·감사 본문·업무 데이터·로그 원문은 계속 제외 | §9.2 보완 |

### 9.2 결정에 따른 설계 변경과 남는 위험

**D-38: 복구 허락 근거가 기술적으로 강제되지 않는다.**
- "고객 별도 확인"은 전화·메일 같은 시스템 밖 절차다. 따라서 **Backbone 관리자가 기술적으로는 단독으로 복구할 수 있다.**
- §4 N-3(시한부 자격은 사원 영역 허락으로만 발급)은 장애 상황에서 다음으로 완화된다: "Backbone 요청 + 고객 확인 기록이 첨부되면 발급".
- 남는 위험을 줄이는 보완(**확정, D-42**):
  1. **확인 기록 필수:** 확인한 고객 담당자, 채널, 시각, 증거(서명 메일·통화 기록 번호)를 요청서에 첨부해야 복구 발급기가 동작한다.
  2. **AD와 무관한 통지 경로:** 설치 시 등록한 소유자들의 외부 연락처(메일·전화)로 비상 진입 시작과 종료를 자동 통지한다. AD가 죽어도 고객이 알 수 있다.
  3. **사후 확인 의무:** 복구 후 소유자가 정상 로그인하면 첫 화면에서 비상 진입 내역 확인을 요구한다. 확인 전까지 해당 사건을 "미확인"으로 표시한다.
  4. 복구 키 M-of-N은 **선택 기능**으로 남긴다. 규제가 강한 고객은 설치 시 켜서 기술 강제로 올릴 수 있다.
- §6.1 최초 인계 3단계(복구 키 생성)는 "고객 외부 연락처와 확인 담당자 등록"으로 바꾸고, 복구 키는 선택으로 둔다.

**D-39: 동결에 전 사원 세션 차단을 포함한다.**
- §7의 "전체 SSO 세션 강제 종료는 C3" 문장을 대체한다. Backbone이 동결과 함께 **전 사원 SSO 세션을 끊을 수 있다.**
- 조건(**확정, D-43**):
  - 세션 차단은 동결과 함께만 쓴다.
  - 사유 기록과 외부 연락처 즉시 통지는 필수다.
  - 새 로그인은 막지 않는다. 기존 세션만 끊어 재인증을 강제한다. 탈취된 토큰 무효화가 목적이기 때문이다.
  - 소유자가 해제하거나 24시간 뒤 만료되면 동결만 풀린다. 끊긴 세션은 재로그인으로 회복된다.
- **새 로그인까지 막는 전면 차단은 C3로 유지한다**(확정, D-43).

**D-41: 단위별 사용량이 Backbone으로 넘어간다.**
- 기준선 B-3을 개정한다: "Backbone이 받는 정보는 상태·건강·용량 지표와 **단위별 자원 사용량(단위 이름 포함)**으로 한정한다."
- 여전히 넘기지 않는 것:
  - 할당 내역(누가 어떤 권한을 갖는가)
  - 신청·결재
  - 감사 사건 본문
  - 사원 업무 데이터
  - 로그 원문
- §3 표의 "단위별 사용량" 금지 행을 허용으로 옮긴다(**확정, D-44**). 네임스페이스·라벨의 불투명 ID 원칙은 유지한다. 단위 이름은 지표 라벨이 아니라 Backbone이 Governance에서 받는 **사용량 보고서**로 전달해 공유 관측 기반 전체에 퍼지지 않게 한다.
