## 1. 무엇이 고객 영역인가

| 구성 | 대상 | 예 |
|---|---|---|
| **고객 신원(CIAM)** | 회사의 고객 | 가입, 로그인, 소셜 로그인, MFA, 동의·탈퇴, 계정 복구 |
| **고객 포털** | 로그인한 고객 | 내 정보, 주문·계약·구독 조회, 문의·지원, 다운로드 |
| **공개 웹사이트** | 누구나 | 회사 홈페이지, 제품 소개, 공지, 채용 |
| **고객 대면 서비스·API** | 고객·외부 시스템 | 회사가 만든 고객용 앱과 공개 API(10 관점의 External Web Service) |

**고객 영역이 아닌 것:** 고객 데이터를 다루는 **사내 업무 시스템**(CRM, ERP, 고객 지원 상담 화면)이다. 이것은 사원이 쓰므로 **Workspace(사원 영역)**다. 고객 영역과 사원 영역은 **계약된 API로만** 만난다.

## 2. 권고: 세 번째 영역으로 둔다

```
  admin 영역              사원 영역                           고객 영역
  ───────────            ─────────────────────────           ─────────────────────────────
  Backbone               Workspace · Governance              고객 신원(CIAM) · 고객 포털
  admin 신원             사원 AD                              · 공개 웹사이트 · 고객 대면 앱/API
                         ▲                                    고객 신원(별도)
                         │ 고객 영역의 운영·콘텐츠·고객 응대는   ▲
                         └──── 사원이 사원 신원으로 수행 ──────┘ (등록된 API로만)
```

**세 번째 영역으로 두는 이유:**
1. **신원이 다르다.** 고객은 사원 AD에 들어가지 않는다. 수가 다르고(수만~수백만), 가입 방식(셀프 가입·소셜)과 수명주기(탈퇴·휴면)도 다르다.
2. **노출이 다르다.** 고객 영역은 기본이 인터넷 공개다. 사원 영역은 노출 방식을 회사가 선택한다(D-59). 공격면을 같은 구성요소에 섞지 않는다.
3. **법적 의무가 다르다.** 고객 개인정보에는 개인정보보호법상 수집 동의, 보유 기간, 파기, 접속기록 보관 같은 의무가 따른다. 데이터 분류와 감사가 별도로 필요하다.

**누가 운영하는가:**
- 고객 영역은 **사원 영역의 사원이 운영**한다. 콘텐츠 편집, 고객 계정 지원, 포털 설정이 모두 여기에 들어간다.
- 그래서 고객 영역에는 **별도의 "관리자 신원"이 없다.** 관리 작업은 사원 신원에 Governance 역할을 붙여 수행한다. 예: "웹 편집자", "고객 지원 상담원", "고객 정보 관리자".
- Backbone은 다른 영역과 마찬가지로 **설치·운영·복구만** 한다(B-2 확장).

> **2026-11-17 보완(D-75):** 고객 영역과 사원 영역 사이의 연결은 **교류 계층**으로 구체화했다. B-6의 "계약된 API·이벤트"는 교류 계층을 지나는 교류 객체 계약을 뜻한다. 상세는 [교류 계층](OPENSPHERE-EXCHANGE-LAYER-v0.1.md).

## 3. 경계 불변식 (B 시리즈 확장)

- **B-5:** 고객 신원은 사원 AD, admin 신원과 섞지 않는다. 사원이 고객 계정을 갖는 것은 허용한다. 하지만 사원 권한과 고객 권한은 서로 상속되지 않는다.
- **B-6:** 고객 영역 구성요소는 사원 영역 DB·앱에 직접 접근하지 않는다. 필요한 데이터는 **계약된 API·이벤트**로 주고받는다.
  - 예: 포털의 주문 조회는 ERP의 고객용 읽기 API를 통한다.
- **B-7:** 사원이 고객 개인정보를 볼 수 있는 범위는 Governance가 정한다. 대량 조회·내보내기는 위험 등급에 따라 결재하고 기록한다.
- **B-8:** 고객 영역의 공개 진입점은 사원 영역·admin 영역 진입점과 **분리된 경로**(별도 ingress·도메인·속도 제한·웹 방화벽)를 쓴다.

## 4. 고객 신원(CIAM)

| 항목 | 권고 |
|---|---|
| 제품 | Keycloak(D-56). 아카이브 설계도 Keycloak customer realm이었다 |
| 배치 | **사원용과 다른 별도 Keycloak 인스턴스**(§9 Q-2). 같은 인스턴스에 realm만 나누면, 인터넷에 공개된 고객 로그인 프로세스가 사원 realm과 같은 프로세스·DB·관리 콘솔을 공유한다 |
| 기능 | 셀프 가입, 이메일·휴대폰 인증, 소셜 로그인(선택), MFA(선택·위험 기반), 비밀번호 재설정, 동의 관리, 탈퇴와 파기, 휴면 처리 |
| 수명주기 권위 | 고객 영역(아카이브 설계의 "P8 소관"과 같다). 사원 영역 Governance는 고객 신원을 소유하지 않는다 |
| B2B | 고객이 회사(기업 고객)일 때는 고객 조직, 조직 관리자, 조직 구성원 초대가 필요하다(§9 Q-3) |

## 5. 고객 자격은 누가 정하는가

고객이 무엇을 볼 수 있는가(어느 서비스, 어느 요금제, 어느 문서)는 **업무 데이터**다. 계약, 주문, 구독 상태에서 나온다.

| 대상 | 정본 | 집행 |
|---|---|---|
| 고객의 서비스 자격 | **업무 시스템**(CRM, 주문, 구독)의 계약 상태 | 고객 영역 앱이 고객 토큰 + 업무 시스템 조회로 판단 |
| 사원이 고객 데이터·고객 영역을 다루는 권한 | **Governance**(사원 영역) | Governance 판단부 + 사원 영역 Shell |
| 고객 영역 정책(가입 허용, MFA 요구, 보존 기간, 동의 항목) | **Governance 정의**(관리자 설정, D-37 원칙) | CIAM 설정으로 투영(프로비저닝 어댑터) |

이렇게 나누면 Governance를 고객 수백만 명의 IGA로 키우지 않아도 된다. 동시에 **"회사가 고객 영역을 어떻게 운영하는가"는 Governance가 통제**한다.

## 6. 공개 웹사이트와 고객 포털

| 항목 | 권고 |
|---|---|
| 웹사이트 콘텐츠 | 헤드리스 CMS. 아카이브 계획은 Directus였다. 엔진은 D-28처럼 현 시점 기준으로 재선정한다. **편집은 사원이 사원 신원으로 Workspace에서** 하고, 공개면은 정적 생성·캐시를 우선해 공격면을 줄인다 |
| 고객 포털 | 고객 신원으로 로그인하는 별도 origin이다. 업무 시스템의 고객용 API만 호출한다(B-6) |
| 고객 대면 앱·API | 사원 영역 GitLab에서 개발하고 GitLab CI → PSSS Argo로 배포한다(D-18). 실행 자원은 Governance 서비스 배분(D-30, `unitType: service`)으로 받는다 |
| 노출 | 별도 ingress, 공인 DNS·인증서, 속도 제한, 봇 방어, 웹 방화벽. 노출 설비는 HISS·Backbone 운영이고 정책은 Governance다(O-10) |

## 7. 개인정보·준수

- 고객 데이터는 **"고객 개인정보" 등급**으로 분류한다. 저장 위치, 암호화, 접근 기록, 보존·파기를 Governance 준수 영역에서 정의하고 감사한다.
- 개인정보처리시스템 접속기록(누가 언제 어떤 고객 정보를 봤는가)은 업무 앱과 고객 영역 양쪽에서 남긴다. Governance가 수집·보관한다.
- 고객 탈퇴·파기 요청은 CIAM에서 시작한다. 업무 시스템의 보존 의무(예: 거래 기록)와 파기 의무를 함께 처리하는 흐름이 필요하다.
- 이 항목은 법률 검토가 필요하다. 이 문서는 법적 판단을 하지 않는다.

## 8. 고객 대면 AI 에이전트 (AOA)

고객 응대 챗봇처럼 **고객을 상대하는 에이전트**는 사원 영역 에이전트와 다른 종류다.

| 항목 | 원칙 |
|---|---|
| 권한 | **그 고객의 권한 이하**. 사원 권한이나 부서 에이전트 권한을 쓰지 않는다 |
| 지식 | 공개 지식 + 그 고객 본인의 데이터만 |
| 사람 연결 | 상담원(사원)에게 넘길 때는 대화 맥락만 전달한다. 상담원의 권한으로 에이전트가 행동하지 않는다 |
| 격리·모델 | 별도 격리 실행과 고객 영역 전용 모델 게이트웨이(또는 사원 영역 게이트웨이의 분리된 키·정책). 사용량은 서비스 단위로 Governance에 귀속 |
| 범위 | §9 Q-4 |

## 9. 결정이 필요한 사항

| ID | 질문 | 권고안 |
|---|---|---|
| Q-1 | 고객 영역을 어떻게 두는가 | **세 번째 영역.** 별도 신원·별도 공개 진입점을 두고, 운영은 사원이 Governance 역할로 한다 |
| Q-2 | 고객 신원(CIAM) 배치 | **사원용과 별도 Keycloak 인스턴스** |
| Q-3 | 고객 유형 | 회사 사업 모델에 따라 다르다. 확인 필요 |
| Q-4 | 고객 대면 AI 에이전트 | 1차 범위에 포함할지 확인 필요 |

### 9.1 보스 결정 (2026-11-17)

| ID | 결정 |
|---|---|
| D-62 (Q-1) | 고객 영역은 **세 번째 영역**이다. 별도 신원과 별도 공개 진입점을 두고, 운영은 사원이 사원 신원과 Governance 역할로 한다. Backbone은 설치·운영·복구만 한다. 경계 불변식 B-5~B-8을 채택한다 |
| D-63 (Q-2) | 고객 신원(CIAM)은 **사원용과 별도의 Keycloak 인스턴스**로 둔다 |
| D-64 (Q-3) | **개인 고객(B2C)과 기업 고객(B2B) 모두 지원**한다. 설치 시 회사가 쓸 모드를 선택한다 |
| D-65 (Q-4) | **고객 대면 AI 에이전트를 1차 범위에 포함**한다. 권한은 고객 본인 권한 이하이고, 지식은 공개 지식과 그 고객 본인 데이터로 한정한다. 상담원에게 넘길 때는 맥락만 전달한다(§8) |

### 9.2 결정에서 이어지는 설계 항목

1. **B2B 위임 관리(D-64)**
   - 기업 고객은 **고객 조직, 조직 관리자, 구성원 초대·회수**가 필요하다.
   - 조직 관리자는 **자기 조직 구성원만** 관리한다. 고객 조직 관리자는 OpenSphere Governance 역할이 아니라 **CIAM 안의 고객 측 역할**이다.
   - 기업 고객이 자기 회사 IdP(예: 고객사 Entra ID)로 로그인하는 연동(SAML/OIDC federation)은 B2B의 선택 기능으로 둔다.
2. **고객 대면 에이전트의 실행(D-65)**
   - 고객 영역 전용 격리 실행에서 돈다. 헤드리스이므로 경량 격리(D-52)를 쓴다.
   - 모델 호출은 고객 영역 전용 키·정책을 통한다. 사원 영역 게이트웨이와 키를 공유하지 않는다.
   - 사용량은 서비스 단위로 Governance에 귀속한다.
   - **고객별 대화 기록과 지식 검색 결과는 고객 개인정보로 분류**한다(§7).
   - 프롬프트 인젝션으로 다른 고객 데이터나 내부 데이터에 닿지 않도록, 데이터 조회는 **고객 토큰으로만** 수행한다.
3. **CIAM 운영 주체**
   - 별도 Keycloak 인스턴스는 사원 영역 부트스트랩 집합처럼 **고객 영역 부트스트랩 집합**(CIAM + 그 DB)에 속한다. platform Claim이다(O-2 §8.2 확장).
   - 고객 영역 정책(가입, MFA, 보존, 동의 항목)은 Governance 정의에서 CIAM 설정으로 투영한다.
