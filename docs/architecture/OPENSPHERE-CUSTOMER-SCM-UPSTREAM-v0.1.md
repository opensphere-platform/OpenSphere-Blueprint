## 1. 고객 영역에서 SCM이 맡는 일

SCM은 두 부분으로 나뉜다. 기준선의 영역 경계(B-6: 고객 영역은 업무 시스템과 API로만 연결)에 따라 **배치가 다르다.**

| 부분 | 사용자 | 배치 영역 | 기능 |
|---|---|---|---|
| **SCM 코어(후방 업무)** | 사원(구매·영업·물류·생산·재무) | **사원 영역(Workspace의 ERP 자리)** | 품목·가격, 수주·발주, 재고·창고, 수요·공급 계획, 생산(선택), 출하·배송, 반품, 정산 |
| **SCM 대외 면(고객·협력사 포털)** | 고객(B2C·B2B), 협력사·공급사 | **고객 영역** | 카탈로그·견적·주문, 주문·배송 추적, 재고 가시성(B2B), 발주 확인·납품 예정(ASN), 송장·정산 조회, 반품 요청, 고객 AI 에이전트 |

**보완 필요:** 협력사·공급사도 외부 사용자다. 고객 영역의 CIAM(별도 Keycloak, D-63)에 **협력사 조직(B2B)**을 함께 두는 것을 전제로 한다. 아래 §7 Q-3에서 확인한다.

## 4. 권고 조합

**SCM은 하나의 제품으로 다 덮기보다 "후방 코어 + 대외 커머스 계층"으로 나누는 것을 권고한다.**

```
 고객 영역 (인터넷 공개, 고객 신원 = Keycloak CIAM)
 ┌─────────────────────────────────────────────────────────────┐
 │ 고객·협력사 포털 UI(OpenSphere 자체, 헤드리스) · 고객 AI 에이전트 │
 │        │ GraphQL/REST (고객 토큰)                              │
 │  대외 커머스 계층: Saleor 또는 Medusa (카탈로그·주문·채널·B2B)  │
 └────────┼────────────────────────────────────────────────────┘
          │ 등록된 경계 API + 이벤트(outbox → CloudEvents, D-69)
 사원 영역 (Workspace, 사원 신원 = Keycloak)
 ┌────────┼────────────────────────────────────────────────────┐
 │  SCM 코어: Odoo Community (구매·재고·출하·생산·정산)           │
 │  Governance가 사원의 SCM 권한·고객정보 열람을 통제(B-7)        │
 └─────────────────────────────────────────────────────────────┘
          PFSS: PostgreSQL(StackGres) · RustFS · Valkey · OpenSearch
```

| 순위 | 후보 | 역할 | 선정 이유 | 주의 |
|---|---|---|---|---|
| **1** | **Odoo Community** | SCM 코어(사원 영역 ERP 겸용) | 기능 폭, PostgreSQL, LGPL(독점 확장 가능), 방대한 모듈 생태계, ERP 재선정(D-28) 자리를 함께 채움 | Enterprise 전용 기능 의존 금지 목록 작성, Keycloak OIDC 연동 모듈 실증, 메이저 업그레이드 비용, 한국 현지화 범위 |
| **1** | **Saleor** (대안 **Medusa**) | 고객 영역 대외 커머스 계층 | 헤드리스·PostgreSQL·허용적 라이선스. 고객 영역의 공격면을 코어와 분리 | 코어와의 주문·재고 동기화 계약 설계, B2B 기능 실증 |
| 2 | ERPNext | 코어 대안 | 넓은 무료 기능, 공급사 포털 | GPL 배포 의무, MariaDB(PFSS 확장 필요) |
| 2 | Apache OFBiz | 코어 대안(라이선스 우선 시) | Apache-2.0, OEM 자유 | 개발량과 UX 부담 |
| 보조 | InvenTree, OpenBoxes | 재고·창고 특화 보완 | 특정 산업 요구 시 | 코어와 중복 |
| 비권장 | Axelor(AGPL), iDempiere·metasfresh(GPL, 활동성), Dolibarr(깊이) | — | — | — |

**왜 코어의 포털을 그대로 고객 영역에 노출하지 않는가:**
- Odoo나 ERPNext의 고객·공급사 포털은 **코어 프로세스와 DB를 공유**한다. 이것을 인터넷에 공개하면 B-6(고객 영역은 업무 시스템 DB에 직접 닿지 않음)과 B-8(별도 공개 진입점)이 깨지고, 코어 취약점이 곧바로 외부에 노출된다.
- 그래서 고객 영역에는 **헤드리스 커머스 계층 + OpenSphere 자체 포털 UI**를 두고, 코어와는 API·이벤트로만 연결한다.
- 다만 초기 단계에서 **협력사 포털처럼 사용자가 적은 경우**에는 코어 포털을 별도 진입점 뒤에서 제한적으로 쓰는 선택지를 PoC에서 비교한다.

## 8. Odoo 선정 이유와 Liferay Commerce 비교

### 8.1 Odoo를 1순위로 둔 이유

SCM 코어에 필요한 것은 **사원이 쓰는 후방 공급망 업무 전체**다. 구매·발주, 재고·창고, 수주·출하, 반품, 생산(선택), 정산·회계 연결이 여기에 들어간다.

| 이유 | 내용 |
|---|---|
| 기능 폭 | 구매, 재고(다창고·경로·로트·시리얼), 판매, 생산, 회계가 **한 데이터 모델**로 연결돼 있다. 후보 중 무료 범위에서 후방 SCM을 가장 넓게 덮는다 |
| DB 적합성 | **PostgreSQL 전용**이다. PFSS의 PostgreSQL(StackGres)에 그대로 올라간다. ERPNext는 MariaDB 중심이라 PFSS Provider를 새로 만들어야 한다 |
| 라이선스 | **LGPL-3.0.** 자체 모듈을 독점으로 둘 수 있다. GPL(ERPNext)보다 OEM 배포가 쉽다(D-73으로 제한은 없어졌지만 의무 대응 부담이 작다) |
| 생태계 | ★55.8k, 매일 갱신. OCA(Odoo Community Association) 모듈과 협력사가 많아 기능 공백을 채우기 쉽다 |
| 범위 겸용 | Workspace의 **ERP 자리**(D-28 재선정)를 같은 제품으로 채운다. 업무 시스템이 하나로 모인다 |

**약점(숨기지 않음):**
- 일부 기능이 유료 Enterprise 전용이다(바코드 앱, 품질, PLM, 생산 일정 계획 등). Community에서 쓸 범위를 목록으로 확정해야 한다.
- 매년 메이저 버전이 나오고 모듈 호환성이 깨지기 쉽다. 업그레이드 비용이 크다.
- 자체 사용자·권한 모델이 있다. Keycloak OIDC 연동 모듈과 Governance 프로비저닝 어댑터를 실증해야 한다.
- 한국 현지화(원화·부가세·전자세금계산서) 범위가 제한적일 수 있다.
- 대규모 트랜잭션에서의 Python 서버 성능은 실측이 필요하다.

### 8.3 비교: Liferay는 Odoo의 대체가 아니라 고객 영역 쪽 후보다

| 비교 축 | Odoo Community | Liferay (Portal + Commerce) | Saleor / Medusa (현재 권고) |
|---|---|---|---|
| 위치 | **사원 영역 SCM 코어** | **고객 영역 플랫폼** | 고객 영역 커머스 계층 |
| 후방 SCM(구매·재고 계획·생산·정산) | **있음** | 없음(주문·재고 가시성 위주) | 없음 |
| 대외 B2B 커머스(계정·가격표·주문 승인) | 기본 포털 수준 | **강함** | 중간(Saleor) / 확장 용이(Medusa) |
| CMS·공개 웹사이트 | 기본 웹사이트 빌더 | **강함** | 없음(별도 CMS 필요) |
| 고객·협력사 포털 | 기본 | **강함(계정·권한·사이트)** | 없음(자체 포털 UI 필요) |
| 헤드리스 API | REST/JSON-RPC | REST·GraphQL(헤드리스 API) | GraphQL / REST (헤드리스 전용) |
| 라이선스 | LGPL-3.0 | LGPL-2.1 (DXP 상용 별도) | BSD-3 / MIT |
| 운영 부담 | 중간 | **큼**(Java·OSGi, 메모리·검색 엔진 의존, 학습 곡선) | 작음 |
| 화면 정책(Angular·Clarity) 정합 | 별도 UI | 별도 UI(Clay) | 자체 포털 UI라 정책 준수 쉬움 |

**의미:**
- **Liferay는 고객 영역에서 세 가지를 한 번에 대체할 수 있는 후보다.** 헤드리스 커머스 계층(Saleor/Medusa), 고객·협력사 포털 UI(자체 개발), CMS(재선정)가 그것이다. B2B 계정·주문 승인·사이트·콘텐츠가 이미 있어 **개발량이 크게 줄어든다.**
- 대신 운영이 무겁다. 화면이 OpenSphere UI 정책(Angular·Clarity)과 다른 Liferay UI라는 점도 걸린다. 이미 정한 "헤드리스 커머스 + 자체 포털"(D-71)과는 방향이 다르다.
- **후방 SCM 코어로는 여전히 Odoo(또는 ERPNext·OFBiz)가 필요하다.** Liferay와 Odoo는 경쟁이 아니라 **조합**이다(Liferay 고객 영역 ↔ API·이벤트 ↔ Odoo 코어).

### 8.4 결정 선택지

| 안 | 고객 영역 | SCM 코어 | 장점 | 단점 |
|---|---|---|---|---|
| A (D-71 유지) | Saleor/Medusa + 자체 포털 + CMS(재선정) | Odoo | 가볍고 UI 정책을 지키기 쉬움 | 포털·CMS 개발량 큼 |
| B | **Liferay Portal + Commerce**(커머스·포털·CMS 일체) | Odoo | B2B 포털·CMS 즉시 확보, 개발량 작음 | 운영 무거움, UI 정책 예외, D-71 수정 필요 |
| C | 두 안을 같은 시나리오(§5 S1~S8)로 PoC 비교한 뒤 결정 | Odoo | 근거 있는 선택 | PoC 기간 증가 |

## 9. 업무 코어 위치 정정 (2026-11-17 보스 지적)

**지적:** Odoo가 코어 1순위라면, 고객 영역에 한정할 것이 아니라 원래 성격대로 **ERP·SCM의 코어 위치**를 줘야 한다.

**정정:**
- 이 문서의 제목과 탭 이름("고객 영역 SCM 후보")이 Odoo를 고객 영역 소속처럼 보이게 했다. 실제 배치는 처음부터 사원 영역이었지만 **"Workspace의 ERP 자리"라는 표현이 역할을 좁혔다.**
- 이를 바로잡아 **사원 영역 안에 "업무 코어(Business Core)"를 별도 계층으로 둔다(D-74).**

| 항목 | 내용 |
|---|---|
| 정의 | 회사 업무 데이터의 **정본(system of record)**. 판매·구매·재고·물류·생산·정산·회계 같은 ERP와 SCM이다 |
| 위치 | **사원 영역**(사원 신원·Governance 통제 아래). 데이터 소유자는 회사이고, 운영 주체는 사원이다 |
| 소비자 | ① Workspace: 사원이 쓰는 업무 화면 ② **고객 영역**: 대외 커머스·포털이 **등록 경계 API·이벤트로만** 소비(B-6, D-71) ③ 사원 영역 에이전트: 사원 영역 Shell 경유 |
| 고객 영역과의 관계 | 고객 영역은 SCM의 **대외 면**(주문·배송·협력사 포털)만 가진다. 공급망의 정본은 업무 코어에 있다 |
| 후보 | **1순위 Odoo Community**, 대안 ERPNext·Apache OFBiz(§3·§8) |
| 상태 | ~~정책 판단 대기. PoC 보류~~ → **D-76으로 Odoo Community 선택**(§11). 실증 시작 시점은 별도 지시 |

고객 영역 구성(§8.4의 A·B·C)도 같은 이유로 결정을 보류한다.

## 11. 업무 코어 제품 선택 (D-76, 2026-11-17)

**결정: 업무 코어(ERP·SCM)는 Odoo Community다.** §9의 "정책 판단 대기·PoC 보류" 중 **제품 판단은 끝났다.** 대안인 ERPNext와 Apache OFBiz는 비선정으로 기록만 남긴다.

**선택과 함께 확정하는 실증 조건** (구현 착수 전에 확인한다. 실증 시작 시점은 별도 지시를 따른다):

| # | 조건 | 확인 방법 |
|---|---|---|
| C1 | **Enterprise 전용 기능 의존 금지 목록** | Community에 없는 기능(바코드, 품질, PLM, 생산 일정 계획 등)을 업무 요구와 대조해 대체 방안(OCA 모듈, 자체 모듈)을 정한다 |
| C2 | **신원·권한** | 사원은 Keycloak OIDC 로그인, 권한은 Governance 프로비저닝 어댑터로 Odoo 그룹·역할을 투영(기준선 §6) |
| C3 | **교류 계층 계약** | 견적·주문·ASN·정산·반품 교류 객체를 Odoo API로 구현하고, 고객 쪽 보기와 사원 쪽 보기를 분리한다(X-3) |
| C4 | **이벤트** | Odoo 변경을 outbox → CloudEvents로 내보낸다(D-69). Odoo 자체 큐·웹훅과의 정합을 확인한다 |
| C5 | **한국 현지화** | 원화, 부가세, 전자세금계산서 외부 연동 지점 |
| C6 | **저장·배분** | PFSS PostgreSQL(StackGres)에 Governance 서비스 배분(D-30)으로 배치하고, 백업·복원을 확인한다 |
| C7 | **업그레이드** | 메이저 버전 업그레이드 절차, 자체·OCA 모듈 호환성 검사, 롤백 방법 |
| C8 | **성능** | 대표 주문·재고 트랜잭션 부하와 응답 시간 |
| C9 | **라이선스 대응** | LGPL-3.0 의무(라이브러리 수정분 공개 등)와 자체 모듈 배포 방식 정리(D-73) |

## 10. 교류 계층 반영 (D-75)

SCM의 세 부분은 다음과 같이 배치된다.

| 부분 | 위치 |
|---|---|
| 정본(공급망 데이터) | **업무 코어** |
| 고객·협력사와의 거래(견적, 주문 확인, ASN, 정산 조회, 반품) | **교류 계층**의 교류 객체 |
| 고객이 보는 화면 | **고객 영역** |

- §8.4의 A(헤드리스 커머스 + 자체 포털)와 B(Liferay)는 모두 **고객 영역의 "보여 주는 면" 후보**로 비교한다. 어느 쪽을 골라도 교류 계층의 계약은 같다.
- 단, 헤드리스 커머스 제품(Saleor·Medusa)이 자체 주문 데이터를 갖는 경우에는 그것이 업무 코어 주문과 **두 번째 정본이 되지 않도록** 주의한다. 주문 정본은 업무 코어에 두고, 커머스 계층의 주문은 접수 단계 상태로만 쓴다. 이 경계는 PoC에서 확인한다.
