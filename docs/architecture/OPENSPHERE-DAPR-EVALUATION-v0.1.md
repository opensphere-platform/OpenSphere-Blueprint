## 1. 결론

1. **Dapr는 "단일 채널"의 *공통 사용 방식(API)과 전송 계층*으로는 유력한 후보다.**
   - 서비스 호출, 이벤트(pub/sub), 상태, 비밀, 설정, 워크플로를 모든 언어에서 같은 HTTP/gRPC API로 쓴다.
   - 앱마다 워크로드 신원을 발급하고 mTLS로 암호화한다.
   - 어느 앱이 어느 앱을 부를 수 있는지 허용 목록으로 제한한다.
   - OpenTelemetry로 추적한다.
2. **그러나 Dapr는 데이터 흐름의 *일관성*을 스스로 보장하지 않는다.**
   - 이벤트 전달은 "최소 한 번(at-least-once)"이다. 순서는 아래 브로커에 따라 다르다.
   - 중복 처리 방지(멱등)는 앱 책임이다.
   - 이벤트 내용의 스키마 계약도 관리하지 않는다. 지원하는 것은 CloudEvents 봉투뿐이다.
   - 사람·에이전트의 위임 신원을 판단하지 않는다. 앱 대 앱 신원만 판단한다.
3. 따라서 OpenSphere의 단일 채널은 **"Dapr(전송·신원·관측) + OpenSphere 계약 규칙(스키마 등록, outbox, 멱등키, 위임 토큰, Governance 판단)"**으로 구성해야 한다. Dapr만 깔아서 "일관성이 생겼다"고 볼 수 없다.
4. **권고 범위:**
   - **사원 영역과 고객 영역의 모듈 통합 런타임** 후보로 실증(PoC)한다.
   - **Backbone(admin 영역)에는 도입하지 않는다.** 이미 Rust 내부 버스, Core outbox, Temporal이 있고 감사 후속 정리가 진행 중이다.
   - **영역 사이는 Dapr로 직접 잇지 않는다.** 등록된 경계 API로만 잇는다(B-4, B-6).

## 2. "단일 채널"이 갖춰야 할 요건과 Dapr 충족도

| # | 요건 | Dapr | 설명 |
|---|---|---|---|
| R1 | 모든 모듈이 같은 방식으로 호출·이벤트를 쓴다 | **충족** | 언어 무관 HTTP/gRPC API. 사이드카 방식 |
| R2 | 워크로드 인증과 통신 암호화 | **충족** | 앱별 암호 신원, mTLS, 인증서 자동 회전 |
| R3 | 모듈 간 허용 관계 강제 | **부분** | 앱 ID 단위 호출 허용 목록, 토픽 범위 제한, 컴포넌트 범위 제한. **사람·에이전트 단위가 아니다** |
| R4 | 사람·에이전트 위임 신원(D-15, D-46, D-47)의 전파와 판단 | **미충족** | 토큰은 헤더로 넘길 수 있다. 판단은 Governance 판단부와 Shell이 해야 한다. Dapr 미들웨어(OAuth2, OPA)로 판단을 이중화하지 않는다 |
| R5 | 상태 변경과 이벤트 발행의 원자성 | **부분** | 지원 상태 저장소에서 트랜잭션 outbox 패턴을 제공한다. 지원 범위와 PostgreSQL 조합은 실증이 필요하다 |
| R6 | 전달 보장, 중복, 순서 | **부분** | 최소 한 번 전달. 순서는 브로커와 파티션 설계에 의존하고, 멱등은 앱 책임 |
| R7 | 이벤트·호출 계약(스키마)의 일관성 | **미충족** | CloudEvents 봉투만 있다. 스키마 등록·호환성 검사는 OpenSphere가 따로 둬야 한다(AsyncAPI/JSON Schema 등) |
| R8 | 관측·추적 | **충족** | OpenTelemetry 추적, 지표 |
| R9 | 오래 걸리는 작업의 내구 실행 | **충족**하지만 **중복** | Dapr Workflow(사람 결재 대기, 보상, 버전 관리). 이미 Temporal이 있어 둘을 함께 쓰면 정본이 둘이 된다 |
| R10 | 영역 분리(admin·사원·고객) | **주의** | 제어 평면 하나를 여러 영역이 공유하면 인증서 발급 CA가 공통 신뢰 뿌리가 된다(B-1 위반 위험). 영역별로 제어 평면이나 신뢰 도메인을 분리하는 구성을 실증해야 한다 |
| R11 | 기존 Rust 코드와의 결합 | **부분** | Rust SDK는 알파다. HTTP/gRPC를 직접 호출할 수는 있다 |
| R12 | 라이선스·지속성 | **충족** | Apache-2.0, CNCF graduated, 활발한 릴리스 |

## 3. OpenSphere 기존 구성과 겹치는 부분

| Dapr 기능 | 이미 있는 것 | 판단 |
|---|---|---|
| Workflow | Temporal(Backbone Core, 실행 경로) | **하나만 쓴다**(§9 Q-3) |
| Pub/Sub | Backbone Core outbox + 고정 구독자, 사원 영역은 아직 없음 | 사원·고객 영역의 이벤트 채널로는 빈자리를 채운다 |
| Service Invocation | Backbone 내부 버스, 사원 영역 Shell(D-36) | Shell은 **사람·에이전트 진입 제어**, Dapr 호출은 **모듈 간 내부 호출**로 역할을 나눈다 |
| Secrets | Backbone 비밀 저장소, 사원 영역 비밀 저장소(Governance §8) | 비밀 저장소 위의 접근 방식으로는 쓸 수 있다. 정본은 바꾸지 않는다 |
| Conversation(LLM) | 사원 영역 모델 게이트웨이(D-29) | 쓰지 않는다. 모델 접근은 게이트웨이 하나로 유지한다 |
| Actors, Agents | OpenBot 하네스(D-50), 자리 VM(D-51) | 에이전트 실행은 자리 VM 구조를 유지한다. Dapr Agents는 채택 대상이 아니다 |

## 4. 사이드카가 같은 프로세스 문제(Nexus 감사 R-05)에 주는 효과

- 사이드카는 **앱과 다른 프로세스**다. DB·브로커 자격을 사이드카 컴포넌트에 두면 앱 프로세스가 원문 자격을 갖지 않는다. 컴포넌트 범위를 제한하면 해당 앱만 그 컴포넌트를 쓸 수 있다.
- **한계:**
  - 앱이 침해되면 공격자는 사이드카 API로 그 앱에 허용된 모든 일을 할 수 있다. 자격 원문 노출은 줄지만 **권한 오남용은 막지 못한다.**
  - 사이드카는 같은 Pod 안에 있어 Pod 침해에는 함께 노출된다.
- 그래서 **실제 효과 지점의 최종 판단**(Governance 판단부, 소유 모듈의 검사)은 계속 필요하다.

## 5. 권고 구성

```
 사원 영역 (Dapr 제어 평면·신뢰 도메인 A)         고객 영역 (Dapr 제어 평면·신뢰 도메인 B)
 ┌─────────────────────────────────────┐        ┌────────────────────────────────────┐
 │ Governance · 어댑터 · Workspace 앱    │        │ 고객 포털 · 고객용 앱 · 고객 에이전트 │
 │   └ Dapr 사이드카: 호출·pub/sub·비밀 │        │   └ Dapr 사이드카                   │
 │ 이벤트 브로커 A (영역 전용)           │        │ 이벤트 브로커 B (영역 전용)          │
 └──────────────┬──────────────────────┘        └───────────────┬────────────────────┘
                │      등록된 경계 API(B-4, B-6) · 게이트웨이     │
                └────────────────────────┬───────────────────────┘
                                         │
                       admin 영역(Backbone): Rust 버스 · Core outbox · Temporal (Dapr 미도입)
```

**OpenSphere 계약 규칙** (Dapr와 무관하게 모든 영역에 적용):
1. **이벤트 형식:** CloudEvents 1.0 봉투를 쓰고 `type`은 등록된 이름만 허용한다.
2. **스키마 등록:** 모든 이벤트·호출의 스키마를 버전과 함께 등록한다. 호환되지 않는 변경은 새 버전으로 낸다. 등록되지 않은 type은 브로커 단계에서 거절한다.
3. **상태 변경과 발행:** 같은 트랜잭션 또는 outbox로 처리한다. "DB에는 저장됐는데 이벤트는 안 나감"을 금지한다.
4. **수신 측:** 이벤트 ID로 멱등 처리한다. 결과 불명(unknown)이면 재전송하지 말고 조회로 확정한다(Governance §11).
5. **위임 신원:** 사람·에이전트 위임 토큰(Keycloak 토큰 교환, `act` 사슬)을 호출·이벤트 메타데이터로 전달한다. 판단은 Governance 판단부가 한다.
6. **순서:** 순서가 필요한 흐름(예: 한 사원의 입사 → 이동 → 퇴사)은 **대상 키 단위 순서**를 브로커 파티션 키로 보장한다. 전체 순서는 약속하지 않는다.

## 7. 대안 비교

| 안 | 장점 | 단점 |
|---|---|---|
| A. Dapr + 계약 규칙(권고 PoC) | 공통 API, 워크로드 mTLS, 앱 단위 허용 목록, 브로커 교체 가능성 | 사이드카·제어 평면 운영, 일관성은 계약 규칙에 의존 |
| B. 브로커 직접 사용(NATS JetStream 또는 Kafka) + 계약 규칙 + 서비스 메시 없이 앱 SDK | 구성요소가 적다 | 언어별 SDK와 인증·재시도·추적을 앱마다 구현 |
| C. 서비스 메시(Linkerd 등) + 브로커 + 계약 규칙 | mTLS·정책을 네트워크 계층에서 투명 적용 | pub/sub·상태·비밀 같은 공통 API 없음 |

어느 안이든 **일관성의 핵심은 §5의 계약 규칙**이다. Dapr의 순이익은 "공통 API와 워크로드 보안을 앱마다 구현하지 않는 것"이다. 이 이익을 PoC로 측정한다.

## 8. 실증(PoC) 시나리오

| # | 시나리오 | 합격 기준 |
|---|---|---|
| P1 | Governance 할당 → 앱 어댑터 프로비저닝 이벤트 | 원장 커밋과 이벤트 발행이 원자적(outbox), 중복 수신 시 효과 1회 |
| P2 | 브로커 장애·재시작 | 유실 0, 재전달 후 멱등 처리 |
| P3 | 허용되지 않은 앱 간 호출·토픽 구독 | 거절되고 기록됨 |
| P4 | 위임 토큰 전파(사원 → 부서 에이전트 → 어댑터) | `act` 사슬이 끝까지 전달되고 Governance 판단과 일치 |
| P5 | 영역 분리 | 사원 영역 사이드카가 고객 영역 앱을 호출하거나 신뢰할 수 없음(다른 신뢰 도메인) |
| P6 | 스키마 미등록 type 발행 | 거절 |
| P7 | 자원·지연 | 대표 앱 10개 기준 사이드카 CPU·메모리, 호출 p95 증가를 기준선과 비교 |
| P8 | Rust 모듈 연동 | Governance가 Rust면 알파 SDK 대신 gRPC 직접 호출의 안정성 확인 |

## 9. 결정이 필요한 사항

| ID | 질문 | 권고안 |
|---|---|---|
| Q-1 | "단일 채널"의 범위 | **영역마다 하나의 채널.** 영역 사이는 등록된 경계 API |
| Q-2 | Dapr 채택 방식 | **사원 영역에서 PoC 후 결정.** 통과하면 사원·고객 영역의 모듈 통합 런타임으로 채택. Backbone 미도입 |
| Q-3 | 워크플로 엔진 | **Temporal 유지, Dapr Workflow 미사용.** 정본을 둘로 만들지 않는다 |
| Q-4 | 일관성 요구 수준 | **최소 한 번 전달 + 멱등 + outbox + 키 단위 순서.** 전 구간 exactly-once는 약속하지 않는다 |

|---|---|
