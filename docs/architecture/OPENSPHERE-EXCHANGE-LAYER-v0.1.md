## 1. 왜 두는가

내부 업무(사원 영역)와 외부 고객·협력사(고객 영역)가 실제로 만나는 일은 단순 조회보다 넓다. 견적 협상, 주문 확인, 협력사 납품 예정(ASN)·정산, 상담 대화, 공유 문서, 고객 요청에서 시작되는 내부 결재가 모두 여기에 해당한다.

경계 API 원칙(B-6) 하나만으로는 이런 교류가 앱마다 흩어진다. 그러면 다음 세 가지가 앱마다 달라진다.
- **신원 연결 규칙**: 고객 계정 ↔ 거래처, 건 ↔ 담당 사원
- 개인정보가 넘어가는 범위
- 감사 기록

그래서 **두 영역이 만나는 면을 별도 개념으로 고정한다.**

## 2. 위치

```
 고객 영역      고객 신원(CIAM) · 포털·웹·고객 앱·고객 AI          ← 보여 주는 면
      │  고객 토큰
 교류 계층      유일한 통과 지점 · 교류 객체 · 신원 연결 · 규칙 집행 · 이벤트 연결기   ← 만나는 면
      │  사원 토큰 / 업무 코어 API
 사원 영역      업무 코어(ERP·SCM 정본) · CRM·헬프데스크 · Workspace · Governance
```

**SCM에 적용하면:**
- 공급망 데이터의 정본은 **업무 코어**에 있다.
- 고객·협력사와의 거래는 **교류 계층**을 지난다.
- 고객이 보는 화면은 **고객 영역**에 있다.

## 3. 불변식

- **X-1 유일한 통과 지점:** 사원 영역과 고객 영역 사이의 모든 요청·이벤트는 교류 계층을 지난다. 두 영역 사이의 직접 연결은 네트워크 정책으로 차단한다. B-6을 구체화한 원칙이다.
- **X-2 자체 신원 없음:** 교류 계층은 새 신원 체계를 만들지 않는다. 고객 토큰(고객 CIAM)과 사원 토큰(사원 Keycloak)을 각각 그대로 받아 검증한다(B-1, B-5).
- **X-3 정본 없음:** 교류 계층은 업무 데이터의 정본을 갖지 않는다.
  - 거래 데이터의 정본은 업무 코어다.
  - 상담 건·대화의 정본은 고객 서비스 시스템(사원 영역)이다.
  - 교류 계층이 갖는 것은 **연결 규칙, 보여 줄 형태, 전달 기록**뿐이다.
- **X-4 규칙은 Governance에서:** 넘길 데이터의 범위, 고객 동의 요건, 속도 제한, 사원의 고객정보 열람 조건(B-7)은 Governance 정의에서 받아 집행한다.
- **X-5 만능 중계 금지:** 업무 로직(가격 계산, 재고 할당, 결재 판단)을 교류 계층으로 옮기지 않는다. 그 일은 각 정본 시스템이 한다.

## 4. 구성요소 (논리 단위)

| 구성요소 | 하는 일 |
|---|---|
| 교류 게이트웨이 | 양쪽 토큰 검증, 등록된 교류 계약만 통과, 속도 제한, 감사 |
| 신원 연결 레지스트리 | 고객 계정·고객 조직(B2B) ↔ 업무 코어 거래처, 교류 객체 ↔ 담당 사원·부서 매핑. 연결의 생성·변경은 Governance 결재 대상 |
| 교류 객체 계약 | 견적, 주문, 주문 확인, ASN, 송장·정산 조회, 반품, 상담 건·대화, 공유 문서, 고객 요청 결재. 객체마다 고객 쪽 보기와 사원 쪽 보기의 스키마를 분리한다 |
| 표현 변환 | 정본 데이터에서 고객에게 보여 줄 필드만 투영한다(데이터 최소화). 내부 메모·원가·담당자 개인정보는 기본적으로 제외 |
| 이벤트 연결기 | 사원 영역 채널과 고객 영역 채널을 직접 잇지 않는다(D-66). 등록된 이벤트만 걸러 변환해 전달한다. CloudEvents, 멱등, outbox, 키 단위 순서를 지킨다(D-69) |
| 교류 감사 | 누가(고객·사원·에이전트) 어떤 교류 객체를 언제 보고 바꿨는지 기록한다. 개인정보 접속기록 요건의 한 축이다 |

## 5. 에이전트

- **고객 AI 에이전트(D-65):** 교류 계층에서 **고객 토큰으로만** 교류 객체를 조회한다. 사람 상담원에게 넘길 때는 상담 건 객체로 넘기고 맥락만 전달한다.
- **사원 영역 에이전트:** 사원 영역 Shell을 거쳐 사원 토큰과 위임 사슬로 교류 객체에 접근한다. 고객 영역에 직접 닿지 않는다.
