## 1. 한 줄 정의

Governance는 **"누가(AD) + 무엇을(정의) + 얼마나·언제까지(할당)"를 원장에 확정**한다. 그 결과를 각 앱과 PFSS의 **원하는 상태로 계산해 투영**하고, 실제 상태와 **계속 대조**하는 사원 영역 제품이다.

## 2. 구성요소 (논리 단위, 배포 단위 아님)

```
 Governance 관리 콘솔(별도 주소) ─┐                                        ┌─ 사원 에이전트·CLI(사원 영역 Shell)
 Workspace 셀프서비스(신청·결재) ──┼──── 사원 영역 제어 계약(Governance API) ──┤
                                  └───────────────────┬────────────────────┘
                                              ▼
 AD ──▶ ① 신원 수집기 ──▶ ② 원장(Ledger) ◀── ③ 정의 저장소(revision) ──▶ GitLab 서명 사본
                              │   ▲                    │
                              │   └── ④ 결재 엔진 ◀────┤ (결재선·위험 등급 = 정의)
                              ▼                        ▼
                         ⑤ 판단부(PDP 어댑터 → 채택 엔진)
                              ▼
                         ⑥ 원하는 상태 계산기 ──▶ ⑦ 실행기 ─┬─ 앱 어댑터(SCIM/고유 API)
                              ▲                          ├─ PFSS Claim(⑧ Grant 서명기)
                              │                          └─ AD 관리 그룹(쓰기 허용 모드에서만)
                         ⑨ 대조기 ◀── 어댑터 list · PFSS Binding 상태
                         ⑩ 사용량 수집기 ◀── PFSS 사용량 · 모델 게이트웨이 · 앱 지표
```

| # | 구성요소 | 책임 | 하지 않는 것 |
|---|---|---|---|
| ① | 신원 수집기 | AD의 사람·상태·조직·그룹 변경을 수신한다(변경 추적 + 주기 전체 대조). 퇴사·비활성은 우선 처리 | AD 쓰기(쓰기 허용 모드에서는 ⑦이 담당) |
| ② | 원장 | 단위, 할당, 신청, 결재, 재검토, 배분, 사용량, 감사 기록의 정본. 정의 revision과 같은 시간축에 둔다 | 엔진 상태 보관 |
| ③ | 정의 저장소 | 역할, 정책, 서비스 메뉴, 위험 규칙, 결재 규칙의 revision. 상태는 초안 → 결재 → 활성. 활성 시 GitLab에 서명 사본 | GitLab merge로 활성화 |
| ④ | 결재 엔진 | 신청을 위험 등급으로 나누고, 결재선을 계산하고, 결정을 기록한다. 본인·에이전트 결재 금지 | 범용 워크플로 엔진 신설(기존 엔진 재사용 검토) |
| ⑤ | 판단부 | "이 주체가 이 대상에 이 행위를 할 수 있는가"를 판정. 채택 엔진을 감싼 어댑터 | 정책의 정본 보관(③이 정본, 엔진은 사본을 받음) |
| ⑥ | 원하는 상태 계산기 | 원장과 정의에서 대상(앱, PFSS, AD 그룹)별 원하는 상태를 산출 | 직접 쓰기 |
| ⑦ | 실행기 | 어댑터를 호출해 create/update/disable/delete를 수행. 멱등이며 결과 불명(unknown)을 기록한다 | 판단 |
| ⑧ | Grant 서명기 | PFSS 배분 Claim용 서명 증명 발급. 서명 키는 사원 영역 키 저장소에 둔다 | 키를 원장이나 Git에 보관 |
| ⑨ | 대조기 | 어댑터 list와 원하는 상태를 비교. 초과 권한은 자동 회수, 부족 권한은 보고, 앱 직접 변경은 기록 | 데이터 삭제 |
| ⑩ | 사용량 수집기 | 단위별 사용량 집계, quota 경고·차단 신호, showback | 예산 차감(후속) |

### 2.1 화면 표면 (D-49)

| 표면 | 사용자 | 메뉴(최소) | 접속 조건 |
|---|---|---|---|
| **Governance 관리 콘솔** | 소유자, 정책 관리자, 정의 승인자, 배분 관리자, 자원 담당자, 감사자 | 사용자·조직(내장 AD 모드), 역할·정책·서비스 메뉴(초안·영향 미리 계산·활성화), 배분·quota·공급 풀 현황, 에이전트, 재검토 캠페인 설정, drift·감사·사용량·showback, 비상 진입 허락·통지 확인, 설정(외부 AD 모드, 기본 템플릿) | **별도 주소**와 별도 SSO 클라이언트. MFA 재확인, 짧은 세션(관리자 설정), 다른 Workspace 앱과 세션·쿠키 비공유. 역할이 없는 사원은 접근 불가 |
| **Workspace 셀프서비스** | 모든 사원, 단위 관리자(팀장·프로젝트 소유자) | 내 권한·내 자원·사용량, 신청과 진행 상태, **결재함**, 팀 내 재배분(단위 관리자), 재검토 응답, 내 에이전트·상시 위임, 에이전트 행위 확인 대기함 | 일반 사원 SSO. 높은 위험 결재는 결재 시점에 MFA 재확인 |

- 관리 콘솔의 메뉴는 역할과 **단위 범위**에 따라 다르게 보인다. 예를 들어 "영업본부만"으로 범위가 정해진 배분 관리자는 영업본부 단위만 볼 수 있다. 서버 판단부(⑤)가 같은 조건을 강제하며, 화면 숨김은 보조 수단이다.
- 두 표면 모두 Governance API만 부른다. 화면에만 있는 기능은 두지 않는다(AOA, OS Shell 원칙).
- Backbone Console에는 Governance 메뉴를 두지 않는다. Backbone이 보는 것은 O-6 문서의 C1 운영 정보와 단위별 사용량 보고(D-41, D-44)뿐이다.

## 3. 주체와 역할

모든 사람 주체는 **사원 신원(AD)**이다. Backbone admin 신원은 Governance에 로그인하지 않는다(B-1).

| 역할 | 할 수 있는 일 | 기본 부여 방식 | 사용 표면 |
|---|---|---|---|
| Governance 소유자 | 다른 Governance 역할 지정, 키 교체 승인, 비상 절차 승인 | AD 도메인 관리자 그룹 구성원(D-34). 외부 AD 모드는 설치 시 다른 그룹 지정 가능, §14.2 | 관리 콘솔 |
| 정책 관리자 | 정의(역할, 정책, 서비스 메뉴, 위험·결재 규칙) 초안 작성 | 소유자가 지정(단위 범위 지정 가능) | 관리 콘솔 |
| 정의 승인자 | 정의 revision 활성화 승인(D-35 위험 기반) | 소유자가 지정 | 관리 콘솔 |
| 배분 관리자 | 부서·프로젝트·서비스 단위 quota 할당, 서비스 배분 처리(D-30) | 소유자가 지정(단위 범위 지정 가능) | 관리 콘솔 |
| 단위 관리자 | 자기 부서·팀·프로젝트 안에서 구성원에게 재배분, 1차 결재 | 부서는 AD `manager`, 프로젝트는 Governance 프로젝트 소유자에서 파생 | **Workspace 셀프서비스** |
| 자원 담당자 | 특정 서비스·풀의 2차 결재(보안, 비용 등) | 서비스 메뉴 정의에 지정 | 관리 콘솔 또는 셀프서비스 결재함 |
| 감사자 | 원장, 시점별 권한, drift, 사용량 읽기 전용 | 소유자가 지정(단위 범위 지정 가능) | 관리 콘솔 |
| 사원 | 자기 몫 조회, 신청, 재검토 응답 | 모든 활성 사원 | Workspace 셀프서비스 |
| 에이전트 | 신청 초안·정의 초안 제안, 조회. **결재 불가** | §10 | 사원 영역 Shell |

**위임 관리 역할의 범위:** 정책 관리자, 배분 관리자, 감사자는 **기능 범위**와 **단위 범위**를 함께 지정해 부여한다. Google Workspace의 위임 관리자 + 조직 단위 범위와 같은 방식이다. 범위 밖 단위는 조회·변경 모두 판단부에서 거절한다.

**SoD 불변식:**
- G-INV-1: 본인 신청을 본인이 결재할 수 없다.
- G-INV-2: 에이전트는 결재·활성화를 할 수 없다.
- G-INV-3: Governance 역할 부여 자체도 원장 기록과 결재를 거친다. 예외는 설치 시 최초 지정 한 번이며, 이것도 기록한다.
- G-INV-4: 자기 자신의 Governance 권한을 넓히는 할당은 다른 사람의 결재가 필요하다.

## 6. 정의 모델 (D-27)

정의는 다섯 종류다. 모두 같은 revision 규칙을 따른다.

| 종류 | 내용 | 예 |
|---|---|---|
| role | 업무 역할 = 여러 대상 권한의 묶음 | "영업팀 기본": 메일, 메신저, ERP 영업 모듈 읽기·쓰기 |
| offering | 서비스 메뉴 = 공급 풀의 Profile, 기본 quota, 대상 단위 유형 | "프로젝트 분석 DB 소형": pg-shared-a, 50Gi, 연결 20 |
| policy | 판단 규칙(속성 조건, 상속, 교집합) | "프로젝트 구성원만 프로젝트 DB 접근" |
| risk | 위험 등급 규칙 | "외부 공유 가능 권한 = 높음", "개인 저장공간 10Gi 이하 = 낮음" |
| approval-route | 등급별 결재선 | 낮음: 자동 / 보통: 단위 관리자 / 높음: 단위 관리자 + 자원 담당자 |

**활성화 규칙:**
- 활성화는 하나의 트랜잭션에서 처리한다.
  1. 참조 무결성 검증: 삭제된 역할을 참조하는 할당이 없어야 한다.
  2. 영향 미리 계산: 이 revision이 활성화되면 몇 명의 권한이 어떻게 바뀌는가.
  3. 활성 포인터를 교체한다.
- **영향 미리 계산 결과를 승인 화면에 반드시 보여 준다.** 관리자 의도와 실제 효과의 차이를 사전에 확인하기 위함이다.

## 7. 핵심 흐름

### 7.1 신청 → 결재 → 할당 → 투영 (D-9)
1. 사원이나 에이전트가 신청한다. 신청에는 멱등키를 붙인다. 같은 키와 다른 내용은 충돌로 처리한다.
2. 위험 등급을 판정하고 결재선을 계산한다. 결재자가 없으면(관리자 미지정 등) **대체 결재선**으로 보내고, 자동 승인으로 넘기지 않는다.
3. 승인되면 `assignment`를 생성한다. 원하는 상태를 다시 계산한다.
4. 실행기가 투영하고 결과를 기록한다. 결과 불명이면 재전송하지 않고 대조기의 관측으로 확정한다.

### 7.2 입사·이동·퇴사 (D-21)
- **퇴사·비활성:**
  1. AD 변경을 우선 처리한다.
  2. SSO 세션 회수를 1분 이내에 수행한다.
  3. 모든 대상에서 disable을 수행한다. 목표는 20분 p95다.
  4. 데이터 처리는 보존 정책(D-33)을 따른다.
- **이동:**
  - 부서에서 파생된 할당은 자동으로 재계산한다.
  - 직접 할당은 유지하되 "재검토 필요" 표시를 단다.
- **입사:**
  - 부서와 직책 기반의 기본 역할(role 정의의 자동 부여 조건)을 적용한다.

### 7.3 정기 재검토
- 캠페인 단위로 단위 관리자에게 할당 목록을 보낸다.
- 기한 안에 응답이 없을 때 처리 방식(회수 또는 유지·경고)은 §14 G-4에서 정한다.

### 7.4 서비스 배분 (D-30)
1. Backbone이 앱 설치 시 기반 자원 요구를 **서비스 배분 요청**으로 보낸다. 사원 영역 제어 계약의 등록된 입구 하나만 쓴다.
2. 서비스 배분 정책에 따라 승인한다.
3. Grant를 발급하고 PFSS Claim을 생성한다.
4. Backbone 설치가 다음 단계로 진행한다.

### 7.5 drift (D-20)
- 대조기는 변경 이벤트 직후와 주기 전체 대조 두 가지로 동작한다.
- **초과 권한:** 자동 회수한다. 접근 차단이지 데이터 삭제가 아니다.
- **부족 권한:** 재투영을 시도하고 보고한다.
- **앱 안에서 직접 바뀐 변경:** 기록하고 단위 관리자에게 알린다.

## 8. 실행 대상 어댑터 계약

```
interface ProvisioningAdapter {
  describe() -> { target, schemaVersion, capabilities: [create, update, disable, delete, list], supportsScim }
  list(cursor) -> page of { objectKey, attributes, entitlements, ownerMark }
  apply(op: create|update|disable|delete, objectKey, desiredSpec, idempotencyKey)
       -> accepted(operationRef) | applied | rejected(reason) | unknown
  observe(operationRef) -> applied | failed(reason) | unknown
}
```
- 스키마는 SCIM 2.0 User·Group과 OpenSphere 확장을 따른다(기준선 §6).
- SCIM 서버를 가진 대상은 범용 SCIM 어댑터 하나로 처리한다.
- PFSS 대상은 어댑터 대신 **Claim 생성·삭제**를 쓴다(O-2 계약). Grant는 ⑧이 서명한다.
- 어댑터는 대상 앱의 관리자 자격을 쓴다. 이 자격은 **사원 영역 비밀 저장소**에 두고 Backbone과 공유하지 않는다.
- 모든 쓰기는 대상 객체에 `ownerMark`(Governance, assignment ID)를 남긴다. 대조기가 자기가 관리하는 객체만 회수하기 위함이다.

## 9. 판단 엔진 (D-26)

Governance 코드는 엔진을 직접 호출하지 않고 **PDP 어댑터 인터페이스**만 쓴다.

```
decide(subject, action, resource, context) -> allow|deny + reasons + policyRevision
explain(subject, resource) -> 어떤 할당·정책 때문에 허용되는가
reverseQuery(resource, action) -> 누가 할 수 있는가     (재검토·감사용)
```

**비교 시나리오** (후보: Cedar, Cerbos, OPA, OpenFGA, SpiceDB). 모두 같은 데이터로 수행한다.

| # | 시나리오 | 보는 것 |
|---|---|---|
| S1 | 부서 계층 상속 + 프로젝트 교차 구성원 | 관계 표현력, 성능 |
| S2 | 에이전트 = 할당 역할 ∩ 요청자 권한(D-15) | 교집합 표현, 설명 가능성 |
| S3 | 결재선 계산(관리자 부재 시 대체) | 규칙 표현, 테스트 용이성 |
| S4 | 특정 과거 시점의 권한 재현 | 정책 revision과 데이터 시점 결합 |
| S5 | 누가 이 자원에 접근할 수 있는가(역질의) | 재검토·감사 지원 |
| S6 | 퇴사 반영 지연(1분, 20분 목표) | 캐시·동기화 지연 |
| S7 | 정책 변경 영향 미리 계산(§6) | 차이 계산 지원 |

**판정 기준:**
- 시나리오 통과 여부
- 정책 작성 난이도: 사원 영역 관리자가 화면으로 다룰 수 있는가
- 운영 부담
- 라이선스
- 장애 시 동작

한 엔진이 모두를 충족하지 못하면 "요청 판단 엔진 + 관계 엔진" 조합을 허용한다. 다만 정본은 언제나 ③이다.

## 10. 에이전트 처리 (D-12, D-15, D-16)

- 에이전트는 `unit.type=agent`로 원장에 등록한다. 소속 단위와 할당 역할을 갖는다.
- 판단 시 실제 권한은 다음과 같다.
  - 개인 에이전트: `min(위임자 권한)`
  - 부서·프로젝트 에이전트: `할당 역할 ∩ 요청자 권한`
- 요청자가 없는 예약 동작의 허용 여부는 기준선 O-4로 남아 있다.
- 에이전트의 신청·정의 제안은 `request.requester_kind=agent`, `on_behalf_of`와 함께 기록한다.
- 에이전트는 결재, 활성화, 키 조작, Governance 역할 부여를 할 수 없다(G-INV-2).

## 11. 실패와 재개 의미

Nexus 감사(2026-11-16)의 교훈을 반영한다.

| 상황 | 동작 |
|---|---|
| 판단부·원장 쓰기 실패 | 효과 이전에 거절한다. 기록 없는 할당은 없다 |
| 외부 대상에 전달한 뒤 시간 초과 | `unknown`으로 기록한다. **작업을 중간에 버리지 않는다.** 응답만 끊고, 완료 기록은 관측으로 확정한다 |
| 같은 멱등키·같은 내용 | 기존 결과를 돌려준다 |
| 같은 멱등키·다른 내용 | 충돌로 거절한다 |
| 대상 장애 | 해당 대상만 지연한다. 다른 대상과 원장은 계속 진행한다. 지연은 drift로 보인다 |
| Governance 장애 | SSO 차단(AD 비활성)은 Governance와 무관하게 동작한다. PFSS 기존 Binding도 유지된다(D-31). 새 신청·할당만 멈춘다 |
| Backbone 장애 | Governance는 정상 동작한다. 서비스 배분 요청(§7.4)만 대기한다 |

## 12. 보안 경계

- **Governance가 침해되면** 사원 영역 권한 전체가 위험해진다. 그래서 다음을 지킨다.
  1. 원장 쓰기는 Governance 서비스 하나만 한다. 감사 사건은 해시를 연결해 남기고, 해시 앵커를 **주기적으로 외부(GitLab 서명 사본, 별도 저장소)에 내보낸다.**
  2. Grant 서명 키와 어댑터 자격은 사원 영역 키·비밀 저장소에 분리한다. 키 사용 기록을 남긴다.
  3. 정의 활성화와 Governance 역할 부여는 원장 기록과 결재를 반드시 거친다(G-INV-3).
  4. Backbone admin 신원은 Governance 데이터에 접근하지 않는다. 비상 진입(break-glass)은 기준선 O-6에서 별도로 정한다.
  5. 관리 콘솔은 별도 주소·별도 세션으로 Workspace 앱과 쿠키를 공유하지 않는다. 관리 작업에는 MFA 재확인과 짧은 세션을 강제한다(§2.1, D-49).
- **한계:** 같은 프로세스 안의 악성 코드는 위 장치로 막지 못한다. Nexus 감사 R-05와 같은 문제다. 결재의 독립성을 강하게 보장해야 하는 경우(예: 높은 위험 등급)는 결재자 단말의 서명(WebAuthn 등)을 Governance가 아닌 **대상 집행 지점에서 검증**하는 방식을 후속으로 검토한다.

### 14.2 D-34의 영향과 보완

Governance 소유권이 **AD 그룹 구성원 자격에서 파생**된다. 따라서 **AD를 통제하는 사람이 곧 Governance를 통제**한다. 다음 세 가지를 설계에 반영한다.

1. **G-INV-3 예외의 명시**
   - 소유자 역할은 원장 결재가 아니라 AD 그룹 구성원 자격으로 부여된다.
   - 대신 신원 수집기(①)가 도메인 관리자 그룹의 변경을 **최우선 감사 사건**으로 기록한다.
   - 변경이 생기면 기존 소유자 전원과 감사자에게 즉시 알린다.
   - 변경 이력은 해시 앵커 내보내기 대상에 포함한다.
2. **내장 Samba AD 모드의 최초 도메인 관리자 문제**
   - 내장 AD는 설치(Backbone·Setup)가 만든다. 그래서 **최초 도메인 관리자 계정을 설치자가 쥐게 되고**, 이는 B-2(Backbone은 사원 권한 내용에 관여하지 않음)와 충돌할 수 있다.
   - 보완:
     - (a) 설치 시 고객이 도메인 관리자로 쓸 사원 계정을 지정한다.
     - (b) 설치용 임시 관리자 자격은 인계 직후 비활성화한다.
     - (c) Backbone은 자기 운영에 필요한 **전용 OU 위임 계정**만 보유한다. 기존 Samba Provider의 `OU=OpenSphere` 위임 방식이다.
     - (d) 인계 완료를 기록한다.
   - 이 절차는 기준선 O-6(break-glass)과 함께 정한다.
3. **외부 AD 모드**
   - 고객의 기존 도메인 관리자가 곧 Governance 소유자가 된다.
   - 고객 조직에 도메인 관리자가 많으면 소유자가 과도하게 많아질 수 있다. 이 경우 설치 시 **"Governance 소유자로 인정할 AD 그룹"을 별도 그룹으로 지정**할 수 있도록 설정 항목을 둔다. 기본값은 도메인 관리자 그룹이다.
