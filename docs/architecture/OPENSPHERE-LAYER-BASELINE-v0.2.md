## 1. 목표

OpenSphere는 **한 회사**(D-14)에 full 전산 서비스를 제공한다.

**제품 목적 보강(2026-11-20 보스 요청):** OpenSphere는 업무 데이터 환경을 구성하고 조직 정책과 사용자 권한에 따라 제공·변경·회수한다. 아래의 자원 공급·권한 투영은 이를 실현하는 수단이며, 완료는 사용자가 허용된 데이터로 실제 업무를 수행하고 금지된 접근은 거절되는 것으로 확인한다. 상세 계약·종단 시험 보강안은 [업무 데이터 환경 계약](../specs/BUSINESS-DATA-ENVIRONMENT-CONTRACT-v0.1.md)을 따른다. 기존 D-결정과 구현 상태는 변경하지 않는다.

- 기반 시스템을 만들고, 자원을 배분·통제한다.
- 최종적으로 **회사의 권한 관리자가 의도한 권한이 정확히 투영된 자원**을 사원에게 제공한다.
- 그 투영이 실제로 맞는지 **계속 검증**한다.

OpenSphere 전체는 **AI-Oriented Architecture(AOA)**를 관점으로 삼는다(D-12, D-17).
- 모든 기능과 정보는 에이전트가 쓸 수 있는 계약으로 노출한다.
- 에이전트가 쓸 수 있는 범위는 거버넌스가 정한다.
- OpenSphere의 소스는 모두 내부 Git에 있다. 에이전트가 제안하고 사람이 검토하는 방식으로 스스로 업데이트·확장한다(D-13, D-16).

## 2. 두 영역과 두 신원 평면

OpenSphere는 **admin 영역**과 **사원 영역**으로 나뉜다. 두 영역은 신원, 데이터, 소스 저장소, 에이전트, 모델 키를 공유하지 않는다.

> **고객 영역 (D-60, D-62~D-65):** 고객 신원(별도 Keycloak 인스턴스), 고객 포털, 공개 웹사이트, 고객 대면 앱·API·AI 에이전트로 이루어진 **세 번째 영역**이다.
> - 운영은 사원이 사원 신원과 Governance 역할로 하고, Backbone은 설치·운영·복구만 한다.
> - B2C와 B2B를 모두 지원한다.
> - 경계 불변식 B-5~B-8(신원 분리, API로만 연계, 사원의 고객정보 열람은 Governance 통제, 별도 공개 진입점)을 적용한다.
> - 상세는 [O-9 고객 영역](OPENSPHERE-CUSTOMER-AREA-O9-v0.1.md).

> **교류 계층 (D-75):** 사원 영역과 고객 영역이 만나는 **유일한 통과 지점**이다.
> - 다루는 것: 견적·주문·ASN·정산 조회·상담 건·공유 문서·고객 요청 결재 같은 교류 객체
> - 하는 일: 신원 연결(고객 계정 ↔ 거래처, 건 ↔ 담당 사원), 데이터 최소화·동의·속도 제한·감사 집행, 영역 채널 사이의 이벤트 연결
> - **자체 신원과 업무 데이터 정본은 갖지 않는다**(X-1~X-5).
> - 상세는 [교류 계층](OPENSPHERE-EXCHANGE-LAYER-v0.1.md).

| 구분 | admin 영역 | 사원 영역 |
|---|---|---|
| 목적 | OpenSphere가 서비스를 구성·운영·복구할 수 있도록 지원 | 회사가 사원에게 업무 서비스와 자원을 제공·통제 |
| 제품 | **Backbone** | **Workspace**, **Governance** |
| 신원 원천 | Backbone 관리 Auth(Supabase Auth) | **내장 Samba AD DC**(기본) 또는 **고객 외부 AD**(D-3) |
| 관리자 | 플랫폼 운영자(admin 신원) | 회사 IT·보안·인사 담당자(사원 신원 + Governance 관리 역할)(D-23) |
| 관리 화면 | **Backbone Console** | **Governance 관리 콘솔**(별도 주소, 관리 역할 전용) + **Workspace 셀프서비스**(전 사원·팀장)(D-49) |
| 소스 | Gitea | GitLab |
| 에이전트 | R2D2(관리 지원) | 개인·부서·프로젝트 에이전트(D-12) |
| 모델 | Backbone 모델 관리(Magpie 등) | 사원 영역 전용 모델 게이트웨이(D-29) |

**경계 불변식**
- **B-1:** admin 신원은 사원 영역의 권한을 자동으로 갖지 않는다. 사원 신원도 admin 권한을 갖지 않는다. 같은 사람이 두 역할을 맡더라도 **신원은 따로 쓴다.**
- **B-2:** Backbone 관리자는 사원 영역 제품을 **설치·운영·복구**한다. 하지만 **어느 사원에게 무엇을 줄지는 결정하지 않는다**(D-23).
- **B-3:** 사원 영역의 데이터·대화·지식·키는 Backbone 저장소에 두지 않는다. Backbone이 사원 영역에서 받는 것은 운영에 필요한 **상태·건강·용량 지표와 단위별 자원 사용량(단위 이름 포함, D-41)**으로 한정한다. 할당 내역, 결재, 감사 본문, 업무 데이터, 로그 원문은 받지 않는다. 상세는 [O-6 문서](OPENSPHERE-BREAKGLASS-O6-v0.1.md).
- **B-4:** 경계를 넘는 모든 요청은 등록된 계약으로만 오간다. 공유 DB 직접 접근이나 공유 관리자 계정으로 넘지 않는다.

**관리 표면 세 개 (D-49)**

| 표면 | 쓰는 사람 | 신원·로그인 조건 | 하는 일 | 비유 |
|---|---|---|---|---|
| Backbone Console | 플랫폼 운영자 | admin 신원 | 설치, 운영, 복구, 공급 풀, 비상 진입 요청, 보안 동결 | 클라우드 사업자의 내부 운영 도구 |
| **Governance 관리 콘솔** | Governance 소유자와 위임 관리 역할 | 사원 신원(AD) SSO. 단, **별도 주소·별도 SSO 클라이언트·별도 세션**이다. MFA 재확인과 짧은 세션을 강제하고, 필요하면 접속 위치를 제한한다 | 사용자·조직(내장 AD), 역할·정책·서비스 메뉴, 배분·quota, 에이전트 관리, 재검토 설정, 감사·사용량, 비상 진입 허락 | Google 관리 콘솔(admin.google.com), Entra 관리 센터 |
| **Workspace 셀프서비스** | 모든 사원, 팀장 | 일반 사원 SSO | 내 권한·내 자원, 신청, **결재함(팀장)**, 재검토 응답, 내 에이전트 | myaccount.google.com, Microsoft My Access |

- 관리 콘솔을 Workspace 포털의 메뉴로 두지 않는다. 앱 취약점이 관리자 세션으로 번지지 않게 하고, Workspace 앱이 고장 나도 회수·정지가 가능해야 하기 때문이다.
- 관리 콘솔은 **도메인 관리자 전용이 아니다.**
  - 소유자는 모든 기능을 쓴다. Google 최고 관리자에 해당한다.
  - 위임 관리 역할은 **기능 범위 + 단위 범위**(예: "영업본부 사용자만")로 제한된 메뉴만 본다.
- 팀장의 결재와 팀 내 배분은 관리 콘솔이 아니라 Workspace 셀프서비스에서 한다.
- 관리 콘솔은 Governance API를 부르는 클라이언트 중 하나다. 같은 기능을 사원 영역 Shell(D-36)로 CLI와 에이전트도 같은 조건에서 쓴다. 결재·활성화·역할 부여는 에이전트에게 계속 금지다.

## 3. 계층 정의

| 계층 | 영역 | 책임 | 하지 않는 것 |
|---|---|---|---|
| **HISS** (L1) | 공통 기반 | K8s, 네트워크, DNS, 저장, 인증서, ingress, 공유 관측 기반. 진단 항목과 관리 항목을 구분한다 | 사원·부서별 자원 할당 |
| **PSSS** (L4) | 공통 기반 | 배포(Argo CD), adapter(Crossplane), 백업·복구, 정책 실행 연계. 사원 영역 배포는 **GitLab CI → Argo**(D-18) | Backbone 자기 배포(Gitea Actions가 담당), 업무 판단 |
| **PFSS** (L5) | 공통 기반 | 공유 capability(DB, 객체, 캐시, 검색, 디렉터리, VM 등)의 Provider·Operator·Operand. Plan → Claim → Instance → Binding, 엔진별 권한 투영 어댑터 | 누가 받을지에 대한 판단(Governance 몫) |
| **Backbone** (구 BBSS, L2+L3) | admin | Console, OS Shell, R2D2, 모듈 관리, 관리 신원·데이터, Gitea·CI, 관측, 자체 업데이트, 독립 복구(D-1) | 사원 권한 내용, 사원 데이터 |
| **Governance** | 사원 | 접근·자원·비용·준수의 정본과 판단(D-2, D-10, D-19) | 엔진 직접 운영(PFSS·앱 어댑터에 위임) |
| **교류 계층** (Exchange, D-75) | 사원↔고객 사이 | 두 영역의 유일한 통과 지점. 교류 객체 계약, 신원 연결, 표현 변환(데이터 최소화), 이벤트 연결기, 교류 감사 | 자체 신원, 업무 데이터 정본, 업무 로직(가격·재고·결재 판단) |
| **업무 코어** (ERP·SCM, D-74) | 사원 | 회사 업무 데이터의 정본: 판매·구매·재고·물류·생산·정산·회계. Workspace·고객 영역·에이전트가 API로 소비 | 사람·에이전트 권한 판단(Governance 몫), 대외 공개(고객 영역 몫) |
| **Workspace** (구 L6 흡수) | 사원 | 사원용 업무 제품 전체: 진입점, SSO, 메일·일정·파일, 메신저, 개발(GitLab), ERP·업무 앱, 사원 에이전트(D-7, D-28) | 권한 판단(Governance 몫), 독자 신원 원천 |

## 4. 종단 흐름: 의도에서 사원까지

```
[회사 권한 관리자 · 사원 신원]
   │ ① 정의 편집(역할·정책·서비스 메뉴) ─ 초안 → 결재 → 활성      ← 에이전트·GitLab MR은 초안 제안만
   │ ② 할당(개인·부서·팀·프로젝트·서비스) ─ 화면/API → 원장
   ▼
[Governance] 원하는 상태 계산 ── 입력: AD(누구·소속) + 정의 + 할당 + 결재 + quota
   │                              출력: 대상별 원하는 상태(SCIM 모양 계약)
   ▼
[프로비저닝 어댑터] ── 앱(Workspace 제품) · PFSS Provider(엔진 권한) · AD(관리 그룹, 허용 모드에서만)
   │ create / update / disable / delete / list
   ▼
[대조] list 결과와 원하는 상태 비교 → 초과 권한은 자동 회수 · 부족 권한은 보고 · 앱 직접 변경은 기록(D-20)
   ▼
[사원] Workspace에서 자기 몫만 사용 ── 자격이 없으면 "보이되 진입 불가 + 이유"
```

**사원 셀프 신청(D-9):**
1. 사원이 Workspace 카탈로그에서 신청한다.
2. Governance가 위험도를 판정한다.
3. 저위험이면 정책에 따라 자동 승인하고, 그 밖에는 결재선(팀장, 자원 담당자 등)을 거친다. **본인 승인은 금지한다.** 에이전트도 결재할 수 없다.
4. 승인되면 ②의 할당이 생기고, 이후 흐름은 같다.

**입사·이동·퇴사:**
- AD 변경이 시작점이다.
- 퇴사 시 **SSO 세션과 새 로그인은 1분 이내에 차단**하고, **앱별 계정은 20분 p95 이내에 비활성화**한다(D-21).

## 5. Governance 상세

### 5.1 범위 (D-10)

| 영역 | 내용 |
|---|---|
| 접근 | 역할·그룹·권한 정의, 할당, 신청·결재, 정기 재검토, 앱별 프로비저닝 |
| 자원 | 개인·부서/팀·프로젝트·업무 서비스 단위의 quota와 배분(D-5) |
| 비용·사용량 | 단위별 사용량과 환산 비용을 보여 주기(showback). quota 초과는 차단. 예산 차감은 후속(D-25) |
| 준수·감사 | 의도와 실제 권한의 대조, 시점별 권한 증거, 감사 보고 |

### 5.2 데이터 정본

| 대상 | 정본 | 비고 |
|---|---|---|
| 사람·계정 상태·조직도(부서 계층, 직책, 관리자) | **AD** | 내장 AD 모드에서는 Governance 화면으로 입력해 AD에 기록한다. 외부 AD 모드에서는 읽기 전용이다(D-22) |
| 정의(역할, 정책, 서비스 메뉴/Plan 제공 규칙) | **Governance 내장 버전 기록** | 수정 불가 revision + 내용 해시 + 결재 참조 + 활성 포인터. 활성화할 때마다 **GitLab 보호 저장소에 서명 사본**을 남긴다. GitLab MR은 제안 채널일 뿐 merge가 승인이 아니다(D-27) |
| 할당, 신청, 결재, 재검토, quota, 사용량 | **Governance 원장** | 정의와 같은 시간축에 둔다. "X일에 누가 무엇을 할 수 있었나"에 답할 수 있어야 한다 |
| 엔진의 실제 권한 | 각 엔진 | Governance는 어댑터 list로 관측만 한다 |

### 5.3 실행 위치

- 엔진과 데이터는 **사원 영역**에 둔다(D-19).
- Backbone이 멈춰도 사원의 신청, 결재, 회수는 계속 동작해야 한다.
- 구체적인 배치(네임스페이스, DB 프로필)는 미결 O-1.

### 5.4 판단 엔진

- 직접 만들지 않고 기존 엔진을 채택한다(D-26).
- 후보:
  - 요청별 판단: Cedar, Cerbos, OPA
  - 관계 기반: OpenFGA, SpiceDB
- 같은 시나리오로 실증 비교한 뒤 정한다. 시나리오:
  - 부서·프로젝트 상속
  - 에이전트 교집합 권한(§7)
  - 결재선 계산
  - 시점별 재현
  - 회수 지연

### 5.5 외부 AD 쓰기 모드 (D-6)

설치 시 고객이 고른다.

| 모드 | Governance의 AD 쓰기 | 관리 그룹이 있는 곳 | 직접 AD를 참조하는 앱(파일, 메일 등) |
|---|---|---|---|
| 읽기 전용 | 없음 | Governance 원장 | 어댑터로 앱별 권한을 투영한다 |
| 전용 OU 쓰기 | 고객이 위임한 OU 안에서만 그룹과 구성원을 관리 | AD 전용 OU | AD 그룹을 직접 사용할 수 있다 |

내장 Samba AD 모드는 항상 전용 OU 쓰기와 같은 방식으로 동작한다.

## 6. 프로비저닝 계약 (D-4)

> **2026-11-20 재검토 개시:** 소유자가 제시한 [OS Govern 업스트림 기반 개발 방향](../specs/OS-GOVERN-UPSTREAM-STRATEGY-v0.1.md)에 따라 아래 midPoint 도입 배제는 기반 선정 평가에서 재검토한다. AD 정본·영역 분리는 유지한다. midPoint 채택이나 D-4 전체 대체를 확정한 것은 아니다.

- **스키마:** SCIM 2.0을 따른다.
  - User + EnterpriseUser 확장(employeeNumber, department, manager)
  - Group
  - OpenSphere 확장: entitlement, unit(개인/부서/팀/프로젝트/서비스), quota, validUntil, approvalRef
- **어댑터 인터페이스:** create, update, disable, delete, list.
  - SCIM 서버를 가진 대상: 범용 SCIM 어댑터 하나로 처리한다.
  - 그 밖의 대상: 대상별 어댑터를 둔다. 기존 PFSS Provider의 엔진별 권한 투영 코드를 재사용한다.
- **대상 유형**

| 유형 | 연동 방식 | 프로비저닝 |
|---|---|---|
| A. 디렉터리 직접 사용 | LDAP/Kerberos | 불필요. AD 그룹만 맞춘다 |
| B. SSO 연동 웹 앱 | OIDC/SAML | **필요.** JIT만으로는 퇴사·사전 권한 문제가 생긴다 |
| C. 앱 자체 계정·역할 | PG role, S3 IAM, ACL, 앱 API | **필요** |

- **SSO 중계:** AD를 읽기 전용으로 federation하는 SSO 중계자를 둔다. 기존 설계는 Keycloak이다. 이 중계자는 원천이 되지 않는다. 제품 선정은 미결 O-3.
- **Syncope, midPoint:** 도입하지 않는다. 원천이나 대상 종류가 크게 늘거나 조직 규모의 재인증 캠페인이 필요해지면 재평가한다.

## 7. 사원 영역 에이전트 (D-12, D-15, D-16, D-29)

| 종류 | 신원 | 실제 권한 |
|---|---|---|
| 개인 에이전트 | 사원에게 위임받은 에이전트 | **그 사원의 권한 이하** |
| 부서·프로젝트 에이전트 | **자체 비인격 신원** | Governance가 할당한 역할 **∩ 요청자의 권한**. 요청자를 항상 함께 기록한다 |

공통 규칙:
- 에이전트는 **결재할 수 없다.**
- 에이전트는 **자기 권한을 넓히거나 정책을 완화할 수 없다.**
- 비밀값은 원문이 아니라 참조로만 다룬다.
- 모델 호출은 **사원 영역 전용 모델 게이트웨이**를 거친다. 사용량과 비용은 단위별로 Governance가 집계한다.
- Backbone의 R2D2와 신원, 자격, 데이터, 키를 공유하지 않는다.
- 요청자 없이 스스로 도는 예약·자동화 작업을 허용할지는 미결 O-4.

**실행 구성(D-50~D-53, [에이전트 구성 재검토](OPENSPHERE-AGENT-RUNTIME-REVIEW-v0.1.md)):**
- 에이전트는 **KubeVirt 자리 VM** 안에서 돈다. 헤드리스 에이전트는 VM급 경량 격리도 쓸 수 있다.
- VM 밖으로 나가는 길은 모델 게이트웨이, 사원 영역 Shell, 기록되는 웹 출구 세 개뿐이다.
- 권한 집행은 VM 밖에서 한다.
- 주 하네스는 OpenBot이며, OEM 라이선스 계약이 선행 조건이다.
- 이를 위해 PFSS에 compute(VM) 모델과 compute 공급 풀이 필요하다.

## 8. 소스와 자기 확장 (D-13, D-16, D-18)

| 영역 | 소스 | 빌드·배포 |
|---|---|---|
| Backbone | Gitea | Gitea Actions(Backbone 자기 관리) |
| 사원 영역(Workspace, Governance, 사원 앱) | GitLab | GitLab CI → PSSS의 Argo CD |
| Governance 정의 | Governance 내장 저장소(정본) | 활성화 시 GitLab에 서명 사본 |

**자기 확장 규칙:**
- 에이전트는 **브랜치·PR(MR)까지만** 만든다.
- 해당 영역 담당자가 검토하고 merge한 뒤, 기존 CI/배포 경로로 반영한다.
- 저위험 변경은 정책에 따라 자동 merge할 수 있다. 무엇이 저위험인지는 Governance(사원 영역)나 Backbone 규칙(admin 영역)이 정한다.
- 영역을 넘는 변경은 허용하지 않는다. 사원 에이전트는 Gitea를 수정할 수 없고, R2D2는 GitLab을 수정할 수 없다.
