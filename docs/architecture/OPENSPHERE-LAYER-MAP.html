OpenSphere 계층 지도

기준선 v0.2 · 결정 D-1~D-79 반영 · 업무 코어·SCM 후보 v0.1 · 2026-11-17 · 설계 기준이며 구현·운영 완료를 뜻하지 않음 · 로고: OpenSphere Logos(logos.opl.io.kr, Statically CDN). 로고가 없는 제품은 글자 표식

위쪽 세 열은 신원·데이터가 분리된 세 영역, 아래 세 줄은 모든 영역이 함께 쓰는 Middle-earth(가칭)의 세 묶음입니다(기반·배포 지원·공유 서비스, D-79). 계층을 누르면 아래에 역할·제품·통신·통제가 나옵니다.

admin 영역플랫폼 운영자 · admin 신원(Supabase Auth)
사원 영역회사 사원 · 사원 신원(Samba AD DC → Keycloak)
고객 영역회사의 고객 · 고객 신원(별도 Keycloak CIAM)
선택된 제품(영역 색)후보·미정(회색)결정 기준선에서 확정후보 PoC·협상·선정 진행재선정 현 시점 기준으로 다시 고름

세 영역은 신원과 채널을 공유하지 않습니다. 영역 안에서는 Shell → 판단 → 소유 모듈로 통제되고, 영역 사이는 등록된 경계 API만 지납니다. Middle-earth는 공급·배분·배포 경로로 연결됩니다.

통제: 입구 → 판단 → 소유 모듈 데이터·이벤트 채널(영역마다 하나) 영역 간 등록 경계 API 공급·배분·Binding 설치·운영·배포

통제 경로 (영역 안)

  1. 화면·CLI·에이전트 → Shell (admin: OS Shell · 사원: 사원 영역 Shell)
  2. 현재 신원·위임 사슬 확인 (사람·에이전트 교집합 권한)
  3. 판단: Backbone 정책 / Governance 판단부
  4. 위험 등급이면 사람 확인 대기 · 결재는 사람만
  5. 소유 모듈이 실행, 효과 직전 재검사
  6. 결과 확인 · 결과 불명은 재전송 없이 조회로 확정

데이터 채널 규칙 (D-66·D-69)

  • 영역마다 하나의 채널, 영역 간 신뢰 뿌리 공유 없음
  • CloudEvents 봉투 + 등록된 스키마만
  • 저장·발행은 outbox로 원자적
  • 최소 1회 전달 + 수신 측 멱등
  • 순서는 대상 키 단위
  • 위임 토큰(act 사슬) 전달, 판단은 Governance

영역 간 통제 (B-1~B-8, O-6)

  • 신원 셋은 섞지 않음: admin · 사원 · 고객
  • Backbone은 설치·운영·복구만, 사원 권한 내용엔 관여 안 함
  • C1 운영 지표·단위별 사용량 보고 / C2 내용 중립 조치
  • C3 비상 진입은 소유자 허락 + 시한부 자격 + 기록
  • 보안 동결은 Backbone 단독 가능(24h 만료)
  • 고객 영역 ↔ 사원 영역은 교류 계층만 통과 (D-75): 교류 객체·신원 연결·데이터 최소화·감사

계층별 기본 역할, 배치 제품, 통신 방식, 통제 주체를 한 표로 정리했습니다. 제품 옆 표시는 결정 상태입니다.

계층영역기본 역할배치 제품통신 방식통제 주체

고객 영역의 핵심인 SCM(공급망 관리)의 정본은 전사 업무 코어(ERP·SCM, 사원 영역)에 두고, 고객 영역은 대외 면(주문·배송·협력사 포털)만 가집니다(D-74). 아래는 업무 코어와 대외 커머스 계층의 업스트림 후보입니다. 업무 코어는 Odoo Community로 선택(D-76, 컬러)했고, 나머지는 후보·비선정(회색)입니다. 고객 영역 구성(커머스 계층·Liferay)은 아직 보류입니다. 라이선스는 GitHub의 LICENSE 원문 기준(2026-11-17), 기능은 공개 문서 기준이며 PoC 전입니다.

왜 코어의 포털을 그대로 공개하지 않나

Odoo·ERPNext의 고객·공급사 포털은 코어 프로세스·DB와 같은 곳에서 돈다. 인터넷에 직접 공개하면 B-6(고객 영역은 업무 DB에 직접 닿지 않음)·B-8(별도 공개 진입점)이 깨지고 코어 취약점이 바로 외부에 노출된다. 그래서 헤드리스 커머스 계층과 OpenSphere 자체 포털을 둔다. 사용자가 적은 협력사 포털은 코어 포털을 별도 진입점 뒤에서 제한 사용하는 안을 PoC에서 비교한다.
