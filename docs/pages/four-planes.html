합의 사용자가 동의한 항목   제안 검토 의견, 결정 전   미정 정해야 할 것   위험 그대로 두면 생기는 문제

Workspace는 제품 묶음이 아니라, Governance가 Fabric에서 잘라 준 내 몫이다.

  • Backbone은 공급한다. Fabric의 구성요소는 공급 면과 사용 면을 함께 가진다.
  • Governance는 사용 면을 권한에 맞게 쪼개 나눈다. 판단만 하고, 집행은 Fabric에서 한다.
  • Workspace에서 사원과 에이전트는 받은 자원으로 자유롭게 앱을 만든다. 좋은 앱은 회사 앱으로 승격된다.

Fabric: 구성요소마다 두 얼굴

경계는 구성요소 사이가 아니라 구성요소 한가운데를 지난다. 얼굴을 나눴다고 선언하는 것만으로는 부족하고, 가운데 열(인스턴스)에서 실제로 떼어 놓아야 한다.

엔진코드 · 버전 · CRD공급자(Backbone)가 제공
인스턴스 ★실행 중인 컨트롤러와 그 권한여기서 공유할지 나눌지 정한다
설정·자격·내용AppProject, DB 자격, 메일함, 데이터소비자(영역)가 소유

권한 판단 엔진: OPA 대신 제안

앱 권한 판단(PDP) → OpenFGA 1순위, SpiceDB와 PoC 비교사원·에이전트·앱이 이 자원에 이 행위를 할 수 있나, 누가 접근할 수 있나(역질의). 테넌트(회사) → 영역 → 어셈블리 → 자원, AD 조직·프로젝트 계층. 둘 다 Zanzibar 계열, 관계·역질의·조건(CEL), PostgreSQL 저장소. OpenFGA는 CNCF라 특정 회사에 덜 묶이고, SpiceDB는 일관성 보장이 더 정교하다.
K8s admission(집행) → Kyverno연결 그래프 밖 리소스, 영역 경계 위반 거부. 서명 이미지 검증이 내장되어 "영역 키로 서명된 이미지만 통과"를 정책 하나로 쓴다.

OPA를 빼는 이유: 범용 엔진이라 앱 권한에 필요한 관계 저장·역질의·시점 일관성이 내장되어 있지 않고, Rego는 회사 권한 관리자가 화면으로 다루기 어렵다. D-26 비교를 건너뛰자는 것이 아니라 후보를 둘로 좁히자는 것이다. PDP 어댑터는 AuthZEN 형태로 두어 엔진 교체가 가능하게 한다. Cerbos는 조건 판단 보조 후보로 남긴다.

백업 소유: 실행은 Backbone, 결정과 열쇠는 영역 제안

엔진 · 실행Velero 설치, 백업 operator, 스케줄 실행, 저장 위치(RustFS·외부 사본), 모니터링Backbone

Backbone이 백업과 키를 모두 쥐면 운영 시스템에 손대지 않고도 백업을 다른 곳에 복원해 내용을 읽을 수 있다(B-3 우회). 반대로 클러스터 전체 장애에서 복구할 주체는 Backbone이다(B-2). 플랫폼 백업(Backbone 자신·etcd·HISS·PSSS 설정)은 Backbone이 전부 갖는다. 기준선의 "PSSS: 백업"과 아카이브의 "Velero 설치=Platform Support, 백업 operator=PFS"는 둘 다 공급 면이라 충돌하지 않는다. Velero·StackGres 백업 키를 영역 KMS로 분리할 수 있는지는 PoC에서 확인한다.

Workspace: 화면이 아니라 리소스 풀

사원이 로그인하면 보이는 것은 에이전트와 자기에게 부여된 회사 자원이다. 웹메일이 없어도 메일함과 메일 서비스 권한이 있으면 Workspace는 성립한다.

내 자원

나에게 배정된 몫. 메일함, 일정, 파일 공간, 자리 VM, 모델 사용량, 사원 앱 도메인, 앱 실행 자원

회사 자원에 대한 내 권한

누구의 것도 아닌 회사 공유 자원을 쓸 권한. 업무 코어(Odoo) 거래 데이터, 공유 드라이브, 회사 앱

승격 가능동료들이 쓰고 싶어 하면 팀 앱, 회사 앱으로 승격을 신청한다

회사 기본 앱(웹메일·메신저·결재 등)은 처음부터 제공한다 합의. 모바일, 신규 입사자, 장애 시 대체 수단이 필요하기 때문이다. 기본 앱도 "회사 앱"으로 다뤄 사원 앱과 같은 모델 안에 둔다.

앱 실행 가드레일

위험 "Governance 안에서 일어나니 위험이 아니다"는 성립하지 않는다. Governance는 누가 어떤 자원을 갖는가를 정하지만, 그 자원으로 만든 코드가 무엇을 하는가는 정하지 않는다. 그래서 플랫폼이 Fabric 사용 면에 아래 네 가지를 강제한다. 제안

인증은 플랫폼이앱 앞에 SSO 프록시. 앱이 로그인을 직접 구현하지 않는다. 취약한 인증 코드가 생기지 않는다
기본은 비공개처음엔 소유자만 접근. 공유·외부 공개는 승격 단계에서 연다
소유자 권한 이하위임 신원으로 실행. 위임 사슬 교집합(D-46·D-47) 그대로
나가는 길 통제외부 송신과 데이터 분류 규칙. "메일 읽기 + 외부 송신" 같은 위험한 조합을 막는다

막으려는 것: 앱 취약점으로 인한 메일함 노출, 정당한 권한의 조합을 통한 반출, 외부 메일 본문을 통한 프롬프트 인젝션, 검토받지 않은 웹앱 수천 개.
