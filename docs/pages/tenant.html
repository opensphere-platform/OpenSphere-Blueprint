테넌트는 회사 차원의 리소스 결합이고, Governance는 그 결과를 사원에게 나눠 주는 방법이다. 둘은 리소스 유형 하나로 만난다. 결정 D-82

  • 테넌트가 정한다: 회사에 무엇이 있고(어셈블리), 어떻게 엮였고(연결), 얼마나 줄 수 있는가(용량). 테넌트 콘솔에서 테넌트 관리자가 정한다.
  • Governance가 정한다: 그중 누가 무엇을 얼마나 쓰는가(정의·할당·결재·회수·재검토·승격). Governance 관리 콘솔과 Workspace 셀프서비스에서 정한다.
  • Backbone은 공급만 한다: Genesis를 시작하고 Fabric 용량을 대지만, 테넌트의 키·구성 결정·배분에는 닿지 않는다.
  • 테넌트를 붙드는 것은 연결 객체다. 연결이 있는 자원은 지울 수 없고, 연결마다 전용 신원을 쓰며, 그래프에 없는 통신은 존재할 수 없다.

한눈에

테넌트는 영역 단위다. 사원 테넌트와 고객 테넌트는 교류 계층으로만 만난다. 오른쪽 세 주체는 각자 다른 것만 정한다.

1. 구성과 배분: 테넌트와 Governance의 경계

같은 사람이 두 역할을 맡더라도 하는 일이 다르면 화면도 다르다. 구성 변경과 권한 배분을 한 화면에 두지 않는다. 결정 D-82

테넌트 (구성)Governance (배분)
묻는 질문회사에 무엇이 있고 어떻게 엮였나, 얼마나 줄 수 있나누가 무엇을 얼마나 쓰나
하는 일어셈블리 추가·제거, 연결, 용량, 건강, 검증, 외부 리소스 편입, 해체정의, 할당, 결재, 권한 판단, 회수, 재검토, 사원 앱 승격
다루는 대상구성요소, 연결, 어셈블리, 용량사람, 부서, 프로젝트, 에이전트, 앱
화면테넌트 콘솔(회사 쪽, 별도 주소)Governance 관리 콘솔, Workspace 셀프서비스
쓰는 사람테넌트 관리자 역할Governance 소유자, 위임 관리 역할, 팀장, 사원
Fabric Claim·소유테넌트가 한다(D-30 개정)하지 않는다. 테넌트가 내놓은 리소스를 배분한다
Backbone ─(Fabric 용량 공급)→ 테넌트: 회사 차원 결합 ─(리소스 유형 + 용량 인계)→ Governance: 회사 안 배분 ─(할당)→ 사원·부서·프로젝트·에이전트·앱
인계 예테넌트가 내놓는다: "메일함 mail.mailbox · 사원당 최대 50GB · 전체 5TB". Governance가 정한다: "전 사원 기본 10GB, 영업본부 20GB, 김OO 30GB(결재)".
겹치는 한 가지테넌트 관리자 역할을 누구에게 줄지는 사람에게 권한을 주는 일이라 Governance가 정한다. Governance 엔진 자체는 테넌트의 governance 핵심 어셈블리로 들어 있다. 운영체제 안에 권한 관리 기능이 들어 있는 것과 같은 관계다.

2. 테넌트와 어셈블리

PostgreSQL, Samba AD DC, OpenSearch, Stalwart를 설치했다고 서비스가 생기지는 않는다. 넷은 서로 관계없는 독립 제품이다. 그래서 묶음을 두 단계로 정의한다. 제안

단위정의경계의 뜻예
테넌트하나의 영역을 이루는 Fabric 자원의 결속 묶음. 신뢰의 뿌리(테넌트 KMS, 내부 CA, 첫 소유자 자격, 네트워크 칸막이)를 가진다누구의 것인가사원 테넌트, 고객 테넌트
어셈블리테넌트 안에서 하나의 목적을 위해 묶인 구성요소 조합무엇을 위해 묶였나메일 = Stalwart + PostgreSQL + OpenSearch + AD + DNS
연결(Link)두 구성요소 사이의 선언된 의존. 연결 전용 신원·자격·인증서·네트워크 허용 규칙을 갖는 일급 객체무엇과 무엇이 엮였나Stalwart → PostgreSQL(store)

한 설치 = 한 회사(D-14)이므로 여기서 "테넌트"는 고객사 구분이 아니라 영역 단위 결속 묶음이다. 일반 SaaS 용어와 혼동되면 이름을 바꿀 수 있다 미정 T-Q1

3. 어셈블리 카탈로그: 테넌트가 내놓는 리소스

사원은 "Stalwart"를 받지 않는다. 메일 어셈블리가 내놓는 mail.mailbox(메일함 10GB)를 받는다. 테넌트는 어셈블리를 구성해 리소스 유형과 용량을 내놓고, Governance는 그것을 받아 나눠 준다. 나눠 주는 단위는 구성요소가 아니라 리소스 유형이다. 제안

Fabric 구성요소→ 묶음 →어셈블리→ 내놓음 →리소스 유형→ 등록 →할당 예: Stalwart · PostgreSQL · OpenSearch · RustFS · AD → 메일 → mail.mailbox → 김OO 메일함 10GB

7. Governance와 잇는 방법

테넌트에서 일어나는 일은 구성과 배분 둘로 갈린다. 구성은 테넌트 관리자가 결정하고, 그 결과(리소스 유형·용량)를 Governance가 받아 배분한다. 배분 결과는 다시 Fabric에서 집행되고, 대조가 둘을 잇는다. 제안

테넌트: 구성→ 인계 → 정의→ 할당·신청→ 결재→ 판단(PDP)→ 투영·집행→ 대조→ 회수·보고↺

청록 = 테넌트·Fabric(구성과 집행), 주황 = Governance(배분 판단).

테넌트에서 일어나는 일: 누가 결정하고 Governance는 무엇을 하나

8. 외부 리소스를 테넌트에 편입해 Governance 리소스로 올리기

회사가 이미 쓰는 외부 AD, SaaS, 기존 DB, 클라우드 저장소, 외부 모델 API도 나눠 주려면 먼저 테넌트 관리자가 외부 어셈블리로 테넌트 구성에 편입하고, 그 리소스 유형을 Governance가 받아 배분한다. 앱 설정에 직접 꽂지 않는다. 제안

외부 리소스→연결기 · 연결 객체 · 연결 전용 자격→외부 어셈블리→리소스 유형 ext.*→할당

통제 등급: 신청자가 고르지 않고 시험으로 정한다

관리형 managed조건: 생성·비활성·삭제 API + 권한 목록 API + 회수 시간 측정 + SSOGovernance: 신청·결재·할당·자동 회수·drift 회수·재검토·showback 전부. 에이전트 자율 실행 허용예: SCIM 지원 SaaS, 외부 AD 쓰기 허용 모드
연동형 federated조건: SSO + 권한 목록 API. 생성·비활성 API는 없거나 일부Governance: 입장(SSO 할당)만 통제, 내부 권한은 대조해 보고만. 에이전트는 사람 결재 후 실행예: SSO만 지원하는 SaaS, 외부 AD 읽기 전용 모드
참조형 referenced조건: 통제 API 없음Governance: 원장에 존재·소유자·위험만 등록, 할당은 수작업 기록, 재검토 대상. 통제할 수 없다는 사실을 숨기지 않는다예: 계정 관리 API가 없는 기존 시스템

관리형 조건을 하나라도 시험에서 통과하지 못하면 한 등급 낮춰 등록한다. 재검토 주기마다 등급을 다시 시험한다.

10. 와이어프레임: 테넌트 생성, Governance 인계, 테넌트 뷰

"테넌트를 만든다"의 해석이 서로 같은지 눈으로 맞춰 보기 위한 화면이다. 구성(테넌트 콘솔)과 배분(Governance 관리 콘솔)을 다른 화면으로 나눴다(D-82). 전제: 테넌트에 필요한 모든 자원은 Fabric이 이미 공급할 수 있는 상태다. 화면의 숫자와 이름은 모두 더미다. 제안

이 와이어프레임이 전제하는 해석 — 다른 곳이 있으면 번호로 짚어 주세요

  1. 테넌트는 영역 단위의 회사 차원 리소스 결합이다. 한 설치(한 회사, D-14)에 사원 테넌트 1개, 필요하면 고객 테넌트 1개. 부서·프로젝트마다 테넌트를 만들지 않는다. 부서·프로젝트는 Governance에게서 리소스를 할당받는다.
  2. 세 주체가 차례로 맡는다. 플랫폼 운영자가 Backbone Console에서 선언·시작(A~B), 테넌트 첫 소유자가 테넌트 콘솔에서 인수·구성·검증(C~G), Governance가 리소스 유형을 인계받아 배분을 시작(H).
  3. Backbone은 키를 보지 않는다. 운영자 화면에는 테넌트 ID·공개 키 지문·상태만 나온다. 설치기 자격은 Genesis 끝에 폐기된다.
  4. 핵심 어셈블리 4개는 고정이다. trust·identity·governance·channel은 고를 수 없고 항상 만들어진다. Governance 엔진도 이때 구성요소로 들어온다.
  5. 업무 어셈블리는 테넌트 관리자가 카탈로그에서 고른다. 고르는 것은 제품이 아니라 테넌트가 내놓을 리소스 유형과 용량이다. 생성 때 고르지 않은 것은 나중에 추가한다.
  6. 연결은 사람이 그리지 않는다. 어셈블리 정의에서 자동 생성되고, 테넌트 관리자의 어셈블리 승인으로 결재를 갈음한다. Governance는 연결에 관여하지 않는다.
  7. 생성 완료 = 적합성 시험 통과. Pod가 떴다고 끝이 아니다. 입사 → 계정 → 로그인 → 회수까지 시험을 통과해야 Active다.
  8. 테넌트 뷰는 테넌트 콘솔에 있고 구성만 보인다. 누가 무엇을 받았는지는 Governance 관리 콘솔에만 있다. Backbone Console에는 상태·용량 카드만 있다.
  9. 테넌트와 Governance는 리소스 유형 하나로 만난다. 테넌트는 "무엇을 얼마나 줄 수 있다"를 내놓고, Governance는 "누구에게 얼마나"를 정한다.
