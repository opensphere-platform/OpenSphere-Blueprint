결정 결정 대장에 있음   제안 명세 초안, 결정 전   미정 정해야 할 것

테넌트는 Fabric 자원을 연결로 엮은 묶음이다. 엮은 실이 테넌트를 붙들고, 모든 실은 Governance가 승인하고 대조한다.

  • 만든다: Backbone이 Genesis를 시작하지만, 신뢰의 뿌리(키·CA·첫 소유자 자격)는 테넌트 안에서 태어난다.
  • 유지한다: 구성요소 사이의 의존을 연결 객체라는 일급 객체로 만든다. 연결이 있는 자원은 지울 수 없고, 연결마다 전용 신원을 쓴다.
  • 통신한다: 결속·요청·이벤트·제어 네 종류로 나누고, 연결 그래프에 없는 통신은 존재할 수 없다.
  • 통제한다: Governance가 판단(Claim·연결·권한)하고 Fabric이 집행한다. 대조가 둘을 다시 잇는다.

한눈에

테넌트는 영역 단위다. 사원 테넌트와 고객 테넌트는 교류 계층으로만 만난다. 오른쪽 두 주체가 테넌트에 손대는 방식은 다르다.

1. 테넌트와 어셈블리

PostgreSQL, Samba AD DC, OpenSearch, Stalwart를 설치했다고 서비스가 생기지는 않는다. 넷은 서로 관계없는 독립 제품이다. 그래서 묶음을 두 단계로 정의한다. 제안

단위정의경계의 뜻예
테넌트하나의 영역을 이루는 Fabric 자원의 결속 묶음. 신뢰의 뿌리(테넌트 KMS, 내부 CA, 첫 소유자 자격, 네트워크 칸막이)를 가진다누구의 것인가사원 테넌트, 고객 테넌트
어셈블리테넌트 안에서 하나의 목적을 위해 묶인 구성요소 조합무엇을 위해 묶였나메일 = Stalwart + PostgreSQL + OpenSearch + AD + DNS
연결(Link)두 구성요소 사이의 선언된 의존. 연결 전용 신원·자격·인증서·네트워크 허용 규칙을 갖는 일급 객체무엇과 무엇이 엮였나Stalwart → PostgreSQL(store)

한 설치 = 한 회사(D-14)이므로 여기서 "테넌트"는 고객사 구분이 아니라 영역 단위 결속 묶음이다. 일반 SaaS 용어와 혼동되면 이름을 바꿀 수 있다 미정 T-Q1

2. 테넌트 생성

선언에서 시작해 검증을 통과해야 활성이 된다. 어느 단계든 실패하면 그 단계만 되돌린다. 제안

3. 테넌트를 유지하는 힘

테넌트를 붙드는 것은 연결 객체다. 설정 파일에 흩어진 접속 문자열 대신, 연결 하나하나를 신원·자격·네트워크·보호가 달린 객체로 만든다. 제안

풀 때도 절차로만: 해체는 결속의 역순

결정 · 소유자 2인→ 동결→ 반출 확인→ 연결 해제 · 자격 폐기→ 공급 회수(Backbone)→ 영구 삭제 · 키 파기(D-33)→ 기록 보존

어느 단계든 실패하면 멈추고 보고한다. 강제로 진행하지 않는다. 영구 삭제는 암호화 키를 파기하는 것(crypto-shred)으로 완료를 보장한다.

4. 테넌트 안의 통신

지금까지의 규칙(D-66, D-69)은 이벤트만 다뤘다. 실제 결속 통신은 SQL·LDAP·HTTP 같은 각 제품의 고유 프로토콜이라 규칙이 비어 있었다. 통신을 네 종류로 나누고, 서로 경로와 자격을 공유하지 않게 한다. 제안

5. Governance로 이어지게 하는 방법

테넌트에서 일어나는 모든 변화가 Governance의 판단을 거치고, 그 결과가 Fabric에서 집행되며, 대조가 그 둘을 다시 잇는다. 제안

정의→ 할당·신청→ 결재→ 판단(PDP)→ 투영·정책 생성→ 집행→ 대조→ 회수·보고↺

주황 = Governance(판단), 청록 = Fabric(집행). Governance는 엔진을 직접 운영하지 않는다.
