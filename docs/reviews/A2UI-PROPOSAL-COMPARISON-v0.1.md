# A2UI 도입 정책 제안서와 OpenSphere 정책 비교 v0.1

**대상:** 「OpenSphere A2UI 기반 화면 구성 아키텍처 및 도입 정책」(2026-11-24, 기술 아키텍처 · 개발 정책 제안. 소유자가 검토를 요청함)
**기준:** D-97 [OS 화면 구성 표준 — A2UI v0.1](../specs/OS-UI-A2UI-v0.1.md), D-95 · D-98 · D-99 · D-102, Backbone main(카탈로그 `opensphere.carbon/v1`, Console 렌더러, S4 PR 186 · 188 · 190)
**작성:** 2026-11-24 · Claude
**성격:** 비교 · 권고다. 이 문서로 바뀌는 결정은 없다. 아래 §4의 "받아들일 것"은 각 층을 설계할 때 따로 결정한다.

## 1. 결론

- **방향은 거의 같다.** 제안서의 핵심(A2UI를 기본 화면 언어로, LLM 없이 결정적으로, Angular 실행 환경 + Carbon 카탈로그, 보안 상호작용은 Angular로 직접)은 D-97로 이미 결정했고, 구현해 운영 중이다.
- **차이는 다섯 갈래다.** 백엔드 언어, 화면 명세를 누가 만드는가, 템플릿의 보관과 신뢰, 역할별 화면, 실행 중 LLM 생성.
- **그대로 들이면 충돌하는 것이 둘 있다.** 서명 없이 관리자 승인만으로 Registry에 저장하는 템플릿, Backbone 안에서 실행 중 LLM이 만드는 화면. 둘 다 서명 · 신뢰 체계(D-98 · D-99)를 우회한다.

## 2. 이미 같은 것

| 제안서 | OpenSphere 정책 · 구현 |
|---|---|
| A2UI 자체는 LLM을 부르지 않는다. 결정적 구성이 먼저다 | 패키지 화면은 서명된 선언 문서를 Console이 그린다. 일반 화면 실행 경로의 LLM 호출은 0회다 |
| Angular가 실행 환경, Carbon이 카탈로그 | Console Angular 22. 닫힌 카탈로그 `opensphere.carbon/v1` 24종(기본 14 + Carbon 10)을 직접 만들었다 |
| 공식 Angular 렌더러의 호환을 검증한 뒤 채택 | 검증했다. `@a2ui/angular` 0.14는 Angular 21 전용이라 렌더러를 Console에 직접 두었다(OS-UI-A2UI §3) |
| 껍데기는 Angular, 전문 편집기 등은 자체 컴포넌트 | 레일 · 탐색 · 로그인 · MFA · 승인 · 계획 확인 창 · 레이어 드래그 · Setup은 Angular. A2UI로 표현할 수 없을 때만 UI 모듈(S2) |
| 사양 판 고정 · 스키마 검증 · 계약 시험 | 사양 v1.0 고정, 업스트림 파일을 커밋으로 고정해 생성기로 닫힌 스키마를 만든다. Node · Rust 판정기와 Setup 봉인 사본이 같은 스키마 · 공유 사례로 판정한다 |
| 허용된 컴포넌트 · 액션만, 모든 액션에서 서버 권한 재검증 | HTML · CSS · 스크립트 · 외부 URL · 함수 정의 금지. 동작은 화면에 선언한 Shell 명령만, 변경 · 파괴 명령은 언제나 OS의 확인 · MFA |
| 숨긴 버튼 · 필드로 접근을 통제하지 않는다 | 권한은 서버(Core 계획 판정 · 정책 · 감사)가 정한다. 화면은 표현일 뿐이다 |
| 기존 카탈로그만 쓰는 새 화면을 프론트엔드 재배포 없이 추가 | D-95의 핵심 원칙. S4-3에서 같은 Console 빌드로 패키지 A → B 갱신만으로 화면이 바뀌는 것을 실증했다 |
| 메시지 크기 · 렌더링 상한, 실패 시 안전한 대체 화면 | 화면당 256KiB · 컴포넌트 2,000, 표 500행 · 차트 계열 10 · 깊이 32 · 노드 5,000. 넘거나 읽지 못하면 그 블록만 대체 표시 |
| `createSurface` · `updateComponents` · `updateDataModel` 메시지 | 같은 메시지를 정적인 한 묶음으로 담는다(OS-UI-A2UI §2) |

## 3. 다른 것

| # | 제안서 | OpenSphere | 판단 |
|---|---|---|---|
| 1 | Go 백엔드 · Go UI Service | Core와 Console 서버(BFF) 모두 Rust다(같은 `backbone-server` 바이너리의 `api` · `console` 모드, 운영에서 확인). 직접 개발하는 백엔드는 Rust로 한다는 것이 소유자 지시(2026-11-12)다 | 전제가 다르다. 제안서의 "Go"는 "백엔드"로 읽는다. Go를 새로 들이지 않는다 |
| 2 | UI Service(템플릿 엔진 · 정책 해석)가 실행 중에 사용자마다 화면 구조를 만든다(Dynamic A2UI) | 화면 **구조**는 패키지에 서명된 정적 문서다. 실행 중 호스트가 채우는 것은 **데이터**뿐이다(닫힌 원천 `instance.*` · `instance.metrics` · `service.*` · 선언된 읽기 명령) | 의도한 차이다. 구조를 서명해 두어야 두 판정기로 미리 판정할 수 있다. 실행 중에 구조를 만들면 이 보증이 사라진다 |
| 3 | `updateDataModel`로 실시간 갱신(CPU 지표 등) | 정적 묶음 하나를 REST로 받는다. 스트리밍 없음. 지표는 다시 읽을 때 갱신 | **빠진 부분이다.** 구조를 그대로 두고 데이터 모델만 증분 갱신하는 것은 우리 원칙과 맞는다 → §4 후보 |
| 4 | Registry에 UI Pages · Templates · Navigation · Actions를 저장. LLM이 설계 → 검증 · 관리자 승인 → 저장 | OSR 스토어는 **서명된 패키지만** 받는다(공급자 서명 · 스토어 · 품질 등급 · 설치본의 지문 승인, D-99) | **충돌한다.** 관리자 승인만으로 저장한 템플릿은 서명 · 신뢰 사슬을 우회한다. 같은 목적은 "AI 작성 → SDK 검사 → 서명된 릴리스 → (현장) 로컬 스토어 → 설치"로 이룬다(PQ · MS7 · SS4) |
| 5 | 사용자 · 조직 · 역할별 화면(경영자 · 관리자 · 현장 작업자), UI Governance 영역 | Backbone Console은 플랫폼 운영자 전용이다. 사원의 역할별 화면은 Governance 관리 콘솔 · Workspace의 몫(D-49, 별도 제품 · 주소)이고 **아직 정의하지 않았다** | **실제로 빈 곳이다.** 다만 Backbone이 아니라 Governance · Workspace 층의 과제다. "화면 정책은 거버넌스 결정을 표현할 뿐 권한을 대신하지 않는다"는 제안서 원칙은 그대로 받을 만하다 |
| 6 | 실행 중 LLM이 화면을 생성(Generative A2UI, 예시 10%) | 에이전트 화면은 D-97 범위 밖이다. 에이전트는 봉인된 제안만 하고 사람이 채택한다(D-102 O4). 모델이 읽은 문장을 지시로 따르지 않는다(A6) | 지금은 허용하지 않는다. 연다면 조건: 같은 두 판정기 · 닫힌 카탈로그, 데이터는 호스트 원천만, 동작은 선언된 명령만, AI 생성 표시(Carbon AI label). 사원 쪽이면 사원 영역 모델 게이트웨이(D-29)를 거친다 |
| 7 | 사용자 · 권한 · 서비스 관리 화면을 A2UI First | 패키지 화면은 A2UI만. OS 자체 내용 페이지는 고칠 때 하나씩 옮긴다(②). 승인 · MFA · 역할 부여 같은 보안 상호작용은 Angular(③) | 범위가 다르다. 권한 행렬 같은 **조회 · 편집 화면**은 A2UI 문서가 될 수 있지만, **확정 동작**(결재 · 활성화 · 역할 부여)은 OS 창이 띄운다. 에이전트에게는 계속 금지다 |
| 8 | 카탈로그 후보: DataGrid · TreeView · OrgChart · Chart · UserPicker · FileBrowser · Workflow · Kanban · PermissionMatrix · AuditViewer 등 | 24종. DataTable · TrendChart · FactTable · EventList · StatusTag · CommandButton은 있다. Tree · 조직도 · 사용자 선택 · 파일 · 워크플로 · 칸반은 없다. Image · Video · `openUrl`은 일부러 뺐다 | 확장 후보 목록으로 쓴다. 카탈로그는 OS 자산이라 컴포넌트를 늘리면 카탈로그 판이 오르고 Backbone도 갱신된다(윈도우가 공용 컨트롤을 OS 갱신으로 늘리는 것과 같다) |
| 9 | 외부 서비스(Gitea · LiteLLM · Stalwart · Keycloak 등)는 서비스 어댑터가 UI Service에 데이터를 공급 | 패키지가 선언한 읽기 명령(Shell)과 호스트 원천으로만 데이터를 받는다(모듈 통합 명세의 A2UI 탭) | 목표는 같고 경로가 다르다. 우리 경로는 정책 · 감사를 거친다. 유지한다 |
| 10 | 정적 70% · 규칙 20% · LLM 10%(예시) | 사실상 서명된 정적 문서 100% + 데이터 바인딩 | 제안서도 예시라고 했다. 우리 비율을 정할 필요는 없다 |

## 4. 권고

**유지:** D-97을 그대로 둔다. 이 제안서로 바뀌는 결정은 없다.

**들이지 않는 것**
- Go UI Service
- 서명 없이 관리자 승인만으로 Registry에 저장하는 템플릿
- Backbone 안에서 실행 중 LLM이 만드는 화면

**받아들일 것 — 나중 과제(지금 D-95 · MS 순서를 바꾸지 않음)**
1. **역할별 화면 정책(Governance · Workspace 층):** 역할에 따라 서명된 화면 · 섹션을 **고르기만** 하고, 권한은 서버가 판정한다. Governance 설계 때 정한다.
2. **데이터 모델 증분 갱신:** 모니터링 화면용. 구조는 그대로, 데이터만 갱신한다. A2UI 표준 v0.2 후보.
3. **카탈로그 확장 후보:** Tree · 사용자 선택 · 조직도 · 감사 보기 등. 실제로 쓸 패키지가 생길 때 카탈로그 판을 올린다.
4. **AI 화면 작성 흐름:** SDK · MCP(PQ 단위)로 **패키지를** 만드는 경로로 둔다. 결과는 서명된 릴리스로만 들어온다.
