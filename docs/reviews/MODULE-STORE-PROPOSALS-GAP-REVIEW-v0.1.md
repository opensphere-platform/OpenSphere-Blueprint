**대상(소유자 제공, 2026-11-25):**
- 「OpenSphere 모듈 기능 요구사항과 MCP 연계 기준」(약 1,470줄, 이하 **요구 문서**)
- 「OpenSphere Store 및 모듈 생태계 통합 설계」(약 1,530줄, 이하 **Store 문서**)

**기준:** 청사진 main 689dc49(요구 문서가 스스로 밝힌 기준과 같다), Backbone main(구현 기록 `docs/osr/`).
**작성:** 2026-11-26 · Claude. 문서마다 검토자 하나가 청사진 사양 · 결정 대장과 대조했고, 핵심 주장은 Claude가 직접 다시 확인했다.
**성격:** 비교 · 권고다. 이 문서로 바뀌는 결정은 없다. §5의 2 · 3번은 소유자 결정 뒤 사양으로 옮긴다.

## 1. 두 문서의 성격

| | 요구 문서 | Store 문서 |
|---|---|---|
| 출발점 | **청사진에서 파생됨.** 기준 커밋 689dc49, 출처가 모두 청사진 파일, D-번호와 계약 수치(listing · A2UI 한도 · 명령 · 이벤트 · 로그)가 일치 | **독립 제안.** 처음 방향(GitHub Store · A2UI · npm SDK · Gitea 자체 갱신)에서 따로 키운 문서. 우리 결정을 모른다(`@opensphere/*` SDK, Go · Cobra, Flux, 역도메인 식별자, Git 파일 Store) |
| 우리와 충돌 | 없음(범위 확대 제안 둘) | 여러 곳 — 모두 우리 결정을 유지(§3) |

## 2. 청사진에 부족한 것(중요한 순서)

### 2.1 운영 · 인증 기준에 걸리는 빈 곳

1. **빈칸 5종에 계약이 없다**(두 문서 공통). 외부 노출 · 로그인 연동, 의존성 · 판 호환(잠금 · 상호배타 · 순환), 엔진 판 올림 · 데이터 이행, 백업 · 복원, 자원 할당 · 한도. [에이전트 운용 적합성](../specs/AGENT-OPERABILITY-v0.1.md) 「놓인 자리」에 이름만 있다. 33스펙 중 5개가 비어 있으면 certified 기준을 정할 수 없다. → 계약 v1.3 새 절 + 새 D-결정, [모듈 명세](../specs/MODULE-INTEGRATION-SPECS-v0.1.md) §1 공통 틀에 x.14(지원 · 제외 범위).
2. **데이터 수명주기 계약**(Store 문서 §10.5 · §17). Disable · Stop · Uninstall · Archive · Migrate · Purge, `migration` 선언, 갱신 전 백업, 복원 검증, RPO/RTO. 우리는 "A→B 갱신은 인스턴스 유지", "내리기는 인스턴스가 남으면 거절"과 모듈별 삭제 규칙(D-98)뿐이다. **D-96(백업 비용 금지)은 지금의 운영 전환에 한정되므로, 앞으로의 데이터 이행 원칙은 별도 결정이 필요하다.** D-33(영구 삭제는 Governance 결정)과 패키지 계약도 이어져 있지 않다. → 계약 v1 §8 + 새 part(`dataLifecycle` · `migration`).
3. **판정이 통과 · 거절 둘뿐**(요구 문서 §3.2 · §26). 판단할 자료가 모자라면 `blocked`, 근거 · 검증자를 갖춘 `not_applicable`이 필요하다. 자기 신고보다 제출된 산출물이 우선. 없으면 `enabled:false`로 의무를 피하는 길을 막지 못한다. → [작성 · 품질 표준](../specs/PACKAGE-AUTHORING-QUALITY-v0.1.md) §4 · §6.
4. **공급자 전환 · 계보**(Store 문서 §3.2 · §14 · §15.4). D-101 §1.5는 "현장 빌드는 다른 정체"에서 멈춘다. Family ID · `derivedFrom`이 없고, 기존 인스턴스 · 데이터를 둔 채 내부 수정본으로 옮기거나 원본으로 되돌리는 절차가 없다. 다른 공급자 모듈의 소스 확보 방식(Binary · Mirror · Local Build · Local Managed · Independent)과 `source.json`(커밋 · 빌드 정의 · 잠금 파일 · 라이선스)도 없다. 소스 주권 목표의 핵심이다. → [중립 다중 스토어](../specs/NEUTRAL-MULTI-STORE-v0.1.md) §6.2, 계약 v1 §8, [자체 소스](../specs/BACKBONE-SELF-SOURCE-v0.1.md) 확장.
5. **보안 공지 · 설치본 영향 분석**(Store 문서 §8.2 · §16.4). 취약점 기준은 신규 등록에만 있고(PQ §4), 이미 설치된 판의 처리와 공지 피드(`advisories`)가 없다. → 목록 v2(§6.1), [OSR v0.2](../specs/OPENSPHERE-REGISTRY-OSR-v0.2.md) §8.3.
6. **폐쇄망 · 오프라인 묶음**(Store 문서 §19). D-103 §6.3의 미결 질문 하나뿐이다. → 중립 다중 스토어 §4 · §12.

### 2.2 규격 품질과 도구

7. **요구 원장 · 규칙 레코드**(요구 문서 §26). 요구마다 출처 · 채택 · 강제 수준, 적용 조건식, 책임 주체, 필요 산출물, 검증기 판, 통과 조건, 판정 범위, 승인 경계, 재평가 조건. 정본은 Backbone `infra/contracts/osr/`(Q-2). → 작성 · 품질 표준 새 절 또는 별도 `REQUIREMENT-LEDGER`.
8. **개발 MCP 도구 계약**(요구 문서 §27.2, Store 문서 §21.7). 도구 이름 · 입출력 · 공통 응답 형식(요청 id · 규칙 판 · 대상 digest · 결과 · 사유 · 증거 · 다음 단계)이 없다. Copilot cloud agent는 Tools만 지원하므로 Resources만으로는 부족하다. → PQ §7.
9. **시험군 · 증거 형식**(요구 문서 §28). 요구마다 시험 · 반례, 증거에 프로필 · 정책 · 신뢰 세대 · 기대값 · 실제값 · 검증 못 한 범위. OS 통합 7명제 · 19스펙의 정식 번호표, 모듈 명세 공통 틀의 에이전트 운용(M3 · M4 · M6)과 비상 등급(C1~C3) 칸도 함께. → 계약 v1 §0 · §9, 모듈 명세 §1.
10. **모듈 간 확장 지점**(Store 문서 §9.3 · §12.1). `provides`/`consumes`, 데이터 정본 바인딩. 지금 패키지 사이 연결은 Claim 소비(C-4)뿐이다. → 계약 v1 부록 C.
11. **작은 것:** 복구 승인의 1회성(nonce), 설치본별 갱신 정책(Pinned · SecurityOnly · CompatibleAuto · LocalManaged), Store 상태 시각 구분(마지막 시도 · 성공 · 검증 · 다음 예정), 판정 축 · 승인 4종 한 장 표. 생태계 운영(RFC 절차 · 폐지 예고 · 알 수 없는 필드 · 상용 자격 · 다른 플랫폼 적합성)은 나중 과제.

## 3. 충돌 — 우리 결정을 유지

| Store 문서 | 우리 결정 | 판단 |
|---|---|---|
| Store = Git 저장소 파일(Contents API · ref 고정) | 서명된 OCI 목록 봉투를 GHCR에, Git은 심사 원본(D-99, 중립 다중 스토어 §7) | 신뢰가 서명에 있으므로 우리 쪽 |
| 처음부터 GitHub · Gitea Provider | 처음은 GHCR만, 코드는 레지스트리 · 저장소 · 토큰 경로 분리(§12.5) | 우리 쪽(오프라인은 §2.1-6) |
| Console에서 Store마다 PAT 입력 | 공개 · 익명 읽기, 비공개는 운영자 전용 worker/Secret, Console은 비밀 없음(MS2 · MS6) | 우리 쪽 |
| 관리자가 화면에서 연결 확인 → 등록 | 오프라인 서명 + 소유자 MFA(MS4), 화면은 미리 보기만 | Store 추가는 신뢰 결정 — 우리 쪽 |
| Gitea 한 곳에 미러 · 수정본 · 배포 설정 · 내부 Store | 자체 소스 · 사용자 Gitea(G1) · 로컬 스토어 분리(D-101 · D-103, SS3) | 우리 쪽 |
| Flux GitOps | "클러스터 안의 상시 갱신 서비스나 GitOps를 들이지 않는다"([갱신 분리 v0.2](../specs/BACKBONE-UPDATE-DECOUPLING-PLAN-v0.2.md) §1), 쓰기는 Core 계산 + 승인 웹훅(D-92) | 우리 쪽 |
| Store 차원의 A2UI 소개 화면 | 공통 부분은 A2UI를 모름, listing은 markdown(S99 원칙 4, 계약 §2) | 우리 쪽 |
| 조직 · 팀 · 개인 단위 설치 | 한 설치 = 한 회사(D-14), 배분은 Governance(D-82) | 우리 쪽 |
| 개발 MCP가 파일을 쓰고 시험을 실행(Store 문서) · 운영 인계 묶음 준비(요구 문서) | 로컬 · 읽기 전용(Q-6) | Q-6 유지. 넓히려면 별도 결정 |
| 역도메인 식별자, 여러 SDK 패키지 | `<공급자>/<이름>`(S99-5), 단일 `@triangles-store/store-sdk`(Q-7) | 우리 쪽 |
| 갱신 전 백업을 P0 위험으로 | D-96 · D-98(지금은 백업 범위 밖) | 지금 전환에는 우리 쪽. 앞으로는 §2.1-2로 결정 |

## 4. 같은 결론에 이미 닿아 있는 것

공급자 선언이 운영자 정책을 덮지 못함 · 같은 판 다른 digest는 충돌 · 스냅숏 한 묶음 활성화와 하한 · 만료 시 신규만 멈춤 · 승인을 digest에 묶고 실행 직전 재확인 · 멱등 · `unknown` · 복구 · 자격 참조와 redirect 무자격 · 스토어 간 신뢰 비전파 · Solution과 잠금(어셈블리) · PDP/PEP와 통제 등급 · 실행 격리 · 내부 빌드 격리(SS4) · SBOM과 빌드 출처 · 운영 관측과 매뉴얼 · SDK와 같은 원천 판정기 · A2UI 한도.
요구 문서 §2~§23 · §25는 거의 전부 청사진의 기존 절과 일치한다(정체 · Store · 화면 · 명령 · 원형 · Claim · 갱신 · 어셈블리 · Governance · 업무 데이터 · 신원 · 외부 편입 · 통신 · 이벤트 · 로그 · 에이전트 운용 · HISS · 소스 · 모듈별 범위 · SDK).
