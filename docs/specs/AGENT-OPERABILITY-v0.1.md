## 놓인 자리

- **OS 모듈 = OS 통합(7명제 · 19스펙) + 에이전트 운용 적합성(6명제 · 14스펙) = 13명제 · 33스펙.**
  - OS 통합 19스펙 = 계약 v1 · v1.1의 14종 + 빈칸 5(외부 노출 · 로그인 연동, 의존성 · 판 호환, 엔진 판 올림 · 데이터 이행, 백업 · 복원, 자원 할당 · 한도)
- OS Govern(7명제 · 17스펙)은 OS 쪽 체계다. 모듈은 권한 요청 · Claim으로 만난다.
- **R2D2(OpenClaw) 구축 · 운영은 이 계약을 쓰는 하나의 에이전트일 뿐이다.** 다른 업스트림 에이전트도 같은 계약으로 모듈을 운용한다.
- **2026-11-28 (D-119):** Workspace의 사원 에이전트도 공식 OpenClaw를 쓴다. 사원 영역에서는 같은 계약을 사원 영역 Shell(D-36)의 에이전트 입구로 열고, 이 계약이 하네스가 바뀌어도 남는 경계다([에이전트 전략 투영](../architecture/OPENSPHERE-AGENT-STRATEGY-OPENCLAW-v0.1.md) §5 · RT-8 · RT-10).

## 0. 관점(소유자)

- R2D2(OpenClaw) 구현이 아니라, **모듈 입장에서 OS 통합이 완전하려면 어떤 AI 에이전트든 운용할 수 있게 하는 기술 요소**.
- 다른 업스트림 에이전트에도 적용돼야 한다. 에이전트 구현 · 운영 방식이 표준화돼 있지 않은 것이 어려움이다.

**접근:** 표준을 OS 경계에 둔다. 보장하는 것은 "합의된 기능을 갖춘 클라이언트의 상호 운용"이다(JSON Schema = 입출력 형태, OpenAPI = HTTP 계약, MCP = 도구 발견 · 호출). 에이전트의 승인 UI · 상태 보관 · 재접속 능력은 다르므로 **최소 적합 조건**을 둔다: 지원 계약 판, 신원 제시, 닫힌 오류 처리, 작업 id 보관과 재조회, 사람 승인 인계.

| A6 | 근거와 지시를 가른다. 출처는 OS 관측 사실 · 검증된 릴리스 선언 · 패키지 자유문 · 사용자 입력 넷으로 구분한다. **모델이 읽은 문장을 따르지 않는다는 보장은 할 수 없다** → 응답 최소화 · 범위별 예산 · 설치본 교차 차단 · 사람의 효과 확인을 함께 둔다 | 한계를 명시했다 |

## 3. Nexus 관계(#99)

- 계약에 넣을 문장: "관리자와 위임 주체의 패키지 관리 요청은 호스트가 정한 typed Nexus action으로 받는다. 서버가 면을 정하고 인계 때 현재 신원 · 위임 · 범위를 다시 확인한다. 사전 감사에 실패하면 인계하지 않는다. 요청 종류별 예산을 집행하고 결정 id를 소유 원장의 작업 · 결과와 잇는다. Core와 실행부는 기존 최종 승인 · 대상 · fence 검사를 한다. 패키지 선언은 Nexus action · 면 · 권한을 더할 수 없다."
- **"모든 통합 지점이 Nexus를 지난다"는 사실이 아니다.** 경로별로 표를 따로 둔다: carrier/reader(전용 서비스 신원 · 서명 · 해시), Core ↔ 실행부 · 승인 웹훅(토큰 · 승인 계획 · fence · 객체 대조), Claim의 엔진 데이터 접속(발급 자격 · 망 정책), `/osr-ui` 공개 정적 자산(활성 번들 · 색인 · IP 제한 · CSP).
- 구현 상태: `observe_owner`는 조회 슬롯과 decision id를 적용하지만 `authorize_change`는 위임 차단 · 게이트 · 감사만 하고 변경 슬롯 4개를 잡지 않는다. HTTP 헤더는 상관 표지이고 승인 증거는 Core 원장이다.
- 새 기능의 Nexus 몫: D-99 `osr.store.manage` 계열(Management 전용), D-100 `osr.logs.read`(하나의 판정 · 핸들러), D-100 이벤트는 기존 `SwallowDispatch` 재사용(정책 지문 변화 0), O1은 읽기 · 제안을 나눠 열면 각 1회.

## 5. 순서(#98 H)

- E7a · MS 순서 유지. 문제 코드와 읽기 출력의 출처는 C9 · C10 위에 얹는다.
- P1에는 선택 증거 한 건: 스크립트가 Valkey · Gitea의 기존 Shell 계약 상태 · 진단을 읽고, 회수 뒤 사라지는지. **P1에 새 인증 · MCP · 위임을 넣지 않는다.**
- 승인 뒤: ① 구조화된 문제 · 출처 + 위임 읽기(발견 · 호출) ② 사람 채택이 있는 에이전트 제안 + 감사 연결 ③ 회수 · 예산 · 정지 + 어댑터 교차 · 비결정성 평가. 자동 변경 허용은 별도 결정.
