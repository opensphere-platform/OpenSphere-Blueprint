- 지금 운영 클러스터의 Gitea 둘(2026-11-24 확인):

| Gitea | 위치 | 지금 역할 |

- 그대로 가면 고객 설치본에는 R2D2가 자체 업데이트에 쓸 소스가 없다. 원칙이 개발 현장에서만 성립한다.

## 1. 결정(D-101)

1. **모든 설치본에 "Backbone 자체 소스"를 둔다.** Backbone 구성요소(관리 영역, 스토어 밖)이고 Setup이 설치하며 Backbone과 함께 갱신된다.
2. **사용자용 Gitea 패키지(`delivery.gitea`)와 분리한다.** 패키지가 Backbone 소스를 맡으면 패키지가 Backbone을 통제하는 권한 역전이 생긴다.
3. **두 가지 모드**
   - **정본 모드(Triangles 개발 현장):** Backbone과 Triangles 자체 패키지 소스의 정본이고, 보호 main · 필수 검사 · 게시 경로(지금 `development-source`의 역할)
   - **설치본 모드(고객 현장):** 설치된 판의 소스를 담는다. R2D2가 진단 · 수정 제안(브랜치 · PR)을 한다. **현장 빌드는 기본 꺼짐**이고 운영자가 켠다
4. **R2D2는 브랜치 · PR까지만 한다**(D-16). 병합은 사람이 한다. 에이전트는 승인자가 될 수 없다(G-INV-2).
5. **현장 빌드를 켜면 결과물은 그 현장의 로컬 스토어로 나간다**(D-99). 공급자 = 그 현장, 서명은 현장 운영자 키. Universe의 `triangles/…` 판과 정체가 갈린다.

## 2. 담는 것

| 저장소 | 내용 | 정본 모드 | 설치본 모드 |
|---|---|---|---|
| `backbone` | Backbone 소스 | 정본 | 설치된 판의 원천 커밋(릴리스 `sourceRevision`과 대조) + 현장 브랜치 |
| `packages/<공급자>/<이름>` | 설치된 자체 패키지 소스 | `triangles` 정본 | 설치된 판의 원천 + 현장 브랜치 |
| `upstream/*`(읽기 전용 보호 브랜치) | 새 릴리스의 원천 | — | 새 판이 들어오면 그 원천 커밋을 받는다. 현장 변경은 PR로 그 위에 다시 얹는다 |

- 설치된 판의 원천이 들어올 때 **릴리스 digest · 원천 커밋 · 서명**을 대조한다(SOB §2.6). 맞지 않으면 받지 않는다.
- 비밀값은 저장소에 두지 않는다(SOB §2.7).

## 3. 흐름

**정본 모드(지금과 같음)**
- R2D2 · 개발 에이전트 → 브랜치 · PR → 필수 검사 → 사람 병합 → 보호 main 게시 → Backbone 이미지(소유자 승인 반영) · 패키지(Universe, 오프라인 목록 서명)

**설치본 모드**
1. R2D2가 진단하고, 자체 소스에 브랜치 · PR로 수정안을 낸다(근거 · 시험 결과 포함).
2. 현장 관리자가 검토한다.
3. 갈래
   - **현장 빌드 꺼짐(기본):** 수정안을 Triangles로 보낸다(제안 전달, 방식은 §6 미결). 현장은 다음 릴리스를 받아 적용한다.
   - **현장 빌드 켜짐:** 병합 → 현장 러너가 빌드 → 현장 운영자가 서명 → 로컬 스토어 → 관리자 MFA로 설치 · 갱신. Backbone 이미지는 현장의 Backbone 갱신 승인 경로로.
4. 새 릴리스가 오면 `upstream/*`로 받고, 현장 변경은 PR로 다시 얹는다. 충돌은 사람이 푼다.

## 4. 경계

- **R2D2:** 자체 소스에 읽기 + 브랜치 · PR 쓰기만. 보호 설정 · 필수 검사 · 러너 · 서명 키에는 손대지 못한다(SOB §2.8, 자기 경계 불변).
- **현장 러너:** 빌드에 고권한이 필요하므로 **HISS 클래스**로 둔다(D-88). 외부 기여 코드 실행 규칙(품질 표준 §5)과 같이, 서명 키 · 운영 자격을 러너에 두지 않는다.
- **서명:** 현장 운영자 키는 오프라인. 러너 · R2D2는 서명하지 않는다.
- **영역:** 관리 영역(admin)이다. 사원 에이전트는 자체 소스를 고칠 수 없고, R2D2는 사원 영역 GitLab을 고칠 수 없다(기준선 §8).
- **보존:** 설치본마다 호스트와 무관한 보존 사본을 둔다(SOB §2.11). 정본 모드의 GitHub 보존 사본(`opensphere-platform/OpenSphere-Backbone`, 지금 수동 갱신)도 같은 규칙이다.
- **복구:** 자체 소스나 R2D2가 죽어도 Backbone을 복구할 수 있어야 한다(SOB §2.9). 자체 소스는 복구 경로의 필수 조건이 아니다.

## 5. 기존 결정 · 계획에 주는 영향

- **D95-8 개정:** `backbone-gitea`를 걷어 내지 않고 **Backbone 자체 소스로 다시 정의한다**(사용자 저장소 용도는 뺀다). 옛 사본(커밋 274)은 정리하고 설치된 판의 원천으로 다시 채운다. 사용자용 Git 저장소는 `delivery.gitea` 패키지가 맡는다.
- **G1(Gitea 패키지) 범위:** 사용자용 Gitea만 패키지로 만든다. 관리 Gitea(`backbone-gitea`)의 Stateful/DB 자원과 검증된 소비자 연결(Console Git/CI · Nexus adapter · 지식 수집 · source webhook)은 그대로 둔다. "Core의 Gitea 주소"는 Core에 그런 항목이 없으므로 "Backbone의 자체 소스 바인딩을 유지한다"로 좁힌다. 새 Core 외부 Git 연결은 더하지 않는다.
- **D-99 빌드 증명:** 공급자 `triangles`의 빌드는 정본 모드의 Gitea 보호 main에서 나온다. GitHub 증명과 검토된 Gitea 증명 경로를 **별도 허용 빌더**로 정의하고, 정확한 source · run · workflow · artifact를 공통 증거에 묶는다. 공급자 문자열이나 Gitea API의 성공 표지만으로 신뢰를 주지 않는다(별도 결정).
- **모듈 명세:** x.13 "원천 · 빌드"(소스 저장소, 보호 워크플로, 빌더 정체, R2D2가 고칠 수 있는 범위)를 더한다.

## 6. 미결에 대한 결정(D-103)

1. **수정안 전달:** 첫 경로는 관리자가 명시적으로 반출하는 **수동 제안 묶음**. 원 공식 릴리스 digest, 기준 커밋 · 대상 트리, 선택한 커밋의 patch, 검사 결과, 익명화한 재현 조건. 저장소 전체 · 설치본 데이터 · 비밀값 · 내부 토큰 · 로그 원문은 뺀다. 관리자가 내용과 수신처를 확인한다. Triangles는 기준을 검증하고 일반 PR로 새로 심사한다. 고객 Git에 공급자 쓰기 계정이나 운영망 통로를 두지 않는다. 교류 계층 연결은 후속 단위.
2. **용량 · 보존:** D-96(엔진 운영 데이터)과 분리한다. 최소 보존: 공식 · 현장 ref와 Git 객체, 서명된 소스 묶음의 digest · 출처, 현장 변경 · 검수 증거(LFS를 쓰면 그 객체). PR · 보호 설정까지 되살리려면 Gitea DB의 해당 메타데이터를 따로 묶는다. 실행 로그 · 빌드 캐시 · 임시 export는 뺀다. 저장량은 실측으로 정하고, 기본 상한을 두며, 차면 기존 ref를 지킨 채 새 반입을 거절한다. 설치본 밖 매체에서 실제 복구를 한 번 해 본다. 운영자 키 · 복구 비밀은 Git 보존과 별도.
3. **현장 Backbone 갱신:** 현장 패키지 발행(현장 공급자 · 로컬 스토어)과 Backbone 자체 갱신(스토어 밖)은 승인 · 신뢰를 분리한다. Backbone 갱신은 검토한 소스 · 워크플로 · 빌드 증명, 구성요소별 AMD64 digest, BOM, 이행 순서 · 해시, 정책 · 카탈로그 지문, 현재 설치본 · 이전 수용판을 한 봉투에 묶고, 사람 승인과 독립 신뢰키로 반영한다. 현장 키는 공식 배포 신뢰를 대신하지 못한다. 지금 Setup의 `apply-backbone-bundle` · `adopt-runtime`에는 임의 현장 이미지를 받아 승인하는 동작이 없으므로 후속 계약이 필요하다. "로컬 스토어"가 현장 소유 GHCR 범위인지 망 분리 OCI 레지스트리인지 먼저 정한다(후자는 새 전송 · 인증 · 신뢰 계약).
4. **개발 현장 합치기:** 처음에는 물리적으로 합치지 않는다. 개발 정본과 검증된 보호 main · CI · 게시 신원을 유지하고, 설치본 쪽은 검증된 설치 소스 스냅숏을 둔다. 공통점은 "검증된 자체 소스 바인딩"이다.
5. **현장 변경 충돌:** 설치본에 "공식 upstream"과 "현장 수용판"을 별도 ref · 서명 · 영수증으로 둔다. upstream ref는 서명된 소스 증거를 검증한 공식 importer만 쓴다. 병합 충돌 · 실패한 보안 승인 · DB 이행 호환 문제에서는 자동 강제 갱신을 멈춘다. 공식 보안 수정을 넣기 어려우면 관리자가 현장 패치 재작성이나 공식판 복귀를 정한다. R2D2는 진단과 PR 제안까지.

## 7. 구현 단위(D-103)

| # | 단위 | 내용 |
|---|---|---|

| SS3 | 브랜치 · PR 제안과 G1 분리 | Console reader · 반입자 · 브랜치/PR writer · 보호 정책 관리자 · runner · signer를 나눈다. 보호 ref 쓰기 · merge · 관리 API · 범위 밖 저장소 호출 거절 시험. R2D2 쓰기는 D-102 순서(위임 → 제안)를 따른다. 소스가 있다는 사실로 쓰기를 열지 않는다 |
| SS4 | 현장 빌드 · 출판 · Backbone 승인 | 기본 꺼짐을 먼저 입증. 켤 때는 HISS 격리 빌드, 외부 코드는 품질 표준 격리 기준. PR 코드가 CI 검사 · 게시 경로 · 운영자 정책을 바꾸지 못하게. 허용 빌더(GitHub · Gitea) 정의. 패키지와 Backbone 갱신의 승인 · 서명을 따로 실증 |
| SS5 | 보존 · 장애 격리 | 관리 Gitea나 R2D2가 멈춰도 승인된 이미지 · 정의 · 복구 지침으로 관리 기능을 되살리는 시험. 사용자용 `delivery.gitea`와 관리 자체 소스가 계정 · PVC · 빌드 자격 · 망 · 원장 · 복구에서 분리되고, 한쪽 회수가 다른 쪽을 막지 않음 |

### 7.1 다른 단위와의 순서
- **SS1 · SS2(읽기 전용)는 MS3a 다음에 바로 한다.** SS2에서 Console Git/CI · Nexus adapter · 지식 수집 · source webhook이 같은 설치본 소스 좌표를 실제로 읽는지 검증한다.
- SS3은 G1(사용자용 Gitea 패키지)보다 먼저 한다(G1이 관리 Gitea를 걷어 내지 않도록 경계를 먼저 세운다). R2D2의 쓰기는 D-102 순서(P1 뒤 위임 → 제안)를 따른다.
- SS4는 MS7(로컬 스토어를 포함한 다중 스토어 게시 실증) 뒤다.
- SS5는 P2(운영 전환) 전에 한다.
