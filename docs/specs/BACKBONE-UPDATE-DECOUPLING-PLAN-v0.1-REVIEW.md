# Backbone 업데이트 분리 계획안 v0.1 — 검토 회신

- 작성: Claude / 2026-11-18 KST
- 대상: `BACKBONE-UPDATE-DECOUPLING-PLAN-v0.1.md` (Jupiter 초안)
- 상태: 협의용 회신. 합의·구현·운영 적용 문서가 아니다. 이 회신으로 코드나 운영을 바꾸지 않았다.
- 읽은 기준: Backbone main `989b491` (PR 43까지 병합), 운영 설치본의 2026-11-18 적용 결과

## 1. 결론

방향에 동의한다. Setup은 실행 도구로 두고, 버전별 갱신 정의를 서명된 불변 Bundle로 밖에 두는 것이 맞다.

다만 초안 그대로 구현하면 오늘 운영에서 난 것과 같은 실패가 더 자주 날 수 있다. Setup 새 판을 내는 마찰이 사라지면 Bundle이 더 자주 나오는데, 지금은 실제 적용 경로를 운영 전에 돌려 볼 방법이 없기 때문이다. 아래 네 가지를 조건으로 붙인다(3절).

충돌은 없다. 다만 초안 2절의 확인은 교정 방식(결정 D12)이 들어가기 전의 작업 트리를 읽은 것으로 보인다. `setup/src/backbone-bundle.mjs`, `backbone-bundle-profile.mjs`, `backbone-bundle-assets.mjs`는 `989b491` 기준으로 다시 읽어야 한다.

### 오늘 운영에서 실제로 난 일

초안의 설계 판단에 직접 영향을 주므로 적는다.

1. **마이그레이션의 가정이 제품과 달랐다.** Setup은 Console의 DB 역할을 상속하지 않는 역할(`NOINHERIT`)로 만든다. 묶음 1의 마이그레이션은 권한을 묶음 역할에 주고 Console을 구성원으로만 넣었다. 그래서 Console은 구성원이지만 권한이 없었다(HTTP 403).
2. **검증 규칙이 틀렸다.** 새 원장은 작업 기록이 0건인데 검증이 1건 이상을 요구했다. 1번만 고쳤으면 또 멈췄을 것이다.
3. **둘 다 격리 시험을 통과했었다.** 격리 설치본을 손으로 만들면서 역할을 기본 속성으로 만들었고, 원장에는 이전 실행의 기록이 남아 있었다.
4. **적용 명령 자체는 운영에서 처음 실행됐다.** 격리 설치본에서는 이미지와 SQL을 따로 넣었고, `apply-backbone-bundle`을 끝에서 끝까지 돌린 적이 없다.
5. **봉인 항목은 고쳐 쓸 수 없었다.** 멈춘 설치본의 기록이 항목 지문에 묶여 있어서다. 그래서 "교정"이라는 별도 단계를 새로 만들었다(D12).

## 3. 조건 네 가지

### 3.1 실제 적용 경로를 운영 전에 돌려 볼 곳이 있어야 한다

- Setup의 대상 namespace는 `os-backbone-system`으로 고정이다(`setup/src/contracts.mjs`의 `NS`). 격리 namespace에는 Setup 명령을 실행할 수 없다.
- 그래서 초안 8절 3단계("운영 RKE2의 격리 namespace에서 apply/resume/recovery 시험")는 지금 구조로는 할 수 없다. 할 수 있는 것은 오늘처럼 조각을 따로 넣어 보는 것뿐이고, 그것이 2절의 실패를 놓쳤다.
- 요구: **Setup이 직접 만든 연습용 설치본**에 같은 공개 바이너리로 같은 명령을 실행할 수 있어야 한다. 손으로 만든 설치본은 수용 증거로 인정하지 않는다.
- 방법 후보: (가) 엔진의 namespace와 설치 루트를 연습 profile에서만 바꿀 수 있게 한다. (나) 작은 연습용 클러스터를 따로 둔다. (가)가 기존 자원으로 가능하다. 다만 클러스터 범위 자원(스토리지, 승인 정책, NodePort)을 어떻게 나눌지 설계가 필요하다.
- 이것은 외부 Bundle보다 **먼저** 한다. 내장 profile 그대로도 값이 있다.

### 3.2 멈춘 적용을 이어받는 규칙이 있어야 한다

초안 5절은 "하나의 정확한 predecessor와 직선 체인"만 말한다. 오늘 필요했던 것은 그 밖의 경우다.

- 검증에서 멈춘(`prepared`) 기록이 있는 설치본을 **어떤 Bundle이 이어받는가.** 같은 이미지에 SQL 하나만 더한 Bundle이 필요하다. 지금 체인 검사는 다음 항목이 이전과 다른 이미지를 갖도록 요구하므로 그대로는 안 된다.
- 제안: Bundle에 `corrects: <이전 Bundle 지문>`을 둔다. 교정 Bundle은 이전 Bundle의 단계를 그대로 포함하고 단계만 더할 수 있다. 이미 목격된 단계는 다시 실행하지 않는다. 지금의 `correction:<sha256>` 단계가 이 규칙의 내장판이다.
- **predecessor에는 항목 지문과 적용된 교정 목록이 함께 묶여야 한다.** 교정 1이 적용되지 않은 묶음 1은 다음 Bundle의 올바른 출발점이 아니다.
- 이미 끝난(`ready`) 설치본에 나중에 나온 교정을 넣는 경우도 같은 규칙으로 다룬다.

### 3.3 원장에 Bundle 지문만 적어서는 부족하다

- 이전 작업의 재개는 "묶음 적용 뒤의 기대 상태"를 내장 profile에서 계산한다. `engine.mjs`, `console-chain*.mjs`, `console-refresh.mjs`, `nexus-enforcement.mjs`, `nexus-adoption.mjs`, `nexus-ui.mjs`, `bus-inspection.mjs`가 모두 그렇다.
- profile이 밖으로 나가면, 지문만 적어 둔 원장으로는 Setup 명령마다 과거 Bundle 파일이 있어야 한다. 파일이 없으면 `verify`조차 못 한다.
- 요구: 적용할 때 서명으로 검증한 **전이 사실**을 원장에 함께 남긴다. 최소한 Console·Core 이미지와 판·소스 커밋, 정책·카탈로그 지문 전후, 워크로드 spec 지문 전후, 적용한 자산의 sha256 목록이다. 이후 명령은 원장만 읽는다. Bundle 파일은 끝나지 않은 적용의 재개에만 필요하다.
- **크기:** 원장은 ConfigMap 하나이고 지금 약 115KB다(한도 1MiB). 묶음 기록 하나가 약 7.6KB다. 누적 대책(완료 기록의 요약과 보존본 분리)을 계약에 포함한다.

### 3.4 "선언형 단계"의 닫힌 목록을 먼저 정한다

- 묶음 1은 이미지 교체만 한 것이 아니다. Console에 신뢰 기준 환경 변수를 넣었고(`bundleSpec`), 검증은 릴리스 고유의 항목(버스 한도 값, OSR 원장 열림, 신뢰 기준 설정)을 봤다. 이것들은 지금 코드다.
- 제안하는 v1 단계 종류: `backup`, `image-cache`, `migration`(DB · 역할 · 정확한 바이트), `workload`(대상은 `backbone-api`, `backbone-console`만. 바꿀 수 있는 것은 이미지, 소스 커밋 표식, 이름 규칙에 맞는 **공개 값** 환경 변수), `verify`.
- 제안하는 검증 항목 종류: 워크로드 UID와 spec 지문, 보존 항목(TLS · 발급 키 · 역할 목록 · 콜백), 마이그레이션 표식, 그리고 **Console/Core의 읽기 전용 응답에 대한 필드 비교**(경로, JSON 포인터, 같음 · 이상 · 존재). 2절 2번 같은 규칙이 Bundle 안으로 가서, 틀려도 Setup 새 판 없이 고칠 수 있다.
- 수용 시험: 묶음 1과 교정 1을 이 목록으로 다시 표현해 **같은 단계 순서와 같은 워크로드 spec 지문**이 나오는지 확인한다. 안 되면 목록이 모자란 것이다.
- 목록 밖의 변경(새 워크로드, 새 Secret, RBAC, 비밀 참조 환경 변수, 새 검증 종류)은 Setup 새 판이 필요하다. 초안 1절의 "지원하지 않는 작업은 거절한다"를 이 목록으로 구체화한다.

## 4. 소유자가 알고 정해야 할 것

### 4.1 원래 목표와의 차이

소유자의 목표는 "GHCR에 새 판이 올라오고 Backbone에서 승인하면 바로 적용된다"였다.

- 화면 모듈은 이미 그렇게 된다(OSR `ui` 클래스).
- 이 계획은 Backbone 본체에 대해 **Setup 재패키징**을 없앤다. 운영자가 Setup을 실행하는 단계는 남는다.
- 본체까지 승인 즉시 적용하려면 클러스터 안의 제한 실행부가 필요하다. 초안은 보류했고(3절 대안 3), 동의한다. Core가 자기 자신을 갱신하는 경로가 가장 위험하고, 복구가 Core의 정상 동작에 기대면 안 되기 때문이다.
- 나중의 중간 경로: 승인된 계획을 같은 Setup 엔진의 일회성 Job으로 실행한다. 상시 서비스가 아니다. 이번 범위는 아니다.

### 4.2 키 분리는 지금 이름뿐이다

초안 6절은 CLI 서명 키, Bundle 발행 키, 채널 승격 키, 사람 승인 키를 나눈다. 목적별 분리는 맞다. 하지만 지금 실제 경계는 하나다.

- 소스 쓰기 토큰, 레지스트리 자격, CLI 서명 키, OSR 기준 키와 발행 키, 운영 kubeconfig, 관리자 자격을 **한 운영자 세션이 모두 읽을 수 있다.**
- 실제로 독립된 경계는 지금 등록 중인 **검토자 단말의 승인 키** 하나뿐이다.
- 그래서 키를 몇 개로 나누는지보다, 본체 갱신 승인이 그 독립된 키의 서명으로 이뤄지는지가 실질이다(5절 항목 6).
- 기준 키(root)를 사람만 쓸 수 있게 옮기는 것(암호 문구나 별도 장치)은 소유자 결정이다.

### 항목 3 — 계약 초안

새 서명 형식을 만들지 않는다. **OSR 계약을 재사용한다.**

- OSR 규격은 Backbone 본체를 `core` 클래스로 **기록하되 OSR로 설치하지 않는다**고 이미 정했다. 본체 Bundle을 `core` 클래스의 릴리스로 발행하고, 설치는 Setup이 한다. 초안 1절의 "OSR의 일반 모듈 설치로 Backbone을 갱신하지 않는다"와 맞는다.
- 이미 있는 것: 정규 JSON(RFC 8785, 안전한 정수만), ES256 서명 봉투, SBOM과 출처 증명, 서명 referrer, 기준 키가 서명하는 검증 맥락(신뢰 세대, 키별 클래스 범위, 회수 세대, 정책 판, 만료), GHCR 게시 도구와 CI.
- 더할 것: 본체용 profile 하나(예: `core.backbone-release`)와 3.4의 단계 · 검증 목록 schema, 시험 벡터.

profile에 들어갈 내용(이름은 제안):

| 묶음 | 내용 |
|---|---|
| 식별 | 릴리스 ID, 제품 판, 소스 커밋, 발행 시각 |
| 도구 호환 | 계약 판, 필요한 단계 · 검증 종류 목록. Setup은 모르는 종류가 하나라도 있으면 쓰기 전에 거절한다. 최소 판 번호는 안내용일 뿐이다 |
| 전이 | predecessor 지문(항목 + 교정 목록), `corrects`(있으면), Console · Core 이미지 전후, 정책 · 카탈로그 지문 전후 |
| 자산 | 마이그레이션마다 경로 · sha256 · DB · 역할 · 순서. 이미지 보관본은 Bundle 밖에 두고 digest로만 가리킨다 |
| 단계와 검증 | 3.4의 닫힌 목록에서 고른 순서 |
| 복구 | 백업 요건, 이전 이미지가 새 스키마에서 동작하는지, 되돌릴 수 있는 경계 |
| 증거 | PR, 필수 검사, 이미지 발행 실행, 연습용 설치본 실행 영수증의 지문 |
| 예외 | 범위와 기간. 지금의 의존성 예외 기록과 같은 형태 |

신뢰와 재전송 방어:

- Setup에 고정하는 것은 **기준 키의 공개 키 하나**다. 지금은 묶음 항목 안(`osrTrustAnchor`)에 있다. 도구 쪽으로 옮긴다.
- 발행 키는 검증 맥락 안에서 `core` 범위로 위임받는다. 화면용 키(`ui` 범위)와 다른 키다.
- 원장에 **받아들인 최소 신뢰 세대와 최소 릴리스 세대**를 적는다. 그보다 낮은 맥락과 Bundle은 거절한다.
- 검증 맥락은 30일 만료다. 오프라인에서는 Bundle과 함께 새 맥락 파일을 가져온다. 만료된 맥락으로는 기록 검증과 무변경 재개만 한다. 새 쓰기는 거절한다.

### 항목 4 — 서명 도구 비교

| 후보 | 판단 |
|---|---|
| OSR 봉투 + 검증 맥락 | **추천.** 이미 구현 · 시험돼 있다(벡터 87개). Node 참조 검증기는 외부 의존성이 없다. 세대 · 회수 · 만료 · 범위가 있다 |
| TUF 전체 | 요구(회전, 회수, 재전송 방어)는 같다. 역할 네 개와 메타데이터 네 종류를 새로 운영해야 한다. 검증 맥락에 "최소 세대 기록"을 더하면 필요한 부분은 채워진다 |
| cosign / sigstore | 투명성 로그와 외부 서비스에 기대거나, 키 서명만 쓰면 지금 봉투와 같은 일을 한다. Setup의 외부 의존성은 지금 하나뿐이고 판이 고정돼 있다. 추가하면 도구 지문과 공급망 검토 범위가 커진다 |

새 상시 서비스 없이 가능하다. 할 일은 참조 검증기(`infra/contracts/osr/tools/verify.mjs`, `lib.mjs`)와 그것이 읽는 schema 파일을 Setup 소스에 넣는 것이다. 둘 다 Node 기본 모듈만 쓴다. 마이그레이션 자산과 같은 방식으로, 원본과 바이트가 같은지 시험으로 고정한다. Rust 쪽 검증기와 같은 벡터로 판정이 일치하는지도 계속 본다.

- 검토자가 없거나 키를 잃은 경우의 비상 절차는 소유자가 직접 하는 별도 작업으로 두고, 원장에 "비상 절차로 적용"이라고 남긴다.

## 8. 2차 검토(Jupiter, 6개 조건)에 대한 답

여섯 조건을 모두 받아들인다. 조건마다 지금 코드에서 확인한 것과, 합의안에 넣을 문장을 적는다. 이 절이 3 · 5절과 다르면 이 절이 우선한다.

### 8.1 교정은 무변경 재개가 아니다 — 수용. 지금 코드가 이 조건을 어긴다

확인한 것(`setup/src/backbone-bundle.mjs`, `989b491`):

- 완료된(`ready`) 기록에 아직 없는 교정이 있으면, `apply-backbone-bundle`을 다시 실행했을 때 그 교정을 **자동으로 실행한다.** 확인 문구도 원래 적용과 같다(`APPLY-REVIEWED-BACKBONE-BUNDLE`). 별도 작업 ID도 만들지 않고 원래 기록의 단계 목록에 덧붙인다.
- 오늘 운영의 교정 1도 같은 확인 문구로, 멈춘 작업의 기록에 단계를 덧붙여 실행했다. 추가 단계에 대한 별도 승인 기록은 없다.
- 지금 노출은 없다. 교정은 하나뿐이고 운영에 이미 적용됐으며, 교정을 더하려면 Setup 새 판이 있어야 한다. 그래도 규칙으로는 틀렸다.

합의안에 넣을 것:

- 교정은 **자기 작업 기록**을 갖는다: 작업 ID, 교정 지문, 대상 묶음 기록의 지문, 계획 지문, 승인, 단계 영수증. 원래 묶음 기록과 영수증은 고치지 않는다.
- 일반 적용과 재개는 새 교정을 실행하지 않는다. 빠진 교정이 있으면 "교정이 필요하다"고 알리고 멈춘다.
- 멈춘 작업에 교정이 필요한 경우도 같다. 교정 작업을 승인받아 먼저 끝내고, 그 다음에 원래 작업의 검증을 재개한다.
- 교정 1은 이미 적용된 사실로 남긴다. 기록을 소급해 고치지 않고, 새 규칙 이전의 교정이라고 문서에 적는다.
- PR 순서: 5절 항목 7의 PR 1을 둘로 나눈다. **1a**는 동작 변화 없음(항목별 마이그레이션, 원장 사실 기록). **1b**는 교정 규칙 변경이며 따로 검토한다.

### 8.2 원장의 전이 사실은 근거와 묶여 있어야 한다 — 수용

3.3을 고친다. 원장의 전이 사실은 계산을 빠르게 하는 사본이고, 근거는 따로 보존한다.

- 기록마다 남길 연결: Bundle 지문, 서명 봉투의 지문과 서명 키 ID, 검증에 쓴 검증 맥락의 지문과 세대, 승인 파일의 지문, 실행 도구 지문.
- 전이 사실은 "서명된 Bundle의 어느 부분에서 왔는지"를 지문으로 가리킨다. 원장만 고쳐서는 통과하지 못하게, `verify`는 보존본이 있으면 대조하고 없으면 "근거 보존본 없음"을 결과에 표시한다.
- 큰 자산(Bundle 본문, SQL, 이미지 보관본, 암호화 백업)은 원장 밖 보존본에 둔다. 원장에는 지문, 위치, 복원 절차 ID를 남긴다.
- 오래된 기록을 줄일 때는 요약본에 원본 기록의 지문을 남기고 원본을 보존본으로 옮긴다. 검증 근거는 지우지 않는다.

### 8.3 승인의 독립 검증과 DB 중단 — 수용. 코드로 확인한 것 두 가지

확인한 것:

- 승인 파일(`cli/cmd/os/approval.go`, `backend/server/src/approval.rs`)은 Core가 발급자 키로 서명한 challenge에 검토자가 서명하는 구조다. 내용에는 설치 ID, 작업 ID, 범위, 계획 지문, 결정, 만료가 묶여 있다. 검토자 CLI는 운영자가 고정해 준 발급자만 받아들인다.
- 따라서 **검증은 Setup이 Core 없이 할 수 있다**(발급자 공개 키와 검토자 공개 키만 있으면 된다). **발급은 Core가 살아 있어야 한다.**
- 범위는 닫힌 목록이다(`execution`, `trial`, `release`, `osr`). Core DB 제약과 CLI 양쪽에 있다. 본체 갱신용 범위를 더하는 것은 그 자체가 Core · Console · CLI 변경이다.
- 등록된 승인 공개 키는 Core DB에만 있다. `enroll-approval-key`는 설치 원장에 아무것도 남기지 않는다.

합의안에 넣을 것:

- 정상 경로: Core가 challenge를 발급하고, 검토자가 서명하고, Setup이 두 서명을 직접 검증한다. 한 번 쓴 challenge ID는 원장에 남겨 다시 쓰지 못하게 한다.
- 승인 키의 등록 · 회수를 **설치 원장에도 기록한다**(키 ID, 공개 키 지문, 대상, 세대). 그러면 DB가 죽어도 원장과 그 보존본으로 서명자와 회수 상태를 확인할 수 있다. 지금 진행 중인 검토자 등록은 이 기록 없이 이뤄지므로, 나중에 DB의 현재 상태를 증거와 함께 원장으로 옮기는 작업이 한 번 필요하다.
- Core가 죽어 발급을 못 하는 경우와 DB · 원장까지 없는 경우는 **비상 절차**다. 일반 갱신 명령의 옵션으로 만들지 않는다. 별도 명령, 소유자의 직접 확인, 보존본의 지문 대조, 원장에 "비상 절차" 기록을 요구한다.
- **순서 의존:** 본체 갱신용 승인 범위는 외부 Bundle보다 먼저 들어가야 한다. 전환용 Setup에 내장하는 마지막 묶음(내장 항목 2)에 넣거나, B1을 지금의 운영자 확인 방식으로 적용하고 B2부터 검토자 승인을 요구하는 것 중 하나를 정해야 한다. 앞쪽을 권한다. B1부터 같은 규칙을 쓰기 위해서다.

### 8.4 기준 키와 세대 — 수용

5절 항목 3의 "공개 키 하나 고정"은 초기 상태일 뿐이다. 계약에 다음을 넣는다.

- **회전:** 새 기준 키는 옛 기준 키가 서명한 전환 문서로만 받아들인다. 전환 문서는 세대 번호를 갖고 원장에 기록된다.
- **분실 · 침해:** 옛 키로 서명할 수 없으므로 Setup 새 판으로만 교체한다. 이때의 신뢰 근거는 Setup 배포의 서명이다. 이것이 최종 근거라는 점을 문서에 명시한다.
- **릴리스 세대의 범위:** 제품과 채널별로 따로 센다. 원장의 최소 세대도 그 범위별로 둔다.
- **같은 세대, 다른 지문:** 거절하고 충돌로 기록한다. 어느 쪽도 고르지 않는다.
- **중단 뒤 재전송:** 재개는 잠근 바이트의 지문만 본다. 세대나 채널을 다시 해석하지 않는다.
- **오프라인 신선성:** 보장 한계는 검증 맥락의 만료(지금 30일)다. 그 안에서는 회수를 모를 수 있다고 적는다.
- **TUF와의 차이를 그대로 적는다:** 서명 정족수가 없다. 시각 · 목록 역할이 따로 없어, 오래된 자료를 계속 보여 주는 공격은 만료로만 막는다. 이 차이를 받아들일지, 정족수를 더할지는 소유자 결정이다.

### 8.5 선언형 검증과 환경 변수의 권한 — 수용

3.4를 좁힌다.

- 읽기 응답 비교의 대상은 **설치본 자신의 두 곳뿐**이다: 관리 TLS로 닿는 Console, 사설 포워딩으로 닿는 Core. Bundle은 주소를 적지 않고 미리 정한 이름으로만 고른다.
- 메서드는 GET만. 경로는 Setup이 가진 **명시적 허용 목록**에서 고른다(지금 검증이 쓰는 경로들에서 시작한다). 인증은 지금처럼 운영자 세션이나 한 번 쓰고 지우는 토큰이다.
- 응답 크기와 시간은 지금의 요청 도구가 가진 한도를 그대로 쓰고(기본 1MiB, 30초), 검증 항목 수에도 상한을 둔다.
- 비교할 수 있는 필드도 경로별 허용 목록으로 둔다. 영수증에는 비교 결과와 허용된 값만 남긴다. 응답 본문은 남기지 않는다.
- 환경 변수는 이름 규칙이 아니라 **허용 목록과 값 형식**으로 제한한다. 지금 목록은 둘이다: 소스 커밋 표식, 공개 키 하나의 정해진 JSON 모양인 신뢰 기준. 목록을 늘리려면 Setup 새 판이 필요하다.
- SQL은 계속 특권 코드다. 닫힌 목록은 "어디서 어떤 역할로 실행하는가"만 제한한다. 내용 검토, 제품과 같은 역할 속성에서의 시험, 연습용 설치본 실행이 수용 조건이다.

### 8.6 연습 profile의 격리 — 수용. 입증되지 않으면 진행하지 않는다

3.1의 (가)는 namespace만 바꾸는 뜻이 아니었지만, 그렇게 읽힐 수 있어 조건을 명시한다.

- 따로 가져야 하는 것: 신원(Auth), DB, 저장 볼륨, Secret과 키, 접속 주소와 포트, 설치 ID.
- 클러스터 범위 자원(승인 정책, 스토리지 클래스, 클러스터 역할, 노드 포트)은 목록을 만들어 하나씩 정한다: 이름을 나눌 수 있는가, 공유해도 안전한가, 연습에서 뺄 것인가.
- **대상 오지정 차단:** 연습 profile의 명령은 연습 표식이 있는 설치 루트에만 동작하고, 운영 namespace와 운영 설치 ID를 거절한다. 운영 명령은 연습 표식이 있는 대상을 거절한다. 양쪽 모두 쓰기 전에 검사한다.
- **진행 조건:** 위 격리를 읽기 전용 점검과 거절 시험으로 먼저 입증한다. 입증하지 못하면 실제 적용 시험을 하지 않는다. 그 경우의 대안은 별도의 작은 연습 클러스터이고, 자원이 드는 일이라 소유자 결정이다. localhost RKE2는 되살리지 않는다.

### 8.7 그 밖의 지적

- **B1, B2:** 후보로만 둔다. 포함 범위와 선후 의존은 각 릴리스 계획에서 정한다. 8.3의 순서 의존 때문에 승인 범위 추가가 B1보다 앞설 수 있다.
- **운영 상태는 나의 보고다.** 맞는 지적이다. 독립해서 확인할 수 있는 근거는 다음과 같다. 모두 읽기 전용이다.
  - 공개 Setup 0.6.0-edge.61의 `status` 출력: `phase`, `backboneBundle.steps[0]`의 `status`와 단계 목록.
  - 운영자 폴더 `OpenSphere-Backbone/.runtime/osr-backbone-delivery-20261118/`의 영수증: `bundle61-applied.json`, `bundle61-resumed.json`, `legacy-resumes.json`, `bundle-preservation.json`, `trust-loaded.json`.
  - 이 영수증들도 내가 실행한 결과물이다. 독립 검증은 `status`와 Console의 OSR 화면으로 한다.

### 8.8 합의 뒤 문서 정리

원안을 v0.2로 고칠 때 이 회신의 3절(조건 네 가지), 5절(회신 항목), 8절(조건 여섯 가지)을 본문에 합치고, 이 회신 문서는 검토 기록으로 남긴다. 누가 v0.2를 쓰는지는 소유자가 정한다.
