## 1. 무엇을 하고 무엇을 하지 않는가

**한다.** Setup은 설치 · 갱신 · 복구를 실행하는 도구로 둔다. Backbone 버전마다 달라지는 것(이미지, 마이그레이션, 정책 전이, 검증 항목)은 Setup 밖의 **서명된 불변 Release Bundle**로 발행한다. 같은 계약 안의 새 버전은 이미 배포된 Setup으로 적용한다.

**Setup을 새로 내는 경우.** 실행 기능, 계약, 검증기, 보안 수정이 바뀔 때뿐이다. 외부 Bundle을 처음 지원하는 전환용 Setup은 한 번 내야 한다.

**하지 않는다.**

- Backbone 본체를 "승인하면 바로 적용"되게 만들지 않는다. 운영자가 Setup을 실행하는 단계는 남는다. 화면 모듈은 이미 OSR로 승인 즉시 적용된다.
- 클러스터 안의 상시 갱신 서비스나 GitOps를 들이지 않는다.
- OSR의 일반 모듈 설치로 Backbone 자신을 갱신하지 않는다. 복구가 Console · Core · OSR의 정상 동작에 기대지 않는다.
- Bundle에서 코드, 셸 명령, 플러그인을 받아 실행하지 않는다.

## 4. 산출물과 책임

### A. Setup 실행 도구

- 고정된 신뢰 근거, 서명 검증, 계약과 지원 기능 검사, 대상 관측.
- 승인 검증, 설치 ID와 클러스터 결합, 단일 작성자 잠금, 단계별 적용 · 영수증 · 재개 · 복구.
- 도구 자체의 서명 · 배포 · 지문 검증은 지금대로.

### B. Backbone Release Bundle

- 불변 manifest와 그것이 지문으로 묶는 자산.
- 대상 이미지와 소스 커밋, 정책 · 카탈로그 전이, 닫힌 목록에서 고른 단계와 검증 항목.
- **마이그레이션 SQL은 특권 코드다.** 서명만으로 안전하다고 보지 않는다. PR 검토, 제품과 같은 역할 속성에서의 시험(9절), 정확한 지문, 허용된 DB와 역할, 순서, 승인을 요구한다.

### C. 채널 메타데이터

- `edge` · `candidate` · `stable`은 불변 릴리스 지문을 가리키는 탐색 정보다. 실행 권한도 운영 승인도 아니다.
- 채널 메타데이터도 서명하고 세대와 만료를 검증한다.
- 선택하면 정확한 지문으로 잠근다. 실행과 재개 중에 채널을 다시 읽지 않는다.
- 제품 릴리스와 Setup 릴리스는 판 번호와 발행 경로가 따로다.

## 5. Release Bundle 계약

새 서명 형식을 만들지 않는다. **OSR 계약을 재사용한다.** OSR 규격은 Backbone 본체를 `core` 클래스로 기록하되 OSR로 설치하지 않는다고 이미 정했다. 본체 Bundle은 `core` 클래스 릴리스로 발행하고 설치는 Setup이 한다.

이미 있는 것: 정규 JSON, 서명 봉투, SBOM과 출처 증명, 서명 referrer, 기준 키가 서명하는 검증 맥락(신뢰 세대, 키별 클래스 범위, 회수 세대, 정책 판, 만료), 레지스트리 게시 도구와 CI, 외부 의존성 없는 Node 참조 검증기.

더할 것: 본체용 profile 하나(가칭 `core.backbone-release`), 단계와 검증 항목의 schema, 시험 벡터.

검토한 대안: TUF 전체는 역할과 메타데이터 종류를 새로 운영해야 한다. cosign · sigstore는 외부 서비스에 기대거나, 키 서명만 쓰면 지금 봉투와 같은 일을 한다. Setup의 외부 의존성은 지금 하나이고 판이 고정돼 있어, 추가하면 도구 지문과 공급망 검토 범위가 커진다. 그래서 들이지 않는다. 별도 유료 서비스도 쓰지 않는다.

| 묶음 | 내용 |
|---|---|
| 식별 | 릴리스 ID, 제품 판, 소스 커밋, 발행 시각, 제품 · 채널 범위의 릴리스 세대 |
| 도구 호환 | 계약 판, 필요한 단계 · 검증 종류. 모르는 종류가 하나라도 있으면 쓰기 전에 거절한다. 최소 판 번호는 안내용이다 |
| 전이 | predecessor(이전 릴리스 지문 + 적용된 교정 목록), `corrects`(교정 Bundle일 때), 이미지 전후, 정책 · 카탈로그 지문 전후 |
| 자산 | 마이그레이션마다 경로 · sha256 · DB · 역할 · 순서. 이미지 보관본은 Bundle 밖에 두고 digest로 가리킨다 |
| 단계와 검증 | 6절의 닫힌 목록에서 고른 순서 |
| 복구 | 백업 요건, 이전 이미지가 새 스키마에서 동작하는지, 자동으로 되돌릴 수 있는 경계, 복구 절차 ID |
| 증거 | PR, 필수 검사, 이미지 발행, 부분 시험 결과의 지문(9절) |
| 예외 | 범위, 승인 참조, 시작과 만료. 기존 예외를 자동으로 넓히지 않는다 |
| 서명 | OSR 봉투. 서명 키 ID와 권한 범위 |

v1은 정확한 predecessor 하나와 직선 체인만 지원한다. 분기, 건너뛰기, 의존성 해석은 없다.

### 5.1 교정

- 교정은 `corrects`로 이전 Bundle을 가리키는 별도 Bundle이다. 이전 Bundle의 단계를 그대로 포함하고 단계를 더할 수만 있다. 이미 목격된 단계는 다시 실행하지 않는다.
- 교정은 **자기 작업 기록**을 갖는다: 작업 ID, 교정 지문, 대상 기록의 지문, 계획 지문, 승인, 단계 영수증. 원래 기록과 영수증은 고치지 않는다.
- **일반 적용과 재개는 새 교정을 실행하지 않는다.** 빠진 교정이 있으면 알리고 멈춘다. 멈춘 작업에 교정이 필요하면 교정 작업을 승인받아 먼저 끝낸 뒤 원래 작업의 검증을 재개한다.
- 다음 릴리스의 predecessor에는 이전 릴리스 지문과 적용된 교정 목록이 함께 묶인다.
- 지금 코드는 이 규칙과 다르다. 완료된 기록에 새 교정이 생기면 같은 확인 문구로 자동 실행한다. 교정 1도 그렇게 실행됐다. 교정 1은 새 규칙 이전의 교정으로 남기고 소급해 고치지 않는다. 코드는 PR 1b에서 바꾼다.

### 5.2 신뢰, 세대, 재전송 방어

- Setup에 고정하는 것은 **기준 키의 공개 키**다. 지금은 묶음 항목 안에 있다. 도구 쪽으로 옮긴다.
- 발행 키는 검증 맥락 안에서 `core` 범위로 위임받는다. 화면용 키, CLI 서명 키, 사람 승인 키와 다른 키다.
- **회전:** 새 기준 키는 옛 기준 키가 서명한 전환 문서로만 받아들인다. 전환은 세대 번호를 갖고 원장에 기록된다.
- **분실 · 침해:** Setup 새 판으로만 교체한다. 이때의 신뢰 근거는 Setup 배포의 서명이고, 이것이 최종 근거다.
- **세대:** 원장에 받아들인 최소 신뢰 세대와, 제품 · 채널 범위별 최소 릴리스 세대를 적는다. 그보다 낮으면 거절한다.
- **같은 세대, 다른 지문:** 거절하고 충돌로 기록한다. 어느 쪽도 고르지 않는다.
- **downgrade:** 거절한다. 복구를 위한 downgrade는 별도 승인 작업이고 일반 적용 · 재개의 옵션이 아니다.
- **중단 뒤:** 재개는 잠근 바이트의 지문만 본다.
- **만료:** 만료된 맥락으로는 기록 검증과 무변경 재개만 한다. 새 쓰기는 거절한다. 중단된 작업의 승인이 만료되면 같은 계획에 대한 새 승인을 받는다.
- **오프라인:** Bundle과 함께 새 맥락 파일을 가져온다. 온라인과 같은 검증기를 쓴다. 신선성의 한계는 맥락의 만료(지금 30일)이고, 그 안에서는 회수를 모를 수 있다.
- **TUF와의 차이:** 서명 정족수가 없다. 시각 · 목록 역할이 따로 없어, 오래된 자료를 계속 보여 주는 공격은 만료로만 막는다. 이 계획은 TUF의 보안 성질을 모두 갖췄다고 주장하지 않는다(11절 결정 2).
- 내려받기는 지금의 제한을 재사용한다: 허용 호스트, 리다이렉트 횟수, 크기 상한. 경로 순회, 심볼릭 링크, 중복 경로, 과대 파일을 막는다.

## 6. 단계와 검증의 닫힌 목록

### 단계

| 종류 | 할 수 있는 것 |
|---|---|
| `backup` | core · services DB와 대상 워크로드 spec의 암호화 보관 |
| `image-cache` | Bundle이 digest로 가리킨 이미지를 노드에 넣는다 |
| `migration` | 정해진 DB와 역할로, 정확한 바이트를 한 트랜잭션으로 실행하고 표식을 남긴다 |
| `workload` | 대상은 `backbone-api`, `backbone-console`뿐. 바꿀 수 있는 것은 이미지, 소스 커밋 표식, **허용 목록의 환경 변수** |
| `verify` | 아래 검증 항목 |

환경 변수는 이름 규칙이 아니라 허용 목록과 값 형식으로 제한한다. 처음 목록은 둘이다: 소스 커밋 표식, 공개 키 하나의 정해진 JSON 모양인 신뢰 기준. 비밀 참조는 허용하지 않는다.

### 검증 항목

- 워크로드 UID와 spec 지문.
- 보존 항목: 관리 TLS, 승인 발급 키, 역할 목록, 콜백.
- 마이그레이션 표식.
- **설치본 자신의 읽기 응답에 대한 필드 비교.** 제한은 다음과 같다.
  - 대상은 두 곳뿐이다: 관리 TLS로 닿는 Console, 사설 포워딩으로 닿는 Core. Bundle은 주소를 적지 않고 정해진 이름으로 고른다.
  - GET만. 경로와 비교할 필드는 Setup이 가진 허용 목록에서 고른다.
  - 응답 크기와 시간은 지금 요청 도구의 한도(1MiB, 30초). 항목 수에 상한을 둔다.
  - 영수증에는 비교 결과와 허용된 값만 남긴다. 응답 본문은 남기지 않는다.

### 목록의 수용 시험과 한계

- 묶음 1과 교정 1을 이 목록으로 다시 표현해 **같은 단계 순서와 같은 워크로드 spec 지문**이 나와야 한다. 안 나오면 목록이 모자란 것이다.
- 목록 밖의 변경은 Setup 새 판이 필요하다: 새 워크로드, 새 Secret, RBAC, 비밀 참조 환경 변수, 새 검증 종류, 허용 목록에 없는 경로와 환경 변수.

## 7. 실행 흐름과 원장

1. **선택 · 검증:** 채널이나 오프라인 자료에서 정확한 Bundle을 고르고 서명, 체인, 호환성을 검증한다.
2. **계획:** 설치본과 predecessor를 비교하고 이미지 · 마이그레이션 · 정책 변경과 복구 요건을 읽기 전용으로 보여 준다. 계획 지문이 나온다.
3. **사전 검증:** 증거, 예외, 백업 가능성, 자원, 신뢰 상태. 비밀을 출력하지 않는다.
4. **승인:** 8절.
5. **적용:** 단일 작성자 잠금과 대상 재확인 뒤, Bundle에 고정된 순서로 실행한다.
6. **검증:** 6절의 항목. 통과하면 완료 영수증을 남긴다.
7. **재개 · 복구:** 같은 Bundle 바이트와 원래 작업 ID를 읽는다. 결과를 모르면 먼저 관측하고 효과를 다시 만들지 않는다. 이미지 되돌리기와 DB 복원은 다른 절차다.

### 원장

원장은 하나다. 지금의 설치 원장을 넓히고 두 번째 원장을 만들지 않는다.

| 지금 | 분리 후 |
|---|---|
| `releaseDigest`, `configDigest`, 릴리스의 `installerDigest` | 그대로 |
| 묶음 기록의 `profileDigest`, `steps`, `workloads`, `recovery`, `proof` | 그대로. 외부 항목의 `profileDigest`는 Bundle 지문 |
| (없음) | `toolIdentity`: 이 작업을 실행한 Setup 지문. 다른 판으로 재개하면 덧붙인다 |
| (없음) | `transition`: 이미지 · 판 · 소스 커밋, 정책 · 카탈로그 지문 전후, 워크로드 spec 지문 전후, 적용한 자산의 sha256 |
| (없음) | `evidence`: Bundle 지문, 서명 봉투 지문과 키 ID, 검증 맥락 지문과 세대, 승인 파일 지문 |
| (없음) | `approval`: 승인자, 계획 지문, challenge ID, 만료 |
| (없음) | 최상위: 최소 신뢰 세대, 범위별 최소 릴리스 세대, 승인 키 등록 · 회수 기록 |

- 이후 명령은 원장의 `transition`으로 기대 상태를 계산한다. Bundle 파일은 끝나지 않은 적용의 재개에만 필요하다.
- **`transition`은 사본이고 근거는 `evidence`가 가리키는 보존본이다.** `verify`는 보존본이 있으면 대조하고, 없으면 "근거 보존본 없음"을 결과에 표시한다.
- 큰 자산은 원장 밖 보존본에 둔다. 원장에는 지문, 위치, 복원 절차 ID를 남긴다.
- 원장은 ConfigMap 하나이고 지금 약 115KB다(한도 1MiB). 오래된 기록을 줄일 때는 요약본에 원본 기록의 지문을 남기고 원본을 보존본으로 옮긴다. 검증 근거는 지우지 않는다.
- 다른 판의 Setup으로 재개하는 것은 자동으로 허용하지 않는다. 지원하는 원장 schema와 작업 계약을 확인하고 새 도구 지문을 덧붙인다.
- 다리: 첫 외부 Bundle의 predecessor는 마지막 내장 항목(결정 1에 따라 내장 항목 2)의 지문과 그때까지 적용된 교정의 sha256을 함께 가리킨다. 기존 기록은 고치지 않는다.

### 보존

Bundle, 서명, 공개 신뢰 자료, 이미지 보관본, 소스, 영수증, 암호화 백업을 DevOps 보존 위치에 둔다. 호스트, Console, Gitea가 멈춰도 읽고 복구할 수 있어야 한다.

## 8. 승인과 역할

### 승인

- 발행 서명은 운영 승인을 대신하지 않는다.
- 승인 대상: **Bundle 지문 + 설치 ID + 클러스터 UID + 계획 지문 + 만료.**
- 지금의 승인 파일 형식을 재사용한다. Core가 발급자 키로 서명한 challenge에 검토자가 자기 단말의 키로 서명한다. 검토자 CLI는 운영자가 고정해 준 발급자만 받아들인다.
- **검증은 Setup이 Core 없이 한다.** 발급자 공개 키와 검토자 공개 키만 있으면 된다. 한 번 쓴 challenge ID는 원장에 남겨 다시 쓰지 못하게 한다.
- **발급은 Core가 살아 있어야 한다.** 본체 갱신용 승인 범위를 더하는 것은 Core · Console · CLI 변경이다. 첫 외부 Bundle보다 먼저, 전환용 Setup에 내장하는 마지막 묶음으로 넣는다(11절 결정 1).
- 승인 키의 등록과 회수를 설치 원장에도 기록한다. DB가 죽어도 원장과 그 보존본으로 서명자와 회수 상태를 확인하기 위해서다. 지금은 Core DB에만 있다. 이미 등록된 키는 DB의 현재 상태를 증거와 함께 한 번 옮긴다.
- **비상 절차:** Core가 죽어 발급을 못 하거나 DB · 원장까지 없는 경우다. 일반 갱신 명령의 옵션으로 만들지 않는다. 별도 명령, 소유자의 직접 확인, 보존본의 지문 대조, 원장의 "비상 절차" 기록을 요구한다.

### 역할

| 일 | 권한 경계 | 지금 실제 |
|---|---|---|
| 개발, PR | 소스 쓰기 토큰. main에 직접 쓰지 못한다 | 운영자 세션 |
| 검사, 이미지와 Bundle 게시 | CI 러너와 레지스트리 자격 | 러너. 필수 검사 뒤에만 병합된다 |
| 발행 서명 | 운영자 호스트의 `core` 발행 키. CI에 없다 | 운영자 세션이 읽을 수 있다. 서명 전에 소유자 확인 |
| 검증 맥락 발급 | 기준 키 | 운영자 세션이 읽을 수 있다 |
| 운영 적용 실행 | kubeconfig와 관리자 자격 | 운영자 세션 |
| **적용 승인** | **검토자 단말의 승인 키** | 등록 중. 유일하게 독립된 경계 |

키는 목적별로 나눈다. 다만 지금은 위에서 다섯 가지를 한 세션이 읽을 수 있어 분리가 이름뿐이다. 실질은 적용 승인이 독립된 키의 서명으로 이뤄지는 데 있다. 기준 키를 사람만 쓸 수 있게 옮기는 것은 소유자 결정이다.

## 9. 운영 전 시험

연습용 설치본은 두지 않는다(11절 결정 3). 설치본은 운영 중인 하나뿐이고 업데이트는 거기에 적용한다. Backbone을 하나 더 설치하지 않으며 별도 클러스터도 만들지 않는다.

### 운영 전에 하는 것

- 부분 시험은 운영 클러스터의 임시 namespace(`os-backbone-*`)에서 한다. 게시된 제품 이미지를 쓴다.
- 시험 환경의 DB 역할과 권한은 Setup이 제품에 쓰는 정의로 만든다. 손으로 다시 쓰지 않는다. 2절의 실패 1은 시험용 역할을 따로 만들어서 생겼다.
- 마이그레이션과 교정은 이 환경에서 제품과 같은 역할로 실행해 본다. 검증 항목은 빈 원장과 기록이 있는 원장 둘 다에서 확인한다.
- 중단과 재개(마이그레이션 전후, 배포 전후, 응답 유실, 프로세스 종료)는 Setup의 시험에서 모의 대상에 주입한다.
- 복구는 암호화 백업을 임시 namespace의 DB에 복원해 확인한다. 운영을 멈추는 연습은 하지 않는다.
- 시험이 끝나면 임시 namespace를 지우고 증거는 보존한다.

### 받아들이는 위험

적용 명령이 처음부터 끝까지 실행되는 첫 장소는 운영이다. 부분 시험이 놓친 것은 운영에서 드러난다.

### 운영을 지키는 것

- 적용 전 백업: core · services DB와 워크로드 spec.
- 추가형 변경: 마이그레이션 뒤에도 이전 이미지가 그대로 동작해야 한다. 그렇지 않은 Bundle은 복구 묶음에 그 사실과 절차를 적고 따로 검토받는다.
- 단계마다 기록하고 검증에서 실패하면 멈춘다. 고칠 것은 승인된 교정으로 고친다(5.1).
- 첫 외부 Bundle은 가장 작은 변경으로 한다(10절 B1).
- localhost RKE2는 되살리지 않는다. 로컬 통합 스택도 만들지 않는다.

### 수용 시험

- 같은 Setup으로 서로 다른 서명 Bundle 2개를 적용한다. 도구 지문은 그대로이고 제품만 바뀐다.
- CLI를 바꾸지 않고 새 Bundle을 온라인과 오프라인에서 같게 검증한다.
- 쓰기 전에 거절한다: 변조된 이미지 · SQL · manifest · 서명, 무권한 키, 회수 키, 만료, 재전송, downgrade, 같은 세대의 다른 지문, 모르는 단계 · 검증 종류, predecessor 불일치, 허용 목록 밖의 경로 · 필드 · 환경 변수.
- 거절한다: 다른 설치 ID나 클러스터 UID, 빠지거나 변조된 영수증, 출처 없는 정책 · 신원 변경.
- 채널이 도중에 바뀌어도 잠근 대상은 그대로다. 선택 자료가 없을 때 재개가 최신 채널을 고르지 않는다.
- 마이그레이션 전후, 배포 전후, 응답 유실, 프로세스 종료를 주입한 뒤 중복 효과 없이 재개한다. 동시 실행은 작성자 하나만 허용한다.
- DB는 성공하고 Kubernetes는 실패한 것 같은 부분 적용을 관측하고 검토된 경로로 복구한다. 둘이 함께 바뀐다고 가정하지 않는다.
- 재개는 새 교정을 실행하지 않는다. 교정은 자기 승인과 기록으로만 실행된다.
- 기존 원장의 Nexus 3종, bus-inspection, Console refresh와 chain, 묶음 1과 관련 완료 작업이 무변경으로 재개된다.
- 신원 · 역할 · 키 등록 이력은 승인된 전이 증거로 검증한다. 회수된 권한을 되살리지 않는다.
- Core가 멈춘 상태에서 이미 발급된 승인을 Setup이 검증한다. DB가 멈춘 상태에서 원장의 키 기록으로 서명자를 확인한다.
- Console · Core · Gitea에 기대지 않고 보존된 산출물, 암호화 백업, 독립 도구로 복구한다. 임시 namespace에 복원해 확인한다.
- 시험 뒤 로그와 증거를 보존하고 임시 자원을 정리한다. 일회성 작업은 끝나면 스스로 지워지는 방식(Job과 TTL 등)을 쓴다.

### 멈추는 조건

- 묶음 1의 지문이나 기존 기록의 검증 결과가 달라진다.
- 이전 작업의 재개가 하나라도 무변경이 아니다.
- 9절의 부분 시험을 통과하지 않은 Bundle을 운영에 쓰려 한다.
- 6절의 목록으로 묶음 1과 교정 1을 다시 표현할 수 없다.

### 첫 외부 Bundle 후보

- **B1: Console 이미지에서 `/dummy/` 빼기.** 더미 화면은 이미 OSR 화면 모듈로 발행돼 있다. Console만 바뀌고 마이그레이션이 없다.
- **B2: 검토자의 최소 권한 접근(OSR 결정 D9).** Core, Console, 마이그레이션, 정책이 함께 바뀐다.

후보일 뿐이다. 포함 범위와 선후 의존은 각 릴리스 계획에서 정한다.

## 11. 소유자가 정할 것

1. **본체 갱신용 승인 범위를 언제 넣는가. — 정해짐(소유자, 2026-11-18): 먼저 넣는다.**
   - 전환용 Setup에 내장하는 마지막 묶음(내장 항목 2)에 넣는다. 첫 외부 Bundle(B1)부터 검토자 승인으로 적용한다.
   - 따라오는 것: 내장 항목 2 자체는 지금의 운영자 확인 방식으로 적용된다. 검토자 승인을 요구하는 범위가 그 안에 들어 있기 때문이다. 이것이 운영자 확인만으로 적용되는 마지막 본체 갱신이다.
   - 버린 안: B1을 운영자 확인 방식으로 적용하고 그 다음부터 승인을 요구하는 것.
2. **서명 정족수. — 정해짐(소유자, 2026-11-18): 지금 수준을 유지한다.**
   - 정족수를 더하지 않는다. 발행은 `core` 범위의 발행 키 하나의 서명으로 한다.
   - 받아들이는 것: 여러 사람의 서명을 요구하는 장치가 없다. 오래된 자료를 계속 보여 주는 공격은 검증 맥락의 만료(지금 30일)로만 막는다. 그 안에서는 회수를 모를 수 있다(5.2).
   - 이 차이를 메우는 것: 발행 서명과 별개로, 적용에는 검토자 단말의 독립된 키로 한 승인이 필요하다(8절).
   - 버린 안: 서명 정족수 추가, TUF 전체 도입.
3. **연습용 설치본을 두는가. — 정해짐(소유자, 2026-11-18): 두지 않는다.**
   - OpenSphere는 이미 설치돼 운영 중이다. 문제가 있으면 업데이트하고 필요한 것은 확장한다. Backbone을 하나 더 설치하지 않고 별도 클러스터도 만들지 않는다.
   - 따라오는 것: 적용 명령이 끝까지 실행되는 첫 장소가 운영이다. 부분 시험, 백업, 추가형 변경, 검증 실패 시 멈춤, 교정으로 대비한다(9절).
   - 버린 안: 운영 클러스터 안의 연습용 설치본, 별도의 작은 연습 클러스터.

## 12. 아직 확인하지 않은 것

- 시험 환경의 역할과 권한을 Setup의 정의에서 그대로 만들 수 있는지. PR 2의 첫 일이다.
- 승인 형식에 본체 갱신 범위를 더할 때 계획 지문의 결합이 지금 구조에 그대로 맞는지. 검증 구조는 코드로 확인했고, 범위 추가는 확인하지 않았다.
- 원장 누적 크기 대책의 구체 형식.
- 이미지 보관본을 오프라인으로 가져오는 절차를 Bundle 계약의 어디까지로 볼지.
