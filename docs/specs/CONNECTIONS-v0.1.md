## 1. 결정(D-114)

소유자(2026-11-27): "Backbone에 gitea, github 연결을 관리하는 페이지 · 기능이 있어야 하는 것 아닌가?" → "교체까지 화면에서".

- Backbone은 바깥과 맺은 연결(Gitea · GitHub · GHCR)을 한 화면에서 보여 준다: 무엇에 쓰는지, 어느 계정의 어떤 권한이 필요한지, 마지막 성공과 실패, 만료, 끊기면 무엇이 멈추는지.
- 자격의 교체도 그 화면에서 한다.

**계기.** 2026-11-27에 소유자가 `opensphere-platform`의 GitHub 토큰을 "쓰는 것만 남기고" 지웠는데, 이미지 발행(CI → GHCR)과 예전 채널 읽기가 멈췄다. 어느 토큰이 어디에 쓰이는지 볼 곳이 없었다. 발행 토큰을 다시 넣는 일도 Gitea 화면 로그인에서 막혀, 터미널 스크립트로 처리했다.

**기록해 두는 반대 의견.** Claude는 Gitea 관리 자격과 GHCR 발행 토큰의 교체는 터미널에 두자고 권했다. 지금은 Console이 소스 저장소와 CI를 읽기만 할 수 있고, 그 경계는 Console이 뚫려도 소스와 발행 경로를 건드리지 못하게 하려는 것이다. 소유자는 화면에서 교체하는 쪽을 골랐다. 이 문서는 그 결정을 따르되, 아래 §4처럼 **Console이 관리 자격을 갖지 않는 방식**으로 설계해 경계를 가능한 만큼 남긴다.

## 3. 화면

자리: 설정 → 개발 · 전달 → **연결**. 스토어 관리와 같은 틀을 쓴다.

- 연결마다 제 구역: 이름 · 상태 태그(정상 / 확인 필요 / 끊김 / 만료 임박 / Backbone 밖) · 작업.
- 수치: 마지막 성공, 마지막 실패, 만료일, 자격을 넣은 때.
- 탭: **쓰임**(무엇에 쓰고, 끊기면 무엇이 멈추는가) · **자격**(어느 서비스의 어느 계정, 필요한 권한, 보관 자리 — 값은 없다) · **기록**(누가 언제 바꿨는가).
- **자격 교체**는 오른쪽 서랍: 새 값 입력 → 서버가 그 값이 실제로 되는지 확인한 결과(계정 · 권한 · 대상별 통과 여부)를 보여 줌 → 본인 MFA → 적용.
- Backbone 밖에 있는 연결(운영자 도구의 것)은 목록에 나오되 "Backbone 밖"으로 표시하고, 교체 작업이 없다. 있다는 사실과 필요한 권한을 적어 두어, 토큰을 정리할 때 지우면 안 되는 것을 알 수 있게 한다.

### 3.1 C1에서 실제로 만든 것(PR 261)

- 자리: 설정 → 개발 · 전달 → 연결. `GET /console-api/connections`(읽기만, 자격 없음).
- 구역 다섯: Gitea 소스 읽기 · Gitea 웹훅 서명 · GHCR 이미지 발행 · 스토어 읽기 · 예전 채널 읽기(닫는 경로). Backbone 밖의 자격 넷은 상태 없는 표.
- **탭을 두지 않았다.** 쓰는 곳 · 끊기면 · 자격 · 필요한 권한 · 보관 자리 · 교체를 구역 안에 모두 펼쳐 둔다. 이 화면의 첫 쓰임이 "토큰을 정리하기 전에 맞춰 보는 것"이라 한눈에 보여야 한다고 판단했다(Claude의 판단, 소유자 확인 전). 기록 탭은 교체가 생기는 C3에서 같이 둔다.
- 상태의 근거:
  - Gitea 소스 읽기 — 화면을 열 때 실제로 읽어 본다(소스 화면과 같은 확인).
  - Gitea 웹훅 서명 — 서명이 맞아 받아들인 알림의 수(주기 대조로 채운 것은 뺀다). 한 번도 없으면 "확인 필요".
  - GHCR 이미지 발행 — **마지막 발행 실행의 결과.** 자격이 CI 안에 있어 직접 볼 수 없다. 가장 최근 실행이 실패면 로그에서 레지스트리의 자격 거절을 찾아 "끊김"과 "다른 실패"를 가른다. 성공 뒤에 토큰이 지워진 것은 다음 발행 때에야 드러난다 — 화면에 그렇게 적는다. 이 한계는 C3(화면에서 교체하며 확인)와 주기 확인으로만 없앨 수 있다.
  - 스토어 읽기 — 스토어 관리와 같은 판정. 교체는 스토어 관리로 보낸다.
- 발행 자격을 쓰는 워크플로는 셋(`publish-images` · `publish-module` · `publish-catalog`)이다. 예전 채널을 닫으며(D-113 T6 · T7) `publish-catalog`를 없애면 목록에서도 빠진다(소스 시험이 강제).

### 3.2 운영에서 드러난 것과 수정(2026-11-28)

**Gitea가 둘이다.** 이 문서의 §2 표는 "Gitea 소스 읽기"와 "GHCR 이미지 발행(CI)"을 같은 Gitea의 일로 적었다. 틀렸다.

| 서버 | 자리 | 누가 쓰는가 |
|---|---|---|
| 내장 Gitea | `os-backbone-system/backbone-gitea` | Console(`GITEA_URL`). "소스와 검사" 화면 |
| 개발 저장소 | `os-backbone-development/development-source` | PR · CI · 이미지 발행, 발행 비밀값. Console은 연결되어 있지 않았다 |

A-13의 연결 화면은 발행 실행을 내장 Gitea에서 찾아 "확인 못 함"만 냈다(Claude가 확인 없이 둘을 같은 것으로 전제). 소유자 결정(2026-11-28): **"읽기 전용 연결"** — Console을 개발 저장소에 읽기 전용으로 잇는다.

- 연결 "개발 저장소 읽기"를 새로 둔다. 자격은 개발 저장소의 제한된 비관리자 사용자 `backbone-delivery-reader`(그 저장소 하나에 read 협업)의 토큰, 범위 `read:repository` · `read:user`. 보관은 클러스터 Secret `backbone-delivery-source`.
- 발행 실행과 실패 로그는 개발 저장소에서만 읽는다. 연결이 없으면 발행은 "Console이 개발 저장소에 연결되어 있지 않다"고 답한다.
- 망: 덧붙이는 NetworkPolicy 둘(Console → `development-source:3000`, 한 방향). 기존 정책은 고치지 않는다.
- 화면은 "내장 Gitea"와 "개발 저장소"를 이름과 서버로 구분한다.
- **C2 이후에 미치는 것:** 발행 비밀값의 교체는 개발 저장소의 Actions 비밀값을 쓰는 일이므로, 연결 실행부가 닿아야 하는 곳도 개발 저장소다(내장 Gitea가 아니다). §4.2의 "Gitea 관리 자격"은 개발 저장소의 것으로 읽는다.

## 4. 교체의 설계

### 4.1 원칙

1. **값은 한 번 들어가고 다시 나오지 않는다.** 응답 · 로그 · 감사 기록 어디에도 값이 없다.
2. **넣기 전에 확인한다.** 그 자격으로 실제 대상에 닿는지를 서버가 확인하고, 통과하지 못하면 아무것도 바꾸지 않는다(2026-11-27의 스크립트가 한 것: GitHub가 답한 계정과 권한, GHCR이 내준 push 토큰).
3. **본인 MFA와 승인 기록.** 스토어 토큰 교체와 같은 방식(Core의 결정 기록, 한 번 쓰는 코드 표식).
4. **Console은 관리 자격을 갖지 않는다.** 자격이 놓이는 자리(Gitea Actions 비밀값, 운영 Secret)에 쓰는 일은 Console이 아니라 **연결 실행부**가 한다.

### 4.2 연결 실행부

Console 옆에 따로 도는 작은 구성요소다. 모듈 실행부와 같은 생각이다: 정해진 작업만 받고, 그 작업에 필요한 권한만 가진다.

- 받는 작업은 닫힌 목록이다. 예: `gitea.actions-secret.replace{저장소, 이름}` — 이름은 연결 정의가 적어 둔 것만(`GHCR_PUBLISH_TOKEN` 등). 임의의 Gitea API, 임의의 Secret 쓰기는 없다.
- Gitea 관리 자격은 실행부에만 있다. Console · CI · reader에 마운트하지 않는다.
- Console은 승인 기록(Core가 서명한 짧은 수명의 증명)과 함께 작업을 넘긴다. 실행부는 증명이 그 작업 · 그 연결 · 그 사람의 것인지 확인하고 실행한다.
- 실행부는 결과(성공 · 실패 코드, 때)만 돌려준다.

이렇게 하면 Console이 뚫려도 할 수 있는 일은 "관리자의 MFA가 있을 때, 정해진 비밀값 이름의 값을 바꾸는 것"으로 좁혀진다. 브랜치 보호 · 저장소 설정 · 다른 비밀값에는 닿지 못한다.

### 4.2.1 C2 구체화(2026-11-28, D-115 · 개발 저장소 반영)

- **실행부가 쓰는 곳은 개발 저장소다.** 발행 비밀값 `GHCR_PUBLISH_USER` · `GHCR_PUBLISH_TOKEN`은 개발 저장소(`os-backbone-development/development-source`)의 Actions 비밀값이다(§3.2). 실행부가 받는 첫 작업은 `gitea.actions-secret.replace{repository: backbone-operator/OpenSphere-Backbone, names: [GHCR_PUBLISH_USER, GHCR_PUBLISH_TOKEN]}` 하나다. 이름 목록은 실행부의 코드에 고정한다.
- **실행부의 자격:** 개발 저장소의 전용 사용자(관리자 아님) — 그 저장소 하나에 Actions 비밀값을 쓸 수 있는 최소 권한. 관리자 자격(`.env.step2`)은 쓰지 않는다. Gitea가 저장소 단위 비밀값 쓰기를 어떤 권한으로 허용하는지는 구현 전에 실제 Gitea(28.3.0)에서 확인한다 — 저장소 관리자 권한이 필요하면 그 사실과 위험을 소유자에게 보고하고 진행한다.
- **누가 요청하는가(D-115):** 관리자 + 본인 MFA. Console은 승인 기록(Core의 결정 기록과 한 번 쓰는 코드 표식)을 붙여 실행부에 넘긴다. 실행부는 그 기록이 이 작업 · 이 연결 · 이 사람의 것인지 Core에 확인한다.
- **넣기 전 확인(실행부가 한다):** 새 값으로 GitHub `/user`의 계정과 `write:packages` 범위, GHCR의 push 토큰 발급(이미지 저장소 `opensphere-backbone-core` · `-console`마다)을 확인한다. 하나라도 통과하지 못하면 아무것도 쓰지 않고 이유 코드만 돌려준다. 2026-11-27의 터미널 스크립트(`set-ghcr-publish-token.py`)가 한 확인과 같다.
- **망:** 실행부 → 개발 저장소 3000, 실행부 → `api.github.com` · `ghcr.io` 443. Console → 실행부 한 포트. 그 밖은 없다.
- **확인 화면:** 교체 서랍은 확인 결과(계정 · 범위 · 저장소별 통과)를 보여 준 뒤 MFA를 받는다. 교체 뒤 연결 화면의 "GHCR 이미지 발행"은 다음 발행 실행의 결과로 바뀐다(교체 자체로 "정상"이 되지 않는다).

### 4.3 남는 위험

- 관리자 계정과 그 MFA가 함께 넘어가면 발행 토큰을 공격자의 것으로 바꿀 수 있다. 발행 대상 저장소는 고정이라 남의 토큰으로는 push가 거절되지만, 발행이 멈춘다(가용성).
- 실행부가 Gitea 관리 자격을 갖는 새 구성요소가 된다. 그 자격이 새는 경로가 하나 늘어난다.
- 값이 브라우저 → Console → 실행부를 지난다. 터미널에서는 사람 → 대상으로 바로 갔다.

## 6. 정해야 할 것

- **Q1 — 결정됨(D-115, 2026-11-28): 관리자 권한이 있으면 교체할 수 있다(본인 MFA · 승인 기록).** 아래는 물었던 내용이다. 누가 교체할 수 있는가. 발행 · 소스 경로의 자격이다. 권고: 설치본의 **첫 소유자만**(스토어 신뢰 변경과 같은 규칙). 스토어 읽기 토큰처럼 관리자 전원으로 넓히는 것은 권하지 않는다.
- **Q2. GitHub 보존 push를 Backbone 안으로 들일 것인가.** 지금은 병합할 때마다 운영자 도구가 이 Mac의 gh 로그인으로 push한다. Gitea의 push 미러로 옮기면 병합 즉시 자동으로 보존되고, 그 토큰이 이 화면의 연결이 되어 상태와 교체가 보인다. 대신 GitHub에 쓰는 토큰이 클러스터 안에 놓인다.
- **Q3. 만료 알림.** 만료일을 아는 자격(예: 만료를 둔 토큰)은 며칠 전부터 "만료 임박"으로 보일 것인가, Swallow 알림까지 보낼 것인가.
