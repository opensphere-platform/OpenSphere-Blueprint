## 1. 문제

스토어 패키지는 레이어(면)의 구분을 넘을 수 없다. 그런데 Console에는 레이어마다 기능을 게시할 자리가 먼저 있지 않다.
- 레일에는 Fabric(예시 화면)과 HISS(내장 화면)만 있다. Governance · Workspace는 없다.
- 그래서 기능이 없으면 메뉴가 없고, 메뉴가 없으면 섹션도 없다. 기능을 게시할 대상이 없는 상태다.
- HISS는 반대 문제다. 패키지를 설치하지 않았는데 내장 화면 10개가 있고, 값은 모두 "읽지 못함"이다. 이것은 D-88(HISS는 스토어로 설치)과도 맞지 않는다.

## 2. 결정(D-89) 요지

1. **레이어 섹션은 호스트가 늘 그린다.** 기능이 없어도 자리가 먼저 있다.
2. **섹션 안의 묶음(자리)도 호스트가 정한다.** 패키지는 자기 레이어 안에서 묶음 · 순서만 고른다.
3. **관리자는 섹션을 만들지 않는다.** 레이어를 넘겨 옮기지도 않는다. 조정은 같은 묶음 안의 순서와 숨김만 허용한다(§6, 다음 판).
4. **한 패키지는 자기 레이어에만 메뉴를 낸다.** 다른 레이어의 화면이 필요하면 그 레이어의 별도 패키지로 만든다.

관리자가 섹션을 자유롭게 만드는 안은 택하지 않았다. 이유는 넷이다.
- 레이어 경계가 화면에서 무너진다.
- 주소 · 문서 · 링크가 설치본마다 달라진다.
- 판정기가 맞는 자리를 확인할 기준이 없어진다.
- 메뉴 구성이 백업 · 이전 · 갱신 충돌을 따로 다뤄야 하는 상태가 된다.

## 3. 섹션

레일 순서는 D-87 ①을 따른다: **대시보드 · HISS · Fabric · Governance · Workspace · (화면 모듈) · 설정**.

| 섹션 | 레이어 | 주소 | 비고 |
|---|---|---|---|
| `hiss` | HISS(네 면 아래의 바닥) | `#/hiss` | D-86 · D-87 |
| `fabric` | OpenSphere Fabric | `#/fabric` | 템플릿 예시 화면은 "(예시)" 묶음으로 남는다 |
| `governance` | Governance | `#/governance` | 지금은 패키지가 없다. 섹션 홈만 보인다 |
| `workspace` | Workspace(관리 관점) | `#/workspace` | 사원이 쓰는 화면은 이 Console 밖이다(화면 모듈 · 사원 앱) |
| (설정) | Backbone | `#/configuration` | 스토어 밖. 지금처럼 내장 |

- 이 관리 Console의 Workspace 섹션은 Workspace에 설치된 패키지를 관리하는 자리다. 사원의 업무 화면 자체가 아니다.

> **D-91 개정(2026-11-23):** 섹션 홈은 템플릿 Fabric 화면과 같은 틀(공통 페이지 틀 · 이동 경로 · 묶음 타일 · 대시보드 격자)로 그린다. 기준은 [섹션 홈 · 묶음 개요 기준 v0.1](CONSOLE-SECTION-HOME-v0.1.md) §2를 따른다.

### 3.1 섹션 홈(호스트가 그림)

`#/<section>`과 `#/<section>/overview`는 호스트 화면이다. 패키지가 하나도 없어도 있다.
- 이 레이어가 하는 일을 한두 줄로 설명한다([네 면 구조](../overview/FOUR-PLANES.md) §2의 정의).
- 설치된 패키지 목록을 묶음별로 보인다: 이름(로고 먼저) · 판 · 상태 · 그 화면으로 가는 링크.
- 하나도 없으면 "이 레이어에 설치된 기능이 없습니다"라고 쓴다.
- **"스토어에서 받기"** 버튼을 둔다. 스토어를 이 레이어 묶음으로 걸러 연다.
- 값을 지어내지 않는다. 원장에서 읽지 못하면 "읽지 못함"이다.

### 3.2 보조 탐색

위에서부터 이 순서로 그린다.
1. 개요(섹션 홈)
2. 호스트 묶음별 설치 항목(`order` 순). 빈 묶음은 그리지 않는다.
3. 스토어에서 더 받기
4. (Fabric만) 템플릿 예시 묶음 "(예시)". 설치본이 쓰는 주소는 예시에서 뺀다(X1과 같음).

## 4. 레이어와 묶음의 기준

### 4.1 레이어는 디스크립터의 `plane`이 정한다

스토어 분류(`osr_store::group_of`)와 같은 기준이다. 패키지 확장의 `navigation[].section`은 이 표의 섹션과 같아야 한다. 다르면 등록 판정이 거절한다(`ExtensionInvalid`).

| `plane` | 섹션 | 기본 묶음 |
|---|---|---|
| `hiss` | hiss | (패키지가 §4.2에서 고름) |
| `fabric-shared` | fabric | `shared` |
| `fabric-runtime` | fabric | `shared` |
| `fabric-delivery` | fabric | `delivery` |
| `fabric-engine` | fabric | `engines` |
| `catalog` | fabric | `catalog` |
| `governance` **(새로 더함)** | governance | (§4.2) |
| `employee-area` | workspace | (§4.2) |
| `shell` | 섹션 없음(레일의 화면 모듈 링크, 지금과 같음) | — |
| `customer-area` | 섹션 없음(네 면 밖, D-62) | — |

- 디스크립터에 `plane`이 없는 이전 번들은 클래스로 판단한다. 지금의 규칙과 같다(`hiss` → hiss, `delivery` · `provider` · `engine` · `runtime` · `assembly` → fabric).
- `governance` plane은 디스크립터 스키마의 `plane` 목록에 새로 더한다.

### 4.2 호스트 묶음(자리)

묶음 id는 주소의 한 조각이다(`#/<section>/<group>/<slug>`). 이름은 화면에 보이는 글자다.

| 섹션 | 묶음 id · 이름 | 상태 |
|---|---|---|
| fabric | `shared` 공유 서비스 · `delivery` 배포 지원 | 있음(v1) |
| fabric | `engines` 엔진 · `catalog` 카탈로그 | 새로 더함 |
| hiss | `nodes` 클러스터 · 노드 · `network` 네트워크 · 칸막이 · `edge` 입구 · 인증서 · DNS · `storage` 저장 · `engines` 엔진 설비 · `observability` 관측 바닥 · `backup` 플랫폼 백업 | HISS 구성 계획 §5.2의 메뉴. v1의 `floor`를 대신한다 |
| governance | `policy` 정의 · 정책 · `allocation` 할당 · `approval` 결재 · `reclaim` 회수 · `promotion` 앱 승격 · `domains` 앱 도메인 | 제안. 네 면 구조 §1의 Governance 일을 따랐다 |
| workspace | `apps` 회사 앱 · `teams` 팀 · 프로젝트 · `personal` 개인 자원 · `agents` 에이전트 | 제안. 네 면 구조 §5를 따랐다 |

- 묶음을 더하거나 바꾸는 일은 **호스트 계약의 판 갱신**이다. 패키지가 하지 않는다. 계약 판은 `1.1`이다.
- `contract: "1.0"` 선언도 1.0 규칙 그대로 계속 받는다. 1.0으로는 유효한 HISS 메뉴를 선언할 수 없었다. 1.0의 화면 틀은 `fabric.service` 하나이고, 이 틀은 fabric 메뉴의 화면이어야 하며, `hiss` 클래스는 fabric 섹션을 쓸 수 없기 때문이다. 그래서 `hiss/floor`는 호환하지 않고 1.1에서 없앤다. 주소를 옮겨 읽는 규칙과 이에 따른 원장(SQL) 변경도 두지 않는다. (2026-11-23 개정. Codex 질의 ② 반영)
- **비-Fabric 섹션의 공통 틀 `section.notice`(1.1에서 더함):** 블록은 `note`만 쓸 수 있고, 데이터 원천 · 동작은 없다. HISS · Governance · Workspace 패키지가 자기 자리에 안내 화면을 낼 때 쓴다. HISS 전용 틀과 데이터 원천은 H3에서 정한다(§5). (2026-11-23 개정. Codex 질의 ① 반영)
- 섹션 홈 경로(`<section>/overview`)는 모든 섹션의 예약 경로다.
- HISS 구성 계획 §5.2의 "개요 · 위로 넘기는 것 · 변경 · 이력"은 패키지 자리가 아니다. 호스트의 섹션 홈에 둔다. 인도 지점과 스토어 `hiss` 설치 기록이 원천이다.

## 5. HISS 정리

- 지금 Console에 내장된 HISS 화면 10개(PR 155)는 섹션 홈 하나로 바꾼다. `#/hiss/<page>` 내장 경로는 없앤다.
- 관측 바닥 같은 HISS 항목은 스토어 `hiss` 패키지로 설치한다(D-88). 그 패키지의 확장 선언이 자기 묶음(예: `observability`)에 화면을 낸다.
- HISS 화면 틀(예: `hiss.status`, 탭 다섯: 상태 · 구성 · 실검증 · 변경 · 문서)과 HISS 데이터 원천은 HISS 스토어 경로(H3) 설계에서 정한다. 이 문서의 범위가 아니다.
- Core의 관측 바닥 읽기(`/api/v1/hiss/*`)와 Console 중계(`/console-api/hiss/*`)는 그대로 둔다. 나중에 HISS 데이터 원천으로 쓴다. 화면에서만 뺀다.

## 6. 관리자 조정(다음 판, v0.2에서 정함)

- 할 수 있는 것: 같은 묶음 안의 순서 바꾸기, 설치된 항목의 메뉴 숨기기 · 보이기.
- 할 수 없는 것: 섹션 만들기, 레이어 넘기기, 이름 바꾸기.
- 저장: 원장의 Console 설정. 설치 판정 · 권한과 무관하다. 숨긴 항목도 직접 주소와 섹션 홈 목록에는 남는다.
