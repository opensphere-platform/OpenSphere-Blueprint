## 1. 외부 리소스란

**Fabric이 만들지 않았지만 회사가 이미 쓰거나 새로 쓰려는 자원**이다.

| 종류 | 예 |
|---|---|
| 외부 디렉터리 | 회사가 이미 운영하는 Windows AD, 외부 LDAP |
| 외부 SaaS | 이미 쓰고 있는 협업·개발·영업 SaaS |
| 외부 데이터 저장소 | 사내 기존 DB, 클라우드 객체 저장소 버킷 |
| 외부 모델 API | 외부 LLM 제공자의 API |
| 외부 업무 시스템 | 기존 ERP·그룹웨어, 협력사 API |

외부 리소스도 사원·부서·프로젝트에게 나눠 주려면 먼저 테넌트 관리자가 **테넌트 구성에 편입**하고, 그 리소스 유형이 Governance에 인계되어야 한다(D-82). 이 문서는 그 경로와 규칙을 정한다.

## 2. 경로: 외부 어셈블리

외부 리소스는 앱 설정에 직접 꽂지 않는다. **외부 어셈블리**로 묶어 들인다.

```
 외부 리소스 ──▶ 연결기(connector) ──▶ 외부 어셈블리 ──▶ 리소스 유형(ext.*) ──▶ Governance 할당
                 연결 객체 · 연결 전용 자격      어댑터 · 대조          등급: 관리형 / 연동형 / 참조형
```

| 내부 어셈블리와 같은 점 | 다른 점 |
|---|---|
| 연결 객체, 연결 전용 신원, 삭제 보호, 연결 결재(T-6), 대조(T-8) | Instance를 만들지 않는다. 이미 있는 것을 **등록**한다 |
| 리소스 유형 정의 형식 | 제어할 수 있는 정도가 리소스마다 달라 **통제 등급**을 판정한다 |
| 적합성 시험 | 외부 쪽 장애·약관 변경을 Fabric이 통제하지 못한다는 위험을 기록한다 |

## 3. 통제 등급

외부 리소스가 Governance 통제를 얼마나 받을 수 있는지에 따라 세 등급으로 나눈다. **등급은 신청자가 고르지 않는다. 적합성 시험 결과로 정해진다.**

| 등급 | 조건(모두 충족) | Governance가 할 수 있는 것 | 예 |
|---|---|---|---|
| **관리형**(managed) | 계정·권한의 생성·비활성·삭제 API, 실제 권한 목록 API, 회수 시간 측정 가능, SSO 연동 | 신청·결재·할당·**자동 회수**·drift 회수·재검토·showback 전부 | SCIM을 지원하는 SaaS, 외부 AD(쓰기 허용 모드) |
| **연동형**(federated) | SSO 연동, 권한 목록 API. 생성·비활성 API는 없거나 일부 | **입장(SSO 할당)**만 통제. 내부 권한은 대조해 **보고**만 한다 | SSO만 지원하고 내부 권한은 자체 관리하는 SaaS |
| **참조형**(referenced) | 통제 API 없음 | 원장에 **존재·소유자·위험만 등록**. 할당은 수작업 기록, 재검토 대상 | 계정 관리 API가 없는 기존 시스템 |

- 관리형 조건 하나라도 시험에서 실패하면 **한 등급 낮춰** 등록한다.
- 참조형은 위험을 숨기지 않기 위한 등급이다. 통제할 수 없다는 사실을 원장에 남기고, 재검토에서 다시 보게 한다.
- 에이전트의 자율 실행(D-46)은 관리형 리소스에만 허용한다. 연동형·참조형에는 사람 결재를 거친 실행만 허용한다.

## 4. 편입 규칙

| ID | 규칙 |
|---|---|
| **ER-1** | **선언으로만 들어온다.** 외부 리소스는 외부 어셈블리 정의로 등록한다. 앱 설정·스크립트·개인 토큰으로 직접 연결하지 않는다 |
| **ER-2** | **소유와 책임을 적는다.** 소유 단위, 운영 책임자, 계약(라이선스·이용 약관·데이터 처리 계약)의 위치를 기록한다. 없으면 등록하지 않는다 |
| **ER-3** | **연결 전용 자격을 쓴다.** 외부 쪽에 연결 전용 서비스 계정을 만들고, 자격은 테넌트 KMS에 둔다. 개인 계정·외부 관리자 계정·장기 고정 토큰은 쓰지 않는다. 회전할 수 없는 자격은 위험으로 기록한다 |
| **ER-4** | **등급은 시험으로 정한다.** §5 적합성 시험 결과로 관리형·연동형·참조형을 판정한다 |
| **ER-5** | **신원을 매핑한다.** 외부 계정과 사원(AD)·에이전트·서비스 신원의 매핑 규칙을 정한다. 매핑되지 않는 외부 계정은 **고아 계정**으로 보고하고, 관리형이면 비활성 후보로 올린다 |
| **ER-6** | **나가는 길은 등록된 출구 하나다.** 외부로 가는 통신은 기록되는 출구(D-53)만 지난다. 연결 그래프에 외부 노드로 표시하고, 외부 쪽 인증서 신뢰를 연결 객체에 등록한다 |
| **ER-7** | **데이터 분류를 선언한다.** 외부로 가는 데이터의 분류 등급, 개인정보 포함 여부, 국외 이전 여부를 적는다. 개인정보·기밀 등급이나 국외 이전이 있으면 결재 위험을 높음으로 올린다 |
| **ER-8** | **리소스 유형을 등록해야 할당할 수 있다.** 이름은 `ext.<종류>` 형식이고, 카탈로그 문서 §3의 리소스 유형 정의를 따른다 |
| **ER-9** | **감사 경로를 정한다.** 외부 쪽 감사 로그를 테넌트로 수집하는 경로를 정한다. 수집할 수 없으면 "감사 불가"로 표시하고 위험으로 기록한다 |
| **ER-10** | **비용 단위를 맞춘다.** 외부 과금 단위(사용자 수, 호출 수, 용량)를 showback 단위(D-25)로 대응시킨다 |
| **ER-11** | **한 영역에만 속한다.** 외부 리소스는 사원 영역이나 고객 영역 중 하나에만 편입한다. 두 영역을 잇는 외부 리소스는 교류 계층 우회이므로 금지한다(T-9, D-83) |
| **ER-12** | **해체 절차를 미리 적는다.** 연결을 끊을 때 외부 쪽 계정·자격 회수, 데이터 반출·삭제 요청 방법을 등록 시점에 적는다 |
| **ER-13** | **편입 자체가 고위험 결재다.** 외부 어셈블리 편입은 회사 관리 콘솔 구성 구역에서 테넌트 관리자와 보안 담당 결재를 거친다(D-82, D-84). 연결 변경도 T-6에 따라 고위험이다. 편입 후 배분은 Governance가 한다 |
| **ER-14** | **정기 재검토한다.** 외부 리소스는 약관·API·보안 상태가 Fabric 밖에서 바뀐다. 등급을 재검토 주기마다 다시 시험한다 |

| 계정 생성 | 어댑터로 계정·권한을 만든다 | 필수 | — | — |
| 권한 목록 | 실제 계정·권한을 목록으로 읽는다 | 필수 | 필수 | — |
| 비활성·회수 | 퇴사 처리 후 외부 계정이 막히는 시간을 잰다 | 필수(D-21 기준 대비 기록) | — | — |

## 6. 외부 어셈블리 정의 예

```yaml
apiVersion: blueprint.opensphere.io/v1alpha1
kind: ExternalAssemblyDefinition
metadata:
  name: ext-collab-saas
  version: "1.0"
spec:
  purpose: 이미 쓰고 있는 외부 협업 SaaS를 Governance로 통제
  tenant: example
  area: employee                           # ER-11
  owner: { unit: "IT운영팀", contact: "운영 책임자" }   # ER-2
  contract: { license: "구독 계약서 위치", dpa: "데이터 처리 계약 위치" }
  endpoint: { host: "saas.example", egress: recorded }  # ER-6, D-53
  connector:
    identity: spiffe://example.tenant/employee/ext-collab-saas/connector
    credential: { kind: oauth-client, ref: kms://employee/links/ext-collab-saas, rotateEvery: 90d }  # ER-3
  identityMapping:                         # ER-5
    key: email
    unmapped: report-orphan
  data:                                    # ER-7
    classification: internal
    personalData: true
    crossBorder: true
  resourceTypes:                           # ER-8
    - id: ext.collab.seat
      control: managed                     # ER-4: 시험 결과로 확정
      actions: [{ id: use, risk: medium }, { id: admin, risk: high }]
      allocation: { units: [person, unit], measure: { unit: seat } }
      provisioning: { adapter: scim, create: true, disable: true, delete: true }
      reconcile: { list: true, interval: 15m }
      revocation: { target: 20m, measured: null }   # 시험에서 채운다
  audit: { source: "외부 감사 API", collect: true } # ER-9
  showback: { externalUnit: seat-month, costUnit: seat-month }   # ER-10
  decommission:                            # ER-12
    - revoke-connector-credential
    - disable-mapped-accounts
    - export-data
    - request-deletion
  review: { every: 90d, retestControlGrade: true }  # ER-14
```

## 7. 절차

```
 신청(소유 단위) → 적합성 시험 → 등급 판정 → 결재(테넌트 관리자 + 보안, ER-13) → 편입(외부 어셈블리 · 연결 객체 · 리소스 유형)
   → Governance 인계 → 할당 가능 → 대조 · 재검토(ER-14) → 해체(ER-12)
```

## 8. 이미 있는 외부 리소스: 외부 디렉터리

외부 AD 연결(`external-directory` Provider, D-3, D-6)은 이 규칙의 첫 사례다.
- 쓰기 허용 모드는 관리형이다. 읽기 전용 모드는 연동형이다.
- 설치 시 고객이 모드를 고른다는 기존 결정(D-6)과 등급이 그대로 대응한다.
