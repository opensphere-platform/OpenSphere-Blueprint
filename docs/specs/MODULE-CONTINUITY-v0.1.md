## 0. 놓인 자리

- 이 문서는 **P2(운영 전환) 뒤의 정상 운영**을 다룬다. 지금 진행 중인 전환(D-95 · P2)은 D-96 그대로다. 기존 인스턴스는 지우고 새 경로로 새로 설치하며, 데이터 보존 · 백업 · 복구 비용을 쓰지 않는다.
- 공통 원칙(기존 결정의 연장):
  - **선언은 패키지, 판정 · 집행은 호스트**(계약 v1 §0). 패키지가 선언한 값이 운영자 정책 · 신뢰를 넓히지 못한다.
  - **새 이름 없이 일반 기능으로**(D-95). 아래 기능은 모두 계약 원천 · 판정기 · 호스트 공통 경로로 들어오고, 특정 패키지 이름 분기를 두지 않는다.
  - **사람 승인과 MFA**. 데이터를 지우거나 되돌릴 수 없게 바꾸는 동작, 공급자를 바꾸는 동작은 계획 확인 · MFA를 거친다.

## 1. 데이터 수명주기와 이행

### 1.1 지금 있는 것

- 계약 v1 §8: A→B 갱신은 인스턴스를 유지한다. 패키지 내리기는 인스턴스가 남아 있으면 거절한다.
- 모듈별 삭제 규칙(D-98): Keycloak · Samba AD는 인스턴스 삭제 때 디스크도 지운다. Gitea는 저장소를 유지한다.
- 회수 정책(OSR v0.2 §8.3): 회수된 판의 현재 서비스는 자동 중단 · 삭제하지 않는다.
- 없는 것: 엔진 판 올림 때 데이터 변환, 되돌릴 수 없는 변경의 사전 보호, 보관 · 반출, 패키지 사이에 일관된 삭제 의미.

### 1.2 동작의 이름을 고정한다

| 동작 | 대상 | 데이터 | 승인 |
|---|---|---|---|
| 정지(Stop) | 인스턴스 | 그대로 | 기존 계획 · MFA |
| 내리기(Uninstall) | 설치본 | 인스턴스가 남으면 거절(지금 규칙) | 기존 |
| 인스턴스 삭제(Delete) | 인스턴스 | 패키지 선언(§1.3)의 기본값대로 | 기존 + 계획 화면에 데이터 효과 표시 |
| 보관(Archive) | 인스턴스 | 반출본을 남긴 뒤 삭제 | 계획 · MFA |
| 영구 삭제(Purge) | 남은 볼륨 · 반출본 | 되돌릴 수 없게 지움 | 계획 · MFA. **사원 영역 업무 데이터는 D-33(Governance 결정)** |
| 이행(Migrate) | 인스턴스 | 판 올림 때 형식 변환 | 갱신 계획에 포함, 되돌릴 수 없으면 §1.4 |

### 1.3 패키지 선언: `dataLifecycle` · `migration` part

- `dataLifecycle`(인스턴스 종류마다): 데이터의 위치(데이터 PVC · 외부 버킷 Claim 등), 삭제 기본값(`delete` · `retain`), 반출 지원 여부와 형식, 패키지가 밝히는 RPO/RTO(**정보 표시용이며 호스트가 보장하지 않는다**).
- `migration`(판 범위마다): `from` 판 범위 → 이 판, 종류(`compatible` 그대로 기동 · `job` 변환 Job · `export-import` 반출 후 재적재 · `unsupported`), 전제(최소 여유 공간 등), **되돌릴 수 있는지**.
- 판정기가 두 part를 판정한다. 선언이 없는 판은 지금과 같이 취급한다(데이터 효과 미선언 → 계획 화면에 "데이터 효과 미선언" 표시). 선언 없는 `unsupported` 경로의 갱신은 거절한다.

### 1.4 되돌릴 수 없는 이행의 사전 보호

- 갱신 계획이 되돌릴 수 없는 `migration`을 포함하면 계획 화면에 그 사실과 영향 인스턴스를 보이고, 승인 때 별도 확인을 받는다.
- **사전 보호의 주체(Q-C1):** 권고는 **호스트 공통 볼륨 스냅숏**이다. HISS 저장 엔진(Longhorn 등)이 스냅숏을 지원하면 Core가 이행 직전 대상 PVC의 스냅숏을 만들고, 기한 뒤 정리한다. 패키지 반출(`export`)은 선택 보강이다.
  - 이유: 패키지마다 백업 Job을 만들게 하면 품질이 제각각이다. 스냅숏은 패키지를 몰라도 되는 일반 기능이다(D-95).
  - 스냅숏을 지원하지 않는 저장소면 되돌릴 수 없는 이행은 기본 거절하고, 소유자가 위험 수용 사유를 남길 때만 연다.
- 이행 실패: 효과가 불확실하면 기존처럼 `unknown` → 복구 경로. 스냅숏이 있으면 복구 계획에 "스냅숏에서 되돌리기"를 선택지로 보인다(자동 실행 없음).

## 2. 공급자 전환 · 계보

### 2.1 지금 있는 것

- 정체는 `<공급자>/<이름>`(D-99 S99-5). 현장 빌드는 다른 정체가 된다(D-101 §1.5).
- 없는 것: 다른 공급자의 패키지에서 파생됐다는 계보, 설치된 인스턴스 · 데이터를 둔 채 공급자를 바꾸는 절차, 다른 공급자 모듈의 소스를 확보하는 방식.

### 2.2 계보 선언

- 디스크립터 v2에 `lineage`를 둔다: `derivedFrom`(원 패키지 정체 · 판 · 번들 digest · 원천 커밋)과 계보 이름(family).
- **계보는 주장일 뿐 신뢰를 물려받지 않는다.** 새 공급자의 서명 · 스토어 범위 · 품질 등급은 각자 따로 판정한다(S99 원칙 3). 원 공급자의 키 · 등급 · 프로필 승인을 넘겨받지 않는다.
- 판정기는 `derivedFrom`의 원 번들이 설치본이 아는 검증된 출처인지(원장에 있는지)만 확인하고, 모르면 "계보 미확인"으로 표시한다.

### 2.3 공급자 전환 계획

- 설치본 A(공급자 X)를 B(공급자 Y, `derivedFrom` A)로 바꾸는 별도 계획 종류를 둔다. 조건:
  1. B가 A를 `derivedFrom`으로 선언하고, 같은 실행 원형이며, A의 현재 판에서 B로의 `migration`이 선언돼 있다(§1.3).
  2. B의 프로필은 B 정체로 **새로 승인**한다(프로필은 정체에 묶인다).
  3. A의 Claim을 소비하던 다른 패키지의 의존성 잠금은 영향 목록으로 보이고, 전환과 같은 그룹에서 다시 묶거나 전환을 거절한다.
  4. 계획 화면에 출처 변화(스토어 · 공급자 · 키 지문 · 등급)를 그대로 보이고, 소유자 MFA로 승인한다.
- 되돌리기는 B → A로의 또 하나의 전환이다(같은 조건).
- **허용 범위(Q-C3):** 권고는 **계보 선언이 있는 전환만** 허용하는 것이다. 계보 없이 아무 패키지로나 바꾸는 것은 "새로 설치 + 데이터 반출 · 재적재"로 다룬다.

### 2.4 다른 공급자 모듈의 소스 확보

| 방식 | 뜻 | 들어오는 곳 |
|---|---|---|
| 이진만(기본) | 서명된 번들만 받는다 | 스토어 |
| 소스 미러 | 공급자가 낸 원천을 받아 둔다(수정 안 함) | **사용자용 Gitea(G1)**의 미러 저장소 |
| 현장 빌드 | 원천을 그대로 현장에서 빌드해 같은 결과를 확인 | SS4 현장 빌드 경로(기본 꺼짐) |
| 현장 관리 | 원천을 고쳐 현장 공급자 이름으로 발행(§2.3로 전환) | G1 저장소 + 로컬 스토어(D-103) |

- 공급자는 디스크립터에 `source`(저장소 · 커밋 · 하위 경로 · 빌드 정의 · 잠금 파일 · 라이선스)를 선언하고, 빌드 출처(provenance)와 일치해야 한다.
- **Backbone 자체 소스(관리 Gitea)와 섞지 않는다**(D-101 · SS3). 다른 공급자의 원천은 사용자용 Gitea(G1)에 둔다(Q-C4).

## 3. 보안 공지와 설치본 영향

### 3.1 지금 있는 것

- 회수(OSR v0.2 §8.3): 회수된 판은 신규 설치 · 새 변경 금지, 현재 서비스는 유지하며 경고, 진단과 안전 퇴역은 허용.
- 품질 표준의 취약점 기준(PQ §4)은 **신규 등록**에만 적용된다.
- 없는 것: 회수까지는 아닌 보안 공지, 설치된 판에 대한 영향 계산, 위험 수용 기록.

### 3.2 공지 문서

- 스토어가 서명한 `advisories` 문서를 목록 v2 옆에 둔다. 항목마다: 공지 id, 대상 패키지 · 영향 판 범위 또는 번들 digest, 심각도, 고친 판, 권고 조치(`update` · `mitigate` · `revoke-pending`), 참고.
- 공지는 **회수가 아니다.** 회수는 지금처럼 목록 · 등록부의 회수 기록으로만 한다(§8.3). `revoke-pending`은 곧 회수될 수 있다는 예고다.
- **서명 키(Q-C5):** 권고는 그 스토어의 목록 키로 서명하는 것이다(등록부가 위임한 목록 키 체인 재사용, 새 키 용도 없음).

### 3.3 호스트 동작

- MS2 reader가 공지를 함께 수집하고, Core가 설치본 영향(설치된 번들 digest · 판 범위 일치)을 계산한다.
- Console 스토어 관리 · 패키지 상세 화면에 "이 설치본에 영향 있는 공지"를 보이고, 계약 v1 §10 이벤트로 관리자에게 알린다(Swallow).
- **자동 조치는 하지 않는다.** 관리자가 고르는 조치:
  - 고친 판으로 갱신(범위 안에 있으면)
  - 위험 수용: 사유와 만료일을 기록하고, 만료되면 다시 알린다(Q-C6)
  - 인스턴스 정지(기존 동작)
- **다른 스토어의 공지:** 같은 번들 digest가 설치돼 있으면 다른 스토어의 공지도 **정보로만** 보인다. 조치 권한이나 회수 효과는 원 출처 스토어에서만 온다(스토어 간 신뢰 비전파, S99 원칙 3).

## 4. 폐쇄망 반입

### 4.1 지금 있는 것

- Backbone 이미지: Setup의 오프라인 OCI 반입(`importOfflineImages`)이 있다.
- 스토어: MS2는 `https://ghcr.io`만 받는다. 로컬 스토어 매체는 미결(D-103 §6.3).

### 4.2 오프라인 묶음

- 스토어 쪽 도구가 **서명된 자체 완결 묶음**을 만든다: 목록 스냅숏 · 등록부 · 골라 낸 번들(OCI 레이아웃) · 공지 · 신뢰 증거.
- 설치본 쪽 Setup이 묶음을 검증한다. 규칙은 온라인과 같다(서명 · 하한 · 범위 · 만료). 검증을 통과하면 **설치본 안의 OCI 레지스트리**에 올린다.
- **같은 스토어의 다른 출처(mirror):** 그 레지스트리를 원 스토어 정체의 대체 출처로 MS4 신뢰 변경(소유자 MFA)으로 등록한다. 신뢰는 원 스토어와 같고(같은 root · 키), 매체만 다르다. reader의 주소 허용 목록에 "승인된 mirror"를 더하는 계약 변경이 필요하다(지금은 GHCR만).
- **최신성:** 묶음의 목록 만료가 지나면 지금 규칙대로 신규 설치 · 갱신이 멈추고 운영은 유지된다. 오프라인 현장을 위해 스토어가 긴 만료의 채널을 따로 낼 수 있다(스토어 결정).

### 4.3 설치본 안의 레지스트리(Q-C8)

- 권고는 **HISS 구성요소로 둔다**(HISS 패키지 클래스, D-88)는 것이다. Backbone 이미지 반입과 패키지 반입이 같은 레지스트리를 쓰고, Backbone은 그 주소를 승인된 mirror로만 읽는다.

## 6. 구현 단위와 순서(D-104)

| 단위 | 내용 | 시기 |
|---|---|---|
| L1 | `dataLifecycle` · `migration` part 계약 · 판정기 · 계획 화면 데이터 효과 표시 | P2 뒤, 첫 판 올림 패키지 전 |
| L2 | 되돌릴 수 없는 이행의 스냅숏 사전 보호(HISS 저장 엔진 연동) | L1 뒤 |
| L3 | 계보 · 공급자 전환 계획 · 원천 선언 | SS4 뒤 |
