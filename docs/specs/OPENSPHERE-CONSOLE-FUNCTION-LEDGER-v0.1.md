- 조사 기준: Backbone main `f06b340`. 소스를 읽어 작성했다. 운영 화면을 브라우저로 다시 확인하지 않았다.

## 1. 먼저 알아야 할 것

1. **템플릿의 Configuration은 지금 서버와 연결되지 않는다.** `/dummy`의 톱니바퀴 아래에는 화면 14종이 있지만, 모두 예전 Console의 API(`/api/v1/bbss/…`)를 부른다. 지금의 Backbone 서버는 그 API를 제공하지 않는다. 화면 모양은 있고 서버가 없다.
2. **지금의 Backbone 기능은 서버가 있고 틀이 다르다.** 기존 Console은 `/console-api/…` 72개 경로를 쓰고, 이미 "톱니바퀴 아래 Backbone 메뉴" 구조로 돼 있다. 틀만 템플릿과 다르다.
3. **그래서 이관의 실체는 "템플릿의 틀 + 기존 Console의 API와 권한 계약"이다.** 템플릿의 Configuration 화면을 켜는 것으로는 되지 않는다. 템플릿 화면은 모양의 참고이고, 연결은 새로 한다.
4. **Console에는 역할이 하나뿐이다.** 관리자 목록에 있으면 모든 관리 기능을 쓸 수 있다. 검토자 구분은 Core에만 있고, 승인도 관리자 세션이 있어야 할 수 있다. "reviewer가 전체 관리자 권한 없이 검토만 한다"는 완료 기준은 화면 정리만으로 충족되지 않는다. 서버 변경이 필요하다.
5. **템플릿의 왼쪽 레일과 메뉴는 사실상 전부 다른 회사 것이다.** 메뉴 136개 중 126개가 IBM Cloud 기준이고, 실제 화면으로 가는 것은 대시보드, Containers, Fabric, HISS, AI 공급뿐이다. 그 화면들도 고정 예시 데이터다.

## 2. 기존 Console 기능 원장

상태 표기는 다음과 같다.

| 표기 | 뜻 |
|---|---|
| 소스 | main에 화면과 서버 경로가 있다 |
| 배포 | 운영 Console 이미지에 들어 있다(이미지의 소스 커밋 기준) |
| 운영 응답 | 운영에서 그 API가 기대한 값을 돌려주는 것을 Setup 검증으로 확인했다 |
| 미확인 | 이번 조사에서 운영 동작이나 활성 여부를 확인하지 않았다 |

모든 행은 관리 plane이고, 로그인한 관리자 세션이 필요하다. "승인"은 Core의 독립 서명 승인을 뜻한다. 새 위치의 번호는 4절의 묶음 번호다.

### 2.1 로그인 전 화면과 세션

| 최초 관리자 설정 | `setup/status`, `setup/claim` | 설치 토큰. 세션 없음 | 소스 · 배포 | 셸 밖(로그인 전) | 유지. Setup의 권위를 웹으로 넓히지 않는다 |

## 3. 템플릿(`/dummy`) 원장

| 구분 | 내용 | 제안 |
|---|---|---|
| 틀 | 머리줄, 왼쪽 레일, 보조 탐색, 페이지 틀, 반응형, 보조 패널(OS Shell · AI) 자리 | **유지.** 새 Console의 기반 |
| 디자인 체계 | Carbon, 글꼴 | 유지. 잔재가 아니라 선택한 체계다 |
| Configuration 화면 14종 | 운영 인증, 관리자 목록, 권한 관리, DB, 저장소, AI Agent, 모델, OS Shell, 모니터링, 리소스 Registry, 변경 요청과 승인, 백업, 감사, 매뉴얼 | **모양만 참고.** 예전 API를 부르는 코드는 연결하지 않는다 |
| 템플릿의 로그인 · 세션 코드 | 브라우저 저장소에 토큰을 두는 방식, 개발용 로그인 버튼 | **쓰지 않는다.** 기존 Console의 서버 세션을 쓴다 |
| 왼쪽 레일의 다른 회사 항목 | API Management, 인프라, Cloud Pak, Partner Center, Satellite, VMware, watsonx 등 | **폐기** |
| 머리줄 "관리" 메뉴, 비용 추정기, 둘러보기 | 계정, 청구, 엔터프라이즈, IAM 등 | **폐기**(계정 화면은 2.1의 "접근 및 세션"으로 대체) |
| 대시보드 | IBM Cloud 대시보드의 사본 | **폐기.** 공통 홈이 필요하면 새로 정한다 |
| Containers, 상태(167개 서비스), 마켓플레이스, 검색 결과, 문서 센터, 메시징 | 다른 회사 예시 | **폐기** |
| Fabric · HISS · AI 공급 화면 | 공유 서비스 21종, PostgreSQL, Argo CD, Crossplane, 쿠버네티스 리소스, AI 공급 | **보류.** 상위 레이어 몫이고 지금은 예시 데이터다. 설치된 것으로 보이지 않게 격리한다 |
| 운영 경보 알림 화면 | 관측 알림 목록 | 모양 참고. 연결할 API가 지금 서버에 없다 |
| AI 에이전트 패널, OS Shell 패널 | 미리보기 / 세션 필요 | **보류.** 자리만 남기고 끈다. 연결할 서버 계약이 정해진 뒤 |
| 모든 경로의 "데모" 안내 화면 | 없는 경로를 받는 화면 | 유지하되 문구를 "없는 화면"으로 바꾼다 |
| 예시 데이터 | 약 4,800줄 | 운영 틀에서 분리한다. 예시가 정상 상태처럼 보이면 안 된다 |

**먼저 지워야 할 것.** 메뉴 데이터에 다른 사람의 계정 정보로 보이는 잔재가 한 줄 있다. 운영 이미지에 들어 있으므로 정리 순서와 무관하게 먼저 지운다.

**라이선스.** 다른 회사의 화면 문구와 그림(레일 아이콘, 마켓플레이스 그림, 제품 로고)의 표기 의무는 이 조사에서 확인하지 않았다. 폐기 대상은 지우는 것으로 해결하고, 남기는 로고만 따로 확인한다.

## 4. Configuration 내부 매핑안 (회신 1)

## 5. 범위와 경계 (회신 2)

재정의 문서의 v1 범위에 동의한다. 관리 Console을 먼저 하고, 회사 관리 영역과 Workspace는 이 사업에 넣지 않는다.

- **지금 역할은 하나다.** 관리자 목록에 있으면 모든 관리 기능이 열린다. 검토자 구분은 Core에만 있다.
- **검토자도 관리자여야 승인할 수 있다.** 승인 경로가 관리자 세션 뒤에 있다. 오늘 등록한 검토자에게 관리자 역할을 함께 준 이유다.
- **화면 정리로는 이 경계가 바뀌지 않는다.** "검토자가 전체 관리자 권한 없이 검토만 한다"는 서버 변경(검토자용 세션과 경로 제한)이 있어야 한다. 이 사업의 조회 이관과 분리해 별도 단계로 두기를 제안한다.
- **역할별 접근표(지금 사실).**

| 주체 | Console 로그인 | 관리 기능 | 승인 |
|---|---|---|---|
| 관리자 | 된다 | 전부 | 검토자이기도 하고 요청자가 아닐 때만 |
| 검토자만(관리자 아님) | 안 된다 | 없음 | 못 한다 |
| 에이전트 토큰 | 해당 없음 | 조회 다섯 경로만 | 못 한다 |
| 로그인하지 않은 사람 | — | 없음 | — |

로그인하지 않아도 정적 파일은 받을 수 있다. 지금의 `/dummy/`와 공개로 선언된 화면 모듈이 그렇다. 새 Console의 틀도 정적 파일이므로 받을 수는 있지만, 데이터는 세션이 있어야 나온다. 틀 안에 예시 데이터를 남기면 안 되는 이유다.

## 6. 템플릿 잔재와 미연결 기능의 분리 (회신 4)

1. **지운다.** 다른 회사의 메뉴 데이터, 대시보드, Containers, 상태, 마켓플레이스, 검색 예시, 문서 센터, 메시징, 머리줄의 계정 · 청구 메뉴. 새 Console의 소스에 넣지 않는다.
2. **격리한다.** Fabric · HISS · AI 공급의 예시 화면은 새 Console의 빌드에서 빼고, 지금처럼 별도의 예시 묶음(`ui.dummy-screens`)으로 둔다. 실제 계약이 생긴 화면만 하나씩 새 Console로 옮긴다.
3. **끈다.** AI 패널과 OS Shell 패널은 자리만 남긴다. 눌렀을 때 "아직 연결되지 않았다"고 말하고, 예시 대화를 보여 주지 않는다.
4. **상태를 다섯 가지로 구별한다.** 정상 / 오류 / 미구성 / 권한 없음 / 아직 없는 기능. 빈 화면이나 예시 값으로 대신하지 않는다.
5. **메뉴는 서버가 가진 것만 만든다.** 메뉴 데이터 파일을 손으로 채우지 않고, 4절의 화면 목록과 OSR이 내려주는 화면 모듈 목록으로 만든다.

## 7. 기존 계약을 재사용하는 경로와 서버 변경 범위 (회신 5)

- **세션.** 기존 `login` · `session` · `logout`과 서버 쿠키 세션을 그대로 쓴다. 템플릿의 세션 서비스는 `/console-api`를 부르는 얇은 클라이언트로 바꾼다. 템플릿에 있지만 쓰이지 않던 경로 가드를 이 세션에 연결한다.
- **API.** 2절의 경로를 그대로 쓴다. 조회 이관에는 서버 변경이 없다.
- **화면 모듈.** 적용 중인 모듈 목록(`osr/installations`)으로 제품 영역의 메뉴를 만든다. 지금 Console이 하는 방식과 같다.
- **주소 방식.** 서버는 확장자 없는 경로를 기존 Console의 첫 화면으로 돌린다. 그래서 새 Console은 템플릿처럼 `#` 뒤에 경로를 두는 방식을 유지해야 한다. 깊은 링크와 새로고침은 이 방식으로 동작한다. 정식 주소를 바꾸려면 서버 변경이 필요하다.
- **조회 이관에 필요한 서버 변경:** 없음.
- **뒤 단계에 필요한 서버 변경(새 기능이라 따로 합의):** 검토자용 접근, 감사 조회, 관리자 · 검토자 목록, 정식 주소, 알림 전달 이력.

## 8. 첫 이관 기능군과 PR (회신 3 · 6)

기존 Console은 전환할 때까지 지금 주소에서 그대로 동작한다. 새 Console은 다른 경로에서 자란다. 문제가 생기면 새 경로를 끄는 것이 복구다.

| PR | 내용 | 수용 시험 | 구 경로 · 복구 |

## 9. 기준 커밋과 배포 경로 (회신 7)

- **기준 커밋.** main `f06b340`에서 전용 작업 공간을 만든다. 화면 소스는 `console/`과 `modules/`에 있고, 진행 중인 업데이트 분리 작업은 `setup/`과 `infra/contracts/`에 있다. 겹치는 파일이 없다.
- **배포 경로는 두 가지가 가능하다.** 아래 제안대로 정해졌다(소유자, 2026-11-18).

| 경로 | 방식 | 장점 | 한계 |
|---|---|---|---|
| 화면 모듈 | 새 Console을 OSR `ui` 모듈로 내고 승인하면 바로 적용된다. 접근은 관리자 전용으로 선언한다 | Setup 릴리스가 필요 없다. PR A~E를 운영에서 작은 단위로 올릴 수 있다 | 주소가 `/ui/…` 아래다. 검토자의 승인 키 등록이 먼저 끝나야 한다 |
| 본체 릴리스 | Console 이미지에 넣어 본체와 함께 올린다 | 정식 주소에 놓을 수 있다 | 묶음이 적용된 뒤라 Console만 따로 올리는 체인을 더 쓸 수 없다. 외부 Bundle 경로는 아직 없다 |

- **정해진 것.** PR A~E는 화면 모듈로 올리고, 전환(PR F)만 본체 릴리스로 한다. Backbone 결정 D6("화면은 OSR `ui` 모듈로, Console 골격은 본체 경로로")과 같은 방향이다.
- **업데이트 분리 계획과 부딪히는 곳.** 그 합의안은 첫 외부 릴리스 후보를 "Console 이미지에서 `/dummy/` 빼기"로 적었다. `/dummy`가 새 Console의 기반이 됐으므로 그 후보는 바꿔야 한다.
- **시험 환경.** 재정의 문서의 "운영 RKE2의 격리된 시험 환경"은 운영 클러스터의 임시 namespace에서 하는 부분 시험으로 읽었다. 두 번째 Backbone을 띄우지 않는다는 2026-11-18의 결정을 따른다.

## 10. 정해야 할 것

1. **배포 경로. — 정해짐(소유자, 2026-11-18): 이행은 화면 모듈, 전환만 본체 릴리스.**
   - 따라오는 것: 운영에 올리려면 검토자의 승인 키 등록이 먼저 끝나야 한다. 이행 기간의 주소는 `/ui/…` 아래다.
2. **검토자의 최소 권한 접근.** 이 사업 안에 넣을지, 별도 단계로 둘지. 제안은 별도 단계다.
3. **예시 화면의 처리.** Fabric · HISS · AI 공급 예시를 새 Console에서 빼고 별도 묶음으로 두는 것에 동의하는지.
   - **결정(소유자, 2026-11-18): Fabric은 새 Console에 넣는다.** 레일에 OpenSphere Fabric 큰 메뉴와 그 아래 메뉴 · 예시 화면을 두고, 메인 인덱스(대시보드)도 예시 화면으로 둔다. 화면마다 "예시 화면"이라고 밝히고 서버를 부르지 않는다. 8절 2항의 "격리한다"는 Fabric에 대해 이 결정으로 바뀐다. HISS · AI 공급 예시는 지시가 없어 그대로 별도 묶음에만 있다.
4. **공통 홈.** 로그인 직후 무엇을 보여 줄지. 제안은 Configuration의 현황으로 바로 가는 것이다. 제품 영역에 실제 제품이 생기면 그때 홈을 만든다.
5. **감사 조회와 계정 · 역할 목록.** 화면을 만들려면 서버에 조회 API가 필요하다. 언제 넣을지.

## 11. 이 조사에서 확인하지 않은 것

- 운영 화면의 실제 렌더링. 소스와 서버 경로만 읽었다.
- 기능 스위치의 운영 값(모델 관리, 시험 배포, 배포). 켜져 있는지에 따라 2절의 일부 화면은 운영에서 "미구성"으로 보인다.
- 다른 회사 자산의 라이선스 표기 의무.
- 템플릿 화면이 `/dummy/` 아래에서 예전 API를 불렀을 때 서버가 실제로 돌려주는 응답.
- 2절의 "운영 응답" 외 기능의 운영 수용 여부. 소스가 있고 이미지에 들어 있다는 것까지만 확인했다.
