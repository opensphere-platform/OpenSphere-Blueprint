## 1. 제품 정의

**OpenSphere-Console은 OpenSphere의 관리 경험을 제공하는 공통 진입점·탐색·작업 표면이다. Backbone은 그 안의 기반 관리 영역이며 Console 전체의 동의어가 아니다. **Backbone 소속 기능·메뉴는 모두 톱니바퀴의 Configuration 아래에 배치한다.****

/dummy의 화면 골격·탐색·패널 구성을 출발점으로 사용하고, 기존 Console의 검증된 업무·API·권한·감사·지속 작업을 새 틀로 이관한다. 화면을 복사하는 사업이나 백엔드를 새로 만드는 사업이 아니다.

기존 Blueprint D-84는 Admin Console·회사 관리 콘솔·Workspace를 구분한다. 이번 명칭 변경만으로 세 신뢰 영역을 하나로 합치지 않는다. v1은 관리 Console을 중심으로 기존 Backbone 기능을 보존한다. 회사 관리 영역은 경계·계약이 확정된 기능부터 확장하고, Workspace는 별도 사용자 경험으로 연결한다. 전체 사용자 화면까지 이 이름에 포함할지는 추가 합의 대상이다.

같은 화면 틀·도메인·로그인을 선택하는 것과 권한 통합은 서로 다른 문제다. 사용자 신원으로 운영 관리자 권한을 얻어서는 안 된다.

## 3. 확정된 배치 원칙과 세부 정보 구조

### 3.1 보스 결정 — 2026-11-18

1. /dummy를 새 OpenSphere-Console의 기반으로 사용한다.
2. 지금까지 구현한 결과물을 기능적·개념적으로 정리하여 통합한다.
3. **Backbone에 소속된 기능·메뉴는 모두 톱니바퀴: Configuration 아래에 배치한다.**
4. OpenSphere-Console 전체와 Backbone 관리 영역을 동일시하지 않는다.

Configuration은 단순한 개인 환경설정 창이 아니라 Backbone의 운영·관리 작업 영역이다. 기반 서비스의 설정뿐 아니라 조회·작업·승인·감사도 해당 소속에 따라 이곳에 둔다. 이를 별도의 최상위 Backbone 메뉴와 병행해 이중 구조로 만들지 않는다.

### 3.2 전체 구조

```text
OpenSphere-Console
├─ 공통 셸: 탐색·검색·알림·도움말·허용된 보조 패널
├─ 상위 레이어·제품 영역
│  ├─ 제품·서비스별 관리 또는 사용 화면
│  └─ 회사 구성·배분 영역 등 (계약 확정 후 확장)
└─ 톱니바퀴: Configuration [Backbone 전체]
   ├─ Backbone 현황
   ├─ 기반·서비스·저장
   ├─ Nexus·연결·모듈 계약
   ├─ OSR·등록·검증·설치
   ├─ 개발·전달
   ├─ R2D2·관리용 AI
   ├─ 접근·정책·승인
   └─ 운영 관측·알림·감사
```

위에서 Configuration 배치는 확정 원칙이고, 그 안의 묶음 이름·순서·페이지 깊이는 협의안이다. 상위 레이어·제품 메뉴는 지원 계약과 권한이 있는 기능만 연결한다. 사용자 Workspace를 이번 사업에서 완성한다고 선언하지 않는다.

### 3.3 Configuration 내부 기능 매핑안

| 내부 묶음 | 포함 기능 | 기존 결과물·보존 조건 |
|---|---|---|
| Backbone 현황 | 설치본·버전·기반 서비스 상태·운영 작업·주의 항목 | 기존 overview·status. 관측 시각·연결 실패·미구성 구별 |
| 기반·서비스·저장 | 기반 서비스 상세·기능 연결·초기 설정·저장 프로필 | 서비스 조회·Foundation. 초기 저장 선택의 웹 재선택 금지 유지 |
| Nexus·연결·모듈 계약 | 버스·액션·연결·모듈 계약·어댑터 | Nexus·modules·adapters. 등록된 액션과 실행 권한을 구별 |
| OSR | 구성원 등록·규격·신뢰·검증·설치·활성 상태·UI 기여 관리 | OSR 원장·Core 영수증. 등록/검증/설치/활성/메뉴 노출을 구별 |
| 개발·전달 | Backbone 관리용 소스·PR·CI·산출물·릴리스·업데이트 현황 | 기존 Git/CI·release·배포 증거. 빌드 성공과 운영 적용 성공 구별 |
| R2D2·관리용 AI | 관리 요청·대화·모델 역할·제품 지식·관리용 공급 설정 | R2D2·Magpie·knowledge. 등록과 실제 활성화·사용 구별 |
| 접근·정책·승인 | 관리 접근·역할·세션·정책·검토·실행 이력 | 기존 Auth·독립 승인·Core. reviewer와 전체 관리자 권한 구별 |
| 운영 관측·알림·감사 | Backbone 건강·사건·통지 관리·감사·작업 상관관계 | 관측·Swallow·감사. 상위 업무 데이터 수집 권한 확대 없음 |

이 표는 소속에 따른 이관안이지 새 기능의 완성 선언이 아니다. 키 등록·교체처럼 운영자 전용인 작업은 현황과 절차만 제공하고, 이번 메뉴 정리로 웹 실행 권한을 신설하지 않는다. Setup의 독립 설치·승인·복구 권위를 웹으로 이전하지 않는다.

### 3.4 안과 밖을 구별하는 사례

| 대상 | Configuration 안 | Configuration 밖 |
|---|---|---|
| OSR·제품 | 제품 등록·검증·설치·UI 기여 관리 | 설치된 제품의 실제 관리/사용 화면 |
| R2D2·에이전트 | Backbone 운영용 R2D2·모델·지식 설정 | 상위 제품의 업무용 에이전트 경험 |
| Git·전달 | Backbone 자가 운영의 소스·CI·배포 작업 | 별도 개발 제품이 제공하는 사용자 업무 |
| 알림·관측 | Backbone 통지 설정·운영 사건·감사 | 제품별 사건·사용자의 허용된 알림 |
| 저장·DB | 기반 저장 프로필·운영 설정 | 상위 제품이 제공하는 업무 데이터 기능 |

이름만 같다고 기능을 복제하지 않는다. 같은 자원의 상세 화면·API·원장을 재사용하고 문맥·권한에 따라 접근을 나눈다. HISS·Fabric·AI 공급 등 템플릿 항목도 실제 소유 경계를 확인하여 분류하며, 무조건 Backbone으로 편입하거나 실제 설치된 것으로 표시하지 않는다.

### 3.5 공통 셸과 보조 진입점

검색·알림·도움말은 공통 셸에 둘 수 있다. 관리용 OS Shell·R2D2 패널도 허용된 문맥에서 보조 진입점을 제공할 수 있지만, Backbone 기능의 대표 메뉴·페이지는 Configuration에 둔다. 별도 최상위 관리 메뉴를 중복 구성하지 않는다.

공통 홈이 있다면 접근 가능한 제품과 필요한 요약을 제시한다. Backbone 전용 상세 운영 대시보드는 Configuration 안에 둔다. 글로벌 검색·알림에 표시되는 Backbone 정보도 해당 권한으로 필터링하고 상세 화면은 Configuration으로 연결한다.

OS Shell은 무제한 셸이 아니다. 보조 진입점·메뉴 숨김·URL 경로 자체는 보안 경계가 아니며, 서버의 신원·설치본·역할·승인 검사를 유지한다.

## 4. 기능 인수 원장

Claude의 첫 산출물은 전체 화면·액션별 매핑표다. 모든 기존 기능과 새 템플릿 경로에 다음 필드를 작성한다.

- 기존 화면·액션 / 소속(Backbone 또는 상위 레이어·제품) / 새 위치 / 사용 목적·사용자 / 관리·회사·사용자 plane
- 기능 소유 모듈 / API·데이터 정본 / 설치 ID·자원 ID / 요구 역할·승인
- 현재 상태: 소스 존재 / 배포 확인 / 수용 검증 / 미연결·예시·계획
- 유지·통합·이관·보류·폐기 제안 및 근거 / 시험·영수증 / 복구·구 경로

특히 초기 설정·저장 프로필, Nexus·모듈, OSR, Git/CI·전달, 서비스 조회, 승인/실행, R2D2·모델·지식, 세션·감사·관측을 누락하지 않는다. 컴포넌트 수나 메뉴 수를 완성률로 쓰지 않는다.

## 5. 요구사항의 문제·보완점

1. **기반으로 채택하는 것은 타당하지만 그대로 운영화하는 것은 부적절하다.** 예시 데이터·placeholder·미연결 동작과 인증 없는 미리보기 전제를 제거/격리한 뒤 실제 계약을 연결해야 한다.
2. **OpenSphere 전체 화면이라는 표현은 범위가 모호하다.** v1 관리 Console, 회사 관리 확장, Workspace의 경계를 명시한다. 기존 Blueprint와 달라지는 부분은 결정 기록으로 남긴다.
3. **현재까지의 결과물 전체가 완성 기능은 아니다.** 코드를 찾았다는 사실, 서버가 응답한다는 사실, 실제 사용자 동작이 검증됐다는 사실을 분리한다.
4. **템플릿은 기능 요구서가 아니다.** IBM/Paver 등 잔재·공급자 예시·중복 검색/알림/카탈로그 메뉴를 정리한다. 제3자 자산의 라이선스·표기 의무도 확인한다. 메뉴에 존재하는 엔진을 새로 설치하지 않는다.
5. **독립 앱을 iframe으로 넣는 조립은 목표에 맞지 않는다.** 공통 세션·탐색·테마·대화상자·지속 작업을 갖추되 업무 소유자·승인 경계는 보존한다.
6. **/dummy는 이행 경로이지 제품 이름이 아니다.** 최종 정식 경로는 후속 설계에서 고정하고, 구 경로·북마크·콜백·정적 자산 경로·실행 중 작업에 대한 호환 계획을 둔다. 즉시 / 경로를 덮어쓰지 않는다.
7. **UI 갱신과 Backbone 배포 도구 변경을 불필요하게 묶지 않는다.** Bundle 분리 작업을 따라가되 완료되지 않은 외부 Bundle 경로를 가정해 배포하지 않는다.

## 6. 단계별 진행과 수용 기준

1. 정의·Configuration 배치 원칙을 기준으로 기능 인수 원장 합의. Backbone 기능을 바깥 최상위 메뉴에 분산하지 않고 실제 지원 기능과 역할을 매핑한다.
2. 공통 세션·탐색·오류·알림·작업 문맥 연결. 인증 만료·권한 회수·직접 URL/API 우회·설치본 혼동을 시험한다.
3. 조회부터 기능군 단위 이관, 이후 쓰기·승인·긴 작업 이관. 기존 API·Nexus·Core의 승인/멱등/감사/회수 계약을 재사용한다.
4. 운영 RKE2의 격리된 개발/시험 환경에서 검증. 운영 Secret·계정·데이터·DB·저장소와 분리한다. localhost 통합 환경은 만들지 않는다.
5. 대표 사용 시나리오·모바일·키보드·깊은 링크·새로고침·장기 작업 재접속·오류/거절 상태를 브라우저로 검증한다. 소스/HTTP 확인을 렌더링 검증으로 대체하지 않는다.
6. 필수 CI·PR·불변 산출물·공개 Setup/지원된 갱신 경로와 연결해 단계적 운영 전환한다. 복구용 구 이미지·경로·검증 자료를 보존한다.

완료 기준: 합의한 기존 기능 전부가 매핑되어 누락·권한 확대 없이 실제 동작한다. 운영 화면에 예시 성공·가짜 정상·불명확한 빈 화면이 없다. reviewer가 전체 관리자 권한 없이 허용된 검토만 수행한다(해당 권한 기능 구현 시). 작업 중 화면 전환·세션 갱신 후에도 원장 기반 상태를 되찾는다. Console 장애 시 독립 복구가 가능하다.

## 7. Claude에게 요청할 회신

- Backbone 전체를 Configuration에 배치하는 원칙에 맞춘 내부 메뉴·화면 매핑안은 무엇인가?
- 위 v1 범위와 회사 관리·Workspace 경계에 동의하는가?
- 기존 기능 → 새 화면 전수 매핑표, 중복 통합 및 폐기 제안은 무엇인가?
- 템플릿 예시·외부 명칭·미연결 기능을 어떻게 분리할 것인가?
- 기존 세션·API·UI 모듈 등록 계약을 재사용할 구체 경로와 서버 변경 범위는?
- 첫 이관 기능군, 각 PR의 수용 시험·구 경로·복구 방법은?
- Bundle 분리 작업과 충돌하지 않는 기준 커밋·배포 경로는?

이번 문서는 위 합의를 위한 초안이며 Claude에게 직접 전송하거나 구현을 지시한 기록이 아니다.

## 8. 역할·진행 범위·산출물

- 보스: 제품 정의·메뉴 소속 원칙 결정. 기존 결정에 따른 통상 구현 선택은 반복 승인 대상으로 만들지 않는다.
- Claude: 기능 전수 매핑, 내부 탐색·화면·API 연결 설계 및 합의된 범위 구현.
- 팀장: 개념·소유권·권한·기존 기능 보존·배포/복구 계약 검토와 수용 근거 확인.
- 필수 산출물: 기능 인수 원장, 정보 구조, 역할별 접근표, 화면별 데이터/액션 계약, 단계별 PR·시험·배포/복구 증거.
- 구현 순서: 공통 세션·Configuration 골격 → Backbone 조회 → 변경·승인·지속 작업 → 상위 제품 연결 → 운영 전환.
- 미확정: 회사 관리·Workspace 포함 범위, 내부 묶음 세부 명칭, 정식 URL, 첫 전환 기능군, 기준 커밋과 배포 시점.
- 이번에 하지 않는 일: 운영 교체, 신규 엔진 설치, 권한 확대, 기존 데이터 이전/삭제, 배포 서명 키 변경.

## 9. 핵심 수용 체크리스트

- [ ] 모든 기존 기능·액션이 매핑되어 누락 및 의도치 않은 폐기가 없다.
- [ ] Backbone의 모든 대표 기능 메뉴가 Configuration 아래에 있다.
- [ ] 설치된 상위 제품의 사용 화면을 Backbone 설정으로 잘못 편입하지 않는다.
- [ ] 공통 보조 진입점은 권한을 지키며 Backbone 관리 메뉴를 중복 생성하지 않는다.
- [ ] 운영 화면의 예시·미연결·오류·미구성·정상 상태가 명확히 구별된다.
- [ ] 인증·역할·승인·감사·작업 ID·원장·키 회수 및 멱등 계약이 보존된다.
- [ ] 깊은 링크·로그인 복귀·새로고침·브라우저 재접속·모바일·키보드 동작을 검증한다.
- [ ] 필수 CI와 격리 RKE2 시험, 운영 전환 후 관측·복구 근거가 있다.
- [ ] Console이 중단돼도 독립 Setup·검증 자료·복구 산출물에 접근할 수 있다.

## 10. 결론

**/dummy를 OpenSphere-Console의 공통 기반으로 채택한다. Backbone 기능은 모두 톱니바퀴 Configuration 안에 정리하고, 그 기반 위에 구성되는 상위 레이어·제품 경험은 밖에 배치한다. 기존 기능·신뢰 경계를 유지하면서 화면과 탐색을 통합한다.**

문서의 제품 기반과 Configuration 배치는 보스 결정이며, 세부 기능 분류·이관 순서·운영 적용은 본 문서의 원장과 검증 절차를 통해 구체화한다.
