# OpenSphere 운영 UX · 관리 기능 수용 요구사항 v0.1

**상태:** 2026-11-20 소유자가 KubeSphere 비교 후 정리된 10개 항목의 청사진 반영을 요청했다. 아래는 수용 요구사항과 수용 시험안이며 구현·운영 검증 완료가 아니다. 새 D-번호나 운영 배포 승인을 만들지 않는다.
**목적:** 업무 데이터 환경 제공이라는 제품 목적을 유지하면서, 운영자가 현재 상태 → 원인·증거 → 허용된 조치 → 결과 확인을 한 흐름에서 수행하도록 한다.

## 1. 적용 원칙과 책임 경계

- KubeSphere의 운영 방식에서 참고한 요구사항이며 코드·화면 복제나 제품 도입 결정이 아니다. 기존 OpenSphere 기능·API·관측 도구를 먼저 재사용한다. 새 도구·중복 원장·별도 관측 플랫폼 도입을 요구하지 않는다.
- Backbone 소속 기능은 모두 톱니바퀴 **Configuration** 안에 둔다. 테넌트 어셈블리 구성·Governance·Workspace는 각 책임 영역을 유지한다. 기능 이름이 아니라 소속·목적으로 분류한다.
- 화면 간 연결은 서버 권한 경계를 넘는 자동 권한 부여가 아니다. 목록·상세·검색·로그·관계 조회에도 대상별 권한을 적용하며 비인가 대상의 이름·존재·업무 데이터가 누출되지 않게 한다.
- 어셈블리는 서비스 목적에 맞게 Fabric 인스턴스·전용 신원·자격·연결·설정·초기화·검증·수명주기를 결합해 배분 가능한 리소스 유형·용량을 내놓는 구성 단위다. 서명된 비실행 정의와 실제 구성된 서비스를 구별한다.
- 공급 API 접수·객체 저장·파이프라인 성공·로그 존재는 실제 효과 또는 업무 환경 수용 완료를 대신하지 못한다. 미관측·오래된 관측·부분 실패·결과 불명을 정상으로 표시하지 않는다.

## 2. 우선 수용 5개

| ID | 요구사항 | 필수 표시·동작 | 수용 시험안 |
|---|---|---|---|
| UX-01 | 자원 관계 탐색 | Fabric 인스턴스 ↔ Claim ↔ 어셈블리 ↔ 소비 제품의 관계, 소유 UID·목적·차용 여부. 관계 유형을 구별하고 선형 전용 관계로 가정하지 않음 | 기존 인스턴스 하나에서 소비 어셈블리로, 어셈블리에서 실제 공급 인스턴스로 왕복 탐색. 비인가 관계는 노출하지 않음 |
| UX-02 | 실행 과정 가시화 | 요청·계획·승인·시도·단계·API 적용·실제 효과 검증, 실패·unknown·재개 상태 | 중간 단계 실패·응답 유실을 주입해 완료 오표시가 없고, 재개가 기존 계약·권한·점유를 따름을 확인 |
| UX-03 | 운영 증거 연결 | 같은 대상·작업의 지표·이벤트·로그·감사·검증 증거를 상관 ID와 시각으로 연결. 증거 부재·조회 실패도 표시 | 실패 단계에서 해당 시도의 로그·승인·검증 증거로 이동. 다른 시도와 혼합되지 않고 비밀값은 마스킹됨 |
| UX-04 | 설치 전 의존성·영향 확인 | 필수/선택 기반, 호환 버전, 대상, 변경 내용, 소비자 영향, 차단 사유를 계획으로 제시 | 필수 의존성 미준비 시 차단 이유 표시. 승인 후 계획 변경은 기존 재승인 계약을 적용하고 임의 우회 불가 |
| UX-05 | 완료 상태 구분 | 등록·설치·실행 준비·서비스 구성 검증·업무 권한 통합 완료를 별도 상태로 표시 | 설치 성공이나 Pod Ready만으로 업무 권한 통합 완료가 되지 않음. 미지원·미검증 범위를 명시 |

UX-05의 상태는 모든 대상에 공통인 단일 직선 상태 기계가 아니다. 대상에 해당하는 단계만 표시하고, 단계마다 근거·버전·검증 시각·미완료 사유를 연결한다. 사용자 업무 환경 수용은 [업무 데이터 환경 계약](BUSINESS-DATA-ENVIRONMENT-CONTRACT-v0.1.md)의 별도 최종 단계다.

## 3. 후속 수용 5개

| ID | 요구사항 | 필수 표시·동작 | 수용 시험안 |
|---|---|---|---|
| UX-06 | 관리 범위·권한 표시 | 현재 관리 영역·대상·역할, 조회/변경 가능 범위, 제한 사유 | 역할 전환·권한 회수 후 UI와 서버 요청이 일치하며 직접 API 변경도 거절 |
| UX-07 | 변경·배포 이력 추적 | Gitea Actions의 요청·소스 커밋·검사·빌드·산출물 digest·배포 정의·migration·실제 운영 버전·검증 증거 연결 | 성공한 CI와 실제 배포본이 다른 경우 차이를 표시. 사용자 러너가 관리 배포 권한을 얻지 못함 |
| UX-08 | 연결·저장소 사용 관계 | 허용된 통신과 실제 관측 구별, 저장소 소비자·보존 소유자·사용 중 삭제 차단 사유 | 사용 중 자원의 삭제를 서버에서 거절하고 소비 관계를 권한 범위 안에서 제시 |
| UX-09 | 백업·복구 상태 분리 | 백업 생성·보존·접근 가능·실제 복원 검증의 상태와 시각·대상 버전 구분 | 백업만 있는 대상은 복원 미검증으로 표시. 이미지 롤백과 DB 복구를 같은 성공으로 취급하지 않음 |
| UX-10 | 일관된 운영 상세 화면 | 현재 상태 → 원인·증거 → 허용된 조치 → 결과 확인의 공통 흐름 | 대표 두 종류 대상에서 같은 탐색 규칙을 사용하되 대상 고유 계약·안전 조건은 보존 |

UX-06의 권한 강제는 후속 화면 개선 전에도 기존 필수 보안 조건이다. 우선순위는 화면 납품 순서이지 권한·승인·감사·독립 복구를 나중으로 미루는 허용이 아니다. UX-10의 공통 표현 규칙은 우선 항목부터 적용한다.

## 4. 납품·검증 순서

1. 기존 화면·API·원장·관측 기능을 조사해 UX-01~10별 재사용 위치, 부족한 계약, 책임 영역, 검증 상태를 매핑한다. 이미 구현된 기능을 중복 구현하지 않는다.
2. 우선 UX-01·02·03을 기존 PostgreSQL 하나 → Claim 하나 → 시험용 소비자 경로에 연결한다. 테스트 신원·합성 데이터와 기존 승인 절차를 사용한다.
3. UX-04·05를 OSR 설치·업데이트 및 어셈블리 계획에 연결한다. 기존 공급 명세의 승인·예약·점유·자격 세대·재개 계약을 변경하지 않는다.
4. UX-06~10의 화면 요구를 확장하고 업무 데이터 환경의 허용·거절·변경·회수 수용 시험과 연결한다.
5. 각 ID의 완료 보고에 소스/문서 버전, 검증 대상·시각, 기대/실제 결과, 증거 위치, 미지원·미검증 범위를 남긴다. 이 문서의 추가만으로 항목을 완료 처리하지 않는다.

## 5. 자가 운영 · 독립 복구 기준과의 연결

자가 운영 기준선 `/Volumes/DevOps/Operations/Supabase/multihead/R2D2-SELF-OPERATING-BLUEPRINT.md`의 요청부터 변경·검증·배포·관측·복구까지의 추적 목표와 연결한다.

- UX-02·03·07: 요청·커밋·검사·산출물·배포 결과를 연결한다. 기존 Supabase Auth/PG/Storage·Gitea Actions의 검증된 능력을 우선 재사용한다.
- UX-06: 관리 신뢰 영역과 사용자 실행 영역, 빌드와 특권 배포 권한을 구분한다. UI에서 승인 정책을 완화하지 않는다.
- UX-09: Console·Auth·Gitea·R2D2 중단 시에도 별도 운영자 경로로 복구할 수 있어야 한다. 웹 복구 버튼·화면 접근을 독립 복구의 필수 조건으로 만들지 않는다.
- 소스·문서·복구 증거는 DevOps에서 호스트와 독립적으로 보존하고 Windows에서도 읽을 수 있게 한다. OpenSphere 빌드에는 CC1과 ARM을 사용하지 않는다.
