# OS Govern — 공급 주체 계약 기반 동적 프로파일 v0.1

**작성일:** 2026-11-21 (KST)
**근거:** 소유자 Telegram 52758·52762의 요구와 52764의 청사진 반영 요청. 2026-11-21 Telegram 52865·52867: Fabric 자체 리소스도 배정 대상에 포함하도록 보강.
**상태:** 소유자 요구와 설계 방향을 기록한 장. 아래 필드명·상태·형식 조합·시험은 상세 설계 제안이다. D-결정 대장을 자동 개정하지 않으며 구현·제품 선정·설치·배포 완료 또는 착수 승인으로 읽지 않는다.

## 1. 목적과 기존 문서와의 관계

OS Govern은 평면적인 리소스·수량·행위 CRUD를 넘어, **등록된 공급 주체(Fabric 또는 구성·검증된 어셈블리)의 권한·공급 계약을 해석하여 공급 주체별 다단계 프로파일을 구성·검증·발행하고 조직·사람 등에 배정하는 제어 시스템**이어야 한다. 프로파일 작성과 배정은 별도 업무다. StackGres PG 프로파일의 상세 옵션·다단계 경험은 비유이며, PG 인프라 구성 권한을 Governance로 옮기는 요구가 아니다.

- [어셈블리 카탈로그](ASSEMBLY-CATALOG-v0.1.md)의 ResourceType 등록을 대체하지 않고, 그 등록을 권한 의미·옵션·화면·수명주기 계약으로 구체화한다.
- [어셈블리·Fabric 협력 공급 v0.7](ASSEMBLY-FABRIC-SUPPLY-v0.7.md)의 Claim·Binding·예약·승인·공급 실행 경계를 유지한다. 이 장은 공급 기준선을 개정하거나 새 Claim 실행 경로를 만들지 않는다.
- [업무 데이터 환경 계약](BUSINESS-DATA-ENVIRONMENT-CONTRACT-v0.1.md)의 데이터 범위·행위·집행·회수 검증을 이어받는다.
- [업스트림 전략](OS-GOVERN-UPSTREAM-STRATEGY-v0.1.md)에 따라 기반 기능을 재사용한다. 아래 논리 엔진은 각각 신규 서비스나 자체 구현을 지시하는 목록이 아니다.
- [Governance 최소 설계](../architecture/OPENSPHERE-GOVERNANCE-MIN-DESIGN-v0.1.md)의 API/CLI 동등성·관리 신뢰 경계·정본 원칙을 유지한다.

현재 로컬 UI 더미 v0.4는 이 계약 기반 동작을 구현·실증한 증거가 아니다. 화면 성공·모의 적용과 실제 제품의 권한 집행을 구별한다.

## 2. 객체와 책임 경계

| 객체/주체 | 책임과 의미 |
|---|---|
| OSR 어셈블리 정의 | 서명된 비실행 정의. 서비스 목적, 엔진/공유 서비스 조합, Link·전용 신원·자격, 설정·초기화·검증·수명주기 및 제공 유형을 선언한다. 제품 목록이나 설치 묶음만으로 축소하지 않는다 |
| 구성·검증된 어셈블리 | 실제 공급 인스턴스. 검증된 리소스 유형·용량·지원 계약과 연결된다. 정의 등록만으로 할당 가능해지지 않는다 |
| Fabric·구성 영역 | 엔진·인스턴스·복제·스토리지·하부 자격을 구성하고 승인된 공급 경로를 실행한다. 자체 제공 리소스도 검증된 공급 계약을 통해 Govern에 직접 인계할 수 있다 |
| 공급 계약 제공자(Fabric/어셈블리) | 자신이 지원하는 권한·옵션·검증·실행 능력을 선언한다. 스스로 전사 정책·승인을 완화하거나 Governance 소유권을 얻지 않는다 |
| OS Govern | 공급 인계와 계약을 검증하고 프로파일 구성·발행·배정·계획·승인·대조를 통합한다. 서비스가 위임한 범위 밖의 인프라 옵션은 제공하지 않는다 |
| 프로파일 버전 | 계약 버전에 맞춘 재사용 가능한 제공 명세. 아직 누구에게도 배정되지 않은 상태로 존재할 수 있다 |
| 배정 | 발행된 프로파일 버전을 수혜자·기간·수량·공유/개별 방식과 연결한다 |
| Workspace | 배정된 몫을 소비한다. 인프라·Governance 관리 권한을 자동 상속하지 않는다 |

프로파일이라는 말은 이 장의 **Governance 제공 프로파일**, Fabric의 용량 등급, OSR materializer의 설치 허용 범위를 구별해 사용한다. 공급과 배분 원장을 이중 생성하지 않는다.

## 3. 등록 계약 패키지

권고 기본은 **페이지 코드가 아닌 선언형 계약을 전달하고 OS Govern이 렌더링**하는 방식이다. 논리 패키지는 다음을 포함한다. 정확한 직렬화·API·서명 방식은 상세 설계와 OSR 기존 계약 매핑 후 고정한다.

| 부분 | 필요한 내용 |
|---|---|
| 식별·출처 | 계약 ID/버전, 공급 주체 종류·ID, 제공 정의/artifact digest(어셈블리이면 어셈블리 정의 digest), 제공자와 실제 설치본 연결, 지원 API/렌더러 버전, 무결성·출처 검증 |
| 데이터 스키마 | 자료형, 필수·기본·범위, 객체·배열·선택 분기, 불변 필드, 시크릿 참조 |
| 화면 스키마 | 어셈블리별 페이지/단계, 그룹·순서·설명·조건부 표시, 위젯 ID, 접근성·번역 키 |
| 권한 의미 | 안정적인 대상/행위 ID, 데이터 범위, 역할·상속·명시적 거절·충돌·합성, 제품별 매핑과 미지원 범위 |
| 조회·검증 | 선택지 조회, 계층·검색·페이지네이션, 의존 선택 무효화, 실시간 용량·지원 능력, 교차 필드/제품 검증 |
| 적용·관측 | 계획·발급·변경·회수·대조·접근 검증 기능 참조, 멱등성·전제조건·실패/unknown 의미, 세션·토큰·캐시 회수 지원 |
| 수명주기 | 호환성·폐기·이전, 계약 비활성/어셈블리 해체 영향, 보존·복구·감사 |

정적 계약과 동적 리소스 목록·용량은 분리한다. 모든 관리 대상 항목은 지원 범위 안에서 탐색·선택 가능해야 하지만, 지원되지 않거나 위임되지 않은 옵션을 임의 생성하지 않는다. 조회 권한 부족·연결 실패·미수집을 ‘리소스 없음’과 구별한다.

### 3.1 형식과 기존 도구 우선 검토

- 데이터: **JSON Schema**를 우선 검토한다. 지원 dialect와 validator 버전을 고정하고 필수 vocabulary·참조 지원을 시험한다.
- 화면: 별도 선언형 UI Schema. 업계 단일 표준이라고 주장하지 않는다. 단계·배치·위젯·조건·의존성 표현 범위를 명세한다.
- API: **OpenAPI**로 조회·검증·계획 인터페이스를 설명한다. 문서만으로 권한·수명주기가 강제되는 것은 아니다.
- 실행 의미: 버전이 있는 권한·수명주기 계약으로 보완한다. JSON Schema만으로 집행·회수·분산 수렴을 대신하지 않는다.
- 저작용 YAML을 허용하더라도 검증된 JSON 모델로 정규화한다. digest/서명은 OSR 기존 canonical JSON 규칙에 매핑하며 별도 임의 직렬화 규칙을 만들지 않는다.

JSON Forms 등 기존 스키마 폼 프로젝트, 기반 IGA의 스키마·커넥터·정책·승인 확장 기능을 먼저 대조한다. Angular 22·Carbon 네이티브 통합, 라이선스, 유지보수, 조건부/복합 위젯·서버 검증을 확인하기 전 특정 라이브러리를 채택했다고 기록하지 않는다. 이 장은 검토 후보와 요구를 정하며 호환성 시험 결과가 아니다.

## 4. 초기화·공급 인계·활성화

`서명된 정의 → 구성·초기화·적합성 검증 → 계약/공급 등록 요청 → 출처·호환성·권한·능력 검증 → 활성 등록 → 프로파일 제공`

1. 초기화 과정에서 등록 요청을 준비할 수 있지만, 공급 인계·필수 검증이 끝나기 전에는 배정 대상으로 활성화하지 않는다.
2. 같은 등록 재전송은 중복 공급을 만들지 않는다. 테넌트·영역·공급 주체 종류/인스턴스·계약 버전을 식별한다. Fabric 직접 공급에 가상의 어셈블리 ID를 요구하지 않는다.
3. 선언된 실행기·조회 기능은 허가된 어댑터 참조와 최소 권한으로 해석한다. 계약이 보내는 임의 URL·코드·명령을 그대로 실행하지 않는다.
4. 미지원 스키마/위젯/권한 매핑은 해당 계약 활성화를 차단하고 이유를 표시한다. 읽기 전용 진단은 편집·발행 허용과 구별한다.
5. 계약 버전 변경과 공급 상태 변경은 별개다. 중단·오래된 관측·해체에서는 새 배정 가능 여부를 판정하고, 기존 배정·권한 잔존을 추적한다. 어셈블리 삭제가 제품 데이터 삭제를 자동 의미하지 않는다.

## 5. 화면 엔진과 프로파일 업무 흐름

`등록된 공급 주체(Fabric/어셈블리) 목록 → 상세/공급/지원 계약 → 프로파일 목록 → 다단계 작성 → 서버 검증/미리보기 → 승인·불변 버전 발행 → 배정 → 적용/관측/검증`

- UI Shell·탐색·테마·대화상자·작업 상태는 Angular + Carbon 공통 경험을 유지한다. iframe·독립 로그인으로 대체하지 않는다.
- 공통 렌더러: 기본 입력·선택·객체/배열·단계·조건·설명·필드별 오류.
- 특화 렌더러: DB/스키마/테이블 트리, 주체×대상×행위 권한 매트릭스, 폴더 상속/예외, 용량 계획, 변경 전후 비교.
- 어셈블리는 승인된 컴포넌트 ID/버전을 선언한다. 임의 HTML·JavaScript·원격 페이지를 기본 계약으로 수용하지 않는다. 새 상호작용은 검토·버전 관리되는 확장으로 추가한다. 모든 신규 어셈블리가 무개발로 지원된다고 약속하지 않는다.
- 조건 표현은 제한된 선언형 규칙으로 처리한다. 임의 eval을 금지하고 순환 의존·과도한 중첩·실행 비용·원격 참조 해석을 제한한다.
- DB 선택 변경 등 상위 입력이 바뀌면 종속 선택을 재검증한다. 숨겨진 필드의 이전 값도 서버에서 검증하며 숨김을 접근 통제로 사용하지 않는다.
- 초안 저장, 프로파일 발행, 실제 배정 적용은 별도 상태다. 발행 후에는 변경본을 새 revision으로 만든다.
- 프로파일 발행은 모든 미래 배정에 대한 포괄 승인이 아니다. 배정 시 대상·최신 공급·정책·충돌·기간을 확인한다.

## 6. 특성이 다른 두 어셈블리의 설계 예

다음은 화면/계약 수용 예이며 실제 PG·문서 제품의 해당 기능 지원을 입증하지 않는다.

| 단계 | 데이터 서비스(PG) | 문서 서비스 |
|---|---|---|
| 1. 목적·제공 방식 | 기존 DB 공유 또는 계약이 허용한 DB 발급 요청 | 기존 공간 공유 또는 독립 공간 발급 |
| 2. 대상 선택 | DB → 스키마 → 테이블 조회·선택 | 공간 → 폴더 → 하위 범위 선택 |
| 3. 권한 | 로그인 역할, 조회·쓰기·DDL 중 지원 행위 | 읽기·편집·공유·다운로드 중 지원 행위 |
| 4. 특화 조건 | 지원되는 행 범위·접속 조건·연결 한도 | 상속·하위 폴더 예외·외부 공유 조건 |
| 5. 용량·수명주기 | 집행 가능한 할당량·기간·회수·보존 | 공간 용량·기간·소유 이전·보존 |
| 6. 검토 | 제품 권한 변환, 권한 확대·제약·한도 미집행 경고 | ACL 변환, 상속 영향·외부 공유·소유권 경고 |

PG 복제·CPU·스토리지 등 하부 인스턴스 구성과 실행은 Fabric·구성 영역이다. 단, Fabric이 명시적으로 배정 가능하게 인계한 CPU·스토리지 등의 용량·사용 권한은 Govern 프로파일의 대상이 될 수 있다. 인프라 구성의 소유권과 자원 사용분 배정을 혼동하지 않는다. 허용된 DB 발급 요청도 기존 공급 계약과 승인을 사용한다. 행 단위 통제나 DB별 하드 용량 제한이 제품에서 지원되지 않으면 설정을 유효한 보장처럼 발행하지 않는다.

## 7. 배정·계획·실행 엔진

논리 책임은 계약 레지스트리, 프로파일 구성/검증, 대상 해석·계획 계산, 승인/실행, 관측/대조, 버전/이전으로 나눈다. 기존 기반에서 제공하는 기능은 재사용하고 새로운 중복 원장을 만들지 않는다.

- 배정은 개인·조직 조건·프로젝트·서비스 등 기존 허용 수혜 단위를 따른다. 조직 공유 용량은 한 번 예약하고, 구성원별 독립 발급은 유효 대상 수만큼 계산한다.
- 여러 프로파일·조직 규칙·개인 예외·거절이 중첩될 때 최종 권한과 근거를 설명한다. 하나의 배정 회수가 다른 유효 근거를 제거하지 않는다.
- 승인 계획은 계약 digest·프로파일 revision·대상 집합/변경 정책·공급 세대·정책 revision을 묶는다. 승인 후 관련 입력이 바뀌면 재계산하고 필요한 재승인을 받는다.
- 예약·동시 실행·멱등키·세대 전제조건은 기존 공급/배분 소유자와 연계한다. UI 계산만으로 용량을 확정하지 않는다.
- 부분 실패·응답 유실을 전역 성공으로 표시하지 않는다. unknown 작업은 관측/멱등성 확인 후 재개하고, 회수 불명 용량은 가용으로 환원하지 않는다.
- 기대/승인/제품 관측/실제 접근 검증을 구별한다. 개인 전체 리소스와 리소스별 사용자 역조회에서 프로파일·배정·실행 근거까지 연결한다.

midPoint는 신원·역할·할당·승인·프로비저닝·대조 기반 후보, OPA/Cerbos 등은 필요한 요청 시 판단 후보다. 어셈블리 계약·프로파일 계층과 각 기반 기능의 매핑을 검증해야 하며 midPoint+OPA 선정 완료로 읽지 않는다.

## 8. 저장·정본·버전·복구

저장 설계 제안은 **관계형 메타데이터 + 가변 설정 JSONB**다. 기존 PostgreSQL/제공 저장 기능을 호환 범위에서 우선 활용한다. 기반 선정 뒤 각 논리 객체를 기존 저장 구조에 매핑하며 별도 DB/원장 생성을 선결정하지 않는다.

| 논리 객체 | 저장·추적 대상 |
|---|---|
| 계약 버전 | 불변 스키마·권한/화면/수명주기 정의, digest·출처·지원 버전 |
| 공급 등록 | 테넌트/영역·공급 주체 종류/실제 인스턴스 ID, 원천 리소스/용량 풀 참조, 계약 참조, 검증·활성 상태, 용량 소유자·관측 세대 |
| 프로파일 버전 | 선택값 JSON, 계약 버전/digest, 초안·검증·승인·발행 이력 |
| 배정 | 수혜자·프로파일 버전, 공유/개별 방식·수량·기간·부여 근거 |
| 실행·관측 | 승인 계획, 제품별 작업/멱등키·세대·결과, 관측 시각·검증 증거·재개 이력 |

불변 ID·검색·소유권·상태·참조 무결성은 관계형 구조로 관리하고, 공급 주체마다 다른 선택값은 스키마 검증한 JSONB로 관리한다. 비밀 원문은 넣지 않고 권한이 제한된 시크릿 참조만 저장한다. 테넌트/관리/사용자 권한은 서버에서 강제한다.

- 프로파일은 계약 버전, 배정은 발행된 프로파일 버전에 고정한다. 최신 스키마로 기존 값을 조용히 재해석하지 않는다.
- 변경 절차: 새 계약 등록 → 호환성/영향 비교 → 명시적 변환 → 서버 검증 → 필요한 승인 → 단계적 적용·대조. 의미 변경·옵션 삭제·위젯 교체도 영향 대상이다.
- 계약 폐기는 새 발행 차단과 기존 배정 처리로 나눈다. 폐기됐어도 기존 권한 회수·관측에 필요한 계약/실행 경로를 보존한다.
- UI 롤백, 계약/프로파일 되돌리기, 실제 데이터·ACL·발급 자원 복구를 구별한다. 파괴적 변경은 단순 버전 전환으로 복구된다고 약속하지 않는다.
- 승인된 정의·확장 소스·복구 절차는 DevOps에 호스트 독립적으로 보존하고 Windows에서도 읽을 수 있게 한다. Git에 비밀값·실사용 데이터를 넣지 않는다. 운영 백업은 접근 통제된 별도 절차로 관리한다.

## 12. Liferay에서 흡수한 권한 프레임워크 개념 (2026-11-21)

소유자 요청(청사진 흡수 및 권고 기반 더미 개편)에 따라 아래를 설계 기준으로 보강한다. 참고 기준은 Liferay Portal `7.4.3.120-ga120`이며, OSGi·XML·비트마스크·역할 이름을 복제하거나 Liferay 채택을 확정하는 결정이 아니다. midPoint는 신원·할당·승인·프로비저닝·대조 기반 후보, OPA/Cerbos는 필요한 요청 시 판단 후보로 유지한다. 동적 화면만으로 권한 프레임워크 완성을 주장하지 않는다.

### 12.1 독립된 네 축과 원장

1. 대상 조건: 조직·직무·재직 등으로 수혜자를 해석한다.
2. 역할 배정 문맥: 특정 업무 공간·어셈블리 문맥에서 역할이 유효한지를 결정한다.
3. 자원 범위: 해당 역할이 접근하는 자원 종류·집합·인스턴스를 식별한다.
4. 요청 조건: 상태·원작성자·직무분리 등 지금 이 행위를 수행할 수 있는지를 판단한다.

역할 정의, 문맥별 역할 배정, 자원·행위 카탈로그, 실제 허용, 제공 프로파일을 분리하되 정본을 중복 생성하지 않는다. 프로파일의 용량·TLS·회수 설정은 업무 역할 자체가 아니다. 조직 구조와 업무 공간도 동일한 트리로 강제하지 않는다. 사용 권한과 권한을 부여/위임하는 관리 권한은 별도다. 위임은 허용 대상·행위·범위·기간의 상한을 갖고 자신의 권한을 넘겨 확대하지 못한다.

### 12.2 등록 계약의 필수 의미

기존 JSON Schema/UI Schema/OpenAPI 계약에 다음 의미를 추가한다.

- 자원: 이름 공간이 있는 안정 ID, 테넌트/업무 공간, 소유자와 원작성자, 생성·삭제·이관 처리.
- 행위: 안정 ID와 의미, 지원 범위, 초기 기본값, 위험도. 기본값 변경과 기존 권한 이전은 분리한다.
- 집행: 실제 단건 조회·변경 API·상태 전이의 검사 지점, 제품 ACL/RLS 또는 검토된 어댑터 참조.
- 조회: 목록·총개수·검색·집계·내보내기별 지원 방식과 누출 방지 증거. 단건 검사에서 자동 번역된다고 가정하지 않는다.
- 수명: 중지·재설치·완전 제거, 저장된 권한·배정 참조·감사·복구의 보존/정리 정책.
- 변경: 새 행위, 이름 변경, 계약 이전, revision 전파, 캐시·색인·토큰·세션 무효화와 대조.

등록 상태는 수신 → 형식·출처 확인 → 의미/어댑터 적합성 검토 → 필수 경로 실증 → 활성화로 나눈다. 계약 제공자가 전사 정책을 완화할 수 없다. 미지원 경로는 숨기지 않고 명시하며 필수 경로 누락은 해당 기능 활성화를 차단한다. OSR 비실행 정의와 실제 구성·검증된 어셈블리의 공급 등록은 계속 구분한다.

### 12.3 판정 합성과 오류

논리 결과는 허용 / 거절 / 해당 없음 / 오류를 구분한다. 명시적 필수 금지·직무분리는 모듈의 허용이나 일반 관리자 역할로 우회하지 않는다. 필요한 신원·자원·정책 의존성이 불명/오류이면 접근은 차단하되 거절과 다른 운영 오류로 기록한다. 유효한 문맥 안의 허용을 합성하고 적용 가능한 허용이 없으면 기본 불허한다. 한 근거의 체크 해제는 다른 허용을 무효화하는 명시적 거절이 아니다.

조건 평가 순서·충돌 규칙·정책 revision·입력 스냅샷·결정 근거를 추적한다. 소유자/공개/관리자 특별 경로와 비상 접근은 명시적 계약 없이는 자동 허용하지 않는다. 원작성자 자기승인 금지와 상태 전이는 최종 업무 변경 지점에서도 검사한다. Liferay의 첫 non-null 결과 단락 평가를 전사 금지까지 우회하는 규칙으로 복제하지 않는다.

### 12.4 배포와 완료 증거

새 행위 등록은 기존 역할 권한의 자동 확대가 아니다. 발행 버전 고정 → 영향 비교 → 필요한 승인 → 이전 → 관측/대조로 처리한다. 회수는 원장 변경뿐 아니라 제품 ACL/RLS·검색·캐시·토큰·기존 세션·직접 API를 확인해야 완료다. 관측 불명은 성공으로 표시하지 않는다. 동일 제품 내 검사기 등록과 외부 제품 통합을 구별하고, 제품별 집행 능력이 없는 기능은 미지원으로 남긴다.

더미는 별도의 합성 MES 예제로 등록 적합성·네 축·판정 근거·조회 지원표·회수 완료 조건을 표현한다. 기존 정책/프로파일 원장과 통합하거나 실제품 권한을 입증한 구현이 아니다. 실제 구현은 기존 업스트림 기능 재사용을 우선하며 독립 복구, 관리/사용자 신뢰 경계와 요청→소스→검증 증거의 추적 원칙을 유지한다.

### 12.5 추가 수용 시험

- 같은 역할을 A 문맥에만 배정했을 때 B 자원 접근은 기본 불허.
- 다른 허용이 남은 체크 해제와 명시적 필수 금지의 차이 검증.
- 자기승인·관리자 예외·의존성 오류가 허용으로 단락되지 않음.
- 누락 어댑터/필수 조회 경로 미지원은 활성화 차단.
- 새 행위·계약 이전으로 기존 배정이 조용히 확대되지 않음.
- 검색·총개수·내보내기·직접 API·기존 세션의 회수와 결과 불명 처리 확인.

## 13. Fabric 자체 리소스의 직접 배정 (2026-11-21)

소유자 Telegram 52865·52867에 따라 **어셈블리 공급은 배정 경로의 한 유형이며, Fabric 자체가 제공하는 리소스 역시 직접 배정 대상**임을 명시한다. 이 절은 공급 대상 범위의 설계 보강이다. 협력 공급 v0.7의 Claim·Binding·예약·제한 실행 기준선을 변경하거나, Fabric 직접 소비자용 API/실행부가 이미 존재한다고 선언하지 않는다.

### 13.1 두 공급 경로와 공통 배정 모델

- Fabric 직접 공급: 검증된 Fabric 제공 인스턴스 → 자체 리소스·권한·용량 계약 등록 → 프로파일 구성·발행 → 배정 → Fabric 집행·관측·회수.
- 어셈블리 공급: 서비스 목적에 맞게 구성·검증된 어셈블리 → 제공 리소스 계약 등록 → 프로파일 구성·발행 → 배정 → 어셈블리/제품 집행·관측·회수.
- 직접 공급을 위해 내용 없는 어셈블리를 만들도록 강제하지 않는다. 반대로 실제 서비스 조합을 단순 Fabric 자원 목록으로 축소하지 않는다. OSR 비실행 정의와 가동·검증된 공급 인스턴스도 계속 구별한다.
- 논리 공급 참조는 공급 주체 종류(Fabric/assembly), 안정 ID·실제 인스턴스, 계약 버전/digest, 원천 리소스·용량 풀·관측 세대를 식별한다. 이는 상세 설계 요구이며 확정된 API 필드나 migration이 아니다. 기존 어셈블리 참조의 전환은 명시적 호환·이전 절차로 처리한다.

### 13.2 옵션·권한·공급 소유권

- 예시 후보는 Fabric Provider가 직접 제공하는 DB·버킷·인덱스와, 지원 계약이 있는 컴퓨트·스토리지·네트워크 사용분이다. 후보 표시는 실제 공급·하드 한도 집행 지원의 증명이 아니다.
- Govern은 공급자가 위임한 등급·용량·범위·기간·사용 행위만 구성·배정한다. 하부 토폴로지·복제·설치·스토리지 구조 변경은 기존 관리·승인 경로에 남는다.
- 자원 사용 권한은 Fabric 운영·제어면 관리 권한을 자동 부여하지 않는다. 관리 권한을 배정할 필요가 있으면 별도 고위험 행위·범위·승인으로 명시한다. Workspace 소비가 관리 신뢰 영역을 넘지 못한다.
- Fabric 직접 배정과 어셈블리의 하부 사용이 같은 용량 풀을 소비하면 원천 공급/예약 원장에서 함께 계산한다. 어셈블리가 이미 예약한 용량의 사용자별 분배는 그 예약의 하위 몫으로 추적하며 원천 용량을 이중 차감하거나 중복 가용량으로 표시하지 않는다.
- 기존 Claim·Binding·승인·멱등 실행·대조 기능을 우선 재사용한다. 직접 소비자 표현이 기존 어셈블리 전용 계약에 맞지 않으면 차이와 필요한 확장을 별도 명세·검증하며, 임의 우회 경로나 두 번째 원장을 만들지 않는다.

### 13.3 화면·수명주기·수용 기준

공급 목록·프로파일·배정·개인 종합/역조회에서 Fabric/어셈블리 종류와 실제 공급 인스턴스를 구별한다. 동일한 선언형 화면 엔진으로 공급자별 옵션을 렌더링하고 계약/프로파일 버전 고정, 승인 계획 전제조건, 오류·회수 불명, 보존·복구 기준을 두 경로에 동일 적용한다. 화면 변경이나 운영 활성화는 이번 문서 반영의 범위가 아니다.

| ID | 시험과 필요한 증거(미실행) |
|---|---|
| GP-11 | 실제 검증된 Fabric 직접 리소스를 어셈블리 없이 등록→프로파일 발행→배정→집행·관측·회수. 어셈블리 경로와 공통 계약/승인 모델 사용 확인 |
| GP-12 | 직접 배정과 어셈블리 하부 사용이 동일 풀에서 경합해도 초과·중복 예약/차감 없음. 회수 unknown을 가용으로 조기 반환하지 않음 |
| GP-13 | 사용자 자원 배정으로 Fabric 운영 권한을 획득하지 못함. 미검증 공급·미지원 옵션·변조/타 영역 공급 참조 차단 |
| GP-14 | Fabric 중단·제거·계약 개정 시 새 배정 통제, 기존 참조·회수·보존·복구 이력 유지. 기존 어셈블리 프로파일이 조용히 재해석되지 않음 |


## 14. 역할 모델 구체화 (2026-11-21)

소유자 Telegram 52873에 따라 [OS Govern 역할·권한 모델 v0.1](OS-GOVERN-ROLE-PERMISSION-MODEL-v0.1.md)을 이 장의 역할 정의·배정·자원 범위 규약으로 적용한다. REGULAR(테넌트) / SITE(업무 공간) / ORGANIZATION(조직)을 명시적 유형으로 도입하며, 역할 버전·권한 규칙·문맥별 배정을 별도 객체로 연결한다. §12의 원칙만 있는 상태를 이 상세 모델로 구체화한다. 제공 프로파일은 역할과 동일하지 않다. 운영 IAM/제품 집행·기존 규칙/프로파일 통합은 이 문서만으로 완료되지 않는다.
