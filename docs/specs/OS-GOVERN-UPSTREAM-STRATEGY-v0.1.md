# OS Govern — 업스트림 기반 개발 전략 v0.1

**작성일:** 2026-11-20
**상태:** 소유자가 제시한 업스트림 기반 개발 방향을 정리한 설계 장. midPoint는 우선 평가 후보이며 채택 확정이 아니다. 상세 절차·평가표는 제안이다. 구현·배포 승인이나 운영 검증 완료를 뜻하지 않는다.
**근거:** 소유자는 “커버리지가 가장 큰 제품을 베이스로 OS Govern을 만드는 방향”을 제시하고 관련 내용을 청사진의 별도 장으로 정리하도록 요청했다.

## 1. 목적과 결론

OpenSphere는 MES·그룹웨어·메일 등의 업무 데이터 환경을 구성하고 조직 정책과 사용자 권한에 따라 제공·변경·회수한다. **OS Govern은 기존 Governance를 구체화하는 제품 명칭이며 별도 중복 제어면이 아니다.** 명칭의 최종 확정과 패키징은 후속 결정 대상이다.

개발의 우선 방향은 **넓은 기능 범위를 가진 업스트림을 기반으로 재사용·확장하여 OS Govern을 만드는 것**이다. 신원 수집, 역할·할당, 승인, 프로비저닝, 동기화·대조를 모두 바닥부터 다시 만들지 않는다.

다만 업스트림을 단순 재브랜딩하거나 별도 관리 콘솔 링크로 붙이는 것으로 완료하지 않는다. 조직의 업무 의도를 실제 제품의 데이터 범위·행위 권한으로 연결하고, 변경·회수의 실제 효과까지 검증하는 것이 제품의 목적이다.

## 2. 기존 결정과의 관계

[계층 구조 기준선](../architecture/OPENSPHERE-LAYER-BASELINE-v0.2.md)의 D-4와 §6은 Syncope·midPoint를 도입하지 않는 기존 기준을 담고 있다. 참고 아키텍처도 midPoint를 참고서로만 분류했다.

이번 장은 **그중 ‘midPoint를 기반 후보에서 사전 제외’하는 취급을 재검토 대상으로 연다.** 기반 평가를 기존 배제 문구로 막지 않는다. 그러나 다음을 구분한다.

| 항목 | 이번 장의 취급 |
|---|---|
| 업스트림 기반 재사용·확장 방향 | 소유자 제시 방향을 문서화 |
| midPoint | 첫 평가 후보. 선정·설치·전환 확정 아님 |
| D-4의 제품 배제 | 재검토 개시. 기반 선정 결과와 함께 결정 대장을 정식 개정할 대상 |
| D-3·D-22의 사람·조직 정본 AD | 유지. 기반 제품을 쓴다는 이유로 대체하지 않음 |
| D-27의 Governance 정의 revision | 논리적 정본과 추적성 유지. 물리 저장·활성화 구현은 기반 평가에서 매핑 |
| D-77의 Syncope Provider 드롭 | 이번 요청으로 복원하지 않음 |

문서 정리는 특정 제품 채택으로 읽지 않는다. 향후 선정 시 유지·대체할 결정과 migration을 함께 명시한다.

## 3. 후보를 보는 세 관점

| 분류 | 예 | 평가 목적 |
|---|---|---|
| 기반 제품 | midPoint 등 IGA 제품 | 신원·역할·할당·승인·프로비저닝·대조의 전체 흐름을 얼마나 재사용하는가 |
| 판단 부품 | OpenFGA·SpiceDB, OPA·Cedar·Cerbos | 관계·조건·정책 판단 중 부족한 기능을 충족하는가 |
| 연동 표준 | SCIM 2.0, AuthZEN 등 | 제품 간 계약과 교체 가능성을 확보하는가 |

이들은 동일한 역할의 경쟁 후보가 아니다. OpenFGA나 OPA 하나를 고르면 Controller 전체가 확보되는 것은 아니다. 반대로 모든 부품을 함께 도입할 필요도 없다. 기반 제품의 내장 기능으로 충분하면 추가 엔진을 두지 않는다.

### 3.1 우선 평가 후보: midPoint

현재 조사한 후보 중 midPoint를 우선 검증한다. 사람·조직·역할·할당, 정책·승인, 제품별 계정·권한 매핑, 커넥터, 동기화·대조, 재검토 기능이 기반 후보로서 관련성이 높다.

이것은 커버리지·성능·보안·라이선스 합격을 입증한 평가 결과가 아니다. 계정·그룹 수명주기 지원을 업무 데이터 거버넌스 전체 지원으로 간주하지 않는다. 제품별 데이터 범위, 세부 행위, 회수·세션 종료는 별도 확인한다. 선정 전 같은 시나리오로 대안 기반 제품과 비교한다.

## 4. 재사용과 고유 확장의 경계

| 구분 | 대상 | 원칙 |
|---|---|---|
| 우선 재사용 | 신원 수집·상관관계, 역할·할당, 승인, 프로비저닝, 동기화·대조, 감사 | 지원되는 기능과 실제 동작을 확인하고 기반 기능에 맡김 |
| 설정·확장 | 조직·직무 모델, 업무 역할, 데이터 범위, 정책·결재선, 제품별 권한 매핑 | 가능한 한 스키마·설정·커넥터·공식 확장 지점 활용 |
| 부족분 개발 | 어셈블리 인계, 제품별 업무 권한 어댑터, 실제 허용·거절 및 회수 검증 | 기반에 없는 부분만 개발 |
| 네이티브 통합 | 로그인·탐색·관리 화면·감사·작업 상태 | 별도 앱 이동·iframe만으로 완료하지 않음. 서버 권한 경계 유지 |

**같은 할당·승인·대조를 두 시스템에서 각각 정본으로 운영하지 않는다.** 기반의 저장소를 OS Govern 내부 구현으로 사용할 수 있다. 별도 원장을 만들 경우에도 그 필요와 필드별 소유권·파생 사본·충돌 해결을 먼저 증명해야 한다.

사람·조직 정본 AD, Governance의 정책·할당, 각 업무 제품의 업무 데이터 정본은 서로 다르다. 기반 제품 채택으로 이 경계를 합치지 않는다.

## 5. 반드시 표현할 업무 계약

엔진 선정과 함께 다음 표를 대표 업무에 구체적으로 작성한다.

`업무 역할 → 데이터 범위 → 허용·금지 행위 → 조건·기한 → 승인 → 제품별 집행 → 변경·회수 → 검증 증거`

필수 설정 묶음:

1. **주체·조직:** 불변 ID, 조직·직무·겸직, 에이전트와 위임자, 정본 출처·변경 감지.
2. **업무 권한:** 서비스·데이터 범위·행위·조건·유효 기간, 명시적 거절과 상속·합성 규칙.
3. **할당·통제:** 조직 자동 부여·개별 할당, 예외, 직무 분리·위임의 교집합·만료.
4. **신청·승인:** 위험 등급, 결재선·대체 결재자, 자기 승인 금지, 영향 미리보기, 정의 revision.
5. **제품별 매핑:** 대상 ACL·레코드 규칙·API, 지원 범위와 미지원 권한, 어댑터 자격 참조.
6. **적용·회수:** 순서, 멱등성, 세대·동시 변경·부분 실패·unknown·재개, 세션·토큰·캐시 회수.
7. **운영·검증:** 실제 상태 조회, 대조 주기, 회수 기한, 실패 알림·감사·보존·독립 복구.

위 항목은 필요한 계약의 목록이며 구체적인 기본값·스키마는 아직 확정하지 않는다. ‘원하는 권한’, ‘제품에서 관측된 권한’, ‘실제 접근으로 검증한 권한’을 구분한다.

## 6. Controller와 요청 시 집행의 분리

제어 루프:

`AD·정책·할당 변화 → 원하는 상태 계산 → 실제 상태와 차이 → 승인된 변경 적용 → 효과 검증 → 지속 대조`

- Controller는 업무 의도를 제품별 상태로 투영하고 변경·회수·재개를 책임진다.
- PDP는 요청의 허용·거절을 판단한다. 제품 내부 ACL·레코드 규칙·API 집행 지점은 이를 강제한다.
- 그룹 생성·API 저장 성공은 업무 권한 통합 완료가 아니다.
- 직접 API, 기존 세션, 캐시를 통한 접근도 검증 대상이다.
- 대상 제품의 생산·결재 규칙 자체를 Governance가 중앙에서 재구현하지 않는다.

기반 제품이 제공하는 실패 의미를 그대로 합격으로 간주하지 않는다. 응답 유실 후 무조건 재전송하지 않으며 관측·멱등성 계약을 검증한다. 다중 제품 변경을 전역 원자적 트랜잭션으로 약속하지 않고 제품별 완료·지연·실패·결과 불명을 드러낸다.

## 7. 선정·검증 절차와 산출물

| 단계 | 작업 | 산출물·통과 근거 |
|---|---|---|
| 1. 요구 고정 | 대표 업무의 데이터 범위·허용·금지·이동·퇴사 작성 | 업무 계약표와 실제 제품의 집행 가능성 조사 |
| 2. 기반 비교 | midPoint 우선 조사, 대안에 같은 기준 적용 | 기본 제공 / 설정 / 확장 / 코어 수정 / 지원 불가 표, 근거 버전 |
| 3. 경계 매핑 | 원장·정의·승인·계산·실행·대조 기능을 기반에 대응 | 정본 소유권, 신뢰 영역, 자격·키, 중복 제거 설계 |
| 4. 단일 제품 실증 | 실제 데이터 범위·행위의 부여·이동·회수 | 허용·거절, 직접 API·세션 회수, 장애·재개 증거 |
| 5. 두 제품 실증 | 업무 환경의 제품 간 일관성 확인 | 한 제품만 실패·지연한 경우 추적과 수렴, 금지 권한 잔존 탐지 |
| 6. 선정 결정 | 유지비·라이선스·복구·업데이트까지 평가 | 채택/기각 근거, D-4 등 개정안, 확장·코어 수정 범위 |

이 절차는 검증 계획이며 이번 문서화 요청만으로 운영 설치·데이터 전환을 실행하지 않는다.

### 7.1 합격 기준

- A공장 담당자의 데이터 범위·세부 행위를 표현하고 실제 제품에서 강제한다.
- 이동 시 이전 범위 회수·새 범위 부여, 겸직·직접 할당·예외의 처리 근거를 설명한다.
- MES·문서·메일 같은 대상별 매핑 가능성과 부족분을 구분한다. 최초 실증에 모두 설치할 필요는 없다.
- 부분 실패·응답 유실·재시작·동시 변경에서 권한이 잘못 확대되거나 예전 세대로 역행하지 않는다.
- 실제 접근·세션·토큰·캐시 회수를 검증하거나 지원 한계를 명시한다.
- 사원 영역의 Governance 권한을 Backbone 관리 신원이 자동 상속하지 않는다.
- 정책·할당·승인 revision과 제품별 실행·관측·검증을 연결한다.
- 네이티브 UI, API/CLI 계약, 백업·복구, 업그레이드 가능성을 입증한다.
- 라이선스·종속성·커넥터별 조건, 재배포·수정·브랜딩, 유지보수·보안 수정 경로를 확인한다. 유료 기능·지원 계약을 자동 승인하지 않는다.

기능 개수보다 **실제로 재사용할 수 있는 커버리지와 남는 개발·운영 부담**으로 판단한다. 현 단계에서 점수·비율을 임의로 부여하지 않는다.

## 8. 업스트림 유지 전략

기본 순서는 **설정 → 공식 확장/API/커넥터 → 필요한 최소 코어 수정**이다. 대규모 포크부터 시작하지 않는다. 공식 확장만으로 목적을 충족하지 못하면 코어 수정 가능성을 배제하지도 않는다.

선정 시 고정 버전·소스 커밋, 의존성·라이선스, 패치 목록, upstream 보안 수정 반영, 데이터 migration, 대표 업무 회귀 시험과 복구 절차를 관리한다. UI 통합을 위해 서버의 권한 검사·감사·revision·승인을 우회하지 않는다.

소스·설정·확장·빌드 정의·복구 문서는 DevOps 디스크에서 호스트와 독립적으로 보존한다. OpenSphere 빌드에 OCI CC1을 사용하지 않으며 ARM 빌드를 실행하지 않는다.

## 9. 유지하는 책임 경계와 미결

- 테넌트 관리자는 서비스 목적의 어셈블리와 용량을 구성·검증한다. OSR에 등록된 어셈블리 정의 자체는 실행 서비스가 아니다.
- Governance는 그 산출물을 조직·사용자·에이전트에게 정책에 따라 배분·허용·회수한다.
- Workspace는 할당된 업무 환경을 소비한다.
- Backbone 소속 기반 운영 기능은 Configuration에 유지한다. Governance의 업무 권한 관리가 Backbone 관리 권한으로 흡수되는 것은 아니다.

남은 결정: 기반 제품·버전, 정책/할당 저장과 revision 구현, 네이티브 UI 통합 방식, 제품별 집행 매핑, 추가 PDP 필요성, 회수 기한·재검토 기본 템플릿, 기존 상태 편입·이전 방식. **midPoint 선정 완료나 기존 Governance 구현의 존재·완성 여부를 이번 장에서 주장하지 않는다.**

- [midPoint 공식 문서](https://docs.evolveum.com/midpoint/) — 역할·할당·프로비저닝·동기화·대조 모델
- [midPoint 동기화 유형](https://docs.evolveum.com/midpoint/reference/master/synchronization/flavors/)
- [OpenFGA](https://openfga.dev/docs) · [SpiceDB](https://authzed.com/docs) — 관계 기반 판단 후보
- [OPA](https://www.openpolicyagent.org/docs) — 정책 판단 후보
- [SCIM RFC 7644](https://www.rfc-editor.org/rfc/rfc7644.html) — 계정·그룹 프로비저닝 프로토콜

## 11. 어셈블리 계약·프로파일 후속 요구 (2026-11-21)

[어셈블리 계약 기반 동적 프로파일 v0.1](OS-GOVERN-ASSEMBLY-PROFILES-v0.1.md)을 함께 평가한다. 기반의 스키마·역할·할당·승인·커넥터·대조 기능을 먼저 매핑하고, 선언형 UI와 제품별 권한 의미·계약 버전/이전의 부족분만 확장한다. 계약 등록 → 어셈블리별 프로파일 작성·발행 → 배정 → 적용·관측·검증을 표현해야 하며 평면적 CRUD나 midPoint+OPA 연결만으로 완료하지 않는다. 제품 선정·중복 원장 신설·운영 실행 승인을 추가하지 않는다.
