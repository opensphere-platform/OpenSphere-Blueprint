# 새 패키지의 Console 승인과 이미지 레지스트리 확장 v0.1

**상태:** 설계 초안. 결정이 아니다. 스토어 기본 구성(S1~S6) 뒤의 개선 과제로 소유자가 등록을 지시했다(2026-11-28: "대장에 등록하고 설계해 둬"). §6의 질문은 소유자가 정한다.
**작성:** Claude.
**대장:** [검증 추적 대장](VERIFICATION-TRACEABILITY-LEDGER-v0.1.md) V-66(Console 승인) · V-67(레지스트리 확장).
**관련 결정:** D-99(중립 다중 스토어: 스토어 서명은 배포만 보증, 권한 · 이미지는 운영자 프로필에서만), D-102 A3(위험의 하한은 OS가 정한다), D-109~D-113(레포 스토어 · 기본 스토어 · 스토어 중심 설치), D-114 · D-115(연결 · 자격 관리), D-95(패키지 설치에 Backbone 재빌드 0회).

## 1. 문제

OS 모듈 표준대로 만든 패키지를 연결된 스토어에 올리면 Console에 **보이는 것은 5분 안**이다. 같은 패키지의 판 올림은 실행 프로필이 같으면 관리자 MFA 한 번으로 **바로 설치 · 업데이트**된다.

그러나 **처음 들어오는 패키지**(또는 실행 프로필이 바뀐 판)는 설치 버튼이 열리지 않는다. 설치본의 서명된 신뢰 맥락에 그 프로필이 없기 때문이다. 지금 이것을 여는 길은 다음과 같다.

1. Backbone 저장소에 프로필 파일을 넣는 PR(`infra/contracts/osr/profiles/`)
2. 운영 앵커 키(`osr-anchor-2026a`, 오프라인)로 새 검증 맥락과 스토어 신뢰 변경(제품 권한)에 서명
3. 소유자가 터미널에서 Setup `apply-osr-trust`로 적재(비밀번호 + MFA)

권한 범위를 사람이 승인한다는 목적은 맞다. 하지만 이 길에는 문제가 셋 있다.
- 모듈 하나마다 Backbone 저장소 변경, 오프라인 서명, 터미널 작업이 필요하다.
- 승인하는 사람이 무엇을 승인하는지(권한 · 이미지 · 자원)를 화면에서 보지 못한다.
- 결과적으로 "스토어 = 앱스토어"라는 제품 경험과 거리가 멀다.

이와 별도로, 프로필의 이미지 규칙이 `ghcr.io/opensphere-platform/`으로 묶여 있다(`materializer-profile.schema.json` 76행 · 792행). 그래서 다른 공급자가 자기 레지스트리의 이미지를 쓰는 패키지는 표준을 지켜도 설치할 수 없다. 이는 중립 다중 스토어(D-99)와 어긋난다.

## 2. 목표

- 표준을 지킨 새 패키지가 연결된 스토어에 올라오면, 소유자(또는 지정된 관리자)가 **Console에서** 그 패키지가 요청하는 권한 · 이미지 · 자원을 읽고 **본인 MFA로 승인**해 설치를 연다.
- 승인할 수 있는 범위는 **앵커가 서명한 정책 상한 안**이다. 상한을 넘는 요청은 Console 승인으로 열 수 없고, 지금처럼 앵커 서명이 필요하다.
- 앵커 키는 계속 오프라인이다. Console이나 Core에 앵커 키를 두지 않는다.
- 스토어마다 허용할 이미지 레지스트리를 정하고, 그 레지스트리의 이미지를 digest로 고정해 쓸 수 있다.

## 3. 설계 — V-66 Console 승인

### 3.1 신뢰의 두 층

| 층 | 서명 · 승인 | 바꾸는 것 | 빈도 |
|---|---|---|---|
| **앵커 층**(지금 그대로) | 오프라인 앵커 키 + 소유자 터미널 적재 | 정책 상한(클래스별 허용 capability · effect · 자원 상한 · 금지 자원), 신뢰 키, 스토어 추가 · 제거, **설치본 승인 권한의 위임** | 드물게 |
| **설치본 층**(새로) | Console에서 소유자(또는 위임받은 관리자)의 본인 MFA | 정책 상한 안에서 새 패키지 프로필의 채택 | 모듈마다 |

앵커는 한 번, 다음 위임 문서에 서명한다(이름은 제안): **"이 설치본은 이 정책 판의 상한 안에서, 이 스토어들의 이 공급자들이 낸 프로필을, 이 역할의 MFA 승인으로 채택할 수 있다. 만료 ○일."**

- 위임 문서는 신뢰 맥락의 일부로 적재한다. 처음 한 번은 지금처럼 터미널 적재다.
- 철회하거나 범위를 바꾸려면 다시 앵커 서명이 필요하다.

### 3.2 프로필은 어디서 오는가

- 지금은 Backbone 저장소의 호스트 작성 파일이다.
- 바꾼 뒤에는 **패키지가 서명된 프로필 제안을 낸다.** 별도 part로 두며, 형식은 지금 프로필 스키마와 같다.
- 호스트는 그 제안을 그대로 믿지 않는다. 정책 상한과 대조해 **넘는 항목이 하나라도 있으면** Console 승인 대상에서 빠진다. 그 경우 "앵커 승인 필요"로 표시된다.
- 상한과의 대조는 판정기 세 곳(Node · Rust · Setup)이 같은 결과를 내야 한다(공유 사례).

### 3.3 Console 흐름

1. 스토어 화면에서 새 패키지가 **"승인 필요"**로 보인다(지금의 "스토어에 있음 · 설치할 수 없음" 대신).
2. 승인 서랍이 열린다. 요청 내용을 사람이 읽을 수 있게 펼친다.
   - 실행 원형
   - 만드는 쿠버네티스 객체 종류와 개수
   - RBAC(무엇에 어떤 동사)
   - 이미지(레지스트리 · digest · SBOM · 취약점 요약)
   - 자원 상한 · 저장소
   - 망 출구
   - 발급하는 Claim 종류
   - 상한 대비 위치(여유 / 상한에 닿음)
3. 다른 판과의 차이가 있으면 차이를 강조한다(판 올림에서 권한이 넓어지는 경우).
4. 승인자가 본인 MFA로 승인한다. Core가 **승인 기록(누가 · 무엇을 · 어느 정책 판 · 어느 위임 아래)**을 남기고, 그 프로필을 설치본의 채택 목록에 더한다.
5. 그다음부터는 지금과 같다. 관리자 MFA로 설치 → 실행부 → 웹훅 대조.

### 3.4 지켜야 할 것

- **정책 상한은 OS가 계산한다**(D-102 A3). 패키지가 낸 위험 표지는 올리는 데만 쓴다.
- **권한이 넓어지는 판 올림은 다시 승인을 받는다.** 같은 프로필 id라도 지문이 바뀌면 승인 대상이다.
- 승인과 설치는 다른 행위다. 승인자와 설치자가 같아도 되지만 기록은 따로 남긴다.
- 위임이 만료되거나 철회되면 새 승인은 막힌다. 이미 채택한 프로필로 설치된 것은 계속 돈다(지금 신뢰 맥락 만료 때와 같은 원칙).
- 감사 기록에 위임 문서 digest · 정책 판 · 승인 MFA 영수증을 함께 남긴다.

## 4. 설계 — V-67 이미지 레지스트리

| 항목 | 설계 |
|---|---|
| 허용 레지스트리의 자리 | **스토어 신뢰 설정**(스토어 추가 · 범위 변경 때 앵커 서명 + 소유자 MFA로 정함). 스토어마다 `allowedImageRegistries`(호스트 + 경로 접두사 목록). 기본 스토어는 `ghcr.io/opensphere-platform/` |
| 프로필의 이미지 규칙 | 고정 패턴 대신 "그 패키지를 낸 스토어의 허용 레지스트리 접두사 + `@sha256:` digest". digest 고정은 그대로 필수 |
| 끌어오기 자격 | 비공개 레지스트리는 연결 · 자격 관리(D-114)의 자격을 쓴다. 실행부가 그 설치 namespace에 끌어오기 Secret을 두고, 자격 값은 원장 · 화면에 나오지 않는다 |
| 망 | 노드가 그 레지스트리에 닿아야 한다. HISS의 출구 정책 · 미러 설정과 함께 확인하고, 닿지 않으면 설치 계획 단계에서 거절한다(문제 코드) |
| 공급망 증거 | S6 등급 B(SBOM · 취약점 · 빌드 증명)를 그 레지스트리의 이미지에도 똑같이 요구한다. 증거 없는 이미지는 Console 승인 대상에서 빠진다 |
| 오프라인 설치본 | 미러 레지스트리를 허용 목록에 둘 수 있게 한다(D-104 L5와 잇는다) |
