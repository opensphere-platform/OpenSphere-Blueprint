# 실행 쪽 분리 계획 v0.1 — Codex 검토와 Claude 판단

**대상:** [PACKAGE-EXECUTION-DECOUPLING-PLAN-v0.1.md](PACKAGE-EXECUTION-DECOUPLING-PLAN-v0.1.md)
**검토:** 2026-11-23 · Codex. 소유자 "Codex 검토 먼저"에 따라 Claude가 Codex 세션에 요청했다(채널 #17).
**정리 · 판단:** Claude. 결정은 소유자가 내린다.

## 총평(Codex)

형식이 제한된 실행 원형에 동의한다. 구현에 앞서 E2에서 세 가지를 먼저 확정해야 한다.
1. Core가 신뢰할 원형 · 권한 자료
2. Claim Job에 엔진 자격을 맡기는 기준
3. 기존 작업을 새 판에서도 복구하는 방법

이 경계를 정하지 않고 구현하면 E6의 패키지 단독 설치를 입증하기 어렵다.

## 2. 실행 원형 · digest · 일반 `p7.accept`

- **`stateful-engine`은 지금 객체를 재현할 수 있다.**
  - 정답 비교 합격 기준에 다음을 넣는다.
    - 설치 · 생성 · 삭제 · 복구 전체의 `planned_writes`와 삭제 순서
    - 실제 API 서버 기본값이 적용된 객체의 `judge` 결과
  - 운영 전환에서는 StatefulSet · PVC · PV · Secret UID와 데이터 보존도 확인한다.
- **`claim-job`과 `operator-cr`은 별도 경계가 필요하다.**
  - Claim Job 이미지와 인자는 E4에서 의도적으로 바뀐다. 그 차이를 밝히고 Secret · 망 정책 · 회수 효과가 같은지 확인한다.
  - 지금 Job은 엔진 관리자 Secret과 데이터 PVC를 읽고, 소비자 Secret은 실행부가 쓴다. 이 경계는 유지한다.
  - PostgreSQL은 SGCluster 생성을 먼저 옮긴다. SCRAM · SGScript · 실제 로그인 확인 · 회수 · Keycloak 그룹 연동은 따로 검증한다.
- **일반 `p7.accept`는 가능하다.**
  - Core가 신뢰하는 원형 · 프로필에서 동작별 쓰기 · 삭제 목록을 **독립적으로 계산**하고, 제출된 목록과 정확히 맞춘다.
  - 계획에 묶을 것: 번들 · runtime 문서 · 프로필 지문, 원형과 렌더러 판, 이미지 digest, 대상과 fence
  - 생성 자격은 형식과 슬롯만 승인에 묶는다. 작업 중 붙는 추적 주석은 승인 digest에서 파생시킨다.
  - `p7.admission_deleting`도 같은 목록을 쓴다.
  - idempotency · 예약 · 점유 · 감사 · 복구의 원래 계획과 UID 대조는 유지한다.
- **Claude 판단:** 수용. 이 조건들을 v0.2 §3.2(보안 경계)와 E2 · E3 합격 기준으로 옮긴다.

## 5. 과소평가한 위험(Codex)

1. **키 · 이미지 회수 뒤에 남은 Claim의 정리 경로.** 회수된 패키지 코드를 다시 실행하지 않고도 기존 앱 권한을 끊을 수 있어야 한다. 다음 경우를 시험에 넣는다.
   - 발급은 끝났는데 소비자 Secret 쓰기가 실패한 경우
   - 실행부가 재시작된 경우
   - 같은 이름의 Secret이 충돌하는 경우
2. **객체 동등성과 운영 상태 보존은 증거가 각각 필요하다.** 렌더 결과가 같아도 적용 과정에서 필드 소유권 · 기본값 · 컨트롤러 동작이 다를 수 있다. 그래서 전환 전후의 실제 쓰기 목록 · 객체 UID · 볼륨 · 데이터를 함께 기록한다.
3. **판 혼재와 되돌리기는 E2에서 다룬다.** 새 Core와 옛 실행부, 옛 계획과 새 렌더러가 만날 때 어떤 계획을 실행할 수 있는지 정한다. 새 판을 적용한 뒤에도 기존 점유와 미확정 효과를 보존하고, 그 계획에 맞는 판으로 복구할 수 있어야 한다.

**Claude 판단:** 셋 다 수용한다. 1은 E4, 2는 E3 · E5, 3은 E2b의 합격 기준으로 넣는다.
