## 1. 문제: 지금 새 패키지 하나가 바꾸는 곳

예를 들어 Fabric 서비스 하나를 더하면 다음을 모두 고친다. 수치는 2026-11-23 Backbone main 기준이다.

| 층 | 지금 패키지마다 하드코딩된 것 | 크기(근사) |
|---|---|---|
| Console 메뉴 | Fabric 메뉴(`examples.ts` FABRIC_MENU), HISS 메뉴(`hiss.ts`), 설정 메뉴. 설치 여부와 무관하게 고정 | — |
| Console 화면 | 서비스마다 화면 · 변환 코드(PostgreSQL · Samba AD · Keycloak · OpenSearch/RustFS · HISS) | Fabric 약 3,000줄 |
| Core 렌더러 | 객체를 만드는 Rust(`osr_render` · `osr_samba` · `osr_keycloak` · `osr_storage_provider`) | 약 2,700줄 |
| Core 동작 | 인스턴스 계획 · 발급 · 해제(`osr_install` 안 분기, `osr_issue` · `osr_storage_claim`) | 약 1,600줄 + 분기 |
| 실행부 · 웹훅 | 상태 읽기 · 세부 읽기(mechanism별 분기), 판정 허용 목록(kind별) | 분기 다수 |
| 원장 SQL | 서비스별 함수 · 표(claims_of · storage_claims_of · directory_binds …) | 마이그레이션 20여 개 |
| 계약 | 배치 규칙 mechanism 열거, 스토어 설치 허용 클래스 | — |

**결과**
- 새 패키지 · 새 판마다 Core · Console 이미지를 다시 만든다.
- DB 마이그레이션 · 실행 규칙 · 신뢰 세대를 손으로 운영에 반영한다.
- Codex와 Claude가 같은 파일(`osr_executor.rs` · `osr_install.rs` · Fabric 화면)을 동시에 고쳐 충돌하고, 반영 순서에 따라 화면이 되돌아간다(2026-11-22에 실제로 겪음).

**이미 있는 반례:** 화면(`ui`) 클래스 모듈은 재빌드 없이 동작한다.
- 서명된 정적 번들을 원장에서 `/ui/<module>/`로 내보낸다.
- 레일에 메뉴가 스스로 생긴다(`descriptor.ui.navigation`).
- 다만 Console 셸 밖의 별도 페이지다. 같은 세션 · MFA 패널 · 표준 틀을 쓰지 못한다.

## 2. 원칙

1. **Backbone = 운영체제, 패키지 = 프로그램.**
   - Backbone이 가진 것: 셸, 로그인 · MFA, 스토어 · 원장, 계획 · 승인, 실행부 · 웹훅, 표준 화면 틀과 부품, 데이터 원천 API
   - 패키지가 싣는 것: 자기 메뉴 · 화면 · 동작 · 객체 정의
2. **설치는 원장 기록과 패키지 내용의 활성화일 뿐이다.** Console · Core는 다시 빌드하지 않는다.
3. **신뢰 경계는 그대로 둔다.**
   - 패키지 내용은 서명되고 판정된다.
   - 사람의 승인(MFA), 실행부, 승인 대조 웹훅은 Backbone의 고정 부분이다.
   - 패키지가 실은 것이 이 경계를 건너뛰지 못한다.
4. **Backbone은 플랫폼 기능이 늘 때만 갱신한다.** 새 부품 종류, 새 계약 판, 새 실행 방식이 그 경우다. 패키지가 늘어난다고 갱신하지 않는다.
5. **패키지는 자기가 요구하는 계약 판을 선언한다**(기존 `backboneCompat`). Console · Core는 지원하는 판 범위를 밝히고, 맞지 않는 패키지는 스토어가 설치를 막는다.

## 3. 목표 구조: 세 층

### 3.1 메뉴: 설치된 패키지가 메뉴를 기여한다

- **Console에 내장하는 것은 골격뿐이다:** 레일의 섹션(대시보드 · HISS · Fabric · Governance · Workspace · 설정)과 섹션별 묶음 이름.
- **섹션의 내용은 원장에서 온다.** 설치가 active인 패키지의 `contributes.navigation`이 그 내용이다.
  - 형식: `{ section, group, label, logo, order, route }`
  - Console은 `GET /console-api/navigation`(원장 → 메뉴)로 그린다.
- 설치하지 않은 항목은 메뉴에 없다. 각 섹션 끝에 "스토어에서 더 받기"를 둔다.
- 설정(Backbone 자신)의 메뉴는 Backbone 판에 묶이므로 내장으로 남는다.

### 3.2 화면: 기본은 선언형, 예외는 격리 확장

**(a) 선언형 화면(기본)**
- 패키지가 화면 선언(`screens/*.json`, JSON Schema로 검증)을 싣는다.
  - 표준 틀을 하나 고른다.
    - Fabric 서비스 개요 · 인스턴스 목록 · 인스턴스 세부(13개 탭, `FABRIC-INSTANCE-DETAIL.md`)
    - HISS 항목(탭 5개)
    - 목록 · 상세
  - 틀 안의 블록을 적는다.
    - 블록 종류: 지표 타일 · 표 · 항목/값 · 차트 · 알림 · 미터 · 토폴로지
    - 각 블록에 **데이터 원천**과 **표현 규칙**(필드 매핑, 태그 규칙, 단위, "읽지 못함" 문구)을 정한다.
- **데이터 원천**은 Backbone이 정해 둔 것만 쓸 수 있다.
  - 원장 조회(자기 설치본 · 인스턴스 · Claim · 계획 이력)
  - 실행부 상태/세부 읽기(자기 설치본 namespace, §3.3)
  - HISS 이름 붙은 질의(자기 인스턴스 범위)
- 버튼은 **선언된 동작**(§3.3)만 가리킨다. 누르면 Backbone의 MFA 패널이 열린다.
- Console의 일반 렌더러가 그린다. **패키지 코드는 Console에서 돌지 않는다.** 값은 모두 글자로 다룬다(HTML 삽입 없음).
- 패키지 판이 오르면 화면도 바뀐다. Console 재빌드는 없다.

**(b) 격리 확장 화면(예외)**
- 선언형으로 표현할 수 없는 화면만 쓴다. 예: 대화형 편집기, 특수 시각화.
- 패키지가 서명된 정적 번들(Web Component)을 싣고, Console 셸 안의 **격리 iframe**에 띄운다.
  - iframe은 `sandbox`이고 `allow-same-origin`을 주지 않는다. 그래서 관리자 쿠키 · 세션에 닿지 않는다.
  - 셸과는 정해진 host API(postMessage)로만 이야기한다.
  - host API: 자기 설치본 범위의 데이터 원천 읽기, 선언된 동작 요청(→ 셸의 MFA 패널), 테마 · 로고 · 이동
- 지금의 `ui` 클래스(`/ui/<module>/` 별도 페이지)는 이 방식으로 합친다.

### 3.3 동작 · 객체 · 상태: 패키지가 선언하고 Backbone이 집행한다

- **동작 선언**(`actions.json`)
  - 예: `instance.create` · `instance.delete` · `claim.issue` · `claim.release` · `install` · `update` · `stop`
  - 각 동작에 입력 스키마(검증 규칙), 효과 등급, 만드는 객체(§아래)를 적는다.
  - Core는 동작 이름별 Rust 분기 대신 **선언을 읽어 계획을 만든다.** 계획 → MFA → 실행부 → 웹훅 → 원장 흐름은 그대로다.
- **객체 정의:** 두 방식을 함께 둔다(결정 C2).
  - **(i) 템플릿 매니페스트.** 패키지가 객체 틀과 형식 있는 인자를 싣는다.
    - 실행부가 안전한 치환기로 렌더링한다. 문자열 치환만 하고, 반복과 조건은 선언된 범위에서만 쓴다.
    - 웹훅은 렌더링 결과와 대조한다.
    - HISS 패키지(렌더된 매니페스트)와 StackGres처럼 객체 모양이 고정된 엔진이 여기에 맞는다.
  - **(ii) 패키지 컨트롤러.** 동작에 실행 시간 논리가 필요한 엔진에 쓴다. 예: 자격 발급 SQL, LDAPS 확인, 인덱스 권한.
    - 패키지가 자기 컨트롤러 이미지를 싣는다. 컨트롤러는 설치본 namespace 안에서 배치 규칙 권한으로만 돈다.
    - 실행부는 승인된 **요청 객체**(예: `OsrInstance` · `OsrClaim`)만 쓰고, 컨트롤러가 그것을 실현한다. 결과는 요청 객체의 status로 보고한다.
    - 사람의 승인과 웹훅 대조는 요청 객체에 걸린다. 컨트롤러 권한은 배치 규칙이 묶는다.
- **상태 · 세부 읽기**(`status.json`)
  - 패키지가 무엇을 어떻게 읽을지 선언한다(종류 · 라벨 선택자 · 노출할 필드 경로 허용 목록).
  - 실행부의 일반 리더가 자기 설치본 namespace 안에서 읽는다.
  - 비밀(Secret · env)은 선언해도 읽지 않는다. 일반 리더의 금지 목록에 있다.
- **원장:** 서비스별 표 · 함수 대신 일반 표를 쓴다(설치본 · 인스턴스 · Claim · 계획 · 이력). 서비스 고유 값은 패키지 스키마로 검증한 JSON 칸에 둔다.

## 6. 보안과 신뢰

- **선언은 데이터다.** 스키마로 검증하고 번들 서명에 포함한다. 렌더러는 글자만 그리고, URL은 허용 형식만 받는다.
- **데이터 원천의 범위:** 패키지는 **자기 설치본** 범위만 읽는다(설치본 id로 묶음). 다른 패키지 · Backbone 내부 · Secret은 읽지 않는다.
- **동작:** 모두 계획 → MFA → 실행부 → 웹훅이다. 화면 선언이 동작을 직접 실행하지 못한다.
- **격리 확장 화면:** opaque origin(sandbox, same-origin 없음)이라 쿠키가 없다. host API는 셸이 자기 설치본 범위로 줄여 대신 부른다.
- **패키지 컨트롤러:** 자기 namespace, 배치 규칙 권한만 갖는다. 요청 객체 밖의 일은 할 수 없다. 이미지는 digest 고정 · 서명이다.
- **판 호환:** 패키지가 요구하는 계약 판을 지원하지 않는 Backbone이면 스토어가 설치를 막는다.

2. 템플릿 렌더러 대 패키지 컨트롤러의 경계: 지금 Rust에 있는 서비스별 논리(발급 SQL · 해제 · 저장 엔진 자격 · LDAPS 확인) 가운데 어느 것이 템플릿으로 충분하고, 어느 것이 컨트롤러가 필요한가?
3. 웹훅 대조: 패키지 컨트롤러가 만드는 하위 객체는 웹훅이 무엇과 대조하는가? 요청 객체만 승인하고, 하위는 배치 규칙 경계로만 묶어도 지금의 승인 보장(Q11)과 같은 수준인가?
4. 일반 원장으로 옮길 때 지금의 예약 · fence · held(어셈블리 공급 v0.8)를 어떻게 지키는가?
5. 격리 iframe host API의 최소 집합과, 같은 origin에서 열 수밖에 없는 경우가 있는지.
6. 이행 순서: X1 → X2 → X3 → X4가 맞는가? 지금 진행 중인 OpenSearch/RustFS 작업을 어디서 멈추고 옮기는가?
