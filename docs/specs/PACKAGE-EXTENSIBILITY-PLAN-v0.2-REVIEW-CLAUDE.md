# 패키지 확장 구조 개선 계획 v0.2 검토 (Claude)

**대상:** [PACKAGE-EXTENSIBILITY-PLAN-v0.2.md](PACKAGE-EXTENSIBILITY-PLAN-v0.2.md)
**작성:** 2026-11-23 · Claude. 소유자가 Codex에게 넘기기 위한 검토 의견이다.

**확인한 사실**(Backbone main `1a3613e`, 운영 RKE2 읽기 전용)
- Backbone PR #156(`Build only requested OSR module assets`)이 main에 있다.
- 모듈 디스크립터(`opensphere.module/v1`)에는 기존 `contributions` 칸(manual · commands · oci · knowledge)이 있다.
- `ui` 클래스는 원장의 활성 모듈과 `/ui/<module>/` 링크로 레일에 나온다.
- 운영에 `os-backbone-mod-provider-opensearch` namespace가 있다.
- 같은 클러스터에 격리 설치본 `os-backbone-osr-fixture-20261118`이 있다.

## 총평

방향은 맞다. v0.1에서 약했던 두 곳을 바로잡았다.
- 패키지 컨트롤러: "요청 객체 승인 + namespace RBAC"이 Q11 수준이 아니라는 점을 짚고, 결정 뒤로 미뤘다.
- 원장: 쓰기를 바로 일반화하지 않고 읽기 모델부터 둔다.

검증 대상을 OpenSearch · RustFS로 좁히고, §5.1에 "A 설치부터 B 적용 · 회수까지 Console 재빌드 · 이미지 게시 · 배포 0회"라는 증거 기준을 둔 것도 좋다.

## 1. 반드시 정해야 할 것

### ① §5.1의 "운영 리소스와 분리된 RKE2 시험 설치본"은 지금 조건으로 실행할 수 없다

- 소유자 결정(2026-11-18): 별도 클러스터 · 예행 설치본은 두지 않는다. 허용된 것은 같은 RKE2 안의 임시 `os-backbone-*` namespace뿐이다.
- 같은 클러스터의 격리 설치본에서 OpenSearch · RustFS를 스토어로 설치하면 운영과 이름이 겹친다.
  - 설치본 namespace `os-backbone-mod-provider-<module>`(운영에 이미 있음)
  - 배치 규칙 ClusterRole `osr-profile-*`
  - 실행부 웹훅 설정
- 2026-11-20에 같은 이유로 운영 실행부 권한을 지운 사고가 있었다.

**문서에 둘 중 하나를 정해야 한다.**
- **(a) 운영 설치본에서 직접 실증(권장).** A · B는 시험용이 아닌 실제 릴리스로 낸다. B는 메뉴 이름 · 순서 · 표시 항목만 바꾼 정식 판이다.
  - 운영 서명 키로 시험 내용에 서명하지 않는다는 규칙과도 맞는다.
  - 다만 §5.1-4의 "릴리스 회수"는 운영의 실제 모듈을 회수하는 일이다. 그래서 내리기 · 회수 증거는 둘로 나눈다.
    - 운영에서는 "활성 인스턴스 · Claim이 있으면 거절 · 데이터 보존"만 확인한다.
    - 메뉴 · 직접 주소의 제공 중단은 쓰지 않는 다른 모듈(예: 화면 모듈)로 확인한다.
- **(b) 격리 설치본이 겹치지 않게 하는 제품 기능을 먼저 만든다.** 설치본 namespace 접두와 클러스터 범위 이름을 설치본마다 다르게 하는 기능이다. 범위가 커진다.

### ② 기존 Fabric 주소를 유지하는 규칙이 없다(§3.1 · C4)

- `screenId`와 설치 ID로 호스트가 주소를 만든다고 했다. 그러나 지금 북마크 · 문서 · 화면 사이 링크는 `#/fabric/shared/opensearch`, `#/fabric/shared/postgres/<탭>?instance=<이름>` 꼴이다.
- **제안:**
  - 기여에 안정된 `slug`를 둔다.
  - 호스트가 `#/<section>/<group>/<slug>[/<탭>]`으로 주소를 만든다.
  - 같은 slug를 두 패키지가 주장하면 설치 판정에서 거절한다.
  - 그러면 X1 전환 때 주소가 바뀌지 않는다.

### ③ 동작 입력 스키마의 주인이 문서 안에서 엇갈린다(§3.3 82~83행 대 §3.2 77행)

- 83행은 "동작 이름과 입력 스키마는 패키지 기여"이고, 효과 · 권한 · 계획 내용은 호스트가 정한다고 한다.
- 화면의 폼(패키지 스키마)과 서버 검증(지금 Rust 규칙)이 다르면, 화면은 받는데 서버가 거절하거나 그 반대가 생긴다.
- **제안:** 입력 스키마는 호스트 동작 정의에 속하고, 패키지는 표시 이름 · 순서 · 도움말만 정한다.
- 다른 길은 패키지 스키마를 서버도 그대로 검증하는 것이다. 이 경우 서버 검증 규칙이 패키지로 넘어가므로 Q11 · 계획 digest와의 관계를 따로 정해야 한다.

### ④ 첫 블록 목록에 폼(동작 입력)이 없다(§3.2 75행)

- "지표 · 항목과 값 · 표 · 시계열 · 알림"만으로는 X2 범위(개요 · 인스턴스 목록 · 앱 연결)를 그릴 수 없다.
- 입력 폼이 필요한 동작:
  - 인스턴스 만들기: 이름 · 크기 · 저장 방식 · 프리셋
  - 앱 연결: 받을 곳 · Secret 이름
- **제안:** 동작 버튼 + 입력 폼 블록을 첫 블록 목록에 넣는다. 폼의 칸은 ③에서 정한 호스트 스키마로 그리고, 제출은 공통 계획 · MFA 패널로 넘긴다.

## 2. 보강하면 좋은 것

### ⑤ 읽기 허용 필드의 책임

- "읽기 가능한 필드만 반환"(§3.2 76행)을 누가 정하는지가 비어 있다.
- `status.json`이 경로를 선언해도, 일부 CRD는 spec에 자격이나 민감 값을 담는다.
- **제안:** 호스트에 종류별 금지 경로 표를 둔다. 배치 규칙 검토에서 노출 경로를 함께 본다. Secret · env 금지만으로는 부족하다.

### ⑥ 로고

- 제품명 앞 로고는 소유자 지시다.
- **제안:** 기여의 `logo`는 둘 중 하나로 한정한다.
  - Console 내장 로고 목록의 키
  - 번들에 든 SVG를 `<img>`로만 그림(`<img>`의 SVG는 스크립트를 실행하지 않는다)

  외부 URL과 인라인 SVG는 받지 않는다.

### ⑦ §5.1에 넣을 증거 둘

- **B → A 되돌리기:** 이전 판을 다시 적용하면 A 표시로 돌아오는지 본다. 선언이 어딘가에 남아 B로 고정되지 않음을 보인다.
- **열려 있던 화면:** B를 적용할 때 이미 열려 있던 Console 탭의 기대 동작을 정한다.
  - 다시 불러온 뒤 B를 보이는지, 그 자리에서 바뀌는지 정한다.
  - 브라우저 캐시와 선언 캐시의 무효화 기준(활성 digest 변경)을 적는다.

### ⑧ 관측 질의는 X2 필수가 아님을 밝히기

- 데이터 원천에 "명명 관측 질의"가 있으나 HISS 관측 바닥은 아직 운영에 없다.
- X2 합격 기준에서는 빠지고 "읽지 못함"으로 표시되는 것이 정상이라고 적어 두어야 판정이 흔들리지 않는다.

### ⑨ 작업 나눔

- v0.1에서 문제로 적은 "같은 파일 동시 수정"(`osr_executor.rs` · `osr_install.rs` · Fabric 화면)을 막을 규칙이 없다.
- **제안:** X1 · X2를 둘로 나눠 맡는다.
  - 호스트 쪽: 계약 스키마, `GET /console-api/navigation`, 렌더러, 데이터 원천 API
  - 패키지 선언: OpenSearch · RustFS의 `screens` · `actions`
