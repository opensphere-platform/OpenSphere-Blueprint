## 1. 문제: 지금 새 패키지 하나가 바꾸는 곳

예를 들어 Fabric 서비스 하나를 더하면 다음을 모두 고친다. 수치는 2026-11-23 Backbone main 기준이다.

| 층 | 지금 패키지마다 하드코딩된 것 | 크기(근사) |
|---|---|---|
| Console 메뉴 | Fabric 메뉴(`examples.ts` FABRIC_MENU), HISS 메뉴(`hiss.ts`), 설정 메뉴. 설치 여부와 무관하게 고정 | — |
| Console 화면 | 서비스마다 화면 · 변환 코드(PostgreSQL · Samba AD · Keycloak · OpenSearch/RustFS · HISS) | Fabric 약 3,000줄 |
| Core 렌더러 | 객체를 만드는 Rust(`osr_render` · `osr_samba` · `osr_keycloak` · `osr_storage_provider`) | 약 2,700줄 |
| Core 동작 | 인스턴스 계획 · 발급 · 해제(`osr_install` 안 분기, `osr_issue` · `osr_storage_claim`) | 약 1,600줄 + 분기 |
| 실행부 · 웹훅 | 상태 읽기 · 세부 읽기(mechanism별 분기), 판정 허용 목록(kind별) | 분기 다수 |
| 원장 SQL | 서비스별 함수 · 표(claims_of · storage_claims_of · directory_binds …) | 마이그레이션 20여 개 |
| 계약 | 배치 규칙 mechanism 열거, 스토어 설치 허용 클래스 | — |

**결과**
- 지원하는 공급자 버전의 설치·인스턴스 생성은 기존 운영 경로에서 가능하다. 메뉴·화면 추가나 새 실행 방식이 내장 코드에 결합돼 이때 Core·Console 이미지 변경이 필요해졌다.
- 새 실행 계약을 도입할 때는 DB 마이그레이션·실행 규칙·신뢰 세대를 따로 반영해 왔다. 공급자 번들 조립에서 불필요한 Console 빌드는 Backbone PR #156에서 제거했다.
- Codex와 Claude가 같은 파일(`osr_executor.rs` · `osr_install.rs` · Fabric 화면)을 동시에 고쳐 충돌하고, 반영 순서에 따라 화면이 되돌아간다(2026-11-22에 실제로 겪음).

**이미 있는 반례:** 화면(`ui`) 클래스 모듈은 재빌드 없이 동작한다.
- 서명된 정적 번들을 원장에서 `/ui/<module>/`로 내보낸다.
- Console 레일은 설치 원장이 반환하는 활성 모듈 이름과 `/ui/<module>/` 링크를 사용한다. 관리자용 화면 파일은 현재 Console 세션으로 제공된다.
- 기존 `/ui`는 독립 화면 호환 경로다. Fabric 보조 메뉴와 공통 네이티브 MFA 패널은 이 계약에서 새로 연결한다.

## 2. 원칙

1. **Backbone = 운영체제, 패키지 = 프로그램.**
   - Backbone이 가진 것: 셸, 로그인 · MFA, 스토어 · 원장, 계획 · 승인, 실행부 · 웹훅, 표준 화면 틀과 부품, 데이터 원천 API
   - 패키지가 싣는 것: 서명된 메뉴·화면 선언, 호스트가 지원하는 동작 참조, 승인된 실행 정의
2. **설치는 서명된 패키지를 승인해 적용하고 원장에 활성 판을 기록한다.** 지원하는 계약의 패키지 설치와 화면 갱신은 이미 배포된 Console·Core로 수행한다.
3. **신뢰 경계는 그대로 둔다.**
   - 패키지 내용은 서명되고 판정된다.
   - 사람의 승인(MFA), 실행부, 승인 대조 웹훅은 Backbone의 고정 부분이다.
   - 패키지가 실은 것이 이 경계를 건너뛰지 못한다.
4. **Backbone은 플랫폼 기능이 늘 때만 갱신한다.** 새 부품 종류, 새 계약 판, 새 실행 방식이 그 경우다. 패키지가 늘어난다고 갱신하지 않는다.
5. **패키지는 자기가 요구하는 계약 판을 선언한다.** 기존 `backboneCompat`과 확장 계약 판을 확인한다. 스토어는 실제 배포된 Console·Core·실행부가 요구 기능을 지원할 때 설치를 제공한다.

## 3. 목표 구조: 세 층

### 3.1 메뉴: 설치된 패키지가 메뉴를 기여한다

- **Console에 내장하는 것은 골격뿐이다:** 레일의 섹션(대시보드 · HISS · Fabric · Governance · Workspace · 설정)과 섹션별 묶음 이름.
- **섹션의 내용은 원장에서 온다.** 원장이 가리키는 설치된 활성 번들 digest의 서명된 기여를 사용한다. 내리기·회수와 직접 주소 조회는 같은 활성 판 기준으로 처리한다.
  - 새 계약에는 `section`, `group`, 안정된 `slug`, `label`, `logo`, `order`, `screenId`를 둔다. 호스트는 허용한 섹션·그룹과 slug로 주소를 만들고 설치 ID·화면 ID로 데이터를 조회한다.
  - 같은 섹션·그룹·slug를 다른 패키지가 쓰거나 호스트 예약 경로와 충돌하면 거절한다. 설치 계획에서 확인하고, 동시 설치도 같은 경로를 차지할 수 없도록 활성화 트랜잭션에서 다시 검사한다.
  - 버전이 있는 확장 계약으로 표준화한다. 기존 `opensphere.module/v1`의 닫힌 디스크립터와 `contributions`는 이전 번들의 판정 규칙으로 유지한다.
  - Console은 `GET /console-api/navigation`(원장 → 메뉴)로 그린다. 호스트는 `#/fabric/shared/opensearch`, `#/fabric/shared/rustfs`와 PostgreSQL의 기존 탭·`instance` 링크를 보존한다. 활성 판을 바꾸어도 공개 경로는 안정적으로 유지한다.
  - 메뉴와 직접 주소는 활성·미회수 digest를 같은 규칙으로 조회한다. 선언과 응답 캐시는 설치 ID·활성 digest를 기준으로 다시 검증한다. 이미 열린 탭은 새로고침하면 새 판을 표시하고, 이전 판의 폼은 제출 때 현재 판과 대조한다.
- **이전 계약 번들의 호환 표:** 새 탐색 기여가 없는 **유효한 이전 계약의 활성 번들**(지금의 PostgreSQL · Keycloak · Samba AD)은 새 판으로 갱신될 때까지 호스트의 호환 표(모듈 id → 섹션 · slug · 이름)로 기존 메뉴와 주소를 제공한다. 새 계약 번들이 활성화되면 그 선언이 대신한다. 회수된 번들이나 새 계약 검증에 실패한 항목은 호환 표로 되살리지 않는다.
- 아직 설치하지 않은 항목을 찾는 곳은 스토어다. 각 섹션 끝에 "스토어에서 더 받기"를 둔다.
- 설정(Backbone 자신)의 메뉴는 Backbone 판에 묶이므로 내장으로 남는다.

### 3.2 화면: 네이티브 선언형

- 패키지가 번들 서명에 포함된 화면 선언(`screens/*.json`)을 제공한다. 호스트는 버전이 고정된 JSON Schema로 검사하고 공통 Angular 화면 틀에서 그린다.
- 첫 화면 틀은 **Fabric 공유 서비스의 개요·인스턴스 목록·앱 연결**이다. OpenSearch는 인덱스, RustFS는 버킷을 같은 틀에서 표시한다. 두 공급자의 실증 뒤 PostgreSQL 인스턴스 세부 13개 탭, Samba AD·Keycloak 및 HISS를 옮긴다.
- X2에서는 지표·항목과 값·표·알림과 **동작 버튼·입력 폼**을 사용한다. 크기·저장 방식·실제 상태·앱 연결처럼 현재 원천에서 확인할 수 있는 값을 표시한다. 원천이 응답하지 않은 값은 “읽지 못함”으로 표시한다.
- 호스트가 정의한 원장 조회와 실행부 상태·세부 읽기를 먼저 쓴다. 호스트는 활성 설치 ID·bundle digest를 확인한 뒤 응답 타입과 필드 허용 목록을 적용하고, 패키지는 그 범위에서 표시할 값을 고른다. 시계열과 HISS 관측 질의는 후속이며 X2의 합격 기준은 이 원천의 가용성에 의존하지 않는다.
- Console은 호스트 동작 정의로 폼을 그린다. 인스턴스 생성은 이름·용량·저장 프로필·프리셋, 앱 연결은 용도·받을 준비가 된 namespace·Secret 이름을 받는다. 서버가 실제 계획과 변경 내용을 만들고, 공통 패널이 그 계획과 파괴적 효과를 표시한 뒤 MFA를 받는다.
- X2 로고는 Console의 기존 로고 키를 사용한다. 번들 로고를 지원하는 후속 계약은 서명된 digest의 파일을 이미지로 표시하는 범위에서 검토한다.
- 패키지에서 받은 텍스트와 값은 데이터로 렌더링한다. 이행 기간에는 기존 `/ui/<module>/` 호환 경로와 설치된 패키지의 네이티브 Fabric 화면을 각자의 계약으로 제공한다.

### 3.3 동작 · 객체 · 상태: 패키지가 선언하고 Backbone이 집행한다

- **동작 선언**(`actions.json`)은 호스트가 지원하는 `instance.create` · `instance.delete` · `claim.issue` · `claim.release` 등을 참조한다. 첫 검증은 이미 배포된 타입과 권한 검사를 재사용한다.
- 입력 스키마, 동적 선택지, 서버 검증, 효과 등급, 권한·계획 내용은 호스트 동작 정의와 기존 승인 계약이 정한다. 패키지는 동작을 참조하고 표시 이름·순서·도움말을 제공한다.
- **(i) 템플릿 매니페스트.** 고정된 객체 틀과 형식 있는 인자를 사용한다. 계획·실행·웹훅은 승인된 digest에서 같은 결과로 렌더링하고 실제 API 서버 형태와 대조한다. 엔진 자격 발급·회수와 검증에는 현재의 제한 Job·SGScript 등 이미 검토한 경로를 사용한다.
- **(ii) 패키지 컨트롤러 검토.** 요청 객체 승인과 namespace RBAC는 승인 계획에 없는 쓰기를 판단하기에 충분하지 않다. 컨트롤러가 기존 실행부에 효과를 요청하거나, 별도 쓰기 계정의 실제 요청도 승인된 단계와 객체 내용에 대조하는 모델이 결정된 뒤 검토한다(Q11).

- **상태 · 세부 읽기**(`status.json`)
  - 호스트가 검토한 읽기 동작과 그 응답 필드만 선언에서 선택할 수 있다. 실행부 또는 원장 조회가 설치 ID로 범위를 고정한다.
  - 반환 형식을 정할 때 종류별 민감 필드를 확인한다. 원시 객체·임의 경로·환경 변수·Secret을 화면으로 전달하지 않는다.
- **원장:** 설치본·인스턴스·Claim·계획·이력의 공통 읽기 모델을 먼저 둔다. Services의 예약·용량과 Core의 승인·점유·fence를 정본으로 삼는다. 쓰기 구조는 기존 UID, 멱등 키, `held`, `unknown`, 감사 이력이 이행되는 것을 확인한 뒤 다룬다.

## 4. Backbone에 남는 것 (플랫폼)

- 셸 골격, 로그인 · MFA, 설정(Backbone 자신)
- 스토어 · 원장 · 서명 검증 · 판정 · 계획 · 승인 · 실행부 · 웹훅
- 표준 화면 틀과 블록 렌더러, 데이터 원천 API, HISS 관측 질의 엔진
- 일반 리더 · 형식이 제한된 템플릿 렌더러
- 계약 판(패키지 선언 스키마의 판)

이것들이 바뀔 때만 Backbone을 갱신한다.

| **X5 정리** | 이행한 내장 화면과 중복 경로 정리 | 이전 주소·긴급 복구·활성 예약·이력이 검증된 뒤 구 경로 종료 |

OpenSearch·RustFS의 첫 검증은 기존 설치 및 인스턴스 실행 경로를 기준으로 한다. 호스트 작업은 확장 계약·메뉴 API·렌더러·승인 연결을 맡고, 공급자 작업은 합의된 계약에 맞춘 OpenSearch·RustFS 선언을 맡는다. 같은 소스 파일의 변경은 담당자 한 명이 통합한다. HISS는 [구성 계획 v0.2 §7](HISS-COMPOSITION-PLAN-v0.2.md)의 전용 실행부·고권한 프로필 경계를 적용한 뒤 메뉴 기여를 연결한다.

### 5.1 첫 실증의 완료 기준

1. **부분 시험과 운영 실증.** 기존 운영 RKE2의 임시 `os-backbone-*` namespace는 스키마·렌더링·권한 거부 등 부분 시험에 쓴다. 운영과 이름이 겹치는 공급자 namespace·ClusterRole·웹훅을 시험 목적으로 적용하지 않는다. 정식 OpenSearch·RustFS의 A→B 종단 실증은 별도 승인 후 기존 운영 설치본에서 진행한다. 운영 기준선 반영 전에는 시험 키로 서명한 두 공급자의 A·B 기여를 격리 원장에 연결한다. 같은 Console 산출물에서 메뉴와 네이티브 화면이 바뀌는 부분 시험과 소스 검사 결과를 기록한다. 운영 OSR의 발행 키·카탈로그와 공급자 리소스는 운영 승인 범위에서 다룬다.
2. **기준선과 A.** 선택한 설치본에 공통 메뉴·화면 계약이 갖춰지면 Console·Core·실행부 이미지 digest, Console 배포 세대와 DB 마이그레이션 판을 기록한다. A는 새 탐색·화면 계약을 담은 서명 릴리스다. 기존 활성 판이 이 계약을 지원하면 그 판과 인스턴스를 기준으로 기록한다. 기존 판이 내장 화면만 제공하면 같은 호스트 기준선에서 A를 MFA로 적용한 뒤 A→B 시험을 시작한다. 필요한 정식 신규 설치와 인스턴스 생성은 관리자 MFA로 진행한다. Ready·볼륨 연계와 시험용 인덱스·버킷의 발급, 실제 읽기·쓰기, 회수 뒤 접근 차단과 데이터 보존을 확인한다. 활성 작업의 예약·점유 때문에 진행할 수 없는 경우 기존 복구 절차로 먼저 해결한다.
3. **패키지 B만 적용.** B는 메뉴 이름 또는 순서와 화면 표시 항목을 바꾼다. 엔진 이미지·배치 규칙·실행 객체는 A와 동등해야 한다. 카탈로그 게시 직후에는 A가 보이고, B를 MFA로 활성화해 새로고침하면 같은 Fabric 주소에서 B 메뉴와 B 화면이 보인다. 인스턴스 UID·볼륨·데이터를 확인한다. **B 작업의 쓰기 목록에 인스턴스·Claim 객체가 없고**, 쓰기 대상 전부(설치 뼈대와 모듈 설치 객체: OpenSearch·RustFS의 `storage-instance-tls` ConfigMap, PostgreSQL의 SG 설정 객체 등)에서 적용 전후 차이는 **작업 추적 표식**(모든 쓰기 객체의 `opensphere.io/osr-operation` 주석, `osr-execution` ConfigMap의 operation·planDigest·fence)뿐이어야 한다. 권한·네트워크 정책·워크로드 설정은 같다. 부분 시험에서 A·B 렌더링 결과를 먼저 대조하고, 운영 실증에서 승인된 B 작업의 쓰기 목록과 그 객체의 적용 전후 상태를 함께 기록한다. 화면 복원은 지원되는 OSR 되돌리기로 검증한다. 그러한 경로가 없으면 A 화면 선언을 담은 새 서명 릴리스 C를 정상 적용하고 화면 복원으로 기록한다.
4. **내리기·회수와 직접 주소.** 사용 중인 운영 공급자는 내리기 계획 단계의 거절과 데이터 보존을 확인한다. 메뉴 제거와 직접 주소 제공 중단은 **같은 새 네이티브 탐색·화면 계약**을 사용하는 폐기 가능한 시험 패키지로 검증한다. 시험 증거는 해당 패키지의 범위에 귀속한다. 실제로 쓰이는 운영 공급자 릴리스의 회수는 이 시험에 포함하지 않는다.
5. **합격 증거.** 두 공급자에서 A·B의 서명·digest, 활성화 MFA 작업 ID, 새로고침 전후 브라우저 메뉴·화면, 기존 데이터 확인 결과를 남긴다. A 기준선 확정부터 B 적용과 표시 복원까지 **Console 재빌드·이미지 게시·배포 0회**여야 하고, 최초 digest와 배포 세대가 일치해야 한다. 새 계약의 메뉴 회수 시험까지 기록하면 X2가 완료된다.

## 6. 보안과 신뢰

- **선언은 데이터다.** 스키마로 검증하고 번들 서명에 포함한다. 렌더러는 글자만 그리고, URL은 허용 형식만 받는다.
- **데이터 원천의 범위:** 패키지는 **자기 설치본** 범위만 읽는다(설치본 id로 묶음). 다른 패키지 · Backbone 내부 · Secret은 읽지 않는다.
- **동작:** 모두 계획 → MFA → 실행부 → 웹훅이다. 화면 선언이 동작을 직접 실행하지 못한다.
- **공급자 화면:** 설치본의 활성 digest에 묶은 JSON을 호스트가 렌더링한다. 사용자 승인과 서버 정책은 호스트에서 처리한다.
- **실행:** 승인된 계획과 실제 쓰기는 웹훅에서 대조한다. 일반 원장에 투영하는 상태는 검증된 실행 결과와 연결한다.
- **판 호환:** 스토어는 미지원 확장 계약·동작·데이터 원천을 명시하며 설치를 거절한다. 이전 계약의 번들은 해당 계약으로 계속 판정한다.
