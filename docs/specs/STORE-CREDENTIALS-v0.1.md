## 0. 평가 기준(소유자)

1. 스토어는 **레포 단위**로 다룬다. 계정 형태는 묻지 않는다.
2. 스토어마다 **필요한 만큼의 권한**을 가진 토큰을 준다. 읽기면 읽기 전용, 관리가 필요하면 그만큼 더.
3. 그 토큰으로 여러 스토어를 **등록 · 운영 · 삭제**할 수 있어야 한다.
4. 약속된 기능이 안 되면 결함으로 리포트한다.

여기에 하나를 지킨다: **토큰은 접근만, 신뢰는 서명 + 소유자 MFA.** 쓰기 토큰이 새도 서명되지 않은 패키지가 설치될 수 없어야 한다(D-99 원칙 2).

**결함 목록**

- **F-1 토큰을 넣고 · 바꾸고 · 빼는 제품 경로가 없다.** kubectl 수작업이고, 누가 언제 넣었는지 원장에 남지 않는다. 소유자 MFA에도 묶이지 않는다(신뢰 변경은 MFA인데 그 신뢰가 가리키는 자격은 MFA 밖).
- **F-2 비공개 스토어 하나마다 Console 쪽 구성을 손대야 한다.** carrier 토큰을 Console 파일로 마운트하는 구조라, 스토어 추가가 Backbone 배포 구성 변경으로 이어질 수 있다(재빌드는 아니지만 "스토어는 설치본의 데이터"라는 D-99 원칙 1과 어긋난다). 마운트가 기존 Secret volume의 키 추가로 끝나는지, Deployment 변경이 필요한지는 Codex 대조 대상(§9-1).
- **F-3 비공개 worker를 띄우는 것도 수작업이다.** 렌더 함수는 있으나 승인된 실행 경로(Core 계산 · 웹훅)를 거치지 않는다.
- **F-4 스토어 삭제가 자격 · worker 정리까지 닫지 않는다.**
- **F-5 관리 권한 토큰의 자리가 없다.** 회사가 자기 비공개 스토어를 OpenSphere에서 운영하려 해도 게시 경로가 OpenSphere 밖에만 있다.
- **F-6 넘치는 권한을 막지 못한다.** 읽기 자리에 쓰기 · 레포 권한까지 가진 토큰을 넣어도 그대로 쓴다.

## 2. GHCR 토큰의 실제 제약(공식 문서 확인, 2026-11-26)

- GitHub Packages(GHCR 포함)는 **personal access token(classic)** 으로만 인증한다. 다른 레포의 비공개 패키지를 받으려면 `read:packages` 이상이 필요하다. [GitHub Docs — Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)
- **`read:packages`는 레포 하나로 좁혀지지 않는다.** 그 토큰의 계정이 볼 수 있는 모든 패키지를 읽는다. fine-grained 토큰은 GHCR에서 공식 지원으로 확인되지 않는다(커뮤니티 보고: 403). GitHub App 토큰은 GHCR 인증에 쓸 수 없다는 GitHub 측 답변이 있다(Actions 안의 `GITHUB_TOKEN`은 그 레포에 연결된 패키지에 쓸 수 있음). [Discussion #38467](https://github.com/orgs/community/discussions/38467) · [Discussion #153160](https://github.com/orgs/community/discussions/153160) · [Discussion #24636](https://github.com/orgs/community/discussions/24636)

**뜻:**
1. "레포 하나만 읽는 토큰"은 GHCR에서 **토큰 범위로는 만들 수 없다.** 최소 권한은 **그 스토어 패키지만 볼 수 있는 전용 계정(기계 계정)** 의 classic PAT `read:packages`로 만든다. 계정 형태는 여기서도 상관없고, "무엇을 볼 수 있는 계정인가"만 중요하다.
2. 그래서 OpenSphere는 토큰 범위를 믿지 않고 **자기 쪽에서 범위를 다시 좁힌다**: worker는 신뢰 변경에 적힌 정확한 레포만 pull 교환을 요청한다(MS2에 이미 있음).
3. 쓰기는 classic PAT `write:packages` 또는 Actions `GITHUB_TOKEN`. **GitHub App 설치 토큰으로 GHCR에 쓰는 MS7b 계획은 고쳐야 한다**(§5).
4. 레지스트리마다 사정이 다르다(다른 OCI 레지스트리는 레포 단위 토큰을 줄 수 있음). 그래서 설계는 GHCR 제약을 기본으로 삼되 자격 자리를 레지스트리 중립으로 둔다.

## 3. 설계 원칙

1. **자격 자리(slot)는 스토어마다.** 한 스토어 = 0개 이상의 자격 자리. 등급은 둘: `read`(목록 · 등록부 · 번들 pull) · `publish`(그 스토어 레포에 push). 공개 스토어는 `read` 없이 익명.
2. **토큰 값은 Console · 원장 · 로그 · 화면에 없다.** 원장에는 자격 **세대 id**, 등급, 레지스트리, 대상 레포 목록, 넣은 사람 · 시각, 소유자가 적은 만료일, 마지막 성공 · 실패만 남는다. 토큰 지문도 남기지 않는다(짧은 토큰의 지문은 추측 공격에 쓰일 수 있음).
3. **자격 변경은 소유자 MFA.** 등록 · 교체 · 폐기는 스토어 신뢰 변경과 같은 무게로 다룬다. 다만 토큰 값은 서명 문서에 넣지 않는다(서명 문서는 내려받아 오프라인 서명하는 대상이라서).
4. **스토어를 늘려도 Backbone 배포 구성을 건드리지 않는다.** worker · Secret · 망 경계는 승인된 실행 경로가 스토어 활성화 때 만들고, 정지 · 삭제 때 지운다. Console 마운트 변경 없음(F-2).
5. **토큰은 접근만.** `publish` 자격이 있어도 서명은 오프라인 키(또는 하드웨어 서명기)로만 한다. 호스트는 서명되지 않은 목록 · 등록부 · 릴리스를 게시하지 않는다.
6. **넘치는 권한은 거절.** 등록 때 레지스트리가 알려 주는 범위(GitHub classic PAT는 응답 헤더의 scope 목록)를 확인해, `read` 자리에 `write:packages` · `repo` · `admin:*` 등이 있으면 거절한다. 확인할 수 없는 레지스트리는 "범위 미확인"으로 표시하고 소유자 확인을 받는다.
7. **실패는 닫힌 쪽.** 자격이 만료 · 거절 · 확인 불가면 그 스토어 읽기만 멈추고(마지막 검증 head의 만료는 계속 계산), 다른 스토어는 영향 없음.

### 4.1 토큰을 넣는 경로

- **1단계(권고): Setup 소유자 터미널.** `setup store-credential set|rotate|revoke <store> --grade read` — 토큰은 표준 입력(화면에 안 보임, R1 `recover.py`와 같은 방식), MFA, Setup이 소유자 kubeconfig로 지정된 reader namespace의 Secret을 직접 쓰고 Services에 세대 기록을 남긴다. Console은 값을 보지 않는다.
- **2단계(선택): Console 화면.** 브라우저가 토큰을 **자격 기록 담당 구성요소의 공개 키로 봉인**해 보내고, Console은 봉인본만 전달한다. 그 구성요소만 reader namespace의 라벨 붙은 Secret을 쓸 수 있다(좁은 RBAC). Console의 "비밀 없음"(MS6) 원칙을 지키면서 화면에서 넣을 수 있다. 1단계 합격 뒤 별도 결정(C-2).

### 4.2 `publish` 자격(관리 권한)

- 쓰임: 설치본이 **자기 비공개 스토어**(회사 스토어 · 로컬 스토어)를 운영할 때.
- 게시는 승인된 실행 경로의 **게시 Job**(MS7a 게시 도구와 같은 코드, 호스트 이미지)이 하고, `publish` 자격은 그 Job에만 투영된다. Console · Core · reader는 받지 않는다.
- 입력은 **이미 서명된** 목록 · 등록부 · 릴리스 봉투다. 서명은 오프라인. Job은 서명 · 순서 · 하한을 다시 검증하고, MS7a 규칙(읽기 대조 뒤 불변 태그, 채널 포인터는 마지막)으로 쓴다.
- Universe 같은 공개 스토어의 게시는 지금 계획대로 **GitHub Actions 보호 environment**(`GITHUB_TOKEN` 또는 게시 전용 PAT)에서 한다. OpenSphere 설치본이 Universe 쓰기 자격을 갖지 않는다.

## 6. 위협과 막는 방법

| 위협 | 막는 방법 |
|---|---|
| 토큰 유출(화면 · 로그 · 원장 · 서명 문서) | 값은 Secret에만, 입력은 표준 입력 또는 브라우저 봉인, 원장에 지문도 없음 |
| `read` 토큰이 다른 패키지까지 읽음(GHCR 제약) | 전용 계정 권고 + worker가 정확한 레포만 요청 + 화면에 "이 토큰의 계정이 볼 수 있는 범위는 OpenSphere가 좁힐 수 없음" 고지 |
| 넘치는 권한 | 등록 때 scope 확인 · 거절(원칙 6) |
| 쓰기 토큰으로 악성 게시 | 게시 Job은 서명된 봉투만, 설치본은 서명 · 하한 · 공급자 지문을 독립 검증(D-99) |
| 스토어 하나의 자격 장애가 다른 스토어로 | 스토어별 worker · Secret · 망 경계, 실패는 그 스토어만 |
| 삭제 뒤 자격 잔존 | 삭제 영수증에 Secret · worker 부재 확인 |
| 자격 변경이 MFA 밖 | 등록 · 교체 · 폐기 모두 소유자 MFA, 세대 기록 |

| **C-2** | 토큰 입력 경로 | **1단계 Setup 소유자 터미널**(표준 입력 + MFA). Console 화면 입력(브라우저 봉인)은 1단계 합격 뒤 따로 |
| **C-3** | `publish` 자격을 OpenSphere 안에 둘까 | **둔다, 단 비공개 · 로컬 스토어 운영용으로만.** 게시 Job만 자격을 받고 서명은 오프라인. Universe 게시는 GitHub Actions 쪽 그대로 |
| **C-4** | 순서 | **MS7b와 병행, 선행 조건 아님.** 비공개 스토어 첫 사용 전에 SC1~SC3. Backbone 반영은 A-6 다음 묶음(D-106 구현과 같은 회차 후보) |

## 8. 구현 단위(제안)

| 단위 | 범위 |
|---|---|
| **SC1 원장 · 계약** | 자격 자리 · 세대 · 이력 원장(값 없음), 신뢰 변경의 자격 참조와 결합, 범위 확인 규칙 · 공유 사례 |
| **SC2 수명주기 실행** | Setup `store-credential set · rotate · revoke`(표준 입력 · MFA), 비공개 worker · Secret · 망 경계를 승인된 실행으로 생성 · 교체 · 정리, carrier 토큰을 Console 배포 변경 없이 전달(F-2), 스토어 삭제의 정리 닫기(F-4), 만료 경고 |
| **SC3 게시 Job** | `publish` 자격 투영, MS7a 게시 코드 재사용, 서명된 봉투만, 격리 왕복 |

합격: 같은 Backbone 빌드 · 같은 배포 구성에서 (1) 비공개 시험 스토어 둘을 각자 `read` 토큰으로 등록 · 읽기, (2) 하나의 토큰 교체 · 폐기가 다른 스토어에 영향 없음, (3) 넘치는 권한 토큰 거절, (4) 스토어 삭제 뒤 Secret · worker 없음, (5) `publish` 토큰만으로는 서명 없는 목록이 게시되지 않음, (6) 화면 · 로그 · 원장에 토큰 값 0건.

## 9. 열린 질문(Codex 대조 요청)

1. F-2: 지금 carrier 토큰 마운트가 기존 Secret volume의 키 추가로 끝나는지, Console Deployment 변경이 필요한지. 변경 없이 전달하는 가장 작은 구조.
2. 비공개 worker 생성을 승인된 실행 경로(Core 계산 · 웹훅 · 실행부)로 옮길 때 필요한 권한과 VAP, 기존 원형 권한을 넓히지 않는 방법.
3. 원칙 6의 범위 확인: reader의 허용 호스트는 지금 `ghcr.io`와 blob 호스트뿐이다. scope 확인(`api.github.com` 응답 헤더)을 어디서 할지 — Setup이 등록 때 한 번 하는 안이 가장 작은지.
4. 스토어 삭제(MS4)에 정리 닫기를 더할 때 기존 정지 · 하한 · 복구 증거 규칙과의 관계.
5. `publish` 게시 Job을 실행 원형 안에 둘지, 호스트 전용 Job으로 둘지.
6. 내가 놓친 결함(MS2 · MS4 · MS6 · MS7a에서 자격과 관련된 것).
