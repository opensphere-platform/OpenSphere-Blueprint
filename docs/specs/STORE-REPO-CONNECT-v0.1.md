# 스토어 연결 — 레포에서 직접 읽기 · 스토어 추가 화면(v0.1)

- **상태:** 소유자 결정(2026-11-27, D-109). 구현 · 적용 · 시험은 Claude가 직접 한다(소유자: "외부 스토어 연결은 네가 직접 모든 구현과 적용 테스트 전과정을 책임지고 진행한다").
- **소유자 원문:**
  - "스토어 연결은 사용자가 스토어 추가 프로세스를 통해서 처리 되어야 하고 이때 스토어 레포에서 발행한 토큰을 사용자에게 입력하게 해서 비공개 레포에 대한 접근이 가능 해야 한다."
  - (스토어 내용을 어디서 읽을지) "레포에서 직접"
- **이 문서가 바꾸는 것:** D-99(중립 다중 스토어)의 전송과 등록 방식. 스토어 자격 초안(`STORE-CREDENTIALS-v0.1.md`)의 C-1~C-4는 이 문서로 대체한다.

## 1. 원칙

1. **레포가 곧 스토어다.** 스토어는 비공개 Git 레포일 수 있다. 그 레포 하나에만 닿는 읽기 전용 토큰으로 연결한다.
2. **연결은 사용자가 화면에서 한다.** Console의 스토어 추가 과정에서 주소와 토큰을 넣고, 스토어 정체를 확인하고, MFA로 승인한다. kubectl 수작업이나 오프라인 서명 파일 전달은 제품 경로가 아니다.
3. **토큰은 접근만 준다. 신뢰는 서명에서 온다.** 토큰으로 읽은 바이트는 지금과 같은 서명 · digest 검증을 통과해야 한다. 검증 규칙과 서명된 문서 형식은 바꾸지 않는다.
4. **스토어 서명은 배포만 보증한다.** 패키지가 무엇을 할 수 있는지(권한 · 이미지)는 계속 운영자 프로필이 정한다. 스토어를 추가했다고 설치 권한이 생기지 않는다.
5. **공개 전환을 전제하지 않는다.**

## 2. 레포 안의 스토어 트리

스토어 레포의 `store/` 아래에 서명된 바이트를 그대로 둔다. `channels/<채널>/catalog.json`만 바뀌는 파일이고, 나머지는 내용 주소(digest)로 이름 붙인다.

| 경로 | 내용 |
|---|---|
| `store/store.json` | 배치 판(`store.repository-layout/v1`), 스토어 이름, 채널 목록 |
| `store/trust.json` | 공개 신뢰 정보: root 공개키, 채널 서명 키, 승인된 공급자 키 지문 |
| `store/channels/<채널>/catalog.json` | 지금 유효한 서명된 채널 목록 |
| `store/channels/<채널>/catalog-<순번>.json` | 같은 목록의 순번별 사본 |
| `store/publishers/sha256-<hex>.json` | 서명된 공급자 등록부 |
| `store/bundles/<공급자>/<이름>/sha256-<번들 digest>/manifest.json` | 번들 manifest |
| `…/blobs/sha256-<hex>` | 번들의 part 바이트 |
| `…/signature.json` · `sbom.json` · `provenance.json` | 릴리스 서명과 증거 |

- 게시는 서명된 파일을 레포에 커밋하는 것으로 끝난다. 서명은 오프라인에서 하고, 레포와 CI에는 개인 키가 없다.
- 스토어 정체와 서명 문서 안의 값(`store`, `storeIdentity`)은 지금 형식 그대로다. 레포 주소는 **읽는 위치**이고 정체가 아니다(D-99 MS3b: 릴리스 하나 · 출처 여럿).

## 3. 읽기(전송 `github-repo/1`)

- reader는 GitHub REST API(`api.github.com`)의 contents 읽기만 쓴다. 토큰은 그 레포의 **Contents 읽기 전용** fine-grained 토큰이다.
- 한 번의 읽기는 한 커밋에 고정한다: 브랜치의 현재 커밋을 먼저 확인하고, 그 커밋에서 모든 파일을 읽는다.
- 리다이렉트를 따르지 않는다. 호스트는 `api.github.com` 하나, 경로는 그 레포의 `store/` 아래로 한정한다.
- 읽은 뒤의 검증은 지금과 같다: root · 채널 키 · 공급자 키 서명, 순번이 뒤로 가지 않는지(floor), digest · 크기 일치.
- 토큰이 틀리거나 만료되면 읽기가 실패하고, 직전 상태와 그 만료 시각이 그대로 유지된다. 공개 읽기로 떨어지지 않는다.

## 4. 스토어 추가 과정(Console)

1. 스토어 관리 › **스토어 추가**: 레포 주소(`<소유자>/<레포>`), 브랜치, 읽기 토큰을 넣는다.
2. **확인 단계:** Backbone이 그 토큰으로 레포를 읽어 검증하고 보여 준다 — 스토어 이름, 스토어 정체, root 키 지문, 채널, 공급자, 패키지 수. 서명이 맞지 않으면 여기서 멈춘다.
3. **승인:** 사용자가 지문을 확인하고 MFA(TOTP)로 승인한다.
4. Backbone이 스토어를 등록하고 토큰을 보관한다. 이후 reader가 주기적으로 읽는다.
5. 스토어 화면에 그 스토어의 패키지가 나타난다.

- **토큰 교체 · 스토어 정지 · 삭제**도 같은 화면에서 MFA로 한다. 삭제하면 토큰도 지운다.
- **토큰 보관:** 값은 암호화해서 Services DB에 둔다(AES-GCM, 키는 Console의 Secret에만 있고 DB에는 없다. R2D2 자격 보관과 같은 방식). Console은 Kubernetes에 쓰지 않는다는 기존 원칙을 지키기 위해서다. 화면과 로그, API 응답에 값을 돌려주지 않는다. reader에게는 읽기 작업을 줄 때만 내부 채널로 건넨다.
- **권한:** 스토어 추가 · 변경은 활성 관리자(관리 plane의 스토어 관리 권한) + 그 사람 자신의 MFA다(D-110, 2026-11-27 개정. 처음 구현은 설치본의 첫 소유자 계정만 허용했다). 위임 계정과 에이전트는 못 한다.
- 처음 추가할 때의 신뢰는 "화면에 보인 root 지문을 사용자가 확인하고 MFA로 승인"이다. 그 뒤로는 그 root에 고정된다. root 교체는 기존 root가 서명한 교체 문서로만 받는다.

## 8. 구현 결정(코드 대조 뒤, 2026-11-27)

기존 스토어 원장(MS1~MS5)을 대조한 결과 화면에서 추가하는 스토어를 그 표에 그대로 넣을 수 없다. 기존 경로는 운영자 키로 서명한 변경 문서, Setup 터미널 전용 MFA, 키 작업 역할(`osr_keyops`)만의 적용, 운영자 맥락에 승인된 공급자 키를 전제로 하고, 설치 때 그 서명 문서를 다시 검증한다. 그래서 이렇게 만든다.

1. **추가형 원장.** 레포 스토어는 새 표(`osr.repo_stores` · 후보 · 채널 head · 패키지)에 둔다. 기존 표 · 함수 · 권한은 바꾸지 않는다. 기존 스토어 흐름과 운영에 영향이 없다.
2. **스토어 정체와 서명 형식은 그대로.** 정체는 지금 식(`registry` · `namespace` · 최초 root 지문)을 쓴다. 레포 주소는 읽는 위치로만 기록한다.
3. **읽기는 전용 reader가 한다.** 새 실행 모드 `repo-store-reader`가 GitHub API만 읽는다(망 허용은 `api.github.com` 443 하나). Console은 외부로 나가지 않는다. 화면의 "확인 단계"도 이 reader가 읽어 온 것을 Console이 검증해 보여 준다(몇 초 걸린다).
4. **검증은 기존 판정기 그대로.** 스냅숏(root · 채널 키 · 순번 · 유효 기간) · 서술자 · 릴리스 서명 판정을 같은 코드로 한다.
5. **승인은 Console의 TOTP 확인.** 설치 계획 승인과 같은 방식이다(활성 관리자 · 관리 plane · 위임 계정 불가 · 코드 재사용 불가, D-110).
6. **1차 범위는 "추가하면 패키지가 보인다"까지다.** 스토어 관리 화면에 스토어와 패키지(이름 · 판 · 설명)가 나온다.
7. **설치는 그다음이다.** 패키지 설치는 지금처럼 운영자 프로필(이미지 · 권한)이 있어야 한다(§1-4). 레포 스토어의 검증된 번들을 기존 설치 경로에 잇는 일과, 프로필을 어디서 승인할지는 1차 뒤에 정한다.

## 9. D-111 개정(2026-11-27): 주소 · 내장 스토어 · 자기 소개

- **주소:** 스토어는 `https://호스트/경로` Git 레포 주소로 등록한다(포트 · 자격 · 질의 · 주소 리터럴 없음, `.git` · 끝 `/`는 뗀다). 원장의 `repository` 열이 이 주소를 담는다(Services 050).
- **읽기:** Git smart HTTP 프로토콜 v2(능력 확인 → `ls-refs` → 얕은 `fetch` 1회 → pack을 메모리에서 해석). 호스트별 API를 쓰지 않는다. GitHub와 Gitea에서 확인했다. 한도: pack 32 MiB, 객체 2만, 풀린 크기 96 MiB, 파일 2000개 / 32 MiB.
- **내장 스토어:** `osr.repo_store_builtins`에 주소와 신뢰 문서를 검수된 바이트로 둔다. 설치가 끝난 설치본에 행이 자동으로 생기고(토큰 없음, "읽기 토큰 대기"), 관리자가 `token` 변경(MFA)으로 토큰을 넣는다. 삭제할 수 없다. 첫 내장 스토어는 OpenSphere Default Store(정체 `sha256:77f1efe8…`, root `sha256:f803a731…`).
- **신뢰 갱신:** 스토어 트리의 `store/trust.sig.json`(신뢰 문서를 root 키로 서명한 봉투)이 있으면, 같은 스토어 · 같은 root 키 · 더 늦은 발급 시각일 때 고정한 신뢰 문서를 새 것으로 바꾼다. 신뢰 문서의 유효 기간(계약의 rootDays)이 지나도 새 승인 없이 이어진다.
- **자기 소개(D-106):** 목록이 프로필을 묶으면(`store.channel-catalog/v3`) `store/channels/<채널>/profile.json`, `product.json`(A2UI `store.home`), `media.json` + `store/media/`를 읽어 기존 표현 계약으로 검증한다(Services 051). Console은 프로필, `store.home`(A2UI 렌더러, 투영은 `store.profile` 하나), 묶음별 패키지 카드(호스트가 그림)를 보인다. 이미지는 검증만 하고 아직 보관 · 제공하지 않는다.
- **망 경계:** reader는 공인 주소의 443만 나간다. 사내 Git 호스트는 반영 때 `internalHosts`로 이름을 지정한다.
- **남은 것:** 스토어 패키지의 설치 연결(설치 경로는 운영 신뢰 앵커가 서명한 스토어 신뢰 변경과 제품 권한을 요구한다), 프로필 이미지 보관 · 제공, v3 게시 도구(SP3), 주간 목록 재서명 자동화.

## 10. 설치 연결 설계(2026-11-27, 소유자 "설치까지 연결")

### 10.1 지금 있는 설치 경로가 요구하는 것(코드 조사)

스토어 패키지의 설치(qualified 경로, `inst-pkg-…`)는 "보이는 것"과 "설치할 수 있는 것"을 나눈다. 설치 계획이 접수되려면 다음이 모두 있어야 한다.

| 요구 | 누가 만드는가 |
|---|---|
| 스토어가 서명 원장(MS)에 활성으로 등록 — 운영 신뢰 앵커가 서명한 스토어 신뢰 변경(MS4) | 소유자(앵커 키) · Setup MFA |
| 제품 권한(product authority) — 허용 공급자 · 종류 · plane · 프로필 결합, 운영 신뢰 앵커 서명 | 소유자(앵커 키) |
| 현재 채널 스냅샷 · 항목 · 번들 바이트 · 릴리스 증거 · 제품 판정(reader 수집 결과) | reader + Console |
| 패키지의 실행 프로필이 서명된 맥락(`osr.profiles`)에 있음 | 소유자(맥락 서명) |
| Core의 증거 연결(`OSR_QUALIFIED_EVIDENCE_DATABASE_URL` · `OSR_QUALIFIED_ACTIVATION_KEY`) — 운영은 지금 닫혀 있음 | 운영 반영(소유자 승인) |
| 패키지 이미지가 노드에 있음(pull 자격 없음) | 노드 적재 |

### 10.2 방향: 레포는 전송 수단이다

레포 스토어에 별도의 설치 권한 체계를 만들지 않는다. **같은 스토어 정체**(registry · store · root 지문의 digest)가 서명 원장에 등록돼 있으면, 레포에서 읽은 바이트를 기존 수집 경로(스냅샷 · 번들 · 제품 판정 · 증거)에 그대로 넣는다. 그 뒤의 제안 · 계획 · 승인 · 실행 · 활성화는 지금 경로를 바꾸지 않고 쓴다.

- 관리자가 주소 + 토큰으로 추가한 스토어 = **목록만**(지금까지의 D-109/D-110). 화면 문구 "패키지를 설치할 권한이 생기는 것은 아닙니다" 그대로.
- 그 스토어의 정체에 대해 운영 신뢰 앵커가 서명한 신뢰 변경과 제품 권한이 적재되면 = **설치 가능**.
- 내장 Default Store는 OS 공급자(소유자)가 신뢰 변경 · 제품 권한을 한 번 서명해 둔다.

### 10.3 구현 단위

1. **R-I1 수집 연결:** 서명 원장의 reader 작업에 Git 원천(주소 · 브랜치 · 토큰)을 붙이고, reader가 스냅샷에서 목록 · 등록부 · 표현 · 번들을 꺼내 기존 carrier 단계(`metadata` · `metadata-presentation` · `bundles`)로 제출한다. 번들 좌표는 지금처럼 `ghcr.io/<store>/<package>` 논리 좌표를 쓴다(정체 식과 CHECK가 그 형태를 요구).
2. **R-I2 격리 실증:** Valkey 격리 시험(`tests/osr/valkey-rke2.py`)의 스토어 원천을 레포로 바꿔 등록 → 수집 → 설치 → 인스턴스까지.
3. **R-I3 화면:** 스토어 카드의 패키지에서 설치 계획 만들기(기존 `POST /console-api/osr/packages/{공급자}/{이름}/plans`).
4. **R-I4 운영 준비물(소유자):** Default Store에 대한 신뢰 변경 · 제품 권한 서명, Valkey 프로필이 든 맥락 서명 · 적재, Core 증거 연결 반영.

R-I4의 서명은 운영 신뢰 앵커로 하는 것이라 소유자 터미널 절차가 필요하다(시험은 시험 키로 한다).

### 10.4 구현 결과(2026-11-27, Backbone PR 257 · main `757e2e2`)

- **R-I1 구현됨.** 서명 원장 수용부(`osr_store_carrier`)에 레포 reader용 범위를 더했다. 레포 carrier의 토큰과 스토어 정체 하나로 들어오고, 그 정체가 지금 읽히는 레포 스토어(활성 · 토큰 있음)이며 원장 행에 레지스트리 자격이 없을 때만 받는다. **한 스토어에 전송 수단 하나**: 주소로 연결된 스토어는 레지스트리 reader에게 작업을 주지 않는다(읽기를 중단한 동안에도 레지스트리로 넘어가지 않는다). reader(`osr_repo_reader`)는 받아 둔 트리를 status → metadata(-presentation) → wanted → bundles 순서로 넘기고, 파일은 서명된 문서가 묶은 digest로 찾는다. 수용부의 판정은 바꾸지 않았다.
- **R-I3 구현됨.** 스토어 조회가 배치된 패키지마다 서명 원장을 읽어 판정한다(쓰기 없음). 그 스토어가 서명 원장에서 활성이고, 채널의 머리가 관측된 것이며, 그 머리가 지금 이 번들을 내놓을 때만 `available` · 설치 가능. 아니면 `store_not_qualified`(목록만 연결) 또는 `store_offer_not_ready`. 화면은 서버가 준 네 값(`storeIdentity` · `channel` · `snapshotDigest` · `bundleDigest`)을 그대로 기존 계획 경로에 낸다. 설치된 패키지는 어느 스토어도 내놓지 않게 돼도 보이고 내릴 수 있다.
- **확인한 범위.** 격리 PostgreSQL(Services 이행 51개 전부)에서 레포 트리의 번들이 제품 판정을 통과해 qualified 증거로 기록되는 것(`tests/osr/repo-store-signed-native.py`), 화면의 목록 → 제공 → 설치 → 내리기(가짜 응답 브라우저 시험). **R-I2(격리에서 실제 Valkey 설치)는 Codex의 V1 실증 도구에 레포 원천을 붙여 진행 중이다.**

## 11. D-112: 패키지 배치와 화면(2026-11-27)

소유자: "스토어 추가 작업은 우측 서랍 페이지로 처리 하자", "등록이 완료된 스토어에 대한 페이지 내에서의 개별 영역을 좀더 강화", "추가된 스토어에서 받은 패키지를 … 스토어 배치 시켜 줘야 하지 않나?"

### 11.1 두 화면의 역할

- **스토어 관리:** 어디서 받는가. 스토어를 연결하고(서랍), 스토어마다 읽기 상태 · 목록 유효 기간 · 신뢰 값 · 소개를 본다.
- **스토어:** 무엇을 설치하는가. 레이어(Fabric · Governance · Workspace · HISS)별로 패키지를 고른다. 연결된 스토어의 패키지도 여기 나온다.

### 11.2 배치 규칙

1. 배치는 자동이다. 패키지마다 사람이 올리는 단계는 없다. 스토어를 MFA로 승인한 것이 그 스토어의 목록을 보이겠다는 결정이다.
2. 나오는 조건: 스토어가 읽는 중(활성 · 읽기 토큰 있음), 이 설치본이 따르는 채널, 목록이 유효 기간 안, 릴리스가 서명 검증 통과. 하나라도 아니면 스토어에 나오지 않고, 스토어 관리의 패키지 표가 까닭을 적는다.
3. 레이어는 호스트가 패키지 종류로 정한다(`provider` → Fabric). 스토어가 적은 말로 정하지 않는다. 호스트가 모르는 종류는 "구분이 정해지지 않은 패키지"다.
4. 같은 판(같은 패키지 · 같은 번들)을 여러 스토어가 내놓으면 한 줄이고, 출처를 모두 적는다. 릴리스 하나 · 출처 여럿이라는 MS3b 판단과 같다.
5. 읽기를 중단하거나 스토어를 지우면 그 스토어의 패키지는 스토어에서 빠진다(다른 스토어가 같은 판을 내놓고 있으면 남는다).
6. **배치는 설치를 열지 않는다.** 설치 연결(§10)이 끝나기 전에는 상태 "스토어에 있음", 설치 버튼 없음, 사유 `repo_store_install_pending`. 설치 연결 뒤에는 같은 줄에서 설치 계획을 만든다(R-I3).

### 11.3 화면

- 스토어 추가는 오른쪽 서랍 하나에서 끝난다: 주소 · 토큰 → 지문 확인 → MFA. 읽기 거절 사유는 서랍 안에 나온다. 레포를 읽는 동안에도 닫을 수 있다.
- 연결된 스토어마다 제 구역: 이름 · 상태 태그(정상 · 읽기 토큰 대기 · 첫 읽기 대기 · 읽기 실패 · 목록 만료 · 읽기 중단) · 작업, 수치 넷(패키지 · 채널 · 목록 유효 기간 · 마지막 읽기), 탭 셋(패키지 · 소개 · 연결과 신뢰).
- 구현: Backbone PR 256. 원장 변경 없음(`osr.repo_store_view()`를 스토어 조회도 읽는다).
