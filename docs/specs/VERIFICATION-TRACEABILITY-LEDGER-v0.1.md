# 검증 추적 대장 v0.1 — 승인된 요구가 심사 · 구현 · 패키지 · 운영까지 갔는가

**상태:** 관리 대장. 2026-11-28 첫 판. 결정이 아니다. 각 행의 처리 방침(§4)은 소유자 확인 뒤 정한다.
**작성:** Claude(프로젝트 관리 책임).
**계기:** 소유자 지적(2026-11-28): 통합 메시지 · 통합 로그(D-100)가 승인됐는데 모듈 적격성 심사에 들어가지 않았다. "누락된 검증 포인트가 이 두 가지뿐인가?" — 아니었다. 이 대장은 그 답이고, 같은 일이 다시 생기지 않게 하는 장치다.
**기준:** Backbone main `b95cee60`(2026-11-28), Blueprint main, 운영(A-18 채택 83 · 84). 세 갈래 전수 대조(통합 계약 · 모듈 명세 / 에이전트 운용 · 품질 표준 / 결정 대장)를 코드에서 확인했고, 핵심 주장은 Claude가 표본으로 다시 확인했다(§5).

## 1. 읽는 법

각 행은 승인된 요구 하나다. 다섯 칸을 본다.

| 칸 | 뜻 |
|---|---|
| 심사 | 판정기(Node · Rust · Setup 봉인 사본) 또는 품질 검사가 그 요구를 보고, 어긋난 패키지를 거절하거나 표시하는가 |
| 호스트 | Backbone이 그 요구의 실행 쪽을 구현했는가 |
| 패키지 | 스토어 패키지가 선언 · 번들에 담았는가(Vk Valkey · Rf RustFS · Os OpenSearch · Pg PostgreSQL · Sb Samba AD · Kc Keycloak · Ui 더미 화면) |
| 운영 | 운영에 반영됐는가 |
| 상태 | ✅ 충족 · ◐ 일부 · ✕ 없음 · ⏸ 보류(사유와 다시 볼 시점이 있어야 한다) |

**관리 규칙(Claude):**
- 결정 · 계약이 바뀔 때, 패키지를 게시 · 운영 반영할 때마다 이 대장을 갱신한다.
- "완료"를 보고하기 전에 그 대상의 빈칸을 확인하고 함께 보고한다.
- 우선순위를 바꿔 미루는 단위는 ⏸로 남기고 사유 · 다시 볼 시점을 적는다. 수용 기준에서 빼는 것은 대장에 옮겨 적은 뒤에만 한다.
- Codex에게 일을 줄 때 이 대장의 행 번호를 적는다.
